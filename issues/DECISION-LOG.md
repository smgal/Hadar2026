## 2026-09-01 — 착수 판정: **조건부 진행**

**질문**: AI 로 시나리오·퀘스트를 자동 생성하는 것이 (a) 불가능한가 (b) 수동보다 비효율인가.

### (a) 불가능한가 → **아니다**

오프라인 배치 생성 + 스키마 강제 + 정적 검증 + 완주 증명은 검증된 방식이다.
런타임에 AI 를 두지 않으므로([D-01](../blueprint/_meta/DECISIONS.md)) 결정론·재현성도 확보 가능하다.
설계는 [`blueprint/`](../blueprint/00_README.md) 34개 장에 이미 완결되어 있다.

### (b) 수동보다 비효율인가 → **지금은 알 수 없다. 그리고 질문이 성립하지 않는 구간이 있다**

실측한 현재 콘텐츠:

| 항목 | 값 |
|---|---|
| cm2 `Talk` 호출 | 393개 (4,056줄) |
| 맵 JSON 이벤트 / 대사 | 76개 / 56줄 |
| **퀘스트** | **0개** |

핵심 발견: **지금 구조에서는 손으로도 퀘스트를 만들 수 없다.**
- 인벤토리가 `food`/`gold` 정수 2개뿐 → "가져오라" 를 표현할 수단이 없다
- `HDMapScript.isFlagSet` 이 빈 스텁(부록 A-3) → 네이티브 조건 분기가 한 번도 동작한 적 없다
- cm2 전역이 맵 전환마다 초기화(§9) → 진행 상태를 들고 다닐 수 없다
- JSON 티어는 좌표당 이벤트 1개·무조건 출력 → 조건부 대사 불가

즉 **병목은 "AI vs 수동" 이 아니라 "퀘스트라는 개념의 부재"** 다.
P0(기반 복구)과 P1(퀘스트 능력)은 **AI 여부와 무관하게 필요**하다.

### 판정

**진행한다. 단 AI 특화 구간(P2) 앞에 측정 게이트를 둔다.**

- P0·P1 은 무조건 진행 — 어느 쪽 길을 가도 필요한 작업이다.
- P2(콘텐츠 서버·MCP·솔버·퍼저·생성 하네스)는 **GATE-1 통과 시에만** 착수한다.
- GATE-1 은 P1 후 **퀘스트 5개를 손으로 만들어 실측**한다. 판정 규칙은 착수 전에 못박았다
  ([MILESTONES.md §4](MILESTONES.md)) — 결과를 보고 기준을 바꾸지 않기 위해서다.

### 이 판정이 틀릴 수 있는 지점

- **목표 물량이 작으면 P1 조차 과하다.** 퀘스트를 5개만 원한다면 cm2 + 네이티브 Dart 로
  임시 대응하는 것이 더 싸다. 물량 목표를 정하는 것이 P0 착수보다 먼저다 — [ISSUE-000](#) 참조.
- **P0 이 예상보다 크면** 전체가 흔들린다. 부록 A~K 는 21건 이상이고 세이브 포맷 변경을 포함한다.
- **1인 개발이면 P2 는 거의 확실히 과하다.** 파이프라인 자체가 게임보다 커지는 위험은
  [BP-52](../blueprint/52_risks.md) 가 리스크로 등재했다.

## 2026-09-01 (2차) — **1차 판정 정정**: 퀘스트는 이미 저작 가능하다

### 무엇이 틀렸나

1차 판정은 "지금 구조에서는 **손으로도 퀘스트를 만들 수 없다**" 를 전제로 P0→P1→GATE→P2 를 짰다.
**이 전제는 거짓이다.** 레포 안에 작동하는 퀘스트 콘텐츠가 **2,441줄** 있다(`assets/L1_ep1d0~d5_1.cm2`).

원작의 퀘스트 시스템은 `assets/flag4ep1.cm2` 다 — **이름 붙인 플래그 상수 + cm2 조건 분기**:

```cm2
GFD0_GET_WALL_REMOVER.assign(1)    # 벽 허무는 도구 획득
GFD0_GET_KEY_FOR_D1.assign(2)      # 열쇠 획득
GFD0_CHECKED_BY_GUARD.assign(3)    # 경비병 검문 통과
```

그리고 `L1_ep1d0.cm2` 의 실제 로직:

```cm2
if (Equal(ScriptMode(), FLAG_TALK))
    if (On(14,30))                              # 좌표로 NPC 식별
        if (Not(Flag::IsSet(GFD0_RENT_ROOM)))   # 조건부 분기
            Select::Init() / Add / Run          # 선택지
            Map::ChangeTile(18,36,30)           # 월드 변화
            Flag::Set(GFD0_RENT_ROOM)           # 진행 기록
```

복합 조건도 동작한다: `And(And(Not(Flag::IsSet(A)), Flag::IsSet(B)), Flag::IsSet(C))`.

### 내가 왜 틀렸나 (같은 실수를 반복하지 않기 위해)

| 1차 판정의 근거 | 실제 |
|---|---|
| 인벤토리가 없어 "가져오라" 를 표현 못 한다 | **원작은 플래그로 표현한다.** `GFD0_GET_KEY_FOR_D1` 이 곧 "열쇠 소지" 다. 인벤토리는 애초에 없었고 필요도 없었다 |
| `HDMapScript.isFlagSet` 이 빈 스텁이라 조건 분기가 전무하다(부록 A-3) | 그건 **네이티브 Dart 경로**다. cm2 의 `Flag::IsSet` 은 `HDGameOption.flags`(256칸, **세이브에 저장됨**)를 정상 참조한다 |
| cm2 전역이 맵 전환마다 소실된다 | 소실되는 것은 **엔진의 변수**(상수 이름 바인딩)이고, 매 로드 시 `include("const.cm2")` 가 다시 만든다. **실제 플래그는 세션 상태라 살아남는다** |

**공통 원인**: 결함 목록을 보고 "그래서 불가능하다" 를 **연역**했고, **작동하는 사례를 찾아보지 않았다.**
레포에 2,441줄의 반례가 있었는데 읽지 않았다.

### 맵과 등장인물 추가도 코드 변경 없이 된다

작동하는 패턴(`LORE_EP` = `Map002.json` + `Map002.cm2` 가 실증):

| 필요한 것 | 방법 |
|---|---|
| 새 맵 | `MapInfos.json` 에 `{"id": 16, "name": "..."}` 추가 (다음 빈 id 는 **16**) + `assets/maps/Map016.json` |
| 새 등장인물 | 맵 JSON 의 objUpper 에 TALK 오브젝트(B 128~143) + cm2 의 `On(x,y)` 핸들러 |
| 퀘스트 로직 | `assets/Map016.cm2` — `include("const.cm2")` + `ScriptMode()` 분기 |
| JSON 폴백 억제 | `Event::Override()` — `Map002.cm2` 에 이미 데모가 있다 |

**즉 샘플 퀘스트 = 파일 2개 + MapInfos 한 줄. 코드 변경 0.**

### 정정된 판정

**"검증부터" 를 버리고 "생성부터" 로 바꾼다. 그리고 top-down 을 버리고 sample-first 로 바꾼다.**

- **S1**: 샘플 퀘스트 1개를 **현재 방식으로 손으로** 만든다(새 맵 + NPC 포함). 이것이 생성의 **정답지**다.
- **S2**: 그 과정에서 **실제로 걸린 것만** 고친다. 미리 짐작해 만들지 않는다.
- **S3**: AI 가 **같은 산출물**(map JSON + cm2 + MapInfos 항목 + 플래그 정의)을 만들게 한다.

**인벤토리·장비·저널·선언적 콘텐츠 팩은 전부 보류**한다. 원작이 플래그로 하던 것을 플래그로 한다.
결과가 원작과 맞으면 되고, 구조 개선은 자동화가 실제로 막힐 때 그 지점에서 한다.

`blueprint/` 34개 장은 폐기하지 않는다 — **그 길이 필요해지는 시점의 설계**로 남긴다.
[deferred/](deferred/) 가 그 경계를 기록한다.

## 2026-09-01 (3차) — 순서 재조정: **게임 시스템 완성이 자동화보다 먼저**

### 무엇이 바뀌었나

2차 판정은 "인벤토리는 보류하고 플래그로 대체" 했다. **두 가지 이유로 뒤집는다.**

1. **재미** — 플래그는 퀘스트 기록은 되지만 **장비할 수도, 팔 수도, 가방에서 볼 수도 없다.**
   게임이 미완성인 상태에서 퀘스트만 늘려도 재미가 늘지 않는다.
2. **부채** — **플래그로 만든 퀘스트 20개는 나중에 인벤토리가 생기면 전부 다시 써야 한다.**
   임시 표현 위에 쌓은 콘텐츠는 부채다. 자동화로 물량을 늘린 뒤라면 더 크다.

### 실측이 판단을 굳혔다

| 사실 | 확인 |
|---|---|
| **원작에 완성된 아이템 시스템이 있다** | `REF_UNITY_LoreEp1/src_as_cs/ObjItem.cs` **877줄** · `GameEventEquipment.cs` **448줄** |
| 아이템 모델 | `Item { res_id, name, param{atta_pow, ac, item_type}, annex }` |
| **원작은 부위 개념을 갖는다** | `ITEM_TYPE`: `WIELD/CHOP/STAB/HIT/SHOOT/SUMMON_*` · `SHIELD` · `ARMOR/HEAD/LEG` · `ORNAMENT` |
| 현재 Dart | `weapon`/`shield`/`armor` **정수 3칸**뿐 → 부위가 늘어나면 또 어긋난다 |
| `books.json` | 무기 5·방어구 3. 앱과 참조본이 **동일** → 샘플이고 실데이터는 원작 바이너리에 있다 |
| 플레이어에게 보이는 미완성 | `"무기1"` 이 전투 로그 2곳(`battle.dart:285,453`) + 상태 메뉴 2곳(`menu_flows.dart:275,277`)에 노출 중 |
| 마법 | 선택 UI·이름만 있고 **효과는 레벨 기반 일반 공식 2개로 뭉쳐 있다**(`battle.dart:155,174`). 45종 개별 효과 없음 |

**즉 인벤토리는 "설계할 것" 이 아니라 "이식할 것" 이다.** 2차 판정이 이를 몰랐다.

### 정정된 순서

```
G1 아이템·장비 이식 ─▶ G2 전투 정합 ─▶ S1 샘플 퀘스트 ─▶ S2 걸림돌 제거 ─▶ S3 AI 생성
(재미 + 부채 방지)      (퀘스트 전투 전제)   (진짜 아이템 사용)
```

- **G1·G2 는 자동화와 무관하게 게임을 위해 필요한 작업**이다. 동시에 자동화의 표현 기반을 안정시킨다.
- **S1 이 G1 뒤로 간다** — 그래야 "기름을 구해 오라" 를 플래그가 아니라 **실제 아이템**으로 쓰고,
  나중에 다시 쓰지 않는다.
- 마법 효과 구현은 **별 트랙**이다. 재미에는 크지만 퀘스트 자동화의 전제는 아니다.

### 2차 판정에서 유지되는 것

- 퀘스트 저작은 원작 방식(플래그 + cm2)으로 **이미 가능**하다 — 그 사실은 변하지 않는다.
- 새 맵·등장인물 추가는 **코드 변경 0**.
- cm2 중첩 `include` 로 퀘스트 파일 분리가 가능하다(부록 L).
- 선언적 콘텐츠 팩·저널·솔버·MCP 는 계속 **보류**다. G1 은 그 노선이 아니라 **원작 이식**이다.

## 2026-09-04 (4차) — **신규 트랙 신설**: 전투를 떼어내 확장한 뒤 되붙인다

**이것은 정정이 아니다.** 3차 판정의 S1→S2→S3 노선은 그대로 유효하다.
전투 재작성이라는 **별개 트랙(B)** 을 추가한다.

### 왜 별개 트랙인가

G2(전투 정합)는 **결함 5건을 고친 것**이고 전투를 다시 만든 것이 아니다.
남아 있는 것은 결함이 아니라 **미완성**이다 — 실측:

| 사실 | 확인 |
|---|---|
| 마법 45종의 효과가 **공식 2개**로 뭉쳐 있다 | `battle.dart:166`(전체) · `:185`(단일). `마법 화살`과 `초냉기`가 같은 피해 |
| 치료 14종이 **아무것도 회복시키지 않는다** | `battle.dart:154` `// Simulate heal resolution` — 메시지만 출력 |
| 상태이상을 담을 자리가 **정수 3개**뿐 | `enemy.dart:22-24` · `player.dart:50-52`. 마법 14~18 이 담길 곳이 없다 |
| 의식불명 단계가 **경로에 따라 다르다** | 독은 2단계(`battle.dart:212-218`), 물리는 즉사(`:486-489`, 주석이 생략을 자백) |
| `agility` 가 **도주 판정에만** 쓰인다 | 사용처 2곳(`:405`·`:412`). 행동 순서는 슬롯 고정(`:130-132`) |
| 전투 중 아이템 사용이 **없다** | 전투 모드 메뉴 8개(`:311-325`)에 항목 없음. G1 의 가방 20칸을 전투가 모른다 |
| 적 행동이 사실상 **2종류** | `:501-530`. `specialCastLevel` 은 읽는 곳이 0곳 |
| 방어가 **`ac` 하나**로만 계산된다 | `:470`·`:548`. 부위 구별 없음. `powOfShield`/`powOfArmor` 는 P0-19 가 죽은 필드로 정리 |
| 속성 개념이 **레포 전체에 0** | `item.dart` `param` 3개 · `enemy_data.dart` 11개 필드 모두 속성 없음 |

이것을 지금 구조 안에서 고치려면 RPG·cm2·Flutter view 를 **동시에 만족시켜야** 한다.
그 제약을 잠시 끊는 것이 이 트랙의 목적이다.

### 판정 — 4구간으로 진행한다

```
B1 전투 분리 ─▶ B2 전투 확장 ─▶ B3 RPG 연결 ─▶ B4 Flutter view
(규칙 무변경)    (제약 없이)      (되붙임)         (model 무변경)
```

구간 정의와 완료 판정은 [MILESTONES §7](MILESTONES.md) 이다.

### 확정한 것

| 결정 | 근거 |
|---|---|
| **전투는 자기 아이템·적 테이블을 갖는다** (RPG 정의를 공유하지 않는다) | 기존 정의에 묶이면 부위별 감쇠·속성 상성처럼 **지금 테이블로 표현이 안 되는 것**이 나오지 않는다 |
| 테이블의 정체성은 정수가 아니라 **snake_case 문자열 키** | 정수로 두면 RPG 의 75종 id 공간과 의미가 다른 정수가 둘 생기고, B3 에서 "어느 쪽 26인지" 를 헷갈린다. 원래 인덱스는 `legacyId` 로 보존해 어댑터가 읽는다 |
| **레벨업은 RPG 가 처리한다.** level 은 개시 입력, 경험치만 반환 | 전투 중에 레벨이 오르는 일이 없다. 21단계 경험치 표와 `checkLevelUp()`(`player.dart:344`, 레포에서 유일한 호출처가 `battle.dart:287`)이 전투 패키지에서 빠진다 |
| **마법 45종 전부를 B2 에 넣는다** | 내용이 나중에 크게 바뀔 것이라 지금 쪼개는 의미가 없다. 단 13종은 효과가 전투 밖이므로(33~44) 전투는 **요청만** 남기고 RPG 가 해석한다 |

- **마법 45종의 개별 서술** — 지금은 카테고리 내 순번이 값을 정한다. 이름마다 다른
  효과(예: `차원 이탈` 이 정말 차원을 이탈시키는 것)는 원작에도 없었다
- **전투 밖 효과 요청의 내용 형식** — `worldEffects` 는 자리만 있고 비어 있다. B3-04

### 이 판정이 틀릴 수 있는 지점

- **Pascal 이 나오면 전부 다시 열린다**(6차 판정). B2 는 C++ 을 참고로만 쓰고 값을
  판단한 결과물이라, 원본이 나오면 어긋난 부분이 드러난다. 각 이슈에 **왜 그 값인지**를
  적어 둔 것이 그때 대조할 근거다
- **B3 가 규격을 다시 열 수 있다.** cm2 어댑터(B3-01)가 `Battle::Start(mode)` 를
  실제로 쓰려 하거나, `worldEffects` 의 형식이 정해지면서 규격이 움직일 수 있다.
  그러면 v2 와 새 판정이 필요하다

## 2026-09-05 (8차) — **B5 신설**: 전투에 위치를 넣는다. 근간은 드래곤 퀘스트로 둔다

7차 판정이 "붙인다(B3)" 였다. 그 직후 **전투가 1990년식이라는 지적**이 들어왔고, 무엇이
문제인지 코드로 확인한 결과 **B3 보다 B5 를 먼저 하는 것이 싸다**고 판단했다.

### 무엇이 문제인가 — 실측

| 문제 | 근거 |
|---|---|
| **대상 선택이 선택이 아니다** | `_aliveEnemyIndices()` 가 살아 있는 적 전부를 같은 비용으로 낸다. 고를 이유는 "HP 가 적은 놈" 하나뿐 |
| **적의 대상 선택이 균등 난수다** | `pickTargetIndex(candidateCount: conscious.length)`. 앞열이 없고, 마법사를 지킬 방법이 없고, **파티 순서가 전투에 아무 영향이 없다** |
| 모든 공격이 같은 공격이다 | `powOfWeapon` 정수 하나가 무기의 전부. 원작 무기 10종이 숫자 사다리 하나로 눌려 있다 |
| 판정 사슬이 밋밋하다 | 명중 19 이상은 절대 안 빗나가고, `저지`는 **아무 일도 일어나지 않음**이다 |

두 번째가 가장 크다. **공격 쪽이 얕은 것보다 방어 쪽 결정이 0개인 것이 더 문제다.**

### 판정

**전투에 위치를 넣는다.** 좌표가 아니라 정수 두 종류다.

```
각자의 rank (자기 진영 안에서 1~3)  +  양측 공통의 gap (0~2)
거리 = gap + (내 rank - 1) + (상대 rank - 1)
```

이것이 격자 게임이 되지 않게 하는 선이다. **측면 우회 · 한 열 안의 개별 위치 ·
특정 적만 골라 밀어내기는 포기한다.**

### 근간은 바꾸지 않는다

드래곤 퀘스트식 — **라운드 시작에 전원 명령 → 일괄 해결 · 자유 이동 없음 · 1인칭**.
이동은 위치 지정 단계가 아니라 **행동의 결과이거나 행동 그 자체**다.

베낀 곳: 대열을 전투 밖에서 정하는 것은 DQ4·5 「대열」, 열 + 무기 사거리는 세계수의 미궁,
**앞을 치워야 뒤가 열리는 것**은 다키스트 던전, 상시 지시는 DQ4 「작전」.
다키스트 던전만 라운드 구조가 다르므로(개별 행동) **"닿는 범위" 개념만** 떼어 왔다.

### 왜 B3 보다 먼저인가

1. **규격이 크게 바뀐다.** `rank` · 무기 사거리 · `partyCapacity` — CONTRACT **v1 → v2**.
   RPG 에 붙인 뒤에 하면 양쪽을 고쳐야 하고, 지금 하면 한쪽이다
2. **B1·B2 가 만든 것이 정확히 이걸 위한 물건이다.** 헤드리스 순수 Dart · 시드 고정 난수 ·
   `dart run` 으로 초 단위 반복. Flutter 재빌드 없이 전투 설계를 굴려 볼 수 있다
3. **7차 판정이 미룬 밸런스 재설계가 여기서 같이 풀린다.** 부록 U 의 두 문제(마법이 물리를
   압도, Black Knight 945)는 피해 사슬을 손대야 풀리는데 B5-05 가 그 사슬을 연다

### 전제가 하나 틀려 있었다 — 5인 파티

논의 중에 **파티는 5인 + 소환수가 기본**임이 확인됐다. 지금까지의 전투 실측은
**fixture 17개 중 14개가 2인 파티**에서 나온 것이다([부록 W](../blueprint/_meta/GROUND_TRUTH.md)).

| | 2인 | 5인 |
|---|---|---|
| 라운드 (Giant+Wolf) | 9 | **4** |
| 라운드 (Orc ×3) | 5 | **3** |
| 적 특수 능력 발동 (Basilisk ×2) | **0회** | **10회** |

**실전은 3~4 라운드**이고, **적의 특수 능력은 5인부터 처음 켜진다**
(`consciousPlayers > 3` 게이트). 그래서 **B5-00(fixture 5인 재작성)이 B5 의 첫 이슈**다 —
그 전에는 어떤 밸런스 측정도 틀린 판 위에서 나온다.

### 이미 이 판정으로 뒤집힌 것

- **7차 판정의 "규격이 닫혔다"** — 닫히지 않았다. v2 로 연다
- **B2-10 의 영입 처리** — 마음을 돌린 적을 판에서 지우고 `slot: -1` 로 넘기는 방식이었다.
  전투 중에 슬롯에 앉아 싸우는 방식으로 바꾼다 (B5-09)
- **B2-05 의 민첩 선제** — 유지한다. 단 연계를 **순서 의존이 아니라 상태 의존**으로 설계해야
  한다("밀려난 상태의 적은 다음 피격에 추가 피해"). 순서에 걸면 민첩 난수 때문에 복권이 된다

### 이 판정이 틀릴 수 있는 지점

- **3~4 라운드에 위치 기제가 안 들어갈 수 있다.** 간격을 좁히는 데 2라운드가 걸리면 전투의
  절반이 걸어다니는 시간이다. B5-01 이 초기 간격 분포를 실측해서 이것부터 확인한다
- **DQ 의 무기 사다리가 표로 바뀐다.** 최소·최대 사거리를 넣으면 "다음 마을에서 더 좋은 검"
  이라는 리듬이 흐려진다. 사거리대마다 사다리를 따로 두면 상점·드랍 표가 3배가 된다
- **이동원이 넷이 된다**(대열 전진 · 전진 공격 · 넉백 · 회피 후퇴). 그중 둘은 예측이 안 된다.
  **"사거리 밖은 벌점이지 무효가 아니다"** 라는 불변식이 무너지면 즉시 재미없어진다
- **Pascal 이 나오면**(6차 판정) B5 는 대부분 우리 판단이라 대조할 것이 많아진다

## 9차 판정 (2026-09-06) — 전투 메뉴를 원작대로 두지 않는다. B6 신설

### 결정

**원작의 전투 메뉴 구조를 버린다.** 규칙(B1·B2·B5)은 그대로 두고, **무엇을 언제 물어보는지**를
다시 짠다. 최상위 메뉴 13줄 → **6줄**, 마법 다섯 갈래 → **기술 목록 하나**(emoji 가 범주를 말한다).
규격은 **v2 → v3**.

`issues/B6-battle-modernize/` 7개 이슈. 실행은 콘솔 → Flutter 실험실 → 게임 순.

### 왜

- **갈래가 곧 메뉴 줄이었다.** 마법 45종을 번호대로 나눈 것이 그대로 최상위 메뉴가 됐다.
  나눔의 기준이 "무엇을 하는가" 가 아니라 "몇 번대인가" 라, `특수 마법` 안에
  **독**(상태이상)과 **능력 저하**(정신계)가 함께 있었다.
- **도망이 자동 성공이었다.** 슬롯 1~4 가 각자 굴리고 하나만 성공하면 전원 도주라,
  다섯 명이 굴리면 거의 언제나 성공했다. 그리고 리더는 도망칠 수 없었다.
- **아이템이 RPG 쪽에 없었다.** B2-06 이 전투에 넣었지만 카탈로그에 장비만 있어
  `held` 를 채울 수 없었다(B3-03 의 「남긴 것」). 검에 바르는 것이 생기면 소비품은 필수다.
- **B4-01 이 실험실을 만들어서 이제 눌러 볼 수 있다.** 메뉴 구조는 수치가 아니라 손에
  닿는 문제라, 재는 도구가 아니라 누르는 도구가 필요했다. 그것이 생긴 직후가 때다.

### 무엇을 베꼈나

- **기술 목록 하나 + 범위 표시**: FF · DQ 의 주문 목록. 갈래를 먼저 고르지 않는다.
- **도망은 파티 명령**: DQ 「도망친다」. 한 번 굴리고 실패하면 라운드를 잃는다.
- **무기 도포**: 위쳐의 오일 · 다키스트 던전의 독 단검. **3 라운드**로 두는 것은
  실전이 3~4 라운드(부록 W)여서다 — 바르는 턴 하나와 남은 전투 대부분을 바꾸는 길이.

### 이 판정으로 뒤집힌 것

- **B5-99 의 "규격 v2 동결"** — v3 으로 연다. `Enemy::ChangeAttribute` 의 적별 덮어쓰기는
  **이번 v3 에 넣지 않는다** — 별개 판정(B3-01 참조). 한 번에 하나만 연다.
- **B2-03 의 "상태이상은 독·의식불명·사망 넷뿐"** — 마비가 생긴다. 단 `Condition` 열거에는
  넣지 않고 **도포 효과의 결과**로만 둔다(적의 다음 행동을 지운다). 원작의 네 상태는 그대로다.
- **B2-06 의 "아이템은 medical · crystal 둘"** — `coating` 이 셋째 종류.

### 지키는 것

B5 의 불변식(사거리 밖은 벌점) · DQ 근간(라운드 시작 일괄 명령) · `hd_battle` 순수성
(emoji 도 한국어도 model 에 없다 — 열거값을 내고 `hd_battle_text` 가 글자를 붙인다).

### 이 판정이 틀릴 수 있는 지점

- **기술 목록이 30줄을 넘는다** (마법 레벨 20). 갈래 선택을 없앤 대신 스크롤이 생긴다.
  누르는 횟수는 줄지만 훑는 시간은 늘 수 있다. 실험실에서 실제로 써 보고 판단한다 —
  길면 **최근 쓴 것을 위로** 올리는 정도로 대응하고, 갈래를 되살리지는 않는다.
- **도포 3 라운드가 너무 강할 수 있다.** 화염병 하나로 언데드 전투가 끝나면 값이 없다.
  `damage_band.dart` 에 도포 열을 추가해 잰다.
- **시작 인벤토리가 원작 난이도를 깨뜨릴 수 있다.** 회복약 3개면 초반 전투가 쉬워진다.
  실측 뒤 개수를 줄인다 — 개수는 숫자 하나다.

## 10차 판정 (2026-09-08) — RPG 핵심을 다시 쓴다. W 트랙 신설

### 결정

**인물·파티·아이템·장비를 새 순수 Dart 패키지로 다시 쓴다.** 기존 코드를 고치지 않는다.
`packages/hd_world` + `packages/hd_world_text` + `hd_world_lab`(OpenAPI 서버 + 마우스 화면).
**전투가 간 길을 그대로 간다** — `hd_battle` 이 `application/battle.dart` 572줄을 고치는
대신 새로 쓴 것과 같은 판정이다.

**겉은 그대로 둔다.** `presentation/`(Bonfire·패널·입력) 3,298줄과 `application/ports/` 는
손대지 않는다. 새 모델은 그 포트 뒤로 들어간다.

### 왜

- **새 기획이 지금 모양에 안 들어간다.** BP-44~47 을 쓰면서 구조가 어긋나는 곳이 넷 나왔다 —
  장비 부위가 단수 함수라 쌍수·횃불이 들어갈 자리가 없고(부록 Z-5), 파티 버프가 저장값인데
  계산값이어야 하고, 인물이 문자열 63가지를 분기하는 형태라 `hands`·`shape`·`classMask` 를
  붙일 데가 없고, 타일 열거가 지형과 스크립트 모드를 겸직한다.
- **세 트랙이 같은 파일 여섯 개를 만진다.** B7(직업·preset) · B8(무기·손) · B9(슬롯·통행)
  이 전부 `player.dart` · `party.dart` · `item_type.dart` 를 고친다. 점진적으로 하면
  같은 파일을 세 번 고친다.
- **다시 쓸 부분에 테스트가 없고 이미 거짓말을 하고 있다.** 마법 시전 0건 · 타일 이벤트 0건 ·
  메뉴 흐름 1건. 부록 Z 의 세 건(절벽이 평지, 늪이 안 아픔, 마법 35·36 이 아무것도 안 함)이
  그 결과다. **지킬 동작이 없으니 회귀 위험도 없다.**
- **세이브를 지킬 이유가 없다.** `save_data_*.json` 은 gitignore 이고 파일이 0개다.
  호환성은 스스로 만든 제약이었다.
- **cm2 결합이 생각보다 느슨하다.** 쓰이는 심볼 43개 중 상위 넷이 지도 칠하기(907회)와
  메뉴(592회)다. `Player::ChangeAttribute` 가 만지는 속성 이름은 **15개**뿐이다.
  전투에서 `cm2_battle_adapter.dart` 218줄이 한 일과 같은 크기다.

### 무엇을 베꼈나

- **명령·이벤트 역전 제어**: `hd_battle` 의 `applyCommand`. `World.apply` 가 유일한 문이고
  **throw 하지 않는다** — 거절은 닫힌 열거를 실은 이벤트다. 그래서 터미널·브라우저·
  테스트·재생이 같은 모양을 쓴다.
- **이름표 분리**: `hd_battle_text`. 한국어와 emoji 는 모델에 없고 화면이 `GET /api/text` 를
  한 번 받아 전부 거기서 찾는다.
- **레지스트리**: 아이템·직업이 전역 `const` 가 아니라 넘겨받는 카탈로그다. 옛 표는
  15곳이 직접 읽어서 **다른 데이터로 규칙을 시험할 방법이 없었다.**
- **OpenAPI + 안내 두 벌**: `tools/mapEditor` 가 이미 하던 것. 규격은 필드를 말하고
  `GET /api/guide` 는 뜻을 말한다.

### 왜 콘솔이 아니라 서버·화면인가

전투는 한 번에 한 물음이라 터미널이 맞았다. 장비는 **부위 여덟이 동시에 보여야** 하고
(왼손을 채우면 오른손이 잠긴다), 고칠 때마다 최종 수치가 다시 계산되며, 후보가
스무 개를 넘는다. 번호를 외워 누르는 일이 아니다.

모델이 이미 명령과 사실로 말하기 때문에 화면과 API 가 **같은 문**을 쓴다 —
서버는 규칙을 하나도 갖지 않는다.

### 지키는 것

- **독립성** — `hd_world` 는 이 레포의 어떤 패키지도 import 하지 않는다.
  `dart:io` · `DateTime.now` · `print` 도 막는다. purity 테스트와 CI 가 확인한다.
- **파생값 무저장** — 무기 종류·최종 수치·통행 능력·시야는 읽을 때 계산한다.
  옛 `PartyBuffs` 네 칸 중 셋이 썩은 것이 저장했기 때문이다.
- **경계 번호 고정** — 부위 `wire` 0~5 는 이전 모델 값 그대로다. 옛 세이브가 그대로 올라온다.
- **`presentation/` 무변경** — 겉은 그대로 보인다.

### 이 판정이 틀릴 수 있는 지점

- **경계가 없어 "게임 전체 재작성" 으로 번질 수 있다.** 전투는 입력·출력이 명확했고
  RPG 는 아니다. 그래서 패키지를 **빼는 것으로** 정의했다(Flutter 없음·렌더링 없음·
  cm2 없음·에셋 없음). 지도·대화·세이브는 **이 판정에 들어 있지 않다** — 첫 조각이
  증명한 뒤에 별개로 판정한다.
- **두 모델이 공존하는 기간이 위험하다.** B3 가 전투에서 겪은 것과 같다. 어댑터가 둘
  붙어 있는 동안은 어느 쪽이 정본인지 흐려진다.
- **직업 17종이 콘텐츠 없이 붙어 있다.** 표는 이식했지만 전직 이벤트도 기술 성장도 없다.
  쓰이지 않는 표가 되면 `powOfShield` 와 같은 종류의 죽은 데이터다.
- **아이템 31종의 손·모양 두 칸은 우리 판단이다.** 원작에 없다. 장검을 양손으로 둔 것
  같은 배정이 플레이에서 이상하면 그 줄만 고친다.
