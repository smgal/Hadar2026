# S3-05 파일럿 — 퀘스트 3개 배치 생성 + 사람 플레이 검수

- **상태**: BLOCKED (S3-02 · S3-03 · S3-04 대기)
- **구간**: S3
- **규모**: M
- **선행**: [S3-02](S3-02-generation-prompt.md) · [S3-03](S3-03-map-generation.md) · [S3-04](S3-04-minimal-validation.md)
- **설계 근거**: [MILESTONES §4 · §5](../MILESTONES.md) · [DECISION-LOG](../DECISION-LOG.md)

> **판정 이슈다.** 산출물은 퀘스트 3개와 **측정값·판정**이고, 기록 장소는 [DECISION-LOG.md](../DECISION-LOG.md) 다.

## 착수 조건

- [S3-02](S3-02-generation-prompt.md) · [S3-03](S3-03-map-generation.md) · [S3-04](S3-04-minimal-validation.md) 전부 `DONE`.
- [S3-01](S3-01-quest-spec-format.md) 서식으로 쓴 **개요 3장**이 준비되어 있어야 한다.
  개요는 **사람이 이 이슈 착수 전에** 쓴다 — 개요 작성 시간을 생성 비용에 섞지 않기 위해서다.

## 문제

[S3-02](S3-02-generation-prompt.md)~[S3-04](S3-04-minimal-validation.md) 가 끝나면 "AI 가 cm2 를 만든다" 가 참이 된다.
그러나 **그것이 도움이 되는지는 별개 질문**이다. [DECISION-LOG 1차 판정](../DECISION-LOG.md) 이
"1인 개발이면 P2 는 거의 확실히 과하다" 를 틀릴 수 있는 지점으로 이미 기록했고,
2차 판정이 노선을 바꿨지만 **그 우려는 소멸하지 않았다.**

측정 없이 넘어가면 파이프라인이 게임보다 커진다([BP-52](../../blueprint/52_risks.md)).

## 무엇을 할 것인가

### 1. 개요 3장 — 기능이 겹치지 않게

| # | 소재 | 반드시 쓰는 것 | 무대 |
|---|---|---|---|
| P1 | 심부름 — 물건을 구해 전달 | 3단계 · 조건부 첫마디 · 완료 대사 | 새 맵(TOWN) |
| P2 | 선택 분기 — 두 사람 중 한쪽 편 | `Select::Init/Add/Run` · `Select::Result()` · 분기별 다른 플래그 | 새 맵(TOWN) |
| P3 | 길 열기 — 막힌 곳을 치운다 | `Map::ChangeTile` 로 월드 변화 · `FLAG_EVENT` 밟기 트리거 | 새 맵(DEN) |

**전투는 넣지 않는다** — 부록 B-2(전투 결과 코드 역전) 때문에 [S3-02](S3-02-generation-prompt.md) 금칙 6번이 금지했다.
겹치지 않게 고르는 이유: 겹치면 두 번째부터 프롬프트가 학습 효과를 받아 **비용이 과소 측정**된다.

### 2. 절차 (3개 각각)

1. [S3-01](S3-01-quest-spec-format.md) 서식으로 개요 확정 (착수 전에 완료).
2. `flag_alloc alloc --quest P1 --count <n>` → 인덱스 배정.
3. [S3-03](S3-03-map-generation.md) 의 curl 시퀀스로 맵 생성 + NPC 배치 → 좌표 목록.
4. [S3-02](S3-02-generation-prompt.md) 프롬프트 실행 → 파일 4종.
5. [S3-04](S3-04-minimal-validation.md) `quest_check.sh` → error 0 까지 최대 3회.
6. **사람이 직접 플레이 검수** (아래 §3).
7. 사람이 손본 것을 커밋. **손본 줄을 별도 커밋으로 분리**해야 줄 수가 측정된다.

### 3. 플레이 검수 항목 (S1 완료 판정과 동일 기준)

- [ ] 새 맵을 **이름으로** 진입할 수 있다
- [ ] NPC 가 각각 말하고, 최소 1명은 **퀘스트 상태에 따라 다른 말**을 한다
- [ ] 수락 → 획득 → 전달 → 보상 **전 과정이 완주**된다
- [ ] 각 단계가 플래그로 기록되고 **중간 세이브·로드 후에도 진행이 유지**된다
- [ ] 완료 후 다시 말을 걸면 **완료 상태의 대사**가 나온다
- [ ] 문장을 읽고 어색하지 않다(원작 문체 — [BP-43](../../blueprint/43_content_style_guide.md))

## 측정 항목

| 항목 | 정의 | 어떻게 |
|---|---|---|
| **생성 성공률** | `quest_check.sh` error 0 에 도달한 퀘스트 / 3 | 재시도 3회 내 도달만 성공 |
| **재시도 횟수** | 퀘스트별 0~3 | 각 회차의 위반 규칙 ID 도 기록 |
| **생성 줄 수** | AI 출력 cm2 의 총 줄 수(주석·빈 줄 제외) | `grep -vc '^\s*\(#.*\)\?$'` |
| **손본 줄 수** | 사람이 고친 + 지운 + 추가한 줄 수 | 별도 커밋의 `git diff --numstat` 합 |
| **손본 비율** | 손본 줄 / 생성 줄 | 아래 판정의 주 지표 |
| **손본 이유 분류** | 문체 / 논리 / 심볼·좌표 / 게임이 표현 못 함 | 4분류. 각 줄에 태그 |
| **플레이 오류 수** | 검수에서 드러난 오류 | `quest_check.sh` 가 **잡지 못한** 것만 |
| **검사 대비 플레이 오류** | 플레이 오류 / (린터 오류 + 플레이 오류) | 검증의 부실도 |
| **소요 시간** | 개요 확정 후부터 검수 통과까지, 퀘스트별 | 실제 시계 |

## 판정 — **착수 전에 못박는다**

> 아래 규칙은 **측정 전에 확정된 것**이며, 측정값을 보고 바꾸지 않는다.
> 바꾸려면 [DECISION-LOG.md](../DECISION-LOG.md) 에 **새 항목**을 추가하고 기존 항목은 고치지 않는다.
> 규칙 변경은 판정과 **같은 커밋에 들어갈 수 없다.** (GATE-01 이 세운 규율을 그대로 따른다.)

### 주 판정 — 손본 비율

| 손본 비율 | 판정 |
|---|---|
| **≤ 20%** | **AI 가 도움이 된다.** 물량을 늘린다 |
| **20~40%** | **조건부.** 손본 이유 분류를 보고 프롬프트를 고쳐 1회 재측정. 재측정도 20% 초과면 아래 칸으로 |
| **> 40%** | **AI 가 도움이 안 된다.** cm2 생성을 중단하고 손 저작으로 간다 |
| **> 70%** | **S3 취소.** 프롬프트·검증 유지비까지 손실이다 |

**40% 를 경계로 잡은 근거**: 절반 가까이를 고치려면 생성물 전체를 읽고 각 줄의 의도를 재판단해야 한다.
읽기 + 판단 + 수정 비용이 처음부터 쓰는 비용에 근접하고, 여기에 **개요 작성·프롬프트 유지·검증 유지** 비용이 얹힌다.
20% 는 그 반대 — 문체 다듬기 수준이며 손 저작보다 확실히 싸다.

### 보조 판정 — 하나라도 걸리면 **보류**

| 관측 | 판정 |
|---|---|
| 생성 성공률이 **3분의 2 미만**(0 또는 1개만 통과) | **보류.** 프롬프트가 아직 계약을 못 지킨다 |
| **플레이 오류가 린터 오류보다 많다** | **보류.** 검증이 부실한 채로 늘리면 손 저작보다 나빠진다 (GATE-01 의 같은 규칙) |
| 손본 이유의 과반이 **"게임이 표현 못 함"** | **보류.** cm2 노선의 한계다 → [MILESTONES §5](../MILESTONES.md) 의 "꺼내야 하는 신호" 2번. [deferred/](../deferred/) 를 꺼낼지 별도 판정 |
| 퀘스트 1개가 **개요 포함 한 시간 이내**로 손으로 만들어진다 | **보류.** 20개를 손으로 만들어도 이틀이다. 자동화 회수가 안 된다 |
| 손본 이유의 과반이 **심볼·좌표** | **보류.** [S2-03](../S2-enablers/S2-03-cm2-linter.md)·[S2-04](../S2-enablers/S2-04-map-editor-cm2-support.md) 를 먼저 고친다. 프롬프트 문제가 아니다 |

**"진행" 은 주 판정 ≤20% 이면서 보조 5행 전부 통과일 때만 성립한다.** 애매하면 보수적인 쪽(보류)을 택한다.

## 완료 판정 기준

- [ ] 퀘스트 3개가 각각 `quest_check.sh` 를 통과했거나, 통과 실패가 기록되어 있다
- [ ] 3개 전부 **사람이 실제로 플레이**해 §3 항목 6개를 판정했다
- [ ] 위 측정 항목 9개가 퀘스트별로 표에 채워져 있다
- [ ] 손본 줄이 **별도 커밋**으로 분리되어 `git diff --numstat` 로 세어진다
- [ ] 손본 줄마다 4분류 태그가 붙어 있다
- [ ] 주 판정 1개 + 보조 판정 5개가 각각 명시적으로 판정되어 있다
- [ ] 최종 판정과 근거가 [DECISION-LOG.md](../DECISION-LOG.md) 에 **새 항목**으로 기록되어 있다
- [ ] 판정이 "보류/취소" 여도 기록한다. **빈 채로 두지 않는다**

## 하지 않을 것

- 퀘스트를 3개보다 많이 만드는 것. 판정 전에 물량을 늘리면 판정의 의미가 없다.
- 전투를 포함하는 퀘스트(부록 B-2).
- 측정값을 본 뒤 임계값을 조정하는 것. **명시적으로 금지**한다.
- 자동 플레이·솔버로 검수를 대체하는 것 — [S3-04](S3-04-minimal-validation.md) §하지 않을 것 과 동일한 이유(부록 B-3 · C-4).
- 배치 실행 파이프라인·큐·병렬화 — [deferred/P2-07](../deferred/P2-07-generation-pipeline.md). 3개는 손으로 순차 실행한다.
- 다른 사람의 검수. **작성자 본인이 플레이**한다(문체 판단이 측정 항목이므로).
