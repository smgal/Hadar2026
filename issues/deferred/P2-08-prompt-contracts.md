# P2-08 프롬프트 계약 운용과 검수 루브릭

> **[보류 — DEFERRED]** 이 이슈는 **무거운 생성 파이프라인 노선**(콘텐츠 서버·MCP·솔버·퍼저·8단계 하네스)에 속한다.
> 2026-09-01 2차 판정([DECISION-LOG](../DECISION-LOG.md))이 노선을 **sample-first + cm2** 로 바꾸면서 보류되었다.
> 경량 대체는 [S3-generation/](../S3-generation/) 이다 — 생성 타깃이 선언적 콘텐츠 팩이 아니라 **cm2 + 맵 JSON** 이다.
> 설계는 [`blueprint/`](../../blueprint/00_README.md) 에 그대로 유효하게 남아 있다.

- **상태**: GATED
- **구간**: P2
- **규모**: M
- **선행**: P2-07
- **설계 근거**: [BP-37](../../blueprint/37_prompt_contracts.md) · [BP-32 §32.4](../../blueprint/32_generation_harness.md) · [BP-43](../../blueprint/43_content_style_guide.md) · [D-14](../../blueprint/_meta/DECISIONS.md)

## 문제

P2-07 이 2·3·7 단계에 LLM 을 부르지만, **무엇을 어떤 계약으로 부르는지**가 파일로 존재하지 않으면
그 세 단계는 재현 불가능한 블랙박스다. 구체적으로:

- 프롬프트가 코드에 인라인이면 **버전이 없다.** 한 글자 바꾼 결과와 이전 결과를 비교할 수 없고,
  manifest 에 기록할 해시도 없다.
- 템플릿 변수가 비어도 모델이 호출된다 → `{{context_pack}}` 이 문자 그대로 들어간 프롬프트가
  전송되고, 모델은 그럴듯한 쓰레기를 낸다. **호출 전에 실패해야 한다.**
- 금칙(세계관 이탈·현대어·고유명사 임의 창작)을 검출할 기준이 없으면 6종 금칙이 규범으로만 남는다.
- Critic 의 채점 결과를 무엇으로 해석할지 정하지 않으면, 점수가 **하드 게이트처럼 쓰이기 시작한다.**
  이것이 가장 흔한 붕괴 경로다.

## 무엇을 할 것인가

프롬프트 6종의 전문, 출력 스키마 6종, 루브릭 8축, 금칙 6종의 검출 방법은
[BP-37](../../blueprint/37_prompt_contracts.md) 에 있다. 재서술하지 않는다.

**배치**: `content_gen/prompts/<role>.<version>.md` — YAML front matter + 본문.
역할 6종: `planner` · `writer_struct` · `writer_prose` · `critic` · `style_editor` · `repair`.

| # | 구현 단위 | 내용 |
|---|---|---|
| 1 | front matter 로더 | `role` · `version` · `outputSchema` · `model{id,temperature,maxTokens,responseFormat}` · `requiredVars` · `changelog` |
| 2 | `requiredVars` 검사 | 하나라도 비면 **호출 전에 실패**한다. `{{…}}` 가 남은 채 모델에 가지 않는다(R-37-7) |
| 3 | 프롬프트 해시 | 본문 전체(front matter 포함)의 SHA-256 을 `manifest.prompts[].sha256` 에 기록. **한 글자만 바꿔도 버전을 올린다**(R-37-9) |
| 4 | 모델 선택 | front matter 의 `model` 을 하네스가 읽어 manifest 에 복사. **오케스트레이터는 모델을 고르지 않는다**(R-37-8) |
| 5 | 금칙 검출 | 6종. 화이트리스트 우선 — 등장 가능한 인물·장소·아이템 목록을 주고 "이 목록 밖은 없는 것으로 취급" |
| 6 | 루브릭 8축 + 합격선 | `total`(0~40) · `minAxis`. `pass`/`conditional`/`revise` 판정식은 BP-37 §37.5.3 |
| 7 | 회귀 비교 절차 | 프롬프트를 바꿀 때 같은 입력으로 이전 버전과 비교(§37.8.2), 승격 판정(§37.8.3) |

**Critic 의 권한 경계 — 이 이슈의 핵심 불변식**
- Critic 은 **소프트 축만** 채점한다: 세계관 정합 · 인물 목소리 · 서사 구조 · 목표 명료성 ·
  보상 밸런스 · 문체 · 중복 서사 · 통합성(8축).
- **하드 항목에는 권한이 없다.** 스키마·미해결 참조·도달 불가 노드·사이클·문자열 키 누락·
  인라인 한국어·길이 상한·앵커 충돌·솔버 증명·재빌드 해시는 프로그램이 판정한다.
  Critic 이 이 항목을 지적하면 하네스가 그 finding 을 **폐기하고 로그에 남긴다**(R-37-14).
- **역으로 소프트 축을 기계가 판정하지 않는다.** 이중 판정을 만들지 않는다.
- `severity: "blocking"` finding 이 하나라도 있으면 `verdict` 는 점수와 무관하게 `revise` 다(R-37-15).
- 합격선(`minAxis ≥ 4` and `total ≥ 34`)은 **처음부터 높게** 잡는다. 대부분이 `conditional` 로
  나오는 것이 정상이며, 그것이 사람이 마지막에 봐야 할 이유다(R-37-16).
  **합격선을 낮춰 처리량을 올리자는 요구는 기각한다** — 처리량은 프롬프트 개선으로 올린다(R-37-17).

**역할 격리**(R-37-6): 한 프롬프트는 한 역할만 한다. "쓰고 검수까지" 를 한 호출에 시키지 않는다.

## 착수 조건

GATE-1 통과 + P2-07 완료.

**왜 그 전에는 안 되는가**: 프롬프트는 **파이프라인 단계의 계약**이다. 어느 단계가 무엇을 입력으로
받고 무엇을 출력해야 하는지가 확정되기 전에 프롬프트를 쓰면, `requiredVars` 목록과 출력 스키마를
추측으로 정하게 되고 파이프라인이 오면 6종 전부를 다시 쓴다. 그리고 프롬프트의 품질은
**실제 산출물을 보고서만** 개선된다 — 굴릴 파이프라인이 없으면 §37.8 의 회귀 비교 절차 자체가
작동하지 않으므로, 첫 버전을 잘 썼는지조차 알 수 없다.

## GATE-1 이 보류/취소로 판정되면

- **버려지는 것**: 프롬프트 6종 전문, 출력 스키마 6종, 재시도·Repair 프롬프트, 프롬프트 버전 관리와
  회귀 비교 절차, 모델 파라미터 관리. LLM 이 없으면 전부 쓸 곳이 없다. **P2 중 가장 잔여 가치가 낮다.**
- **그래도 남는 값**:
  - **루브릭 8축과 합격선**은 **사람이 검수할 때 쓰는 체크리스트**로 그대로 남는다. 손 저작
    퀘스트도 "인물 목소리가 일관한가 / 목표가 명료한가 / 기존 콘텐츠와 중복되지 않는가" 를 봐야 한다.
    취소 시 이 8축을 `blueprint/43_content_style_guide.md` 쪽 검수 체크리스트로 이관한다.
  - **하드/소프트 분리 표**는 검증 도구를 만들 때의 설계 규율로 남는다 — 무엇을 기계에 맡기고
    무엇을 사람에게 남길지의 기준.
  - **금칙 6종의 검출 방법** 중 기계적인 것(현대어 사전 매칭, 화이트리스트 밖 고유명사 검출)은
    사람이 쓴 문장에도 적용된다. P1-12 의 CLI 린트로 이관 가능하다.

## 완료 판정 기준

**[잠정 — GATE-1 통과 시 확정]**

- [ ] 프롬프트 6종이 `content_gen/prompts/<role>.v1.md` 로 존재하고 front matter 를 갖는다
- [ ] `requiredVars` 중 하나를 비우면 **모델 호출 전에** 실패한다
- [ ] 프롬프트 본문을 1바이트 바꾸면 해시가 달라지고, 버전을 올리지 않은 실행이 거부된다
- [ ] Critic 이 하드 항목을 지적한 finding 이 폐기되고 로그에 남는다(회귀 픽스처로 고정)
- [ ] `severity: "blocking"` 이 있으면 점수와 무관하게 `verdict == "revise"` 다
- [ ] 소프트 축을 기계가 판정하는 코드 경로가 **없다**(코드 리뷰 항목으로 고정)
- [ ] 금칙 6종 각각에 대해 위반 샘플 1건씩을 검출한다
- [ ] 좋은 예 1개 + 나쁜 예 1개가 모든 프롬프트에 들어 있다(R-37-2)

## 하지 않을 것

- 파이프라인 오케스트레이션 — P2-07.
- 모델 선택 로직·라우팅. 모델은 front matter 가 정한다.
- Critic 점수를 하드 게이트로 쓰는 것. 반대로 소프트 축을 프로그램이 판정하게 하는 것도.
- 합격선 완화. 조정은 파일럿 후 ±2점 범위이며 `rubricVersion` 을 올린다(Q-37-1).
- 문체 가이드 자체의 집필 — BP-43 소관.
