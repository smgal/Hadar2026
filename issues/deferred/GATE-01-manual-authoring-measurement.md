## 문제

P1 이 끝나면 "손으로 퀘스트를 만들 수 있다" 가 참이 된다. 그러나 **P2(AI 생성 파이프라인) 착수는
그것만으로 결정되지 않는다.** P2 의 가치는 ① 퀘스트 1개의 실제 저작 비용, ② 그 비용이 **어디에** 쓰이는가
(AI 가 줄일 수 있는 부분인가)에 달려 있고, 둘 다 P1 전에는 알 수 없었다.
[DECISION-LOG](../DECISION-LOG.md) 의 2026-09-01 판정이 "조건부 진행" 인 이유가 이것이며,
같은 문서가 **"1인 개발이면 P2 는 거의 확실히 과하다"** 를 틀릴 수 있는 지점으로 이미 기록했다.

## 왜 지금 판정하는가

**결과를 보고 기준을 바꾸지 않기 위해서다.** MILESTONES §4 는 판정 규칙을 P0 착수 **전에** 못박았고,
이 이슈는 그것을 **집행**할 뿐 재정의하지 않는다.

**이 이슈 안에서도, 측정이 끝난 뒤에도 판정 규칙을 바꾸지 않는다.** 측정값이 애매해 판정이 갈리면
**더 보수적인 쪽(보류)** 을 택한다. 규칙을 바꾸려면 [DECISION-LOG.md](../DECISION-LOG.md) 에 **새 항목**을 추가해
이유를 남기고 기존 항목은 고치지 않는다. 규칙 변경은 판정과 **같은 커밋에 들어갈 수 없다.**

## 무엇을 할 것인가

### 1. 측정 항목 — MILESTONES §4 인용 (재정의 금지)

| 측정 항목 | 어떻게 |
|---|---|
| 퀘스트 1개당 소요 시간 | 실제 시계로 기록 (5개 각각) |
| 시간의 배분 | **창작**(문장·구성) vs **기계적 배선**(ID 연결·좌표 찾기·문자열 키) 비율 |
| 검증이 잡은 오류 | `validate` 가 잡은 건수 / 플레이에서야 드러난 건수 |
| 재작업 비율 | 만든 뒤 고친 횟수 |

### 2. 판정 규칙 — MILESTONES §4 인용 (재정의 금지)

| 관측 | 판정 |
|---|---|
| 시간의 **과반이 창작**이고, 기계적 배선은 이미 도구가 처리 | **P2 진행.** AI 가 줄일 수 있는 것이 병목이다 |
| 시간의 **과반이 기계적 배선** | **P2 보류.** 먼저 도구(에디터·CLI)를 고친다. AI 를 붙여도 같은 배선을 AI 가 틀리게 할 뿐이다 |
| 퀘스트 1개가 **한 시간 이내** | **P2 보류.** 20개를 손으로 만들어도 하루다. 파이프라인 구축비가 회수되지 않는다 |
| 플레이에서야 드러난 오류가 **검증이 잡은 것보다 많다** | **P2 보류.** 검증이 부실한 상태로 대량 생성하면 손으로 만들던 때보다 나빠진다 |
| 목표 콘텐츠 물량이 **퀘스트 20개 미만**으로 확정 | **P2 취소.** 손으로 만드는 것이 낫다 |

5행 중 **하나라도 "보류" 에 해당하면 보류**다 — "진행" 은 만장일치를 요구한다.
마지막 행의 물량 목표는 **P0-00 이 확정한 값**을 쓰고 이 시점에 다시 정하지 않는다.

### 3. 무엇으로 5개를 만드는가

**P1-16 의 퀘스트는 표본에 넣지 않는다** — 학습 곡선과 버그 수정이 섞여 정상 저작 비용이 아니다.
새로 5개를 만들되 **기능 커버리지를 겹치지 않게** 고른다(겹치면 배선 비용이 학습 효과로 과소 측정된다).

| # | 소재 | 반드시 쓰는 기능 | 무대(기존 맵만) |
|---|---|---|---|
| Q1 | 심부름 — 물건을 찾아 전달 | `acquire` · `deliver` · 조건부 첫마디 | `TOWN1` |
| Q2 | 토벌 — 특정 적을 n마리 | `defeat`(카운터) · 인카운터 · `battle_won` | `DEN1` |
| Q3 | 선택 분기 — 두 편 중 한쪽 | `choose` · 스테이지 `next` 분기 · `set_npc_state` | `TOWN1` |
| Q4 | 실패 가능 — 시한 안에 | `failConditions` · `timeoutSteps` · `onFail` | `GROUND1` |
| Q5 | 원정 — 맵을 넘나든다 | `reach` · `warp` · `enter_place` · `visited` | `TOWN1` → `GROUND1` → `DEN1` |

- **새 맵을 만들지 않는다** — 맵 제작 비용이 섞이면 측정이 오염된다. 앵커가 요구하는 최소 타일 편집만
  허용하고 그 시간은 **배선**으로 센다.
- 5개 모두 `validate` 통과 + **사람이 플레이해 완주**해야 표본으로 인정된다. 완주 실패분은 시간만 기록하고
  표본에서 제외하되 그 사실을 판정 근거에 남긴다.

### 4. 시간을 어떻게 기록하는가

- **10분 슬라이스 단위.** 작업을 시작할 때 **먼저** 범주를 적고 타이머를 켠다.
  **사후 추정 금지** — "대충 절반쯤 창작이었다" 는 기록으로 인정하지 않는다.
- 범주를 바꿀 때마다 슬라이스를 끊는다. 10분 미만은 우세한 범주에 합친다.
- 기록 파일 `issues/gate01-log.md` — 슬라이스마다 `시각 · 퀘스트 · 범주 · 한 줄 내용`.
  하루를 넘겨 재개하면 첫 5분은 "대기"(문맥 복구)로 센다.

### 5. 창작 vs 기계적 배선 — 분류 규칙

**핵심 판정 질문 하나로 결정한다.**

> **"같은 스펙과 같은 자료를 준 다른 사람이 이 작업을 해도 결과가 같은가?"**
> **예 → 기계적 배선.** **아니오 → 창작.**

**갈리지 않는 경우를 위한 결정 규칙 5개** (순서대로 적용):

1. **산출물이 문장이면 창작, 식별자면 배선.** 대사·요약·저널 문구·목표 label = 창작.
   ID·문자열 키·좌표·정수 id 입력 = 배선.
2. **`validate` 오류 수정은 규칙 계층으로 분류.** **L1(스키마)·L2(참조 무결성) = 배선**,
   **L3(그래프 구조) = 창작**(스테이지 구성·대화 분기를 다시 설계하는 것이므로).
   결정적 규칙이므로 오류마다 규칙 ID(`V-L1-*` 등)를 기록에 남긴다.
3. **"무엇을 시킬까" 는 창작, "그것을 어떻게 참조할까" 는 배선.**
   목표를 `acquire` 로 할지 `flag_set` 으로 할지 = 창작. 그 아이템 ID 를 찾아 넣기 = 배선.
4. **도구·빌드·앱 실행 대기는 어느 쪽도 아니다 — "대기" 로 별도 기록**, 배분 분모에서 제외.
5. **플레이 확인은 "검증" 으로 별도 기록.** 단 플레이 중 발견한 문장 문제 수정은 창작,
   참조 문제 수정은 배선이다.

**배분 비율의 분모는 `창작 + 배선`** 이다. 대기·검증은 총 소요에만 들어간다 —
그래야 "AI 가 줄일 수 있는 것이 병목인가" 라는 원래 질문에 답한다.

**판정 규칙 1행 후단("배선은 이미 도구가 처리")의 판정**: 배선 슬라이스 중
**CLI 나 맵 에디터가 이미 자동화한 작업을 손으로 한 것**을 표 C 에 따로 센다.
그 시간이 배선의 절반을 넘으면 후단이 **거짓**이고 보류다.

## 하지 않을 것

- **판정 규칙 수정** — 결과를 보고 기준을 바꾸는 것이 이 게이트가 막으려는 바로 그 행위다. 바꾸려면 별 항목·별 커밋.
- **코드 변경** — 판정 이슈다. 저작 중 발견한 결함은 이슈로 등록하고 여기서 고치지 않는다.
  (5개를 만들 수 없게 막는 차단 결함만 예외로 별 이슈를 만들어 먼저 처리한다.)
- **새 맵 제작** — 측정 오염.
- **AI 로 퀘스트를 만들어 비교하는 것** — 그것이 P2 이고 지금은 그 착수 여부를 판정하는 중이다.
  "AI 로도 한 번 해 보자" 는 유혹이 이 게이트를 무의미하게 만든다.
- 표본 확대(5개 → 10개) — 5개로 판정한다. 표본을 늘려 원하는 답을 얻으려는 행위를 막는다.
