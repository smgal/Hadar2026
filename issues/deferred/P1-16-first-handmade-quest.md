> **[보류 — DEFERRED]** 이 이슈는 **선언적 콘텐츠 팩 노선**에 속한다.

## 문제

**퀘스트가 0개다.** 실측이 그렇다 — `grep -rn quest hadar2026_app/lib` 는 0건이고,
`assets/` 에도 퀘스트라 부를 수 있는 데이터가 없다. cm2 `Talk` 393개와 맵 JSON 대사 56줄은
전부 **선형 대화**이고, 조건도 목표도 진행 상태도 없다.

P1-01~P1-15 는 각각 "표현 수단" 을 만든다. 그러나 **수단이 실제로 조립되는지는 아무 이슈도 증명하지 않는다.**
지금까지의 완료 판정은 전부 단위 수준이다 — 파서가 파싱하는지, 인덱스가 조회되는지, 화면이 뜨는지.
**퀘스트 하나가 처음부터 끝까지 굴러가는지는 별개의 명제다.**

BP-91 이 이것을 미리 증명하려 했고, 그 과정에서 실제로 결함 13건을 찾아냈다
([BP-91 §13](../../blueprint/91_appendix_worked_example.md)). 그런데 그것은 **문서상의 예제**다.
실물로 돌려 본 적이 없다.

## 왜 지금 고쳐야 하는가

**이것이 P1 의 완료 판정 이슈다.** MILESTONES §3 의 마지막 기준이
"**손으로 만든 퀘스트 1개가 완주 가능하다** — 사람이 실제로 플레이해서 확인" 이다.

그리고 이 이슈가 통과하지 않으면 **GATE-01 의 측정 자체가 성립하지 않는다** —
퀘스트 5개를 만들어 시간을 재려면 먼저 1개를 만들 수 있어야 한다.
GATE-01 의 시간 측정에서 이 첫 퀘스트는 **학습 곡선이 섞여 있으므로 표본에 넣지 않는다**(GATE-01 이 그 규칙을 갖는다).

## 무엇을 할 것인가

**BP-91 의 예제를 참고해 손으로 퀘스트 1개를 만들고 사람이 플레이해 완주한다.**
AI 생성 파이프라인을 쓰지 않는다 — 그것이 P2 이고, 이 이슈는 **수동 저작이 가능해졌는가**를 묻는다.

1. **소재는 BP-91 의 `quest.gen_ep1.name_on_ossuary`("유골에 새길 이름")를 쓴다.**
   그 예제가 이미 원작 실측 재료 위에 세워져 있어(§1.2) 창작 비용 없이 배선만 검증할 수 있다.
   - 무대: `TOWN1` 안 두 장소 — `place.core.lore_tavern`(주점) → `place.core.lore_crypt`(용사 납골당).
   - 인물: `npc.core.lore_tavern_drunk`(주점 취객, 원작 `lore_ep1.cm2` `On(17,37)`) ·
     `npc.core.lore_crypt_keeper`(납골당지기, `On(71,77)`).
   - 신규: 아이템 1개 · 대화 3개 · 앵커 1개. **전투 없음** (tier 1 은 "말 거는 법과 저널 보는 법" 을 가르친다).
   - 좌표는 [BP-91 §1.3](../../blueprint/91_appendix_worked_example.md) 의 `TOWN1.json` 실측을 쓴다 —
     `(17,37)` objUpper 129 → talk, `(16,37)` → move(인접 통행 칸), `(71,77)` objUpper 133 → talk,
     `(62,76)` A5 14 → move(**신규 `trigger` 앵커 자리**), `(62,75)` objUpper 128 → talk(통행 불가).
2. **팩은 `gen_ep1` 이 아니라 `core` 또는 별 팩 `ep1` 로 만든다.**
   `gen_` 접두사는 생성 팩을 뜻하고 이 퀘스트는 **손으로 만든 것**이므로, 이름이 사실과 어긋나면 안 된다.
   팩 id 는 착수 시 확정하고 `pack.json#generatedBy` 에 **사람이 만들었음**을 기록한다.
3. **저작 순서** — [BP-30 §6.1](../../blueprint/30_toolchain_overview.md) 의 "사람이 손으로 퀘스트 하나 만들기" 워크플로를 따른다.
   `new` → 편집 → `validate` → `build` → 실행 → 수정 반복.
4. **저작 과정에서 걸린 것을 전부 기록한다.**
   - `validate` 가 잡은 오류 / 플레이에서야 드러난 오류를 **분리해 센다**.
   - 막힌 지점(스펙이 답을 주지 않는 곳)은 이슈에 append 하고,
     설계와 어긋나는 사실을 발견하면 **`blueprint/_meta/GROUND_TRUTH.md` 를 먼저 고친다**(issues/README.md 규약).
   - 이 기록이 GATE-01 의 측정 양식을 검증하는 예비 실행이 된다.
5. **선행 이슈들의 접합이 실제로 동작하는지 확인한다** — 이 퀘스트가 지나가는 경로:
   - 앵커 → 트리거 인덱스 → 티어 0(P1-10 · P1-11)
   - 조건부 첫마디(P1-07) — 수주 전/수주 후/완료 후 3가지가 달라야 한다
   - `acquire`/`deliver` 목표(P1-05 의 아이템 + P1-08 의 목표 판정)
   - `step_on` 앵커 발화 — `(62,76)` 은 `move` 타일이므로 **타일 비트 무의존**이 여기서 실증된다(D-27)
   - 저널 표시(P1-13) · 소지품 표시(P1-14)
   - `enter_place` 발행(P1-15) · `item_gained` 발행(P1-05 · P1-09)
   - 세이브 → 로드 → 이어서 완주(P1-04)

## 완료 판정 기준

- [ ] **사람이 실제로 플레이해 퀘스트를 완주했다.** 수주 → 목표 진행 → 단계 전이 → 완료 → 보상까지 끊김이 없다
- [ ] 같은 NPC 가 **수주 전 / 진행 중 / 완료 후 3가지 다른 첫마디**를 한다 (플레이로 확인)
- [ ] 저널에서 진행 중 목표가 보이고, 목표 하나를 달성하면 저널 표시가 바뀐다 (플레이로 확인)
- [ ] 소지품 화면에서 퀘스트 아이템이 보이고, 전달 후 사라진다 (플레이로 확인)
- [ ] `move` 타일 위의 `trigger` 앵커가 밟아서 발화한다 — `(62,76)` (플레이로 확인, D-27 실증)
- [ ] **퀘스트 도중에 세이브 → 게임 재시작 → 로드 → 이어서 완주할 수 있다** (플레이로 확인)
- [ ] `hadar_content validate` 가 통과하고, `build` 를 두 번 돌려 산출물 해시가 같다
- [ ] 저작 과정 기록이 남았다 — `validate` 가 잡은 오류 건수 / 플레이에서야 드러난 오류 건수가 **분리되어** 적혀 있다

      **이것이 P1 전체의 통합 회귀 테스트가 된다** — 이후 어떤 리팩터링도 이 테스트를 깨면 안 된다

      퀘스트 중간 상태를 세이브 → 로드 → 남은 경로 완주. P1-04 의 v2 봉투와 P1-08 의 상태 기계 접합을 고정

## 하지 않을 것

- **AI 로 생성하지 않는다.** 손 저작 가능성을 증명하는 것이 목적이다.
- 퀘스트 2개 이상 — **GATE-01** 이 5개를 만든다. 여기서는 1개다.
- 헤드리스 시뮬레이션으로 완주를 증명하는 것 — **P2**(D-26 의 2축 판정). 여기서는 **사람이 플레이한다.**
- 솔버·퍼저·트레이스 비교 — P2.
- 검수 루브릭·문체 채점 — P2([BP-37](../../blueprint/37_prompt_contracts.md)).
- 새 맵 제작 — `TOWN1` 기존 지형만 쓴다. 앵커가 요구하는 최소 편집만 허용한다.
- 전투를 포함한 퀘스트 — tier 1 은 전투 없음. `defeat` 목표 검증은 GATE-01 의 5개 중 하나가 맡는다.
