## 0. 질문과 전제

- **처음 질문**: 월드맵과 마을맵을 나누지 않고, 10000×10000 한 장으로 게임을 만들 수 있는가.
  기획 문제보다 **기술적으로 되는지**를 먼저 본다.
- **이어진 질문**
  - 지금부터 이 방식으로 만들어 두면, 지금의 50×50 지도에서 손해는 없는가
  - 모든 스크립트를 절대 좌표로 바꿔야 하는 것 아닌가
  - 들어올 때 플래그를 보고 지도를 바꾸는 부분은 어떻게 하는가
  - 그 밖에 §5 의 Q4~Q6
- **전제**
  - 지도는 이 레포 밖에서 따로 만드는 **AI 지도 생성기**가 만든다.
  - 빠른 이동은 나중에 기획한다. 이 문서는 다루지 않는다.

## 1. 결론

- **가능하다. Bonfire·Flame 을 바꿀 필요는 없다.** 다만 지금 구조로는 안 되고,
  지도를 64×64 조각(chunk)으로 나눠 **일행 주변만 메모리에 두는** 방식으로 바꿔야 한다.
- **50×50 지도도 같은 코드로 돈다.** 「조각 1개 · 구역 1개」인 세계로 취급하면 된다. 손해는 무시할 수준이다(§5 Q1).
- **스크립트는 지금처럼 구역 안 좌표로 쓴다.** 절대 좌표로 바꾸지 않는다(§5 Q2).
- **설계의 중심은 「지도 모양과 스크립트 실행을 떼어 놓는다」 하나다**(§3). 경계·미리 읽기·플래그 변형 문제가 여기서 같이 풀린다.
- **먼저 정해야 할 것은 엔진보다 콘텐츠 규칙이다**(§8). 칸 하나의 넓이처럼 나중에 변환기로 고칠 수 없는 것이 있다.

## 2. 직접 잰 값

재는 방법은 §10.

### 2.1 지금 구조로 1억 칸(10000×10000)을 만들면

| 항목 | 칸당 | 1억 칸이면 |
|---|---|---|
| 메모리 — 지금처럼 칸마다 `MapUnit` 객체 하나 | 76 B | **7.6 GB** |
| 메모리 — 층별 숫자 배열(`Uint8List` 등)로 바꾸면 | 10 B | 1 GB |
| 지도 파일 — 지금의 RPG Maker JSON | 16 B | 1.6 GB. 한 번에 읽을 수 없다 |
| 세이브 — 지도 전체를 칸마다 JSON 객체로 씀 | 71 B | **7.1 GB** |
| 배포 크기 — 압축한 2진 파일 | 0.28~0.36 B | **28~36 MB** |

- 숫자 배열로 바꿔도 1 GB 라서 웹·모바일에 통째로 올릴 수 없다. **조각으로 나누는 것이 필수다.**
- 배포 크기는 걱정할 수준이 아니다. 단 원작 지도 기준 값이다. AI 가 만든 지형이 더 복잡하면 커진다(후보 7).
- 세이브는 **지금도** 100×100 지도 한 장에 0.71 MB 다.

### 2.2 조각 방식으로 바꿨을 때 드는 비용

| 항목 | 값 |
|---|---|
| 칸 하나 찾기 — 50×50 | 지금 1.3 ns → 조각 5.7 ns |
| 칸 하나 찾기 — 1000×1000 | 지금 1.7 ns → 조각 26 ns |
| 한 프레임에 찾는 칸(110개 남짓) | 26 ns × 110 ≈ 3 µs. 프레임 한 장(16.7 ms)의 0.02% |
| 50×50 지도 메모리 | 지금 190 KB → 조각 1개 41 KB |
| 메모리에 두는 조각 9개 | 약 430 KB. 세계 크기와 상관없이 일정 |
| 조각 하나 만들기 (압축 1.5 KB 풀기 + 바뀐 칸 20개 덮기) | 15 µs |
| 구역 스크립트 처음 읽기 — `town2.cm2` 548줄 | 1.35 ms |
| 구역 스크립트 처음 읽기 — `Map002.cm2` 75줄 | 0.20 ms |

## 3. 설계 원칙 — 지도 모양과 스크립트 실행을 떼어 놓는다

```
지도 모양 = 원본 조각 + 세계 변경 목록 (절대 좌표 → 타일 번호)

Map::ChangeTile 실행  → 변경 목록에 기록 (그 조각이 메모리에 없어도 기록)
                        + 그 조각이 메모리에 있으면 바로 반영
조각을 읽을 때        → 원본을 풀고, 변경 목록에서 그 조각에 속한 칸만 덮음
                        (스크립트는 실행하지 않음)
조각을 읽고 버리는 기준 → 일행과의 거리 (구역 경계와 무관)
구역 스크립트         → 사건(말 걸기·밟기)이 일어난 칸이 속한 구역의 것을 그때 실행
구역 설정(시야 등)    → 스크립트가 아니라 구역 목록에 적어 둔 값
세이브               → 플래그 + 변경 목록
```

- 50×50 지도는 이 그림에서 「조각 1개 · 구역 1개 · 왼쪽 위 (0, 0)」 인 경우다.
- 이 원칙에 이르기 전에 버린 안은 §6.

## 4. 이미 되는 것

- **화면 그리기** — 보이는 칸만 그린다(`lib/presentation/panels/world_map_renderer.dart:107-115`).
  화면이 288×320 이라 한 프레임에 9×10칸 남짓이다. 지도가 1만 배 커져도 그리는 양은 같다.
- **타일의 뜻** — 벽·물·NPC 를 지도 종류가 아니라 타일 번호만 보고 정한다
  (`lib/domain/map/tile_properties.dart:183` `getUnitAction`). 지도 종류별 표 `getAction(tileId, mapType)` 은
  아무도 부르지 않는다. 타일 이미지도 모든 지도가 같은 두 장(`Lore_A5.png`, `Lore_B.png`)을 쓴다.
  그래서 마을 타일과 들판 타일이 한 지도에 섞여도 된다.
- **좌표 크기** — 10000칸 × 32 px = 32만 px. GPU 의 float32 로도 1/32 px 단위까지 정확하고,
  이웃한 타일은 같은 경계 좌표를 쓰므로 타일 사이에 틈이 생기지 않는다.
  **계산으로만 확인했다** — 실기기 확인은 후보 8.

## 5. 의문과 답

### Q1. 50×50 도 같은 코드로 돌리면 손해는 없는가

- 거의 없다(§2.2). 칸 하나 찾는 시간이 1.3 ns → 5.7 ns 로 늘지만, 한 프레임에 찾는 칸이 110개 남짓이라
  프레임 시간의 0.02% 다. 메모리는 오히려 190 KB → 41 KB 로 준다.
- 복잡도는 엔진의 세 군데에 모인다. 50×50 지도에서는 셋 다 가장 단순한 경우로 돈다.

  | 새로 생기는 것 | 50×50 지도에서는 |
  |---|---|
  | 조각 읽기·버리기 | 처음에 조각 1개를 읽고 끝 |
  | 사건 칸의 구역 스크립트 실행 | 구역이 1개라 늘 같은 스크립트 |
  | 구역별 설정(시야·걸음당 시간 등) | 구역 1개의 설정 = 지금의 지도 설정 |

- **위험**: 50×50 지도로만 돌리면 조각 경계와 구역 경계를 넘는 코드가 한 번도 실행되지 않아 버그가 숨는다.
  조각과 구역이 여러 개인 시험용 큰 지도를 CI 시험에 둔다(후보 2).

### Q2. 모든 스크립트를 절대 좌표로 바꿔야 하는가

바꾸지 않는다. 엔진이 구역 왼쪽 위 좌표를 빼서 넘긴다.

```
Map002.cm2:   if (On(30, 20))            ← 지금 그대로 둠
구역 목록:     LORE_EP  왼쪽 위 (5000, 5000)  크기 50×50
일행이 (5030, 5020) 의 사람에게 말을 걸면
            → 엔진이 (30, 20) 으로 바꿔 스크립트에 넘김
```

- 지금 지도들은 「구역 하나, 왼쪽 위 (0, 0)」 이라 빼는 값이 0 이다. 스크립트도 세이브도 지금 그대로다.
- **AI 생성에는 구역 좌표가 더 유리하다.** 마을 위치를 옮겨도 스크립트를 다시 만들 필요가 없다.
  절대 좌표로 쓰면 마을을 옮길 때마다 모든 좌표를 다시 써야 한다.
- 구역 바깥 칸(마을 스크립트가 마을 밖 다리를 놓는 경우)은 `(-3, 25)` 처럼 범위 밖 좌표를 그대로 쓴다.
  덧셈뿐이라 따로 장치가 필요 없다. 아직 메모리에 없는 칸이어도 된다(Q4).
- 고칠 곳은 좌표를 받는 명령과 Dart 스크립트의 도착 좌표뿐이다(후보 4).

### Q3. 들어올 때 플래그를 보고 지도를 바꾸는 부분은 어떻게 하는가

**지금 원작 스크립트는 같은 변경을 두 번 쓴다.** `L1_ep1d3.cm2` 의 빗장 문:

```
# 사건 중 (L1_ep1d3.cm2:31-33) — 빗장을 풀면
Map::ChangeTile(39, 32, TILE_GROUND)
Flag::Set(GFD3_OPEN_FAST_DOOR)

# 지도에 들어올 때 FLAG_MAP (L1_ep1d3.cm2:239-240) — 지도를 다시 그린 뒤
if (Flag::IsSet(GFD3_OPEN_FAST_DOOR))
    Map::ChangeTile(39, 32, TILE_GROUND)
```

- 출하 cm2 8개 파일에 「들어올 때 다시 바꾸는 줄」이 86개 있다.
- 지도에 들어오면 `FLAG_MAP` 을 돌린다(`lib/application/scripting/script_engine_adapter.dart:56-57`).

**그런데 다시 바꾸는 줄이 빠진 곳이 많다.** 사건 중에 칸을 바꾸는 187줄 가운데 81줄은
`FLAG_MAP` 에 같은 줄이 없다. 열어 본 4곳은 모두 원래대로 돌아가면 이상한 변경이다.

| 위치 | 무엇 |
|---|---|
| `assets/L1_ep1d5.cm2:49-50` | 바위가 물길로 떨어짐 |
| `assets/L1_ep1d1.cm2:69-70` | 훔친 열쇠로 문을 엶 |
| `assets/town1.cm2:63-65` | 전투 뒤 지형이 바뀌고 `Flag::Set(flag_battle)` |
| `assets/lore_ep1.cm2:24,27` | 대화 뒤 칸을 바꾸고 `Flag::Set(51)` |

- 지금은 이 지도에 다시 들어오면 위 칸들이 원래대로 돌아간다.
  원작이 의도한 규칙이라기보다 다시 바꾸는 줄을 빼먹은 쪽에 가까워 보인다. **81줄 전부를 확인하지는 않았다.**

**이어진 세계에서는 §3 의 변경 목록으로 처리한다.**

- 사건에서 `Map::ChangeTile` 을 한 번만 쓰면 변경 목록에 남는다. `FLAG_MAP` 에서 다시 바꾸는 줄이 필요 없다.
- AI 가 만드는 콘텐츠도 한 번만 쓰면 되므로, 다시 바꾸는 줄을 빼먹을 위험 자체가 없어진다.
- 기존 지도에도 같은 목록을 쓰면 위 81줄이 영구 변경이 되어 지금 동작이 바뀐다 — §8 에서 정할 일.

### Q4. 아직 메모리에 없는 (-3, 25) 를 바꾸면 적용이 안 되지 않는가

적용된다. 변경 목록은 조각이 메모리에 있는지와 상관없이 기록되기 때문이다.

```
마을 왼쪽 위 = (5000, 5000)
마을 스크립트: Map::ChangeTile(-3, 25, 43)
→ 변경 목록에 (4997, 5025) = 43 을 기록
→ 그 칸이 든 조각이 메모리에 없으면 여기서 끝
→ 나중에 그 조각을 읽을 때 원본 위에 43 을 덮음
```

- 마을 A 의 사건이 마을 B 의 칸을 바꾸는 경우도 같다. 마을 B 의 조각이 언제 읽히든 그때 반영된다.

### Q5. 마을 경계를 1칸 차이로 왔다 갔다 하면 지도를 계속 다시 읽지 않는가

다시 읽지 않는다. 경계는 두 종류이고 둘 다 왕복으로 읽기가 일어나지 않는다.

- **조각 경계** — 조각은 구역이 아니라 **거리**를 보고 읽고 버린다.
  - 일행이 있는 조각을 가운데 둔 3×3 을 읽어 두고, 5×5 밖으로 벗어난 조각만 버린다.
  - 경계에서 왔다 갔다 해도 건너편 조각은 이미 3×3 안에 있어서 새로 읽을 것이 없다.
    버리는 기준(5×5)이 읽는 기준(3×3)보다 멀어서 「버렸다가 다시 읽기」도 반복되지 않는다.
  - 한 방향으로 걸어도 새 조각(한 줄, 3개)은 64칸마다 읽는다. 초당 6.25칸이면 10초에 한 번,
    조각 하나에 15 µs 다(§2.2).
- **구역 경계** — 넘을 때 읽는 파일이 없다.
  - 시야·걸음당 시간 같은 구역 설정을 표에서 찾아볼 뿐이다.
  - 스크립트는 경계를 넘을 때가 아니라 **사건이 일어날 때**, 그 칸이 속한 구역의 것을 실행한다.
    마을 안에 서서 경계 너머 사람에게 말을 걸면 그 사람이 속한 구역의 스크립트가 돈다.
  - 최근에 쓴 구역 스크립트 몇 개는 읽은 채로 둔다. 처음 쓰는 것만 새로 읽는다(548줄에 1.35 ms).
  - 웹은 파일을 받아 오는 시간이 이보다 길다. 조각을 읽을 때 그 조각에 걸친 구역의 스크립트 파일도 미리 받아 둔다.

### Q6. (0, 25) 에서 (-3, 25) 를 보려면 옆 지도까지 읽고 플래그도 다 반영해야 하지 않는가. (0, 0) 이면 지도 4개다

- 메모리에 올리는 단위는 구역(지도)이 아니라 **64×64 조각**이다. 조각은 세계에 고정된 격자라서 구역 경계와 상관없다.
- 어디에 서 있든 메모리의 조각은 늘 9개(약 430 KB)다. 구역 4개가 만나는 모서리에 서 있어도 9개다.
- 그릴 때 플래그를 다시 보지 않는다. 플래그 때문에 바뀐 칸은 사건이 일어난 순간 변경 목록에 이미 기록되어 있다.
- 그래서 (-3, 25) 를 그리는 비용은 (5, 25) 를 그리는 비용과 같다 — 배열에서 값 하나를 읽는다.
- 이웃 구역의 스크립트는 그 구역에서 사건이 일어나기 전까지 실행하지 않는다.

## 6. 버린 안

| 안 | 버린 이유 |
|---|---|
| **조각을 읽을 때 그 구역의 `FLAG_MAP` 을 돌린다** | 지도 읽기와 스크립트 실행이 묶인다. Q4(아직 안 읽힌 칸) · Q5(경계 왕복) · Q6(모서리에서 구역 4개의 스크립트 실행) 문제가 그대로 생긴다. 이웃 구역의 `FLAG_MAP` 이 지금 구역의 설정(`Map::SetType` 등)을 덮어쓰는 문제도 있다 |
| **세이브에 지도를 넣지 않고, 불러올 때 `FLAG_MAP` 을 다시 돌린다** | 위 안을 전제로 한 것이라 함께 버린다. 다시 바꾸는 줄이 빠진 81줄(Q3)의 변경이 불러올 때마다 사라진다 |
| **바뀐 칸을 따로 저장하지 않는다 (원작처럼 다시 들어오면 되돌아감)** | 처음에는 원작 동작과 같다는 이유로 이쪽을 권했다. 그러나 되돌아가는 81줄 중 열어 본 4곳이 모두 누락으로 보여(Q3) 판단을 바꿨다. 이어진 세계에는 「다시 들어오기」라는 순간 자체가 없다 |
| **구역 경계를 넘을 때 스크립트를 교체한다** | 경계를 왕복하면 교체가 반복된다. 사건이 일어난 칸의 구역 스크립트를 실행하는 쪽(Q5)이 경계 처리 자체를 없앤다 |
| **모든 스크립트를 절대 좌표로 쓴다** | 마을을 옮길 때마다 스크립트를 다시 써야 한다. 구역 좌표 + 엔진 변환(Q2)이면 스크립트는 그대로다 |

## 8. 정해야 할 것

### 8.1 콘텐츠 규칙 — AI 생성을 시작하기 전에 정한다

엔진은 나중에 바꿔도 지금 만든 콘텐츠를 거의 다시 쓰지 않는다(지도 JSON 은 변환기, 스크립트는 구역 좌표 그대로).
아래 두 가지는 **변환기로 고칠 수 없다.**

- **칸 하나의 넓이**
  - 한 걸음이 들판 2분, 마을 5초로 갈린 이유는 원작 들판 지도의 한 칸이 마을 한 칸보다 훨씬 넓은 땅이기 때문이다.
  - 하나로 이으면 칸 넓이가 하나가 된다. AI 가 지금의 들판 넓이로 지도를 만들면 나중에 전부 다시 그려야 한다.
  - 후보 5 의 걸음당 시간 값도 여기서 정해진다.
- **마을 출입 사건**
  - 지금은 마을 끝 칸에서 들판 지도로 넘어간다(`assets/town2.cm2:482` `LoadScript("ground1.cm2", 19, 11)`).
  - 이어진 세계에서는 걸어서 나가므로 이런 사건이 필요 없다. 만들어 두면 나중에 지워야 한다.

### 8.2 기술 선택

- **기존 지도에도 변경 목록을 쓰는가**
  - 쓰면 Q3 의 81줄이 영구 변경이 된다. 열어 본 4곳은 그게 맞아 보이지만 81줄 전부를 확인하지 않았다.
  - 정하기 전에 81줄을 한 번 훑어, 일부러 되돌아가게 둔 변경이 있는지 본다.
- **같은 평면에 놓을 수 없는 곳**
  - 건물 안 · 지하 던전 · 위층. 따로 지도로 남기면 `LoadScript` 지도 전환이 계속 필요하다.
  - 세계 지도와 따로 지도를 함께 지원하는 쪽이 자연스럽다.

### 8.3 기획 (이 문서 범위 밖이지만 적어 둔다)

- **걷는 시간**: 초당 6.25칸(`lib/hd_config.dart:3` 200 px/s ÷ 32 px). 1만 칸을 끝에서 끝까지 걸으면 약 27분 → 빠른 이동.
- **원작 지도의 처리**: TOWN1 · GROUND1 등을 세계 어디에 놓을지, 아니면 새 세계에서는 쓰지 않을지.

## 10. 어떻게 쟀나

2026-11-10, Dart 3.11.1, macOS arm64. 웹(dart2js)에서는 재지 않았다.

- **메모리 (§2.1)**
  - `MapUnit` 과 같은 모양(int 6개)의 클래스를 1천만 개 만들고 `ProcessInfo.currentRss` 차이를 쟀다 → 764 MB.
  - 층별 `Uint16List` · `Uint8List` ×4 · `Uint32List` 를 1천만 칸씩 만들어 **모두 채운 뒤** 쟀다 → 99 MB.
    (채우지 않으면 운영체제가 메모리를 실제로 잡지 않아 작게 나온다.)
  - 둘 다 10배 해서 1억 칸 값을 냈다.
- **지도 파일**: `GROUND1.json` 161,320 B ÷ 1만 칸.
- **세이브**: `MapUnit.toJson()` 한 칸을 JSON 으로 쓴 길이(값이 한두 자리일 때) 71 B.
- **압축**: 지금 지도 5장(`GROUND1` · `TOWN1` · `ORIGIN` · `Map010` · `Map002`)의 여섯 층을 u16 로 묶어
  zlib 9단계로 압축 → 칸당 0.28~0.36 B (xz 는 0.24~0.35 B).
- **칸 하나 찾기 (§2.2)**: `dart compile exe` 로 만든 실행 파일. 지금 방식(`List<MapUnit>` + 범위 검사)과
  조각 방식(`Map<int, 조각>` + 조각 안 `Uint16List`)으로 2천만 번씩 찾은 평균. 조각 목록을 해시 대신 배열로 두면 더 빠를 수 있다.
- **조각 하나 만들기**: `GROUND1` 의 64×64 × 6층(u16, 49,152 B)을 zlib 9단계로 압축(1,481 B)해 두고,
  `ZLibCodec().decode` + 바뀐 칸 20개 덮기를 200번 한 중앙값. `dart run`.
- **cm2 읽기**: 문자열을 메모리에 둔 상태에서 `ScriptEngine.loadFromString`(파싱 + init 단계)을 30번 한 중앙값.
  `dart run`. 파일을 읽는 시간은 들어 있지 않다.
- **다시 바꾸는 줄 세기 (Q3)**: 출하 `assets/*.cm2` 에서 맨 앞 `if (… ScriptMode() …)` 블록별로
  `Map::ChangeTile` 을 셌다. `FLAG_MAP` 블록 86줄, 그 밖의 블록 187줄.
  187줄 중 `FLAG_MAP` 블록에 세 인자가 글자 그대로 같은 줄이 없는 것 81줄.
  `L1_ep1d0.cm2` 의 12줄은 좌표가 변수(`temp_x` 등)라 글자로 맞출 수 없어 81줄에 들어 있다.
