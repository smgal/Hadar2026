## 52.1 분류 축과 판정 척도

### 52.1.1 분류 5종

| 분류 | 코드 | 정의 | 대표 질문 |
|---|---|---|---|
| **기술** | TECH | 코드·데이터·런타임이 설계대로 동작하지 않는다 | "만들면 굴러가는가" |
| **콘텐츠 품질** | QUAL | 굴러가지만 생성물이 게임으로서 못 쓸 물건이다 | "만들어진 것이 쓸 만한가" |
| **프로세스** | PROC | 만드는 과정 자체가 정합성을 잃는다 | "여럿(사람+에이전트)이 같은 것을 만들고 있는가" |
| **범위** | SCOPE | 만들기로 한 것이 조용히 불어나거나 원작 감성을 훼손한다 | "이걸 정말 만들어야 하는가" |
| **운영** | OPS | 만든 뒤 유지·배포·비용이 감당되지 않는다 | "1인이 계속 굴릴 수 있는가" |

### 52.1.2 3축 척도 (정의 확정)

| 축 | 값 | 정의 |
|---|---|---|
| **발생 가능성** | 높음 / 중간 / 낮음 | 높음 = 대책 없이 두면 **거의 확실히 일어난다**(현재 코드에 이미 존재하는 것 포함). 중간 = 특정 조건에서 일어난다. 낮음 = 예외적 조건에서만 |
| **영향** | 치명 / 높음 / 중간 / 낮음 | 치명 = 파이프라인·게임이 **성립하지 않는다**. 높음 = 마일스톤 재작업. 중간 = 국소 손실. 낮음 = 불편 |
| **노출도** | 높음 / 중간 / 낮음 | **"실현되었는데 그것을 모르고 지나갈 가능성"**. 높음 = 조용히 실패한다(로그도, 게이트도 없다). 낮음 = 즉시 눈에 띄거나 CI 가 빨개진다 |

> **R-52-1** 노출도를 독립 축으로 두는 이유: 이 프로젝트의 기반 버그 20건 중 다수가
> "실패했는데 성공으로 보고" 하거나(부록 D-2) "아무 로그 없이 no-op"(부록 F-1) 이다.
> 가능성·영향만 보면 이 계열이 과소평가된다. **노출도 높음 = 게이트 신설이 완화의 1순위**다.

### 52.1.3 완화와 대응의 구분

| 구분 | 시점 | 산출물 |
|---|---|---|
| **완화(mitigation)** | 리스크가 실현되기 **전** | 게이트·테스트·불변식·규약·설계 선택 |
| **대응(contingency)** | 실현된 **뒤** | 되돌림 절차·킬 스위치·강등·격리·재계획 |

> **R-52-2** 완화만 있고 대응이 없는 리스크는 등록을 거부한다. "그럴 일 없게 만들었다" 는
> 완화이지 대응이 아니며, 이 프로젝트는 이미 "그럴 일 없다고 믿었던" 20건을 실측으로 발견했다.

### RK-09 에셋 선언이 비재귀라 **웹 배포판에서만 콘텐츠가 통째로 사라진다**

- **⚠ 초판이 원인으로 삼았던 것 중 폐기된 것**: "`dart:io` 는 웹에서 컴파일되지 않는다" 는 **부록 B-4 정정본이 실빌드로 반증**했다(성공: Flutter 3.41.4, 16.5초, exit 0, 산출물 45MB). 이 리스크의 제목과 원인에서 `dart:io` 를 **제거**했고, 계층 위반과 헤드리스 파괴는 **RK-08** 이 소유한다. 부록 B-4 의 지시("'웹 빌드가 깨진다' 를 근거로 쓰지 말 것")를 따른다.
- **완화**: `assets/content/build/` 를 **명시 등록**하고 `build/` 를 **평평하게** 유지(R-35-23/24). CI 가 `pubspec.yaml` 선언과 `build/` 하위 디렉토리 유무를 검사(R-35-25 → [BP-53](53_acceptance_criteria.md) HC-7). **`web_smoke` 잡 신설** — 이 잡의 근거는 "빌드가 깨져 있다" 가 아니라 **"웹 빌드가 CI 에서 전혀 돌지 않아 회귀 감지 구조가 없다"**(수동 `workflow_dispatch` 뿐)이다. 즉 성격이 **파손 수리가 아니라 회귀 방지**다([BP-35 §4](35_ci_and_build.md)).
- **대응**: 웹에서만 깨진 것이 확인되면 **데스크톱 파일 폴백을 임시로 끄고 재현**시킨 뒤 고친다(폴백이 증상을 가린다).
- **잔여 리스크**: ① `web_smoke` 는 필수 상태 검사가 아니다(R-35-33 · AR-8) — `main` 에서만 잡힌다. ② "소스 팩을 싣지 않는다" 는 완화가 **실질적 이득인지 아직 판정되지 않았다** — 부록 B-5 가 "소스가 수 MB 가 아니라면 이득이 작다" 고 경고했고 그 판정은 T-166 이 한다.
- **완화 태스크**: **T-069** · **T-145** · **T-166** (§52.8)
- **소유**: [BP-35](35_ci_and_build.md) · **M0**(웹 빌드 성공 G0-6 = **회귀 게이트**) → **M1**(에셋 선언, 부록 A-4 + 기준선 측정) → **M2**(`web_smoke` 잡)

### RK-10 세이브 크기가 브라우저 저장 한계를 넘어 웹에서 저장이 실패한다

- **분류**: 기술 · **발생 가능성**: 중간 · **영향**: 높음 · **노출도**: 중간
- **징후**: 웹 빌드에서 3~4번째 슬롯 저장이 실패한다. 예외가 `QuotaExceededError` 로 뜨거나 조용히 잘린다.
- **원인**: 부록 C-3 — `map_unit.dart` 의 `toJson()` 이 칸당 ~57 B, 100×100 맵이 약 570 KB, 슬롯 4개면 2 MB 초과. `localStorage` 는 통상 5 MB 이고 UTF-16 저장이라 실질 여유가 절반이다.
- **완화**: `mapDelta`(원본 대비 변경 칸만)를 **선택이 아니라 필수**로 채택. cm2 가 `Map::Init`/`Map::SetRow` 로 만든 맵은 base 종류를 `generated` 로 구분해 5필드 평행 배열 + RLE 로 인코딩(D-22). 저장 전 크기 상한 검사.
- **대응**: 상한 초과 시 저장을 거부하고 사용자에게 슬롯 정리를 요구한다(조용한 절단 금지).
- **잔여 리스크**: `generated` 맵은 델타 대상이 없어 여전히 전체 스냅샷이다. RLE 효율은 맵 내용에 좌우된다.
- **소유**: [BP-25](25_world_state_and_save.md) · **M1**([BP-50](50_roadmap.md) G1-7)

### RK-11 레거시 변환이 분기 의미를 뒤집어 이관한다

- **분류**: 콘텐츠 품질 · **발생 가능성**: 중간 · **영향**: 중간 · **노출도**: 높음
- **징후**: 이관한 대화가 조건을 만족하는데도 엉뚱한 페이지를 보여 준다. 얼굴 그림 파라미터가 헤더 텍스트로 둔갑한다.
- **원인**: 부록 E-2 — RPG Maker MV 는 조건을 만족하는 페이지 중 **번호가 가장 큰 것**을 고르고, 본 기획의 `Dialogue.entry[]`(D-07)는 **위에서부터 첫 true** 를 고른다. 부록 E-1 — `code 101` 은 표시 방식 헤더이지 텍스트가 아니다.
- **완화**: 변환 도구가 `pages[]` → `entry[]` 이관 시 **순서를 뒤집는다**는 것을 규범으로 명문화([BP-24 §24.10](24_dialogue_model.md), REVIEW_BP-12 RQ-2). `code 101` 을 버리는 현행 동작이 **의도적으로 옳다**는 것을 문서에 남긴다.
- **대응**: 이관된 대화는 shadow 모드로 트레이스 diff 를 뜨고, 0 이 아니면 되돌린다.
- **잔여 리스크**: 현재 레포의 모든 이벤트는 `pages` 가 1개뿐이라 이 버그는 **테스트로 재현되지 않는다**. 다중 페이지 데이터가 처음 들어올 때 터진다.
- **소유**: [BP-24](24_dialogue_model.md) · [BP-28](28_migration_and_coexistence.md) · **M3**(부록 E-2 는 [BP-50](50_roadmap.md) 이 M3 으로 배정)

### RK-12 문서가 인용한 코드 사실이 틀려 결정의 근거가 약해진다

- **분류**: 프로세스 · **발생 가능성**: 높음(이미 실현됨) · **영향**: 중간 · **노출도**: 중간
- **징후**: 검수 보고서의 축 A(사실 정확성)가 2~3점으로 나온다. 같은 수치가 장마다 다르다(적 75종 vs 74종, 커맨드 43 vs 40).
- **원인**: 부록 E-3(cm2 는 튜링 완전이 아니므로 "정적 검증 불가" 논거는 성립하지 않음) + 부록 F-0(커맨드 40 / 함수 12 가 정본) + REVIEW_BP-10/11 이 적발한 재인용 전파.
- **완화**: 코드 사실은 GROUND_TRUTH 를 유일 출처로 삼고, 본문은 **파일:줄 + 앵커 문자열**을 병기한다(REVIEW_BP-10 S-02). 심볼 목록·개수는 생성 스크립트로 만든다(S-03). 검수의 기계적 검사 2번(인용 10곳 샘플 대조)을 계속 유지.
- **대응**: 사실 오류가 발견되면 그 사실을 **인용한 모든 장**을 grep 으로 찾아 동시에 고친다(BP-10 → BP-11 → BP-92 로 3단 전파한 선례가 있다).
- **잔여 리스크 (정밀화)**: 남은 것은 **`DECISIONS.md` D-02 본문의 문장 하나**다. 부록 **E-3** 이 정정 내용을 이미 확정했고("D-02 의 실제 근거는 튜링 완전성이 아니라 §9 에 실측된 것들이다. 이 논거들만으로 D-02 는 충분히 정당화되므로 **결정은 유지**하되 근거 문장은 정정할 것"), [BP-51](51_task_breakdown.md) **T-032** 가 그 정정을 태스크화했다. 즉 "미반영" 이 아니라 "태스크는 있고 아직 실행되지 않음" 이다.

### RK-13 재빌드 해시가 불일치해 결정론 게이트가 상시 빨갛다

- **분류**: 기술 · **발생 가능성**: 중간 · **영향**: 높음 · **노출도**: 낮음
- **징후**: 같은 소스로 두 번 빌드했는데 `sha256` 이 다르다. CI 코어 수를 바꾸면 결과가 바뀐다.
- **원인**: `Set` 의 이터레이션 순서가 삽입 순서라 파일 방문 순서에 좌우된다(R-35-14). 병렬 린트가 진단 순서를 흔든다(R-35-31). 정규 JSON 규약(키 순서·이스케이프·개행) 위반.
- **완화**: 정규 JSON 10개 규약을 확정하고([BP-35 §2.1](35_ci_and_build.md)) `V-DET-001~004` 로 검사. `INV-20-02` 는 **별도 프로세스로 2회 빌드**해 비교한다(같은 프로세스 2회는 `hashCode` 기인 흔들림을 못 잡는다). "의미 없음" 배열은 반드시 정렬(R-35-15).
- **대응**: 불일치가 나면 두 산출물의 diff 를 떠서 **어느 배열이 흔들렸는지** 먼저 찾는다. 콘텐츠를 고치지 않는다.
- **잔여 리스크**: 맵 파일은 정규화하지 않고 원본 바이트를 해시하므로(§2.3), 맵 에디터가 포맷을 바꾸면 무관한 재빌드가 유발된다(R-35-27, 의도된 결합).

### RK-14 골든이 습관적으로 갱신되어 회귀 검출력이 0 이 된다

- **분류**: 프로세스 · **발생 가능성**: 높음 · **영향**: 높음 · **노출도**: 높음
- **징후**: PR 마다 골든 파일이 함께 바뀐다. 갱신 사유가 "테스트 통과" 다.
- **원인**: 골든이 깨졌을 때 "회귀인가 의도인가" 를 사람이 매번 판단하면 결국 무조건 갱신하게 된다([BP-35 §6.3](35_ci_and_build.md)).
- **완화**: `--update-golden` 이 `--reason` 없이는 **거부**한다. 갱신 이력을 `<questId>.golden.md` 에 1줄씩 누적. 손대지 않은 퀘스트의 골든이 깨지면 CI 가 `::error` 로 **회귀라고 단정**한다(R-35-39). 골든 갱신은 별도 커밋(R-35-40). 트레이스에는 문자열 **키만** 싣고 한국어 텍스트는 싣지 않아 오탈자 수정이 골든을 깨지 않게 한다(R-35-36).
- **대응**: 같은 커밋 2회 실행 결과가 다르면 갱신 금지 — 그것은 비결정 누출이며 RK-05 로 간다.
- **잔여 리스크**: 콘텐츠 변경 PR 은 골든이 정당하게 깨지므로, 그 안에 회귀가 섞여도 `::warning` 에 묻힌다.

- **분류**: 운영 · **발생 가능성**: **높음** · **영향**: 치명 · **노출도**: 중간
- **징후**: 6개월간 만든 것이 검증기·시뮬레이터·솔버·프롬프트뿐이고 새 퀘스트는 0건이다. 문서가 2만 줄인데 게임은 그대로다.
- **원인**: 이 기획서가 정의한 것 — 검증 규칙 152개, MCP 도구 28종, REST 라우트 31개, 프롬프트 6종, 스키마 6종, 솔버 + 퍼저 + 골든 3종. 현행 앱 코드가 `application/` 3,451줄인데 **툴체인이 그보다 커질 수 있다.**
- **완화**: [BP-32 §32.11](32_generation_harness.md) 의 파일럿을 규모 통제 장치로 쓴다 — 퀘스트 **1건**, 맵 **1개**, NPC **3명**, 아이템 **1개**. 파일럿이 끝나기 전에는 도구를 늘리지 않는다. 헤드리스는 **신규 발명이 아니라 기존 포트 3종의 활용**임을 근거로 범위를 좁힌다(GROUND_TRUTH §3). 맵 에디터 서버를 **같은 프로세스**로 확장해 새 인프라를 만들지 않는다.
- **대응 (2차 개정에서 오발동을 고쳤다)**: 마일스톤 종료 시 "이번 구간에 새로 플레이 가능해진 콘텐츠" 가 **0이면 다음 구간의 도구 작업을 전면 중단**하고 콘텐츠만 만든다([BP-53 R-53-8](53_acceptance_criteria.md) 이 규칙화).
  **초판 대응의 결함** — 이 규칙은 **로드맵의 정상 경로에서 반드시 오발동한다.** [BP-50 §3](50_roadmap.md) 능력 획득표가 M2 완료 직후 "여전히 불가능한 것" 에 "퀘스트 아이템을 주고받는 것, 임무 목록을 보는 것" 을 스스로 적었고, M2 의 유일한 콘텐츠 작업인 MAP003 이관은 **G2-4 가 shadow diff 0 을 요구하므로 플레이 경험이 바뀌지 않는 것이 성공 조건**이다. 즉 **M2 는 정의상 새 플레이 콘텐츠를 0건 만들고, 규칙대로면 M4 착수가 금지된다.** 오발동하는 규칙은 곧 무시되고, 무시되면 **TOP-1 리스크의 유일한 집행 장치가 사라진다** — 그것이 "완화가 선언에 그친다" 는 뜻이다.
  **채택한 해법(규칙을 무디게 하지 않는 쪽)**: [BP-50 R-50-15](50_roadmap.md) 가 **M2·M4 산출물에 "플레이 가능한 산출물 1건" 을 강제**한다 — M2 는 `core` 팩([BP-51](51_task_breakdown.md) T-138)에 **새 대화 1개**를 포함하고(게이트 **G2-9**), M4 는 G4-1 이 MCP 로 만든 대화 1개를 그 구간의 산출물로 계상한다. **규칙의 발동 조건을 완화하는 대신 매 구간이 게임을 한 뼘 자라게 한다.**
  **문구 통일**: 규칙 원문은 "**다음 구간**의 도구 작업" 이다. [BP-53](53_acceptance_criteria.md) M4 체크리스트가 초판에서 "0건이면 **M5** 도구 작업 중단" 으로 적었던 것은 **M5 가 파일럿이지 도구 작업이 아니므로** 오해였고, 이번 개정에서 두 장의 문구를 맞췄다.
- **잔여 리스크**: ① 도구 없이 만든 콘텐츠는 검증되지 않는다 — 이 리스크와 RK-15~RK-20 은 정면으로 상충하며 균형점은 마일스톤마다 사람이 정한다. ② "새로 플레이 가능해진 콘텐츠 1건" 이 **형식 요건으로 전락**할 수 있다(대사 한 줄을 넣고 통과시키기). 조기 경보 ②(툴체인 줄 수 ÷ 앱 줄 수)가 그 보완 지표다.
- **완화 태스크**: **T-138**(`core` 팩 + 새 대화 1개) · **T-164**(P-1~P-7 선결 점검) · T-156 (§52.8)
- **소유**: [BP-50](50_roadmap.md) · 상시

### RK-29 콘텐츠 버전이 오르면 기존 세이브가 죽는다

- **분류**: 기술 · **발생 가능성**: 중간 · **영향**: 높음 · **노출도**: 낮음
- **징후**: 팩을 업데이트한 뒤 세이브를 로드하면 거부된다. 진행 중이던 퀘스트가 사라지거나 스테이지가 존재하지 않는다.
- **원인**: `WorldState.contentVersion: {packId: version}` 이 세이브-콘텐츠 호환을 판정한다(D-08). 콘텐츠 버전이 세이브보다 **낮으면 로드 거부**, 높으면 마이그레이션 규칙 적용. ID 는 불변이지만 스테이지·목표는 바뀔 수 있다.
- **완화**: ID 불변 + `retiredIds` 규칙(D-04). 각 팩이 `migrations` 를 선언(D-08). 팩 롤백 시 진행 중 세이브의 퀘스트 상태 규약을 정의(REVIEW_BP-28 F-11 이 부재를 지적).
- **대응**: 마이그레이션 실패 시 사용자에게 보이는 동작까지 규정된 경로를 따른다([BP-25 §6.5](25_world_state_and_save.md)). 조용한 손실 금지.
- **잔여 리스크**: `frozen` 맵은 롤백 대상이 아니다(RK-28-7) — 되돌릴 수 없는 결정이므로 `migrated` 2주기 유지를 승격 전제로 둔다.
- **소유**: [BP-25](25_world_state_and_save.md) · **M1**(봉투) · **M6**(팩 확대 시)

### RK-30 웹 배포 페이로드가 예산을 넘는다

- **분류**: 운영 · **발생 가능성**: 낮음 · **영향**: 중간 · **노출도**: 낮음
- **징후**: `content.bundle.json` 이 1 MB 를 넘는다. 웹 첫 로드가 눈에 띄게 느려진다.
- **원인**: 대 규모 팩(문자열 14,000)에서 문자열 섹션이 지배적이 된다. v1 은 인터닝·값 중복 제거를 **채택하지 않았다**(가독성·diff 가능성 우선).
- **완화**: "영리한 인코딩이 아니라 싣지 않는 것" 이 v1 전략(R-35-21) — 소스 팩 디렉토리를 `pubspec.yaml` 에 등록하지 않아 수 MB 를 뺀다. GitHub Pages 자동 gzip 으로 실 전송량은 목표치의 20~30%. CI 가 예산 초과를 경고.
- **대응**: 초과 시 **`xref` 분리부터** 한다(R-35-22) — 런타임이 읽지 않는 데이터가 가장 먼저 빠져야 한다. 인터닝은 그다음.
- **잔여 리스크 (정정)**: 초판의 "중 규모 팩이 나오는 시점까지 **실측이 없다**"(Q-35-2)는 **이제 부분적으로 거짓**이다. **전체 페이로드는 실측되었다** — 부록 **B-5**(2026-08-30): `flutter build web --release` 산출물 **총 45MB** = `canvaskit/` **31MB** + `assets/assets/` **9.7MB**(맵 1.2MB + 이미지 1.3MB + cm2 등) + `assets/NOTICES` 1.3MB + 나머지 ~3MB. 없는 것은 **콘텐츠 팩 자체의 실측**뿐이다.
  이 수치가 리스크의 성격을 바꾼다 — ① **canvaskit 31MB 는 콘텐츠와 무관**하므로 최적화 표면에서 제외된다. ② 콘텐츠 팩이 통제할 수 있는 표면은 **게임 자산 9.7MB 쪽**이다. ③ 따라서 "+600 KB 를 아끼는" 작업은 **전체의 1.3%, 통제 가능 표면의 6%** 이며, 그 가치 판단은 이 기준선 없이는 불가능하다. B-5 는 "소스 JSON 을 웹 페이로드에서 빼는 선택이 실질적 이득인지도 이 수치로 판단할 것(소스가 수 MB 가 아니라면 이득이 작다)" 고 명시적으로 지시했다.
- **완화 태스크**: T-069 · **T-166**(기준선 실측·이득 판정) · T-125 (§52.8)
- **소유**: [BP-35](35_ci_and_build.md) · **M1**(예산 설정 + 기준선 기록) · **M6**(팩 실측)

### RK-31 CI 시간 예산이 초과되어 게이트가 우회된다

- **분류**: 프로세스 · **발생 가능성**: 중간 · **영향**: 중간 · **노출도**: 낮음
- **징후**: PR 이 15분 넘게 돌아 리뷰가 멈춘다. 급할 때 필수 검사를 끄자는 말이 나온다.
- **원인**: 콘텐츠 잡(build·validate·lint·`sim --smoke`) + 결정론 잡(별도 프로세스 2회 빌드) + 앱 잡 + 웹 스모크가 겹친다.
- **완화**: 변경 유형별 게이트 표로 불필요한 잡을 스킵(R-35-30). PR 에서 `sim` 은 `--smoke` 만(R-35-31). 예산의 80% 를 넘으면 잡을 쪼개거나 캐시를 손본다(R-35-32). 잡별 소요를 `GITHUB_STEP_SUMMARY` 에 매번 찍어 추세를 본다.
- **대응**: 예산 초과가 상시화되면 `sim --all` 을 야간으로 완전히 이관하고 PR 에서는 증분만 돌린다.
- **잔여 리스크**: 증분 검사는 역참조 인덱스 정확성에 전적으로 의존한다(R-33-29). 그래서 CI 는 항상 `--full` 을 돌려야 하고, 그것이 예산 압박의 근원이다.
- **소유**: [BP-35](35_ci_and_build.md) · **M2**([BP-50](50_roadmap.md) G2-6)

### RK-32 병렬 제작이 같은 개념을 다르게 정의해 SSoT 가 깨진다

- **분류**: 프로세스 · **발생 가능성**: **높음(이미 실현됨 — 이 기획서 자체가 사례다)** · **영향**: 높음 · **노출도**: 높음
- **징후**: 세 장이 각각 "닫힌 집합" 이라고 선언한 목록이 서로 다르다. 같은 필드가 장마다 이름이 다르다.
- **원인 (실제 사례 3건)**:
  - **D-20** — BP-23 / BP-25 / BP-27 이 **월드 이벤트 이름 집합을 각각 닫힌 집합으로 선언**했다. BP-23 은 12종(`talk`/`enter_place`/`dialogue_choice`…), BP-25·BP-27 은 11종(`talked_to`/`entered_place`/`choice_made`…). **5개만 이름이 같고 그중 3개는 payload 도 달랐다.** BP-23 의 objective 커버리지 증명이 이것 때문에 무너졌다.
  - **D-18** — 세이브 v2 봉투를 BP-20 이 스스로 정의했고 그 정의가 BP-25 실물과 세 곳에서 충돌했다(`map` vs `mapDelta`, `nativeScript` vs `legacy.nativeFlags`, `envelope` 누락).
  - **D-20a** — **중재 결정 자신이 같은 실수를 했다.** D-20 이 소유 장(BP-23)의 payload 를 옮겨 적으며 `{itemId, delta, total}` 을 `{itemId, count}` 로 잘못 전재했다. D-20a 가 이를 정정하며 남긴 교훈이 곧 이 리스크의 정의다 — **"소유 장의 정의를 다른 문서로 옮겨 적는 행위 자체가 오류원"** 이며, D-18 의 "비소유 장은 링크만" 규칙은 `DECISIONS.md` 에도 적용된다.
- **완화**: **D-18 SSoT 소유권 표**가 유일한 중재 근거다 — 소유 장이 정의하고 나머지는 링크만 하며, 충돌 시 소유 장이 이긴다. 비소유 장은 자기 서술을 **지우고 링크로 대체**한다(소유 장을 고치는 것이 아니다). 검수 루브릭 축 F(비중복·연결성)와 기계적 검사 5번(중복 grep)이 상시 검출.
- **대응**: 충돌이 발견되면 DECISIONS.md 에 **중재 결정을 신설**해 정본을 못박고(D-20 이 그 방식), 폐기된 이름은 §52.4 의 "다시 쓰지 말 것" 목록에 넣는다.
- **잔여 리스크 (실측, 2026-08-30 · 2차 개정에서 정정)**: 검수 12건 중 **9건이 "수정 필요"**(나머지 3건은 조건부 합격) 판정이고, 그중 다수가 아직 반영되지 않았다. 반영 전에 다음 장이 그것을 인용하면 오류가 전파된다(RK-33).
  **초판 잔여 리스크의 정정** — 초판은 여기서 "`_meta/DECISIONS.md` 의 **D-20 표**와 소유 장 BP-23 을 전수 대조하면 **8행의 payload 가 여전히 다르다**" 며 **payload 8행을 표로 전재**했다. 두 가지가 틀렸다.
  ① **현행 D-20 에는 payload 열이 존재하지 않는다.** D-20 은 이미 개정되어 "**payload 정의는 여기 두지 않는다.** 정본은 소유 장 [BP-23 §23.11.1](23_quest_model.md) 의 12행 표다" 로 바뀌었고, **이름 12종만** 고정한다. 즉 **BP-52 가 존재하지 않는 표를 인용하고 있었다.**
  ② **그 지적을 하기 위해 BP-52 자신이 BP-23 의 payload 8행을 전재했다.** D-25 는 "필드 표·스키마·시그니처를 **전재하지 않는다**" 를 프로세스 규칙으로 못박았고 그 검수 기준은 "**전재하고 있지 않은가**" 다. **RK-32 는 자기가 정의한 리스크를 자기가 실현했다.** 그래서 8행 표를 **삭제**했다.
  현재 남은 것은 하나다 — **payload 를 확인할 때는 D-20 이 아니라 BP-23 §23.11.1 을 본다**(D-20a · D-25 로 종결). [BP-51](51_task_breakdown.md) T-051 의 완료 조건도 그에 맞춰 "**이름 12종**은 D-20 과 문자 단위 일치, payload 는 BP-23 정본" 으로 정정되었다.
- **완화 태스크**: **T-051**(이름 12종) · T-082 · T-031 · T-032 (§52.8)
- **소유**: `_meta/DECISIONS.md`(D-18) · 상시

### RK-33 미반영 검수 결함이 후속 장으로 전파된다

- **분류**: 프로세스 · **발생 가능성**: 높음 · **영향**: 높음 · **노출도**: 중간
- **징후**: 나중에 쓴 장이 앞 장의 잘못된 사실을 근거로 설계한다. BP-10 의 오류 4건이 BP-11 로, BP-12 의 `code 101` 오류가 BP-92 3곳으로 복제된 것이 실제 사례다.
- **원인**: 검수 보고서는 **읽기 전용 산출물**이고 수정은 제작 에이전트가 한다(REVIEW_RUBRIC). 그 사이에 시차가 있다.
- **완화**: 각 검수 보고서 말미의 **재검수 체크리스트**를 반영 추적 단위로 쓴다. 다른 장이 인용하기 전에 "이 장의 판정" 을 먼저 확인한다. `수정 필요` 판정인 장의 서술은 인용하지 않고 **원 근거(GROUND_TRUTH)를 직접 인용**한다.
- **대응**: 전파가 확인되면 grep 으로 인용처를 전수 조사해 **동시에** 고친다.
- **잔여 리스크**: 검수 보고서 12건에 걸쳐 미해결 치명 결함이 다수 남아 있고, 그중 일부(`chance` 시드 규약, `time_of_day`, 전투 결과 정본)는 **결정 레벨의 공백**이라 제작 에이전트가 단독으로 닫을 수 없다.
- **소유**: `_meta/reviews/` · 상시

### RK-39 솔버가 `PROVEN` 을 냈는데 **현행 엔진이 그 신호를 내지 않는다** (미발행 이벤트 의존)

- **분류**: 기술 · **발생 가능성**: **높음(구조적으로 확정 — 이 계획은 이 상태를 반드시 한 번 지나간다)** · **영향**: 치명 · **노출도**: **높음**
- **징후**: 솔버가 `PROVEN` 을 냈고 린트도 초록인데, **게임에서 그 퀘스트의 `acquire` 목표가 진행되지 않는다.** `item_gained` 이벤트가 한 번도 발행되지 않는다. 로그에는 아무 에러가 없다.
- **원인**: D-20 말미가 못박은 것 — `item_gained`/`item_lost` 는 **인벤토리 부재**로, `enter_place` 는 **장소 개념 부재**로 **현재 미발행**이다. 그런데 **정적 증명은 실행 가능성을 보지 않는다.** [BP-91](91_appendix_worked_example.md) W-10 이 실제 사례이며 **D-26 이 그 사례에서 만들어진 결정**이다. 여기에 [BP-50](50_roadmap.md) 의 마일스톤 순서(**M2 검증 < M3 발행 지점 생성**)가 겹쳐 **이 프로젝트는 이 상태를 반드시 통과한다.**
- **RK-22 와 무엇이 다른가**: RK-22 의 원인은 "**솔버는 전지적이다**"(앵커 위치를 다 안다 → 지식 게이팅)이고, 이 리스크의 원인은 "**그 경로가 의존하는 월드 이벤트에 현행 빌드의 발행 지점이 없다**"(실행 가능성)다. **두 원인은 독립이고 완화책도 다르다** — 전자는 `hintCoverage`, 후자는 **레지스트리 대조**다.
- **완화**: **D-26 의 2축 판정** — 모델 증명(`PROVEN`/`REFUTED`/`UNKNOWN`) × 실행 가능(`SUPPORTED`/`UNSUPPORTED`). 빌드가 **이벤트 → 발행 지점 레지스트리**를 굽고(정본 입력은 선언 파일, [BP-35 §1.5.1 R-35-11c~g](35_ci_and_build.md)), 솔버가 경로가 소비하는 이벤트를 그것과 대조한다([BP-34 §5.10](34_headless_sim_and_solver.md)). 하나라도 `unpublished` 면 `UNSUPPORTED`. **12종 전량 선언을 빌드 ERROR 로 강제**(`V-DET-011`)해 "선언을 안 했으니 통과" 라는 조용한 실패를 막는다.
- **대응**: **`PROVEN + UNSUPPORTED` 는 커밋 가능·릴리스 차단.** 그 팩은 **"미활성"** 으로 표시된다 — 마일스톤 진행 중 미리 콘텐츠를 만들어 두는 것은 허용하되 배포는 막는다([BP-53](53_acceptance_criteria.md) H-13·N-74). **M3 종료(G3-1: `unpublished` 0) 후 재판정**으로 활성화한다.
- **잔여 리스크**: 선언 파일을 **사람이 갱신**하므로 낡을 수 있다. "발행 코드가 생겼는데 선언이 `unpublished` 로 남아 있는" 경우는 CI 가 **WARN 으로만** 잡는다([BP-35 Q-35-10](35_ci_and_build.md) · [BP-51](51_task_breakdown.md) Q-51-8) — 이 방향의 오류는 **보수적으로 틀리므로**(활성화가 늦어질 뿐) 배포 사고로는 이어지지 않는다.

### RK-40 장비 시스템을 만들었는데 **장착해도 전투가 바뀌지 않는다**

- **소유**: [BP-42](42_item_and_inventory.md) · **M3**([BP-50](50_roadmap.md) G3-2 앞)

### RK-41 **읽히지 않는 데이터 필드를 재활용하는 설계**를 채택한다

- **분류**: 기술 · **발생 가능성**: **높음(이미 실현됨 — BP-26 의 region 예약안이 그 사례다)** · **영향**: 높음 · **노출도**: **높음**
- **징후**: 문서가 "기존 필드를 재활용하므로 **무영향**" 이라고 주장한다. 그 필드에 값을 넣어도 게임 동작이 **아무것도 바뀌지 않는데**, 아무 에러도 없어 "아직 구현이 안 됐나" 로 읽힌다.
- **원인 (부록 J, 실측)**: **J-1** — `hadar2026_app/lib/application/map_loader.dart:44` 가 region(0~255)을 `ixEvent` **하위 바이트**에 넣는데, `hadar2026_app/lib/domain/map/tile_properties.dart:186-187` 은 **상위 바이트**(`& 0x00FF0000`)만 본다. 즉 **`200 & 0x00FF0000 == 0`** 이므로 **어떤 region 값도 타일 액션을 만들지 못한다.** region 레이어는 **로드되지만 읽히기만 하고 아무 효과가 없다.** 오해의 출발점은 `tools/mapEditor/AI_GUIDE.md` 의 "region: 지역 ID (게임이 `ixEvent` 로 읽음)" 라는 서술이었다 — **읽기는 하지만 쓰이지 않는다.**
- **파급 (J-2)**: BP-26 의 `trigger` 앵커 region 200~255 예약안, BP-31/36 이 그 예약을 전제로 만든 검증·편집 기능, R-31-7 의 "서버가 직접 통행/액션을 검사"(`unitAction` 이 region 을 받지 않으므로 성립 불가)가 전부 무효화된다. 부록 **I-1**("충돌 1칸") 은 **비용** 문제였고 J-1 은 **작동 자체가 안 된다**는 더 근본적인 문제다.
- **완화**: **D-27** — 콘텐츠 티어는 **타일 비트를 거치지 않고 `(map, x, y)` 로 트리거 인덱스를 직접 조회**한다. **앵커는 맵 데이터에 아무 표시도 남기지 않는다**(D-09 의 논리적 귀결). 앵커-타일 정합은 **런타임 요구가 아니라 린트 WARN**([BP-26 R-26-7a](26_entity_registry_and_anchors.md)). 에디터는 앵커를 **오버레이로만** 표시하고 맵 데이터를 바꾸지 않는다. **일반 규칙**: "기존 데이터 필드를 재활용한다" 는 안은 **그 필드가 실제로 읽히는지 코드로 확인하기 전에는 채택하지 않는다**(D-27 말미의 교훈).
- **대응**: 이미 채택된 예약안은 **폐기**한다(비용 산정이 아니라 폐기다 — 작동하지 않으므로 마이그레이션할 대상도 없다). 부록 **I-1 의 정리 태스크(`T-36-1`)도 폐기**한다 — 예약을 하지 않으므로 충돌이 없고, I-1 자신이 `Map001.json` 을 "타일 액션 경계를 훑는 **테스트 픽스처**로 보이므로 함부로 정리하지 말 것" 이라고 경고했다.
- **잔여 리스크**: **같은 오류가 다른 필드에서 반복될 수 있다.** J-3 이 확정한 대로 타일 액션의 실제 출처는 **3개뿐**(맵 JSON `events[]` 접두사 · `ixObj1` B 타일 대역 · `ixTile` A5 대역)이고 **region·objLower·shadow·ground2 는 관여하지 않는다** — 이 넷 중 어느 것을 "재활용" 하자는 안이 다시 나올 수 있다.
- **완화 태스크**: **T-165**(타일 비트 무의존 테스트) + T-075(정합 규칙 WARN 강등) · T-124(오버레이 전용) (§52.8)
- **소유**: [BP-26](26_entity_registry_and_anchors.md) · **M1**(설계) · **M2**(린트) · **M4**(에디터)

> **RK-03 의 배치를 고쳤다** — 초판은 RK-03 을 "높음×**중간**" 셀에 적어 놓고 각주로 "실제로는 높음×높음이지만

> **신설 3건의 배치 근거** — RK-39 는 "구조적으로 확정"(M2 < M3 순서상 반드시 통과) × 치명(검증이 무의미해진다).
