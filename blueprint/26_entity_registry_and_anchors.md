## 1. 문제 정의 — 대사가 좌표에 박혀 있다

### 1.1 현행 조회 코드

`lib/application/tile_event_dispatcher.dart:159`:

```dart
  Future<void> _emitJsonDialog(
    MapModel map, int x, int y, UiHost host, HDTileAction action,
  ) async {
    for (final ev in map.events) {
      if (ev.x == x && ev.y == y) {
        for (final line in ev.dialogLines) {
          if (line.isNotEmpty) {
            await host.addLog(line);
          }
        }
        return;
      }
    }
  }
```

여기서 읽어야 할 다섯 가지:

| # | 사실 | 결과 |
|---|---|---|
| 1 | **선형 탐색** `for (final ev in map.events)` | 맵 이벤트가 늘수록 O(n). Map010 은 이미 8개, 대규모 맵이면 매 상호작용마다 전체 순회 |
| 2 | **좌표 일치 후 즉시 `return`** | **좌표당 이벤트 1개만 유효**. 같은 칸의 두 번째 이벤트는 영원히 죽은 데이터 |
| 3 | **조건 분기 없음** | 같은 NPC 가 언제나 같은 말을 한다. D-16 의 "조건부 대화" 요구를 이 티어로는 만족시킬 수 없다 |
| 4 | **상태 참조 없음** | 퀘스트 진행·플래그·아이템 보유를 볼 수단이 없다 |
| 5 | **식별자는 `(x, y)` 뿐** | 이벤트에 `id`/`name`/`note` 가 있지만 **조회 키로 쓰이지 않는다**. 정체성이 좌표다 |

### 1.2 좌표 결합이 실제로 깨진 사례 (실측)

**사례 A — 고아가 된 대사 파일**

`assets/lore_ep1.cm2` 는 원작 로어성 대사 원본이다. 실측:

| 검사 | 결과 |
|---|---|
| 이 파일을 로드하는 곳 | **0건**. `grep 'LoadScript("lore_ep1' assets/ lib/` 이 비어 있다 |
| 파일 안의 TALK 좌표 | (8,63) (71,72) (50,71) (62,26) (12,26) (20,32) (23,49) (40,9) 등 100×100 맵 기준 |
| 그 좌표의 `TOWN1.json` objUpper 값 | 132 / 129 / 133 / 132 / 131 / 133 / 133 / 133 — **전부 128~143(TALK) 범위** |
| 결론 | 이 파일은 명백히 `TOWN1`(로어성, 100×100) 의 대사다. 그런데 `assets/startup.cm2` 는 `LoadScript("LORE_EP", 32, 25)` 로 **Map002(50×50)** 를 띄운다 |

즉 **맵이 교체되자 대사 파일 전체가 접속을 잃었다.** 대사와 맵을 잇는 것이 좌표뿐이었기 때문에,
연결이 끊어졌다는 사실조차 어디에도 기록되지 않았다. `Necromancer` 29회, `Lord Ahn` 26회,
`MENACE` 21회가 등장하는 원작 서사 자산이 조용히 실행 경로 밖에 놓여 있다.

**사례 B — 대사를 가진 맵과 실제 쓰이는 맵의 분리**

| 맵 파일 | 크기 | `events` 수 | 상태 |
|---|---|---|---|
| `TOWN1.json` (로어성) | 100×100 | **0** | TALK 오브젝트는 타일에 있으나 대사가 없음 |
| `GROUND1.json` (로어 대륙) | 100×100 | **0** | 동일 |
| `DEN1.json` (메너스) | 50×50 | **0** | 동일 |
| `Map002.json` | 50×50 | 18 | 대사가 있으나 "삶은 계란" 등 테스트 더미 |
| `Map010.json` | 65×82 | 8 | note 에 "의뢰인1", "의뢰인의 조수" |
| `Map011.json` | 53×52 | 9 | TALK002 가 (8,40)(10,39)(9,37) **세 칸에 중복 배치** |

`Map011` 의 `TALK002` 3개, `TALK003` 3개는 "같은 NPC 를 세 칸에 놓은" 것이다. 지금 구조에서는
이것이 **이름만 같은 남남 3개**다. 한 명을 고치려면 세 곳을 고쳐야 하고, 두 곳만 고치면 조용히 갈라진다.

### 1.3 좌표 → 이벤트 연결의 또 다른 미묘함 (실측)

`lib/application/map_loader.dart:67` 은 맵을 읽으면서 이벤트 좌표의 타일을 덮어쓴다:

```dart
unit.ixEvent = eventType | parsedEvent.id;
```

| 관찰 | 의미 |
|---|---|
| `ixEvent` 는 원래 z5 `region` 레이어 값(0~255)이다 | region 값은 **비트 0~7** 에 들어가는데 마스크는 **비트 16~23** 을 본다. `200 & 0x00FF0000 == 0`, `255 & 0x00FF0000 == 0` — **어떤 region 값도 타일 액션을 만들지 못한다**(부록 J-1). 즉 region 레이어는 로드되지만 **읽히기만 하고 아무 효과가 없다** |
| 이벤트가 있는 칸에서만 상위 바이트가 채워진다 | `HDTileProperties.getUnitAction` 의 첫 분기는 **맵 `events[]` 가 있는 칸 전용** 경로다 |
| `type` 이 `"NPC"`/`"UNKNOWN"` 이면 `eventType = 0` | `ixEvent = 0 \| id` → 상위 바이트 없음 → 첫 분기를 통과해 `ixObj1`/`ixTile` 규칙으로 떨어진다. **`NPC` 접두 이벤트는 타입이 파싱되지만 판정에 반영되지 않는다** |
| 로더가 region 값을 **파괴한다** | 이벤트 칸의 원래 region 정보는 복구 불가 |

- **G-26-1** `MapEvent._parseTypeString` 은 `NPC` 를 인식하지만 로더는 그것을 액션으로 옮기지 않는다.
  앵커 도입 시 이 경로에 의존하지 않는 것이 안전하다.
- **G-26-2** (부록 J-1) `tools/mapEditor/AI_GUIDE.md` 의 레이어 표는 region 을
  "지역 ID (게임이 ixEvent 로 읽음)" 이라고 적는다. **읽기는 하지만 쓰이지 않는다**는 뜻이며,
  이 서술이 초판 BP-26 의 region 예약안이라는 오해의 출발점이었다. 에디터 문서 정정은
  [BP-36](36_map_editor_extension.md) 소관이다.

### 1.4 앵커가 세우는 경계 (D-09)

```
맵 JSON  ─────────► 지형·배치·통행     (맵 에디터가 소유)
                         ▲
                         │  좌표
                    ┌────┴────┐
                    │  앵커   │        (콘텐츠 팩이 소유)
                    └────┬────┘
                         │  ID
콘텐츠 팩 ─────────► 정체성·의미·상태  (생성 에이전트가 소유)
```

- **R-26-1** 맵 JSON 은 **좌표와 지형만** 안다. 대사·퀘스트·아이템을 담지 않는다.
- **R-26-2** 콘텐츠 팩은 **의미만** 안다. 좌표를 담지 않는다 — 단 하나, 앵커 파일만 예외다.
- **R-26-3** 앵커는 **유일한 결합 지점**이다. 좌표가 바뀌면 앵커 하나만 고치면 된다.
- **R-26-4** 기존 `map.events[].dialogLines` 는 **레거시 폴백**으로만 남고 신규 콘텐츠는 앵커만 쓴다(D-09).
- **R-26-5a** (D-27) **앵커는 맵 데이터에 아무 표시도 남기지 않는다.** 위 그림에서 "좌표" 화살표는
  단방향이다 — 앵커가 맵을 **읽어** 자기 좌표가 말이 되는지 검사할 뿐, 맵에 무언가를 **쓰지 않는다.**
  이것이 D-09(의미와 좌표의 분리)의 논리적 귀결이다: 맵 편집기가 지형만 바꾸고 콘텐츠 팩이 의미만
  갖는다면, **의미가 지형 비트에 기생할 이유가 없다.**
  - 초판은 `trigger` 앵커를 위해 region 레이어에 표시를 남기려 했다(**§3.5.3 폐기 이력**). 그 안은
    (a) 부록 J-1 에 의해 **그대로는 작동하지 않고**, (b) 로더를 고쳐 작동시키더라도
    R-26-1/R-26-2 를 스스로 어기는 것이었다. D-28 이 (b)를 근거로 최종 기각했다 —
    **작동한다는 것이 채택 근거가 아니다.**
  - **교훈**: "기존 데이터 필드를 재활용한다" 는 안은 그 필드가 **실제로 읽히는지** 확인하기 전에
    채택하면 안 된다(D-27 말미).

## 2. 앵커 스키마

### 2.1 파일 형태

`anchors/<MAPNAME>.json` — 파일명이 곧 맵 이름이다([BP-21 §2.2 R-21-7](21_content_pack_spec.md)).

```json
{
  "schemaVersion": 1,
  "pack": "core",
  "map": "TOWN1",
  "anchors": [
    { "id": "anchor.core.town1_gate_guard", "kind": "actor",
      "actor": "npc.core.lore_gate_guard", "x": 34, "y": 12, "facing": "down" },
    { "id": "anchor.core.town1_notice", "kind": "sign",
      "dialogue": "dlg.core.town1_notice", "x": 30, "y": 18 },
    { "id": "anchor.core.town1_to_ground", "kind": "portal",
      "to": { "map": "GROUND1", "x": 50, "y": 50 }, "x": 50, "y": 99 }
  ]
}
```

### 2.2 공통 필드 (모든 kind)

| 필드 | 타입 | 필수 | 기본값 | 제약 |
|---|---|---|---|---|
| `id` | anchor id | ✅ | — | `anchor.<pack>.<slug>`. 팩 전역 유일 |
| `kind` | enum | ✅ | — | `actor` \| `sign` \| `portal` \| `trigger` \| `container` \| `battle` |
| `x` | int | ✅ | — | `0 <= x < map.width` |
| `y` | int | ✅ | — | `0 <= y < map.height` |
| `when` | Condition | ⬜ | `{"op":"true"}` | 이 앵커가 **활성인가**. false 면 그 좌표에 앵커가 없는 것처럼 동작(아래 티어로 폴백) |
| `priority` | int | ⬜ | `0` | 같은 좌표+kind 다중 앵커의 선택 순서(§4.4) |
| `once` | bool | ⬜ | `false` | 1회 발동 후 비활성. `trigger`/`battle`/`container` 만 의미 있음 |
| `activation` | enum | ⬜ | kind 별 기본값(아래) | `interact` \| `step_on` \| `both`. **트리거 인덱스의 키 성분**이며 앵커가 언제 발화하는지를 결정한다(§4.1) |
| `_note` | string | ⬜ | — | 주석 |

**`activation` 의 kind 별 기본값** — D-27 이후 이 필드가 **발화 조건의 유일한 선언**이다.
타일 액션은 여기에 관여하지 않는다.

| kind | 기본 `activation` | 다른 값 허용 | 의미 |
|---|---|---|---|
| `actor` | `interact` | ❌ | 마주보고 확인 |
| `sign` | `interact` | ❌ | 마주보고 확인 |
| `container` | `interact` | ❌ | 마주보고 조사 |
| `portal` | `interact` | ✅ `step_on` / `both` | 원작 ENTER 는 밟아도·확인해도 동작했다. `both` 로 그 동작을 재현한다 |
| `trigger` | `step_on` | ✅ `interact` / `both` | 밟으면 발동이 기본. "조사하면 발동" 도 표현 가능 |
| `battle` | `step_on` | ✅ `interact` / `both` | 기존 `battle.activation` 필드를 공통 필드로 승격한 것 |

- **R-26-5b** `activation` 이 `interact` 를 포함하면 **플레이어가 그 칸을 마주보고 확인**할 때 발화한다.
  `step_on` 을 포함하면 **파티가 그 칸에 올라설** 때 발화한다. `both` 는 둘 다.
- **R-26-5c** `activation` 은 **런타임 발화 조건이고, 타일 액션은 아니다.** 타일이 무엇이든 앵커는 발화한다.
  다만 물리적으로 도달 불가능한 배치는 린트가 경고한다(§3.3).

##### 2.3.1 `onceFlag` 자동 생성 규칙 (BP-91 `W-03` 해소)

자동 생성 형식은 `flag.<pack>.map.<mapKey>.<anchorSlug>_fired` 다. 여기서 `<mapKey>` 는
**맵 이름을 상태 키 문법에 맞게 정규화한 값**이다 — 맵 이름은 대문자·언더스코어를 쓰지만
([BP-21 §4.1](21_content_pack_spec.md)) 상태 키 세그먼트는 소문자만 허용하기 때문이다.
초판은 `<mapname>` 이라고만 적어 `flag.gen_ep1.map.TOWN1.…` 같은 **문법 위반 키**를 낳았다.

**`mapKey` 정규화 (`normalizeMapKey`)** — 결정론적이며 빌드가 수행한다.

| # | 단계 | 예 |
|---|---|---|
| 1 | 소문자화 | `TOWN1` → `town1`, `Template_TOWN` → `template_town`, `LORE_EP` → `lore_ep` |
| 2 | `[a-z0-9_]` 이외 문자를 `_` 로 치환 | `Prolog_B1` → `prolog_b1` (변화 없음) |
| 3 | 연속 `_` 를 하나로 축약, 앞뒤 `_` 제거 | `A__B_` → `a_b` |
| 4 | 결과가 숫자로 시작하면 앞에 `m` 을 붙인다 | `013map` → `m013map` |
| 5 | 결과 길이가 3 미만이면 `_map` 을 덧붙인다 | `t1` → `t1_map` |

현행 등록 이름 15개의 정규화 결과 (실제 적용):

| 맵 이름 | `mapKey` | 맵 이름 | `mapKey` |
|---|---|---|---|
| `Test` | `test` | `Prolog` | `prolog` |
| `LORE_EP` | `lore_ep` | `Prolog_B1` | `prolog_b1` |
| `MAP003` | `map003` | `Prolog_B2` | `prolog_b2` |
| `TOWN1` | `town1` | `Template_DUNGEON` | `template_dungeon` |
| `GROUND1` | `ground1` | `LoreContinent` | `lorecontinent` |
| `DEN1` | `den1` | `CastleLore` | `castlelore` |
| `DEN2` | `den2` | `LastDitch` | `lastditch` |
| `Template_TOWN` | `template_town` | (미등록) `ORIGIN` | `origin` |

- **R-26-39** `normalizeMapKey` 는 **단사(injective)여야 한다**. 두 맵 이름이 같은 `mapKey` 로 접히면
  **빌드 하드 실패**. 위 15개는 충돌이 없다(직접 대조 확인).
  충돌이 생기면 앵커에 `onceFlag` 를 명시해 회피한다.
- **R-26-40** 자동 생성 키도 [BP-21 `CV-06`](21_content_pack_spec.md) 상태 키 문법 검사를 통과해야 한다.

- **R-26-41** `mapKey` 는 `onceFlag` 자동 생성에만 쓰인다. **앵커 파일명·트리거 인덱스 키는
  원래 맵 이름 그대로**(`anchors/TOWN1.json`, `triggers["TOWN1"]`)를 쓴다.

## 3. 앵커와 타일의 정합 — **런타임 요구가 아니라 저작 품질 규칙**

> **D-27 로 이 장의 성격이 바뀌었다.** 초판은 "앵커 kind 마다 요구되는 타일 액션이 있고, 어기면
> 빌드 하드 실패" 였다. 그 전제는 **앵커가 타일 액션 게이트를 통과해야 발화한다**는 것이었는데,
> D-27 이 **콘텐츠 티어는 타일 액션 게이트를 거치지 않는다**(§3.5·§4.1)로 확정했다.
>
> 따라서 이 절의 규칙은 이제 **"이렇게 두지 않으면 플레이어가 실제로 그 앵커에 닿을 수 없다"** 는
> **저작 품질 경고**다. 런타임은 타일이 무엇이든 앵커를 발화시킨다.

### 3.1 실제 판정 코드 — 무엇을 위한 표인가

아래 판정 로직은 **파티의 이동·통행과 레거시 3티어 디스패치**를 지배한다. 콘텐츠 티어(티어 0)는
여기를 **거치지 않는다**. 그럼에도 이 표가 필요한 이유는, 앵커가 **닿을 수 있는 자리에 있는지**를
린트가 계산하려면 통행 규칙을 알아야 하기 때문이다.

`lib/domain/map/tile_properties.dart:183` `getUnitAction` 의 3단 판정:

```dart
static HDTileAction getUnitAction(MapUnit? unit) {
  if (unit == null) return HDTileAction.none;

  // 1) 이벤트 상위 바이트 우선
  int eventType = unit.ixEvent & 0x00FF0000;
  if (eventType != 0) {
    if (eventType == 0x00010000) return HDTileAction.event;
    if (eventType == 0x00020000) return HDTileAction.talk;
    if (eventType == 0x00030000) return HDTileAction.sign;
    if (eventType == 0x00040000) return HDTileAction.enter;
  }

  // 2) 오브젝트(Lore_B, objUpper=ixObj1)
  if (unit.ixObj1 > 0) {
    final objAction = _getObjectAction(unit.ixObj1);
    if (objAction != HDTileAction.move && objAction != HDTileAction.none) return objAction;
    if (objAction == HDTileAction.none) return HDTileAction.none;
  }

  // 3) 지면 타일(Lore_A5, ixTile)
  return _getTileAction(unit.ixTile);
}
```

### 3.2 판정 테이블 (실측 정리)

**1티어 — `ixEvent & 0x00FF0000`** (맵 `events[]` 가 있는 칸에서만 채워짐, §1.3)

| 값 | 액션 | 이벤트 이름 접두사 |
|---|---|---|
| `0x00010000` | `event` | `EVENT` / `EVT` |
| `0x00020000` | `talk` | `TALK` |
| `0x00030000` | `sign` | `SIGN` |
| `0x00040000` | `enter` | `ENTER` |
| `0` | 다음 티어로 | `NPC` / 그 외 (G-26-1) |

**2티어 — `ixObj1`(objUpper, Lore_B)** — `_getObjectAction`

| 범위 | 액션 | 통행 |
|---|---|---|
| `<= 0` | (없음, 다음 티어) | — |
| `1 ~ 63` | `none` (BLOCK) | ❌ |
| `64 ~ 87` | `move` → 다음 티어 | ✅ |
| `88 ~ 95` | `move`(애니메이션) → 다음 티어 | ✅ |
| `96 ~ 111` | `none` (BLOCK) | ❌ |
| `112 ~ 123` | **`sign`** | ❌ |
| `124 ~ 127` | **`enter`** | ❌ |
| `128 ~ 143` | **`talk`** | ❌ |
| `144 ~ 255` | `move` → 다음 티어 | ✅ |

**3티어 — `ixTile`(ground, Lore_A5)** — `_getTileAction`

| 범위 | 액션 | 통행 |
|---|---|---|
| `< 56` | `move` | ✅ |
| `56 ~ 59` | `water` | ⚠ `ixTile == 56` + `walkOnWater > 0` 일 때만 |
| `60 ~ 61` | `swamp` | ✅ |
| `62 ~ 63` | `lava` | ✅ |
| `64 ~ 69` | **`enter`** | ❌ |
| `70 ~ 71` | `cliff` | ✅ |
| `72 ~ 127` | `none` (BLOCK) | ❌ |
| `>= 128` | `move` | ✅ |

맵 에디터 A5/B 규약(GROUND_TRUTH §11, `tools/mapEditor/AI_GUIDE.md`)과 정확히 일치한다.
ground 레이어 원시값은 `1536 + A5인덱스`이며 로더가 `d - 0x600`(= 1536)으로 되돌린다
(`hadar2026_app/lib/application/map_loader.dart:85`).

#### 3.2.1 타일 액션의 출처는 **정확히 3개뿐이다** (GROUND_TRUTH 부록 J-3)

| MV 레이어 | z | 로더가 넣는 곳 | 타일 액션에 관여? |
|---|---|---|---|
| `ground` (Lore_A5) | 0 | `unit.ixTile` | ✅ **3티어** — `_getTileAction` |
| `ground2` | 1 | (읽지 않음) | ❌ |
| `objLower` (Lore_B) | 2 | `unit.ixObj0` | ❌ **순수 장식**. `getUnitAction` 이 `ixObj0` 를 보지 않는다 |
| `objUpper` (Lore_B) | 3 | `unit.ixObj1` | ✅ **2티어** — `_getObjectAction` |
| `shadow` | 4 | `unit.shadow` | ❌ 야간 렌더링 전용 |
| `region` | 5 | `unit.ixEvent` **하위 바이트** | ❌ **마스크(`& 0x00FF0000`)에 걸리지 않는다**(부록 J-1) |
| 맵 JSON `events[]` | — | `unit.ixEvent` **상위 바이트**(`map_loader.dart:60-70`) | ✅ **1티어** — 이름 접두사 TALK/SIGN/EVENT/ENTER |

- **R-26-6a** 즉 타일 액션을 만드는 것은 ① 맵 JSON `events[]` 이름 접두사 ② `objUpper` B 대역
  ③ `ground` A5 대역 **세 가지뿐**이다. `region`·`objLower`·`shadow`·`ground2` 는 관여하지 않는다.
- **R-26-6b** 앵커 배치 도구·린트·콘텐츠 서버는 위 3개 출처만 계산에 넣는다. region 을 입력으로
  받는 `unitAction` 계산은 성립하지 않는다(부록 J-2).

### 3.3 앵커 배치 권장 타일 — **WARN 규칙과 "무엇이 깨지는가"**

런타임은 타일 액션과 무관하게 앵커를 발화시킨다(§3.5). 그래도 배치가 어긋나면
**플레이어가 그 앵커에 물리적으로 닿을 수 없다.** 아래는 그 도달 가능성을 검사하는 규칙이며
전부 **WARN** 이다.

| kind (`activation`) | 권장 타일 액션 | 배치 방법 (맵 에디터) | 어기면 **무엇이 깨지는가** | 심각도 |
|---|---|---|---|---|
| `actor` (`interact`) | `talk` | `objUpper` = B 128~143 | 칸이 통행 가능해지면 **파티가 그 칸을 밟고 지나간다.** 마주 볼 대상이 없으므로 **대화를 걸 수 없다** | **warn** |
| `sign` (`interact`) | `sign` | `objUpper` = B 112~123 | 동일 — **읽을 수 없다.** 또한 디스패처의 SIGN 기본 헤더가 붙지 않는다 | **warn** |
| `container` (`interact`) | `talk` \| `sign` | 상자는 B 128~143, 유골·비문은 B 112~123 | 동일 — **조사할 수 없다** | **warn** |

#### 3.4.1 `A-26-03` 이 "이름 존재" 로는 부족한 이유 (GROUND_TRUTH 부록 D)

`MapInfos.json` 등록 이름 **15개 중 7개가 존재하지 않는 파일로 해석**된다. 더 나쁜 것은
**등록되어 있다는 사실 자체가 로드를 깨뜨린다**는 점이다 —
`hadar2026_app/lib/application/map_navigation.dart:30` 이 폴백 `'<이름>.json'` 을 먼저 세우고
`:43` 이 이름을 찾으면 `Map{id:03d}.json` 으로 덮어쓰기 때문이다.
미등록인 `ORIGIN` 은 폴백이 살아남아 정상 로드된다(부록 F-4).

이것이 앵커 검증에 미치는 영향은 두 가지다.

| # | 영향 |
|---|---|
| 1 | `portal.to.map: "TOWN1"` 은 **이름 검사만 하면 통과하지만 런타임에 맵이 로드되지 않는다.** 그리고 로드 실패가 성공으로 보고되므로(부록 D-2) 파티는 **이전 맵에 남은 채** 좌표만 옮겨진다 |
| 2 | 부록 F-2: `bundle.json == null` 이어도 `mapScriptFactory[bundle.mapName]` 이 있으면 네이티브 스크립트가 **직전 맵 위에 부착**된다. 앵커 좌표·트리거 인덱스가 **다른 맵을 대상으로** 평가되는 상태가 만들어진다 |

- **R-26-43** `A-26-03` 은 **파일 해석까지** 검사한다. 표현의 정본은
  [BP-22 R-22-11](22_world_bible_model.md) 이고, 선행 의존은 [BP-22 T-22-1](22_world_bible_model.md) 이다.
- **R-26-44** 수리 경로는 **기존 데이터뿐**이다. 맵 에디터의 `registerAs` 는 이미 `json` 필드를 쓴다
  (`tools/mapEditor/server/ai_api.ts:592`, 부록 H-4). 신규 맵은 올바르게 등록되므로
  앵커 도구가 새 맵을 만들 때는 이 문제가 재발하지 않는다.
- **R-26-45** 앵커 파일이 존재하는데 그 맵이 해석되지 않으면, 빌드는 **그 맵의 앵커 전량을 하드 실패**로
  보고한다(개별 좌표 검사보다 먼저). 에러 hint 는 T-22-1 을 가리킨다.

### 3.5 `trigger` 앵커의 발화 — **트리거 인덱스 직접 조회** (D-27 확정 · D-28 집행)

#### 3.5.0 원래의 문제 진술 (유효)

**문제**: `HDTileAction.event` 를 만드는 경로는 **오직 1티어**(맵 `events[]` 의 `EVENT` 이벤트)뿐이다.
2·3티어에는 `event` 를 내는 범위가 없다(§3.2 판정 테이블).
즉 **레거시 디스패치 규칙만 따른다면, 맵 JSON 에 이벤트를 만들지 않고서는 step-on 트리거를 만들 수 없다.**

이것은 "맵 JSON 은 지형만" 이라는 R-26-1 과 정면으로 충돌한다. **이 진술 자체는 여전히 참이다** —
바뀐 것은 결론이다. 답은 "타일 액션을 만들어 낼 새 경로를 찾는다" 가 아니라
**"콘텐츠 티어는 타일 액션을 아예 요구하지 않는다"** 였다.

#### 3.5.1 — (결번)

초판의 "region 승격 vs objUpper 오브젝트 — 충돌 규정" 절이 있던 자리다.
D-28 이 region 승격을 기각해 **규정할 충돌 자체가 사라졌다.** 번호는 재사용하지 않는다 —
다른 장([BP-33](33_validation_and_lint.md)·[BP-36](36_map_editor_extension.md)·[BP-91](91_appendix_worked_example.md))이
이 번호를 인용한 이력이 있어 당기면 참조가 깨진다. 폐기 근거는 §3.5.3 에 있다.

#### 3.5.2 검토했던 해결안 4개와 채택 결과 (D-28 최종)

초판은 T1~T3 을 두고 **T1 을 권고**했다. D-27 이 T4 를 만들고, D-28 이 T1 을 기각했다.

| 안 | 방법 | 판정 |
|---|---|---|
| ~~**T1. region 레이어 예약**~~ | z5 `region` 값 중 200~255 를 "content trigger" 로 예약하고, 로더가 그 값을 만나면 `ixEvent \|= 0x00010000` 로 승격 | **기각 (D-28)** — 작동하지만 앵커를 다시 맵 데이터에 묶는다. §3.5.3 |
| ~~**T2. 빈 EVENT 이벤트 유지**~~ | 맵에 `dialogLines` 가 빈 `EVENT` 이벤트만 두고 내용은 앵커가 | **기각** — 코드 수정 0 이지만 맵 파일에 이벤트가 계속 남아 R-26-1 이 형해화. T1 과 같은 병(맵 데이터 결합)을 더 노골적으로 앓는다 |
| ~~**T3. 런타임 오버레이**~~ | 콘텐츠 로드 시 트리거 인덱스를 보고 `MapModel` 의 해당 `unit.ixEvent` 를 메모리에서 승격 | **기각** — 맵 파일은 무변경이지만 `isUnitPassable` 등 **다른 판정에 파급**된다. `event` 는 `isStepOn` 이라 통행 판정이 바뀌어, 트리거를 놓았을 뿐인데 통행 규칙이 변한다 |
| **T4. 트리거 인덱스 직접 조회** | 콘텐츠 티어가 타일 액션 게이트보다 **앞에서** `(map, x, y, activation)` 로 인덱스를 조회하고, 앵커가 있으면 타일 액션과 **무관하게** 처리 | ✅ **채택 (D-27)** — 앵커가 맵 데이터에 아무 표시도 남기지 않는다. §3.5.4 |

**T4 는 T1~T3 과 다른 종류의 답**이다. T1~T3 은 전부 "타일 액션을 어떻게 만들어 낼까" 를 물었고,
T4 는 **"왜 만들어야 하는가"** 를 물어 전제를 지웠다. 부록 J-1 이 T1 의 전제(region 이 읽힌다)를
반증하면서 그 물음이 열렸고, 부록 K 가 T4 의 실행 가능성(진입점에 선검사가 없다)을 실측으로 확정했다.

#### 3.5.3 T1(region 승격) 폐기 이력 — 무엇을 하려던 것이었나, 왜 기각되었나

> **삭제하지 않고 남기는 이유**: T1 은 오답이 아니라 **작동하는 대안**이었다. 로더 1곳을 고치면
> region 트리거가 실제로 발화한다 — 부록 J-1 의 비트 불일치는 승격으로 해소된다.
> 이 기획서는 정정 이력을 보존하는 방식으로 만들어졌으므로(D-08a·D-20a·D-21a·D-28 이 그 예),
> "무엇을 하려던 것이었나 / 왜 기각되었나 / 무엇으로 대체되었나" 를 함께 남긴다.
> 근거를 지우면 같은 안이 다시 제안될 때 같은 논의를 처음부터 반복하게 된다.

**(a) T1 이 하려던 것** — 폐기된 로더 수정안

```dart
// lib/application/map_loader.dart 수정안 — 폐기됨 (D-28). 적용하지 말 것.
const int kContentTriggerRegionMin = 200;   // 200~255 예약
final int region = _getLayerData(rawData, 5, index, size);
map.data[index].ixEvent = (region >= kContentTriggerRegionMin)
    ? (0x00010000 | region)     // step-on event 로 승격
    : region;
```

region(0~255)은 `ixEvent` 하위 바이트에 들어가고 마스크는 비트 16~23 을 보므로
(`200 & 0x00FF0000 == 0`, 부록 J-1) 그냥 넣으면 아무 일도 일어나지 않는다.
위 승격은 예약 대역 값을 **상위 바이트로 옮겨** 그 불일치를 해소한다. **기술적으로 가능하다.**

**(b) 폐기 항목 전량과 각각의 대체물**

#### 3.5.4 채택안 — 인덱스 조회 계약

> **런타임 코드 스케치는 이 장 소유가 아니다.** `check()` 에 조회 경로를 삽입하는 코드,
> `HDAnchorActivation` 열거형, 정합 위반 시의 런타임 동작은
> **[BP-27 §4](27_runtime_engine.md) 소유**다(D-18). 이 장은 **인덱스의 계약**만 확정한다 —
> 키가 무엇이고, 충돌을 어떻게 풀고, kind 별로 언제 활성인가.

**(a) 세 가지 확정**

- **R-26-56** (D-27·D-28) **`trigger` 앵커는 트리거 인덱스 직접 조회로만 발화한다.**
  맵 데이터의 어떤 레이어에도 표시를 남기지 않는다. region 예약 대역은 **존재하지 않는다.**
- **R-26-57** 콘텐츠 티어는 `HDTileProperties.getUnitAction` 의 결과를 **발화 조건으로 쓰지 않는다.**
  타일 액션은 티어 0 에 **진단용 부가 정보**로만 전달된다(경고 메시지에 "실제 타일 액션은 move 였다" 를
  적기 위한 것). 판정에 쓰면 D-27 이 무효화된다.
- **R-26-58** **`map_loader.dart` 는 수정하지 않는다.** `:44` 의
  `map.data[index].ixEvent = _getLayerData(rawData, 5, index, size)` 는 그대로 둔다.
  결과적으로 **region 레이어는 계속 읽히되 계속 아무 효과가 없다**(부록 J-1·J-2).
  - 이것은 방치가 아니라 **결정**이다. 로더를 고치지 않는 것이 앵커 설계의 요구다 —
    고치는 순간 맵 데이터가 콘텐츠 발화에 관여하기 시작한다.
  - 부작용: `region` 값은 앞으로도 **아무 의미가 없다**. 맵 에디터가 region 을 계속 편집할 수 있게
    두더라도 게임 동작은 변하지 않는다. [BP-33 R-33-43](33_validation_and_lint.md) 이
    `region >= 200` 을 검사하는 규칙을 **새로 만들지 않기로** 확정한 것도 같은 이유다.
  - 부록 I-1(`Map001` (2,3) `region=255`)은 **무의미해졌다.** 예약이 없으므로 충돌이 없고,
    `A-26-*` 어느 규칙도 그 값을 보지 않는다. 그 맵은 A5/B/region 경계값을 의도적으로 훑는
    테스트 픽스처이므로 **정리하지 말고 그대로 둔다** — [BP-51 T-165](51_task_breakdown.md) 가
    "같은 앵커를 region 값 `0`/`64`/`128`/`255` 칸에 두어도 발화 결과가 동일하다" 를 단언하는 데
    **입력 픽스처로 쓴다.** 폐기된 `T-26-1` 이 그 값을 지우려 했으므로, 지우지 않는 것이 중요하다.

**(b) 조회 키 — 3단 키는 `activation` 이다** (BP-27 `Q-27-9` 해소)

| 단 | 키 | 값 예 | 왜 이것인가 |
|---|---|---|---|
| 1단 | 맵 이름 (`MapInfos.json#name`) | `"TOWN1"` | 맵 전환 시 그 맵의 서브맵만 상주시키면 된다(R-26-13) |
| 2단 | `"<x>,<y>"` 문자열 | `"34,12"` | JSON 은 정수 키를 못 쓴다. 런타임이 `x<<16\|y` int 키로 재해싱(R-26-12) |
| **3단** | **`activation`** — `interact` \| `step_on` | `"interact"` | **§2.2 의 `activation` 이 발화 조건의 유일한 선언**이다(R-26-5c). ~~`HDTileAction` 이름(`talk`/`sign`/`event`/`enter`)~~ 은 **폐기** — 타일 액션은 앵커 발화에 관여하지 않으므로 키로 쓰면 D-27 이 무효화된다 |
| 값 | 앵커 id **배열** | `["anchor.core.town1_gate_guard"]` | 다중 앵커 허용(§4.4). `priority` 내림차순 정렬 상태로 굽는다 |

- **R-26-59** (D-28, `R-26-10` 대체) **3단 키의 정본은 `activation` 이다.** 굽는 쪽(빌드)과
  조회하는 쪽(런타임)이 같은 키를 써야 하며, 두 표기가 공존하면 **티어 0 이 통째로 죽는다.**
  레거시 티어와의 우선순위는 디스패치 티어 순서(D-10)가 정하고, **로더나 타일 비트가 정하지 않는다.**
- **R-26-60** (D-28, `R-26-48` 대체) **인덱스가 단일 정본이다.** 콘텐츠 서버·빌드·런타임·솔버가
  전부 같은 `content.index.json#triggers` 를 본다. 서버가 타일 비트를 해석해 발화 여부를 판정하는
  경로는 **만들지 않는다** — 그것이 `R-26-48` 이 막으려 했던 이중 구현이고, 인덱스 단일화가 그 문제를 없앤다.
- **R-26-61** `activation: "both"` 는 **소스 표기일 뿐 인덱스 키가 아니다.** 빌드가 `interact` 와
  `step_on` **두 키에 같은 앵커 id 를 펼쳐 넣는다.** 런타임은 `both` 라는 키를 모른다 —
  조회 시점에 3분기를 하지 않게 하려는 것이다(결정론 + O(1) 유지).
  - 따라서 `both` 앵커는 인덱스에 **2회 등장**한다. `once:true` 인 `both` 앵커의 1회성은
    앵커 id 단위의 `onceFlag`(§2.3.1)로 보장되며, **키가 둘이어도 두 번 발동하지 않는다.**

- **R-26-66** `:193` 의 호출은 **fire-and-forget** 이다(부록 K-3). 이동 프레임과 콘텐츠 실행이 겹칠 수 있고
  **재진입 가드(`_isScriptRunning`)가 유일한 보호막**이다. 앵커 설계상 이는 "한 번에 하나의 상호작용"
  규약에 흡수되며, 가드 규약의 테스트 고정은 [BP-27](27_runtime_engine.md) 소관이다.

#### 3.5.5 남은 비대칭 — 같은 앵커가 조작 방식에 따라 다르게 동작한다 (부록 K-2)

`player_sprite.dart:359` 의 `if (action.isInteractive)` 는
**presentation 계층이 콘텐츠 발화 여부를 결정하는 유일한 지점**이다.

```
같은 앵커 anchor.core.town1_gate_guard (kind=actor, activation=interact),
그 칸의 실제 타일 액션이 move 인 경우:

  확인키(:405)로 접근  → 게이트 없음 → 인덱스 조회 → **발화한다**
  벽처럼 부딪혀(:359)  → if (action.isInteractive) 가 false → **호출조차 오지 않는다**
```

**앵커 설계상 이 비대칭이 뜻하는 것**

| # | 의미 |
|---|---|
| 1 | **`activation` 이 "발화 조건의 유일한 선언"(R-26-5c)이라는 계약이 bump 경로에서만 깨져 있다.** 앵커는 `interact` 를 선언했는데 실제 발화 여부가 **타일 비트에 좌우된다** — D-27 이 없애려던 그 결합이 진입점 하나에 남아 있는 것이다 |
| 2 | **정합 규칙을 warn 으로 강등한 것의 대가**가 여기서 나타난다. `A-26-16` 위반(권장 타일과 불일치)이 hard 였다면 이 비대칭은 데이터 수준에서 발생할 수 없었다. warn 이므로 **발생 가능한 상태**가 되었고, 그 상태에서 조작 방식에 따라 동작이 갈린다 |
| 3 | **작성자가 진단할 수 없는 실패**다. 확인키로 테스트하면 정상 동작하므로 작성자는 문제를 보지 못한다. 플레이어가 "부딪혀도 말이 안 걸린다" 고 보고할 때까지 드러나지 않는다 — 이 기획이 cm2 에서 없애려는 침묵 실패(GROUND_TRUTH §9·부록 F-1)와 같은 양식이다 |
| 4 | **런타임 관대 / 게이트 엄격의 2단 구조(R-26-7b)로도 잡히지 않는다.** 솔버는 확인키 경로만 모델링하면 그 앵커를 도달 가능으로 판정한다. 즉 이 비대칭은 **정합 warn 으로도, 솔버로도 자동 검출되지 않는다** |

**해소 경로 — 이 장의 소유가 아니다**

- **R-26-67** 해소는 **`:359` 의 게이트를 제거하거나 콘텐츠 조회를 그 앞에 세우는 1줄 수준의 변경**이다.
  코드 변경의 소유는 [BP-27 `Q-27-10`](27_runtime_engine.md) 이고 실행 태스크는
  [BP-51 T-167](51_task_breakdown.md)(M1, 규모 S) 이다. 이 장은 **링크만** 한다(D-18).
- **R-26-68** 검증은 [BP-51 T-165](51_task_breakdown.md) 의 완료 조건 ④ — **진입점 3개의 동작이 일치한다.**
  같은 앵커를 step-on(`:193`) · bump(`:359`) · 확인키(`:405`) 로 접근해도 같게 발화해야 한다.
  3개 중 2개는 코드 변경 없이 성립하므로(R-26-64), 이 단언은 실질적으로 **T-167 이 게이트를 제거했는지의 검증**이다.
- **R-26-69** T-167 이 적용되기 전까지 **`A-26-16` WARN 이 유일한 방어선**이다.
  따라서 그 경고 메시지는 "부딪혀서는 상호작용할 수 없다" 를 **명시적으로** 말해야 한다
  (§3.3 의 경고 hint 및 [BP-33 `V-MAP-001`](33_validation_and_lint.md) 이 그 문구를 소유한다).
- **R-26-70** 리스크 등록: [BP-52 RK-26](52_risks.md)("같은 타일에서 어떤 때는 콘텐츠 대사, 어떤 때는 JSON 대사")의
  세 번째 원인이 이 비대칭이다. 완화 태스크는 T-165 · T-167.

- **Q-26-1** *(종결)* region 을 트리거 **식별자**로도 써서 `(map, region)` → 앵커 매핑을 만들 것인가 →
  **아니다.** D-28 이 region 승격을 기각했으므로 예약 대역도 식별자 겸용도 없다.
  트리거 식별은 **앵커 id** 가 하고, 좌표 조회는 **트리거 인덱스**가 한다.

## 4. 트리거 인덱스

### 4.1 목적

`(map, x, y, activation)` → 앵커를 **O(1)** 로 찾는다. §1.1 의 선형 탐색을 대체하고,
**타일 액션 게이트를 대체한다**(D-27) — 이 조회가 앵커 발화의 유일한 관문이다. 계약은 §3.5.4.

### 4.2 구조

빌드 산출물 `content.index.json` 의 `triggers` 섹션.

> **3단 키 정정 (D-28 · BP-27 `Q-27-9` 해소)**: 초판 예시는 3단 키를
> ~~`HDTileAction` 이름(`talk`/`sign`/`event`/`enter`)~~ 으로 적었다. D-27 이후 정본은
> **`activation`(`interact` / `step_on`)** 이다(R-26-59). 두 표기가 공존하면
> **빌드가 굽는 키와 런타임이 조회하는 키가 갈라져 티어 0 이 통째로 죽는다.**

```json
{
  "triggers": {
    "TOWN1": {
      "34,12": { "interact": ["anchor.core.town1_gate_guard"] },
      "30,18": { "interact": ["anchor.core.town1_notice"] },
      "17,37": { "interact": ["anchor.core.town1_tavern_drunk"] },
      "50,99": { "interact": ["anchor.core.town1_to_ground"],
                 "step_on":  ["anchor.core.town1_to_ground"] },
      "61,82": { "step_on":  ["anchor.core.town1_crypt_secret", "anchor.gen_ep1.crypt_scholar_clue"] }
    },
    "DEN1": {
      "24,45": { "step_on": ["anchor.core.menace_exit"] }
    }
  }
}
```

`"50,99"` 는 `activation: "both"` 인 portal 앵커다 — **같은 앵커 id 가 두 키에 펼쳐진다**(R-26-61).
`"61,82"` 의 두 앵커는 같은 키를 공유하는 다중 앵커이며 `when` 으로 갈린다(§4.4).

| 요소 | 형태 | 이유 |
|---|---|---|
| 1단 키 | 맵 이름 (`MapInfos.json#name`) | 맵 전환 시 그 맵의 서브맵만 들고 있으면 됨 |
| 2단 키 | `"<x>,<y>"` 문자열 | JSON 은 정수 키를 못 쓴다. 런타임이 `x * 65536 + y` int 키 `Map` 으로 재해싱 |
| **3단 키** | **`activation` 이름** (`interact` / `step_on`) | **§2.2 의 `activation` 이 발화 조건의 유일한 선언**(R-26-5c·R-26-59). 디스패처가 `isInteraction` 을 이미 알고 있으므로 그 값으로 바로 조회한다 — 타일 액션을 계산할 필요가 없다 |
| 값 | 앵커 id **배열** | 다중 앵커 허용(§4.4). `priority` 내림차순 정렬 상태로 굽는다 |

- **R-26-71** 3단 키의 값 집합은 **정확히 2개**(`interact`, `step_on`)다. `both` 는 굽히지 않고
  두 키로 펼쳐진다(R-26-61). 그 외 문자열이 나타나면 **빌드 하드 실패** — 오타로 죽은 키가 생기면
  앵커가 조용히 발화하지 않게 되고, 이는 이 기획이 없애려는 침묵 실패 양식이다.

### 4.3 런타임 표현

```dart
// lib/application/content/trigger_index.dart (D-11 배치)
class TriggerIndex {
  // mapName -> (x<<16|y) -> activation -> anchorIds (priority desc, 이미 정렬됨)
  final Map<String, Map<int, Map<HDAnchorActivation, List<String>>>> _byMap;

  static int key(int x, int y) => (x << 16) | (y & 0xFFFF);

  List<String> lookup(String mapName, int x, int y, HDAnchorActivation activation) =>
      _byMap[mapName]?[key(x, y)]?[activation] ?? const [];
}
```

- **R-26-11** 인덱스는 **빌드가 생성**한다. 런타임은 앵커 파일을 스캔하지 않는다.
- **R-26-12** 맵 폭·높이는 실측 최대 100 이므로 `x << 16 | y` 로 충분하다. 65536 초과 맵은 빌드 하드 실패.
- **R-26-13** 조회는 **현재 맵의 서브맵만** 유지한다. 맵 전환 시 교체(`HDGameSession.loadMapFromFile` 훅).
- **R-26-72** `HDAnchorActivation` 열거형(값 2개: `interact`, `stepOn`)과 `isInteraction` → 열거값 변환,
  `has`/`resolve` 메서드 시그니처는 **[BP-27 §2.2](27_runtime_engine.md) 소유**다(D-18).
  위 스케치는 **키 형태를 보이기 위한 것**이며 클래스 계약의 정본이 아니다.
  이 장이 소유하는 것은 **`_byMap` 의 3단 키가 `activation` 이라는 사실**뿐이다.

### 4.4 다중 앵커 충돌 규칙

같은 `(map, x, y, activation)` 에 앵커가 여럿일 수 있다. 이것은 **에러가 아니라 기능**이다 —
"퀘스트 중이면 다른 대사" 를 앵커 수준에서 표현하는 수단이다.

| # | 규칙 |
|---|---|
| **R-26-14** | 후보는 `priority` **내림차순**, 동률이면 **팩 위상 순서의 역순**(의존하는 쪽이 먼저), 그래도 동률이면 앵커 id 사전순. 이 순서는 빌드가 굽고 런타임은 재정렬하지 않는다(결정론) |
| **R-26-15** | 런타임은 후보를 순서대로 훑어 `when` 이 **true 인 첫 앵커**를 채택한다. 나머지는 무시 |
| **R-26-16** | 전부 false 면 **앵커 없음**으로 취급하고 아래 티어(native → cm2 → JSON)로 폴백(D-10) |
| **R-26-17** | 같은 좌표+같은 `activation` 의 모든 앵커가 `when` 을 생략(= 항상 true)했고 2개 이상이면 **빌드 하드 실패** — 뒤의 것이 영원히 죽은 데이터이기 때문(§1.1 의 문제 2를 재발시키지 않는다) |
| **R-26-18** | 같은 좌표에 **`activation` 이 다른** 앵커는 자유롭게 공존한다(예: `interact` 앵커와 `step_on` 앵커). 조회 키가 다르므로 발동 경로가 다르고, 충돌이 아니다. **초판이 `A-26-13` 으로 금지하려 했던 "같은 칸의 트리거 + 상호작용 오브젝트" 는 이 규칙에 따라 정상**이다 — region 승격이 없으므로 한쪽이 다른 쪽을 조용히 무력화하지 않는다(§3.5.3) |
| **R-26-19** | 같은 좌표에 `actor` 앵커가 2개 이상이면 `when` 유무와 무관하게 **경고**(한 칸에 두 사람) |

## 5. 엔티티 레지스트리 — 역참조 인덱스

### 5.1 목적

"이 ID 가 **어디서 쓰이는가**" 를 O(1) 로 답한다. 세 소비자가 있다.

| 소비자 | 질문 | 사용처 |
|---|---|---|
| 린트 | "이 아이템을 주는 곳이 있는가?" (획득 불가 목표 검출, [BP-22 L-22-29](22_world_bible_model.md)) | 5단계 lint (D-14) |
| 생성 컨텍스트 | "이 NPC 가 이미 등장한 퀘스트는?" (중복 서사 방지) | 1단계 context (D-14) |
| 영향 분석 | "이 플래그를 건드리면 뭐가 깨지나?" | 사람의 편집·리뷰 |

### 5.2 스키마

`content.index.json` 의 `registry` 섹션.

```json
{
  "registry": {
    "npc.core.lore_gate_guard": {
      "kind": "actor",
      "pack": "core",
      "definedIn": "core/actors/lore_gate_guard.json",
      "anchoredAt": [ { "map": "TOWN1", "x": 34, "y": 12, "anchor": "anchor.core.town1_gate_guard" } ],
      "referencedBy": {
        "dialogue":  ["dlg.core.gate_guard_idle", "dlg.gen_ep1.guard_about_scholar"],
        "quests":    ["quest.gen_ep1.missing_scholar"],
        "objectives":["quest.gen_ep1.missing_scholar#ask_guard.talk_guard"],
        "anchors":   ["anchor.core.town1_gate_guard"],
        "lore":      []
      }
    },

    "item.gen_ep1.scholar_notebook": {
      "kind": "item",
      "pack": "gen_ep1",
      "definedIn": "gen_ep1/items/items.json",
      "givenBy":  ["anchor.gen_ep1.menace_notebook_container"],
      "takenBy":  ["dlg.gen_ep1.wife_thanks#node.give.effects[0]"],
      "requiredBy": ["quest.gen_ep1.missing_scholar#deliver.has_notebook"],
      "referencedBy": { "conditions": 2, "effects": 2 }
    },

    "flag.gen_ep1.quest.missing_scholar.met_client": {
      "kind": "flag",
      "pack": "gen_ep1",
      "writtenBy": ["dlg.gen_ep1.wife_plea#node.intro.onEnter[0]"],
      "readBy":    ["quest.gen_ep1.missing_scholar#prerequisites",
                    "npc.core.lore_gate_guard#dialogueRouting[0]"]
    }
  }
}
```

### 5.3 필드 정의

| 필드 | 대상 kind | 의미 |
|---|---|---|
| `kind` | 전부 | 엔티티 타입 |
| `pack` | 전부 | 소유 팩 |
| `definedIn` | 정의가 있는 것 | 소스 파일 경로(팩 루트 기준) |
| `anchoredAt` | `actor` | 좌표 바인딩 목록 |
| `referencedBy` | 전부 | 카테고리별 참조자 목록 |
| `givenBy` / `takenBy` | `item` | `give_item` / `take_item` 이 있는 위치 |
| `requiredBy` | `item` | `has_item` 조건 / `acquire`·`deliver` 목표 |
| `writtenBy` / `readBy` | `flag`, `var` | Effect / Condition 위치 |
| `usedBy` | `enc`, `place` | 인카운터·장소 참조자 |

**참조 위치 표기**: `<entityId>#<path>` — `path` 는 엔티티 내부의 구조 경로다.
`dlg.gen_ep1.wife_plea#node.intro.onEnter[0]` 처럼 읽으면 정확히 어느 Effect 인지 특정된다.
`chance` 의 `evalPath`([BP-21 §6.5](21_content_pack_spec.md))와 같은 표기법이다.
경로는 **실제 스키마 구조를 그대로 따른다** — `entry` 는 Dialogue 최상위 필드이므로
`dlg.x#entry[2]` 이고 `dlg.x#node.intro.entry[2]` 같은 형태는 성립하지 않는다
(REVIEW_BP-21 `F-13` 의 예시 오류가 이 장으로 전파되지 않도록 명시한다).

### 5.4 레지스트리가 즉시 잡는 것

| # | 검사 | 근거 필드 |
|---|---|---|
| **RG-01** | 획득 불가 아이템을 요구하는 목표 | `givenBy == []` && `requiredBy != []` |
| **RG-02** | 아무도 읽지 않는 플래그 (죽은 상태) | `readBy == []` |
| **RG-03** | 아무도 쓰지 않는 플래그 (영원히 false) | `writtenBy == []` && `readBy != []` |
| **RG-04** | 배치되지 않은 액터 (고아 NPC) | `anchoredAt == []` |
| **RG-05** | 아무 대화·퀘스트도 없는 액터 | `referencedBy` 전부 빈 배열 |
| **RG-06** | 어떤 앵커·퀘스트도 가리키지 않는 대화 | `referencedBy == {}` |
| **RG-07** | 참조가 없는 인카운터 | `usedBy == []` |
| **RG-08** | 은퇴 ID 로의 잔존 참조 | `referencedBy != []` && `retiredIds` 에 존재 |

- **R-26-20** 레지스트리는 빌드가 **한 번 순회하며** 만든다. 소스를 두 번 읽지 않는다.
- **R-26-21** 레지스트리는 `content.index.json` 에 들어가고 **런타임도 읽는다** —
  디버그 커맨드(`/whereis <id>`)와 저널 UI 의 "이 아이템은 어디에 쓰이나" 표시에 쓸 수 있다.
  런타임이 필요 없다면 빌드 플래그로 제외 가능(웹 번들 크기 절감).

## 6. 좌표 이동 안전성

### 6.1 시나리오

맵 에디터(사람 또는 AI)가 NPC 를 옮긴다. 앵커가 따라오지 않으면 §1.2 의 사고가 재발한다.

### 6.2 절차 — 에디터가 앵커를 아는 경우 (정상 경로)

```
1. AI/사람이 "34,12 의 위병을 36,12 로 옮겨줘" 요청
2. 콘텐츠 서버가 GET /api/content/anchors?map=TOWN1&x=34&y=12
   → anchor.core.town1_gate_guard (kind=actor) 발견
3. 서버가 한 트랜잭션으로 두 가지를 함께 적용:
   a) 맵 편집: objUpper (34,12) → 0,  objUpper (36,12) → 132
   b) 앵커 편집: anchor.core.town1_gate_guard.x = 36
4. 서버가 §3.3 정합 검사 재실행 → 실패면 전체 롤백
5. content.index.json 재빌드
```

- **R-26-22** 맵 편집과 앵커 편집은 **원자적**이다. 하나만 적용된 중간 상태를 커밋하지 않는다.
- **R-26-23** 콘텐츠 서버는 맵 API 와 **같은 프로세스**여야 한다(D-12). 두 서버로 나뉘면 원자성이 깨진다.
- **R-26-24** 이동 API 는 전용 엔드포인트를 제공한다: `POST /api/content/anchors/{id}/move { "x":36, "y":12 }`
  — 앵커 이동이 맵 타일 이동을 **끌고 간다**(역방향이 아니라). 상세는 [BP-31](31_content_server_api.md).

### 6.3 앵커 없는 이동 감지

사람이 브라우저 에디터로 직접 타일만 옮기거나, 다른 도구로 맵 JSON 을 고치면 앵커가 남는다.

**검출 규칙** (`hadar_content validate` 및 맵 에디터 `/validate` 가 함께 수행)

| # | 증상 | 검출 | 심각도 |
|---|---|---|---|
| **M-26-01** | 앵커 좌표의 타일 액션이 §3.3 **권장값**과 다름 | 앵커 순회 | **warn** (D-27 강등, = `A-26-16` / [BP-33 `V-MAP-001`](33_validation_and_lint.md)) |
| **M-26-02** | 앵커가 가리키던 자리가 통행 가능해짐 (NPC 가 사라짐) | 동일 | **warn** (D-27 강등) |
| **M-26-03** | 앵커 없는 TALK/SIGN/ENTER 타일이 생김 (배치는 됐는데 의미가 없음) | 맵 순회 | warn |
| **M-26-04** | 맵 크기 축소(`resize`)로 앵커가 범위 밖으로 나감 | 앵커 순회 | hard |
| **M-26-05** | 앵커 파일의 `map` 이름에 해당하는 맵이 사라짐 | 파일 존재 | hard |

- **R-26-74** (D-27) `M-26-01`/`M-26-02` 의 강등은 §3.4 의 심각도 배분과 같은 근거다 —
  **런타임은 타일이 무엇이든 앵커를 발화시킨다.** 다만 "요구값" 이라는 말을 **"권장값"** 으로 바꾼 것이
  단순한 표현 변경이 아님을 주의할 것: 이제 이 검출은 **"규격 위반"** 이 아니라
  **"플레이어가 닿지 못한다"** 는 진단이다. 그리고 §3.5.5 의 비대칭 때문에
  `M-26-01` 위반 칸은 **확인키로는 닿고 부딪혀서는 닿지 않는** 상태가 된다 —
  이것이 이 경고를 무시하면 안 되는 실질적 이유다.
### 6.4 자동 수복 규칙

**M-26-01/02 에 한해** 자동 수복을 시도한다. 규칙은 보수적이다.

| # | 규칙 |
|---|---|
| **R-26-25** | 앵커 좌표의 **체비셰프 거리 2 이내**에서 §3.3 **권장 액션**을 만족하는 칸을 찾는다 |
| **R-26-26** | 후보가 **정확히 1개**일 때만 자동 이동한다. 0개면 실패, 2개 이상이면 **모호**로 실패 |
| **R-26-27** | 후보 칸에 **다른 앵커가 이미 있으면** 후보에서 제외 |
| **R-26-28** | 자동 수복은 `--fix` 플래그가 있을 때만 실행된다. 기본은 **보고만** 한다 |
| **R-26-29** | 수복 결과는 앵커의 `_note` 에 `"auto-moved (34,12)->(36,12) at build <hash>"` 로 기록된다 |
| **R-26-30** | `portal` 앵커는 **자동 수복하지 않는다**. 출입구를 잘못 옮기면 맵 연결 구조가 무너지므로 사람이 판단한다 |

```
$ hadar_content validate --fix
[warn] anchor.core.town1_gate_guard: (34,12) 의 액션이 move 입니다 (권장: talk).
       파티가 그 칸을 밟고 지나가므로 부딪혀서는 대화를 걸 수 없습니다.
       반경 2 이내 talk 후보 1개 발견: (36,12).
       → 자동 이동함. anchors/TOWN1.json 갱신.
[warn] anchor.core.town1_notice: (30,18) 의 액션이 move 입니다 (권장: sign).
       반경 2 이내 sign 후보 0개 — 자동 수복 불가.
       hint: objUpper (30,18) 을 B 112~123 으로 설정하거나 앵커를 삭제하세요.
```

- **R-26-75** (D-27) 자동 수복 실패는 **`[fail]` 이 아니라 `[warn]`** 이다. 초판 예시는 두 번째 줄을
  `[fail]` 로 적었는데, 정합 규칙이 warn 으로 강등된 뒤에는 **수복 실패가 빌드를 멈추지 않는다.**
  `--fix` 는 편의 도구이고, 그 실패가 하드 게이트가 되면 warn 강등이 우회되는 셈이다.
  실질적 차단은 솔버의 도달 불가 판정(R-26-7b·R-26-54)이 담당한다.

### 6.5 역방향 안전성 — 앵커가 맵을 만든다

새 앵커를 만들 때 타일이 없으면, **앵커가 타일을 요구**한다.

- **R-26-31** `POST /api/content/anchors` 는 `autoPlaceTile: true`(기본) 옵션을 갖는다.
  §3.3 **권장 액션**의 대표 타일(actor→B 132, sign→B 116, portal→B 125)을 자동으로 놓는다.
- **R-26-32** 그 자리에 이미 BLOCK 이 아닌 다른 오브젝트가 있으면 자동 배치를 거부하고
  `{error, hint}` 로 되돌린다. 덮어쓰지 않는다.

## 7. 런타임 조회 경로

### 7.1 시퀀스 (Content tier 도입 후, D-10 · **D-27 로 순서가 바뀌었다**)

> **티어 0 은 타일 액션 게이트보다 앞에 있다.** 초판 시퀀스는 `getUnitAction` → scripted 판정 →
> `beginNarrative()` → 인덱스 조회 순서였다. D-27 이후 **조회가 게이트 앞으로 올라간다** —
> 게이트를 통과하지 못하는 칸(`move` 위의 `actor` 앵커, 타일 액션이 없는 칸의 `step_on` 앵커)에서도
> 앵커가 발화해야 하기 때문이다.

> 규약이 **맵 이동 시 성립하지 않는다**.

### 7.2 폴백 체인 (D-10 확정 순서)

```
0. Content tier   TriggerIndex 에 활성 앵커가 있으면 ContentRuntime 이 처리하고 handled=true
1. native map script            (HDNativeScriptRunner)
2. cm2 paired script            (Event::Override 로 handled 신호)
3. JSON dialogLines             (_emitJsonDialog, 레거시 폴백)
```

**⚠ 현행 폴백 체인은 이미 고장나 있다** — 티어 0 의 가치를 평가할 때 이 사실을 전제해야 한다.

| # | 실측 | 폴백 체인에 대한 영향 |
|---|---|---|
| 부록 A-1 | `map_navigation.dart:43` 이 `cm2Path = 'Map{id}.cm2'` 를 **무조건** 설정하고, `MapInfos.json` 에 `cm2` 필드가 하나도 없다 → 모든 맵이 **존재하지 않는 cm2** 를 페어링으로 갖는다 | 티어 판정 `currentMapCm2Path != null` 이 **항상 참** |
| 부록 A-2 | `script_engine_adapter.dart:92-99` 은 로드 실패 시 `clearRuntimeState()` 없이 반환한다 → 직전 맵의 스크립트·변수가 남는다 | **3티어 중 cm2 티어가 항상 선택되고, 그 내용은 직전 맵의 것**이다 |
| 부록 A-3 | `map_script.dart:41-48` 의 `isFlagSet`/`setFlag` 가 **미구현 스텁**이라 항상 `false` | 네이티브 티어의 **모든 조건 분기가 죽어 있다** |
| 부록 C-1 | `MapModel.toJson()` 이 `events` 를 저장하지 않고 `fromJson` 도 복원하지 않는다 | **세이브를 로드하는 순간 JSON 대사 티어가 통째로 사라진다**(Map002 18·Map003 3·Map010 8·Map011 9) |
| 부록 C-2 | `save_manager.dart:86` 이 `setNewMap` 을 직접 불러 네이티브 스왑 경로(`game_session.dart:117-128`)를 타지 않는다 | 로드 후 `currentMapScript` 가 **직전 맵의 것으로 남거나 null** |

- **R-26-50** 따라서 "앵커가 없는 맵의 동작은 완전히 그대로다"(R-26-33)는 **현행 동작을 보존한다는 뜻이지
  현행 동작이 옳다는 뜻이 아니다.** 위 5건의 수리는 [BP-28](28_migration_and_coexistence.md) 소관이며,
  티어 0 은 그 수리를 기다리지 않고 **독립적으로** 동작할 수 있다 — 이것이 티어 0 을 맨 앞에 두는 실질적 이점이다.
- **R-26-51** 특히 부록 C-1 때문에 **레거시 JSON 대사는 세이브/로드를 견디지 못한다.**
  "앵커로 이관하지 않아도 JSON 이 남아 있으니 괜찮다" 는 판단은 **성립하지 않는다** —
  §8 의 이관은 편의가 아니라 복구다.

- **R-26-33** 앵커가 없는 맵의 동작은 **완전히 그대로**다. `TriggerIndex.lookup` 이 빈 배열을 돌려주면
  기존 코드 경로가 바뀌지 않는다 → 무중단 점진 이관.
- **R-26-34** `when` 이 전부 false 여서 앵커가 채택되지 않으면 `handled=false` 이고 아래 티어로 내려간다.
  "앵커는 있는데 조건이 안 맞아서 레거시 대사가 나온다" 는 의도된 동작이다(이관 과도기).
- **R-26-35** (D-27 개정) Content tier 의 진입은 **`HDTileEventDispatcher.check` 의 타일 액션 게이트 앞**
  한 곳이다. 초판은 `_dispatchScripted` 맨 앞이라고 적었는데, 그 위치는 **이미 게이트를 통과한 뒤**여서
  `move` 칸의 앵커나 타일 액션 없는 `step_on` 앵커가 도달하지 못한다 — D-27 의 전제가 깨진다.
  기존 3티어 코드는 여전히 **한 줄도 수정하지 않는다**(게이트 자체를 지우는 것이 아니라 그 앞에 조회를 얹는다).
  삽입 코드는 [BP-27 §4](27_runtime_engine.md) 소유다.
- **R-26-73** presentation 계층의 게이트는 이 규칙의 예외다 — `player_sprite.dart:359` 의
  `if (action.isInteractive)` 는 디스패처 **바깥**에 있어서 티어 0 을 앞세워도 우회되지 않는다.
  §3.5.5 가 그 비대칭을 다루고, 해소는 [BP-51 T-167](51_task_breakdown.md) 이다.

### 7.4 상호작용 트리거의 현재 위치 — 헤드리스의 실제 장벽 (GROUND_TRUTH 부록 B-3)

위 시퀀스는 "디스패처가 호출된 뒤" 를 그린 것이다. **그 호출이 어디서 오는가**는 별개 문제이고,
실측은 `application/` 이 아니다:

| 위치 | 내용 |
|---|---|
| `hadar2026_app/lib/presentation/panels/player_sprite.dart:103` | `void update(double dt)` — Bonfire 스프라이트의 **폴링 루프** |
| 같은 파일 `:193`, `:362`, `:405` | `HDGameMain().checkTileEvent(...)` 직접 호출 |

- **R-26-52** `UiHost`/`AssetSource` 포트를 페이크로 바꿔도 **이동과 상호작용 자체를 헤드리스로
  구동할 수 없다.** 현재 `PartyMovementHost` 는 애니메이션 위임용이지 **이동 판정의 소유자가 아니다.**

### 8.5 이관 후 상태

- **R-26-36** 원본 `map.events[]` 는 **삭제하지 않는다**. `_migratedTo` 마커만 붙인다.
  앵커가 먼저 걸리므로(D-10 tier 0) 레거시 경로는 자연히 죽고, 문제가 생기면 마커를 지워 되돌린다.
- **R-26-36a** 다만 **되돌림이 항상 통하지는 않는다.** 부록 C-1 에 따라 `MapModel.toJson()` 이
  `events` 를 저장하지 않으므로 **세이브를 로드한 뒤에는 레거시 JSON 티어가 존재하지 않는다.**
  즉 롤백은 "새로 시작한 세션" 에서만 유효하다. 이 제약을 이관 도구가 경고로 출력한다.
- **R-26-37** A-26-10(앵커와 레거시 이벤트가 같은 칸에 공존) 경고는 `_migratedTo` 마커가 있으면 억제한다.
- **R-26-38** 전 맵 이관이 끝나면 `_emitJsonDialog` 는 **삭제 후보**가 된다. 다만 D-10 은 3티어 보존을
  요구하므로, 삭제는 별도 결정 사항이다(→ Q-26-3).
- **R-26-38a** 이관 완료 판정에는 **세이브 로드 후 동작 확인**이 포함된다. 부록 C-1 때문에
  "새 게임에서는 대사가 나오는데 세이브를 불러오면 안 나온다" 는 상태가 이관 전에도 이미 존재하며,
  이관이 그것을 해소한다 — 앵커는 세이브와 무관하게 번들에서 읽히기 때문이다.
