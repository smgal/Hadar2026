## 12.1 이 장의 목적 · 평가 축 · 판정 규약

### 12.1.1 목적

BP-11 이 "우리 구조가 AI 자동 생성에 왜 부적합한가"를 갭(G-nn)으로 나열했다면, 이 장은 **그 갭을 이미 푼 사람들이 어떻게 풀었는지**를 조사해 우리 설계의 출처를 명시한다. 목적은 세 가지다.

1. **D-01 ~ D-17 의 사후 정당화가 아니라 계보 명시** — 확정 결정이 어느 선행 사례에서 왔는지 밝혀, 나중에 "왜 이렇게 했나"를 되짚을 수 있게 한다.
2. **버린 것의 기록** — 채택하지 않은 설계는 대부분 "틀려서"가 아니라 **우리 규모·제약에 안 맞아서** 버린 것이다. 규모가 바뀌면 다시 꺼낼 수 있도록 기각 사유를 남긴다.
3. **용어 번역** — 남의 용어를 우리 용어로 1:1 대응시켜, 외부 문서를 읽는 사람이 본 기획서를 읽을 때 헤매지 않게 한다.
   **대응표의 SSoT 는 [BP-92](92_appendix_reference_index.md) 다.** 이 장의 절별 대응표는 그 절을 읽는 동안 필요한 **국소 요약**이며,
   통합 색인·신뢰도 등급·역방향 조회는 BP-92 가 소유한다. 두 곳이 어긋나면 **BP-92 가 이긴다.**

> **D-18 (SSoT 소유권) 준수 선언**: 이 장은 어떤 스키마도 소유하지 않는다. `Condition`/`Effect` 의 op·do 는 **이름만 인용**하고
> 시그니처를 재서술하지 않는다(소유: BP-21). `Quest`/`Stage`/`Objective` 는 BP-23, `Dialogue`/`Node`/`Choice` 는 BP-24,
> 앵커는 BP-26, 세이브 v2 는 BP-25 가 소유한다. 이 장의 역할은 **그 결정들이 어디서 왔는지**를 밝히는 것뿐이다.

## 12.2 RPG Maker (MV / MZ) — 이벤트 페이지 + 스위치 조건 모델

> 이 절이 가장 길다. **우리 맵 JSON 이 실제로 MV 포맷이기 때문**이다 (GROUND_TRUTH §6). 즉 다른 참조원은 "배울 것"이지만 RPG Maker 는 **이미 우리 안에 절반쯤 들어와 있고, 우리가 그 절반을 버리고 있는 상태**다.

### 12.2.1 핵심 아이디어

- 맵 위의 **이벤트(Event)** 는 좌표 하나에 붙는 상호작용 단위다.
- 이벤트는 **여러 개의 페이지(Page)** 를 갖는다. 각 페이지는 자기만의 **조건(conditions)**, 겉모습(image), 이동 경로(moveRoute), **발동 조건(trigger)**, 그리고 **명령 리스트(list)** 를 갖는다.
- 런타임은 이벤트를 만날 때 **조건을 만족하는 페이지 중 하나를 골라** 그 페이지만 실행한다. 조건이 바뀌면 같은 좌표의 같은 이벤트가 **다른 대사·다른 겉모습·다른 동작**이 된다. [확인됨 — 포맷 수준]
- 조건 만족 페이지가 여럿일 때 MV 가 고르는 것은 **번호가 가장 큰 페이지**다(뒤에서부터 탐색). 결정론적이며 모호하지 않다. [확인됨 — GROUND_TRUTH 부록 E-2]
  **→ 우리 규칙과 정반대다.** 12.2.4.1 의 경고 참조.
- 페이지 조건에 쓰이는 상태는 세 종류: **전역 스위치(bool)**, **전역 변수(int)**, **셀프 스위치(A~D, 이벤트 로컬 bool)**. 여기에 "특정 액터가 파티에 있는가", "특정 아이템을 가졌는가" 가 더해진다. [확인됨 — 우리 JSON 의 `conditions` 필드가 정확히 이 목록이다]

우리 레포의 실제 데이터로 확인한 `conditions` 객체:

```json
"conditions": {
  "actorId": 1,   "actorValid": false,
  "itemId": 1,    "itemValid": false,
  "selfSwitchCh": "A", "selfSwitchValid": false,
  "switch1Id": 1, "switch1Valid": false,
  "switch2Id": 1, "switch2Valid": false,
  "variableId": 1, "variableValid": false, "variableValue": 0
}
```
(`hadar2026_app/assets/maps/Map003.json` 의 모든 이벤트 페이지. `*Valid` 가 전부 `false` = 조건 없음)

| RPG Maker MV 용어 | 정의 | 본 기획서 대응 | 대응 문서 |
|---|---|---|---|

> **`Node.header` 의 계보 정정** — 초판은 `Node.header` 를 MV 코드 101 의 대응물로 적었으나 **오류였다**(부록 E-1).
> 101 은 얼굴 그래픽·창 배경·창 위치를 지정하는 표시 설정 레코드이고 텍스트도 화자명도 담지 않는다(실측 파라미터 `['', 0, 0, 2]`).
> `Node.header` 는 **MV 계보가 아니라 본 기획서의 독자 개념**이며, 실제 계보는 두 갈래다:
> ① 원작 Hadar 의 푯말 헤더 관습 — `hadar2026_app/lib/application/tile_event_dispatcher.dart:116-117` 의
> `setHeader('@B푯말에 써 있기를:')` (12.14.1), ② Yarn Spinner 의 노드 헤더 메타데이터 (12.7.1).
> 화자 이름 표시는 MV 101 의 기능이 아니라 MZ 에서 추가된 별개 기능이다. [확인됨 — 부록 E-1]

`hadar2026_app/lib/domain/map/map_event.dart:75-88` 의 파싱은 다음과 같다.

```dart
  if (page['list'] != null) {
    for (var item in page['list']) {
      if (item['code'] == 401 && ...) {     // ← 401 만 읽음
        ... ev.dialogLines.add(param);
```

즉 우리는:

| MV 가 제공하는 것 | 우리 코드의 처리 | 결과 |
|---|---|---|
| `pages[]` 다중 페이지 | **`pages[0]` 만 읽음** | 조건부 변형 전멸 |
| `page.conditions` | **파싱조차 안 함** | 상태에 따른 대사 변화 불가 |
| `page.trigger` | 무시 (타일 `HDTileAction` 이 대신 판정) | 접촉/자동/병렬 구분 없음 |
| 코드 101(대화창 설정) | 무시 | **손실 없음 — 의도적으로 옳은 동작.** 얼굴 그림 시스템이 없으므로 버리는 것이 맞다 (부록 E-1) |
| 코드 111/121/122/201 등 | 무시 | 이벤트가 **상태를 바꿀 수 없음.** 단 아래 실측 참조 |
| 코드 401(텍스트) | 유일하게 읽음 | **대사 출력 전용 포맷으로 전락** |
| 같은 좌표의 여러 이벤트 | `_emitJsonDialog` 가 **첫 매치에서 return** (`hadar2026_app/lib/application/tile_event_dispatcher.dart:166-178`) | 좌표당 이벤트 1개만 유효 |

**실측 보강 (부록 E)**: 레포의 전 맵 JSON 을 훑으면 실제로 등장하는 명령 코드는 **`0`(38회) · `101`(25회) · `401`(31회) 세 종류뿐**이다.
`111`/`121`/`122`/`201` 은 **우리 데이터에 하나도 없다.** 즉 "이벤트가 상태를 바꿀 수 없다" 는 결과는
코드가 무시해서만이 아니라 **애초에 그런 명령이 데이터에 존재하지 않아서**이기도 하다.
→ 12.2.6-1(MV 명령 인터프리터 기각)의 논거가 여기서 결정적으로 강해진다: **되살릴 자산이 실제로 없다.**

**부록 A 와의 접속 (도달 경로 정정)**: 위 표는 "JSON dialogLines 티어" 를 살아 있는 폴백으로 전제하지만,
실측상 그 티어에 도달하는 경로 자체가 손상돼 있다.
- **A-1**: `hadar2026_app/lib/application/map_navigation.dart:43` 이 모든 맵에 `Map{id}.cm2` 를 **무조건** 부여한다 — 존재하지 않는 파일이다.
- **A-2**: `hadar2026_app/lib/application/scripting/script_engine_adapter.dart:92-99` 가 로드 실패 시 `clearRuntimeState()` 없이 반환해 **직전 맵 스크립트가 살아남는다.**
- 두 버그가 합쳐져 티어 판정(`currentMapCm2Path != null`)이 **항상 참**이 되고, 디스패치는 사실상 늘 cm2 티어를 탄다.
  JSON 티어는 **이전 맵의 cm2 가 `Event::Override()` 를 부르지 않을 때만** 도달한다.
- **C-1**: 게다가 `MapModel.toJson()` 이 `events` 를 저장하지 않으므로 **세이브를 로드한 순간 JSON 대사 티어는 통째로 사망**한다.

→ "대사 출력 전용 포맷으로 전락" 이라는 이 절의 결론은 그대로 유지된다. 오히려 **더 나쁘다** —
그 전용 포맷조차 안정적으로 도달·보존되지 않는다. D-09(앵커 분리)와 D-10(티어 0 신설)의 시급성이 여기서 나온다.

**결론**: 우리 맵 JSON 은 "RPG Maker 포맷"이 아니라 **"RPG Maker 포맷의 껍데기를 쓴 좌표→고정 대사 사전"** 이다. 조건·상태·분기라는 MV 모델의 본체는 통째로 미사용이다. 이것이 BP-11 의 갭 중 "조건부 대화 불가"의 정확한 기술적 정체다.

### 12.2.4 Hadar2026 적용 가능성: **부분 채택 — 모델은 채택하되 "순서를 뒤집어" 변환, 포맷은 기각**

- **모델 채택 (단, 순서 변환 조건부)**: "하나의 상호작용 지점 = 조건으로 골라지는 여러 변형" 은 조건부 대화의 최소 정답이다.
  D-07 의 `Dialogue.entry[] {when, go}` 가 이것의 번역이다. **다만 직역이 아니라 역순 변환이다** — 12.2.4.1 참조.
- **포맷 기각**: MV 의 `pages[].list[]` 명령열을 **되살리지는 않는다.** 이유:
  1. 명령열은 **텍스트와 부작용이 한 배열에 섞여 있다.** LLM 이 생성할 때 스키마 강제가 어렵고, 정적 검증기가 "이 이벤트가 어떤 플래그를 건드리는가"를 뽑아내려면 명령 코드 인터프리터를 다시 만들어야 한다. D-02 가 요구하는 "정적 검증 가능한 선언적 데이터"와 정면 충돌.
  2. MV 명령 코드는 **문서화된 유한 집합**이다(열린 집합이 아니다). 문제는 개수가 아니라 **우리가 그 중 극히 일부만 구현할 것**이라는 점이다 — 껍데기만 지원하면 AI 가 미구현 코드를 생성하고 **침묵 실패**한다. cm2 의 "Unknown command → 스킵" 과 똑같은 함정(GROUND_TRUTH §9). D-05 가 닫힌 op/do 집합을 요구하는 이유가 정확히 이것이다.
     *(정확한 코드 개수는 이 기획 작업에서 세지 않았다. 논거는 개수가 아니라 "부분 구현 = 침묵 실패" 이므로 수치는 불필요하다.)*
  3. 우리가 실제로 구현할 계획이 있는 것은 **텍스트 출력과 상태 변경**뿐이고, 그 둘은 이미 `Node.lines` / `Effect[]` 로 표현된다.
     애니메이션·오디오·픽처·이동경로 계열은 우리 표현 매체(288×320 타일맵 + 512×320 텍스트 콘솔)에 대응물이 없다.
     *(초판의 "MV 명령의 99%" 라는 수치는 근거 없는 추정이라 삭제했다.)*

#### 12.2.4.1 ⚠ 경고 — **페이지 선택 순서가 우리와 정반대다** (부록 E-2)

이 장 전체에서 **이관 작업자에게 가장 위험한 단 하나의 사실**이다.

| | 조건 만족 후보가 여럿일 때 | 탐색 방향 |
|---|---|---|
| **RPG Maker MV** | **번호가 가장 큰 페이지**를 고른다 | 배열 **뒤에서부터** |
| **본 기획서 `Dialogue.entry[]`** (D-07, R-12-1) | **위에서부터 첫 번째 참**을 고른다 | 배열 **앞에서부터** |

- 둘 다 **결정론적**이다. 초판이 "MV 는 규칙대로 고른다 … 애매함 없음" 이라고 우리 쪽 우위를 주장한 것은
  MV 의 성질이 아니라 **집필 시점의 미확인 상태**를 서술한 것이었다. 정정한다.
- **실질 위험**: `pages[]` 를 `entry[]` 로 옮기면서 **배열 순서를 보존하면 분기 의미가 통째로 뒤집힌다.**
  MV 저자는 "가장 구체적인 조건을 마지막 페이지에" 두는 관습으로 쓰는데, 그것을 그대로 옮기면
  우리 런타임은 **가장 일반적인 첫 페이지**를 골라 버린다. 조용히, 오류 없이.
- **현재 위험도**: 낮음. 레포의 전 맵 38개 이벤트 중 **다중 페이지 이벤트 0건, 조건 활성(`*Valid == true`) 0건**(실측).
  그러나 맵 에디터가 이벤트 CRUD 를 지원하므로(GROUND_TRUTH §11) 다중 페이지 데이터는 **언제든 생길 수 있다.**
  "지금 데이터에 없다" 는 영구 보증이 아니다.
- **규범 (→ R-12-13)**: MV `pages[]` → `Dialogue.entry[]` 변환기는 **반드시 배열을 역순으로 뒤집어야 한다.**
  변환기가 없더라도, 손으로 옮기는 사람이 이 사실을 알아야 한다.
- **인계**: [BP-24](24_dialogue_model.md)(레거시 변환 규칙), [BP-28](28_migration_and_coexistence.md)(이관 절차).

### 12.2.5 차용할 것

| # | 차용 | 우리 구현 |
|---|---|---|
| 1 | **조건부 변형 (페이지 개념)** | `Dialogue.entry[]` — 위에서부터 첫 true 인 노드로 진입 (D-07) |
| 2 | **"우선순위 있는 조건 목록" 의 결정론** | MV 도 우리도 결정론적이다 — MV 는 **최고 번호 만족 페이지**, 우리는 **배열 위에서부터 첫 true**(R-12-1). 우리가 얻는 것은 "애매함 제거" 가 아니라 **읽는 순서와 평가 순서의 일치**다. ⚠ **순서가 반대이므로 이관 시 역순 변환 필수** (12.2.4.1) |

| 5 | **레거시 호환 유지** | `events[].dialogLines` 티어를 지우지 않고 폴백으로 남긴다 (D-10 티어 3). ⚠ **단 이 티어는 현재 세이브 로드 후 사망한다** — `MapModel.toJson()` 이 `events` 를 저장하지 않음(부록 C-1). "폴백으로 남긴다" 가 실제로 성립하려면 C-1 이 함께 고쳐져야 한다 |

### 12.2.7 열린 질문

- **Q-12-1 (셀프 스위치 대응물)**: MV 의 셀프 스위치는 "이 이벤트 하나에만 붙는 bool" 이다. 우리 D-05 에는 전역 `flag` 만 있고 앵커 로컬 상태가 없다. `Choice.once` 와 `npc_state` 로 대부분 대체되지만, "이 상자는 한 번만 열린다" 같은 패턴은 `flag.<pack>.anchor.<anchorId>.opened` 라는 **관례로 푸는 게 맞는지, 스키마에 `anchor_flag` op 를 추가할지** 미결. → [BP-26](26_entity_registry_and_anchors.md) 로 넘김.
- **Q-12-7 (앵커의 메모/태그 자리)**: MV `event.note` 는 레거시 맵에 실재하는 필드인데 D-09 의 `Anchor` 에는 갈 곳이 없다.
  D-14 7단계 `critic` 이 앵커에 검수 메모를 남길 자리도 없다. `Anchor.note?` / `Anchor.tags?` 선택 필드를 둘지 미결.
  **1차 스코프 밖으로 미뤄도 무방하나 "대응 없음" 이라는 사실은 표에 정직하게 남긴다.** → [BP-26](26_entity_registry_and_anchors.md).

## 12.3 Bethesda — Radiant Quest System (Skyrim / Fallout 4)

### 12.3.1 핵심 아이디어

- 퀘스트를 **템플릿**으로 쓴다. "누구에게서 받아 / 어디로 가서 / 무엇을 가져온다" 의 골격만 정의하고, **"누구"와 "어디"를 런타임에 조건으로 채워 넣는다.**
- 채워 넣는 슬롯이 **Alias(별칭)** 다. Alias 는 **조건식으로 대상을 고른다.** [확인됨 — 개념 수준]
  *(예: "레벨에 맞고 아직 클리어하지 않은 던전 하나" — 이것은 **설명을 위한 가상 예시**이며 특정 퀘스트의 실제 조건식이 아니다.)*
- 퀘스트는 번호가 붙은 **Stage** 의 나열이다. **Objective(화면에 보이는 목표)는 Quest 레벨의 독립 목록**이고,
  Stage 는 진행에 따라 그 Objective 의 표시/완료 상태를 바꾼다. 저널 텍스트는 Stage 가 갖는다. [부분확인 — 구조 방향은 확인, 필드 세부는 미검증]
  ⚠ **우리 D-06 은 이와 다르다** — 12.3.3.1 참조.
- 어떤 사건이 어떤 퀘스트를 깨울지는 **Story Manager** 가 중개한다. 사건 발생 → 조건 맞는 퀘스트 템플릿이 인스턴스화되고 Alias 가 채워진다. [확인됨 — 명칭·동작 모두 확인]

### 12.3.2 데이터 구조 대응표

| Bethesda 용어 | 정의 | 본 기획서 대응 | 비고 |
|---|---|---|---|
| Quest | 퀘스트 레코드 | `Quest` (D-06) | 거의 그대로 |
| Quest Stage (번호) | 진행 단계, 저널 텍스트 소유 | `Stage {id, index, journal}` (D-06) | 번호 → id + index 병행 |
| Objective | 화면 표시 목표. **Quest 가 소유하는 독립 목록** | `Objective {id, kind, params}` (D-06) — **단 `Stage` 하위에 nest** | ⚠ **소유 층이 다름** (12.3.3.1) |
| **Alias** | 런타임에 조건으로 채워지는 슬롯 | **`Objective.params` + `Anchor`** (D-06, D-09) | **채우는 시점이 다름** ↓ |

### 12.3.3 Hadar2026 적용 가능성: **부분 채택 — "런타임 Radiant" 는 기각, "빌드타임 Radiant" 로 변환**

Radiant 의 본질은 **"템플릿 + 슬롯 + 슬롯을 채우는 조건"** 이다. 이 셋 중 앞의 둘은 우리에게 매우 유용하고, 셋째의 **실행 시점**만 우리와 다르다.

```
Bethesda:   템플릿 ──[런타임 Alias Fill]──▶ 인스턴스 ──▶ 플레이
Hadar2026:  템플릿 ──[빌드타임 bind]──▶ 구체 퀘스트 JSON ──▶ 결정론 재생
                     └ D-01: 런타임은 해석만 한다
```

- **D-01 이 런타임 절차적 생성을 금지**하므로 Alias Fill 을 게임 안에서 돌릴 수 없다. 대신 **생성 파이프라인 4단계 `bind`(D-14)** 가 정확히 같은 일을 오프라인에서 한다: 퀘스트 개요의 "어떤 마을의 학자" 를 실제 `npc.gen_ep1.xxx` + `anchor.gen_ep1.xxx` 로 해소.
- 이 변환의 **이점**: 슬롯이 채워진 결과가 파일로 남으므로 **검증·검수·리뷰가 가능**하다. Radiant 의 고질적 비판(반복적·맥락 없는 퀘스트)의 원인 중 하나는 결과물을 사람이 미리 볼 수 없다는 점이다. 우리는 D-14 7단계 `critic` 에서 사람/에이전트가 실제 결과물을 본다.
- **손실**: 무한 반복 퀘스트가 안 된다. 우리는 유한한 캠페인이므로 손실이 아니다.

#### 12.3.3.1 ⚠ Objective 의 소유 층이 원본과 다르다 (의도적 이탈)

```
Bethesda:   Quest ── objectives[]        (Quest 소유)
              └── stages[] ── fragment ──▶ objective 표시/완료 상태 변경
            ⇒ 여러 Stage 가 같은 Objective 를 공유할 수 있다

Hadar2026:  Quest ── stages[] ── objectives[]     (Stage 소유, D-06 nest)
            ⇒ Stage 가 바뀌면 목표 집합도 통째로 바뀐다. 스테이지 간 목표 공유 불가
```

| 항목 | Bethesda | D-06 (본서) |
|---|---|---|
| Objective 소유자 | Quest | **Stage** |
| 스테이지 간 목표 공유 | 가능 | **불가** |
| "3단계에 걸쳐 진행되는 하나의 수집 목표" | 하나의 Objective + 카운터 | Stage 마다 목표를 재선언하거나 `var_reach` 로 우회 |
| 목표 완료 판정 위치 | fragment(코드) | `Stage.completion: "all"\|"any"`(선언) |

- **왜 이탈했나**: D-06 은 Stage 를 유한 상태 기계의 상태로 본다. 상태가 자기 목표를 소유하면
  "지금 무엇을 해야 하는가" 가 **한 곳에서 읽힌다** — 검증기와 저널 UI 양쪽이 단순해진다.
- **대가**: 장기 누적 목표(예: "여정 전체에 걸쳐 유물 5개")를 Stage 하나에 담아야 하거나 `var_reach` 로 우회해야 한다.
- **결정은 D-06 이 소유**하므로 이 장은 바꾸지 않는다. **차이가 존재한다는 사실**을 기록하는 것이 이 절의 임무다.
  → [BP-23](23_quest_model.md) 이 이 제약을 명시적으로 다룰 것.

### 12.3.4 차용할 것

1. **Quest = 번호 있는 Stage 의 유한 상태 기계** — D-06 골격 그대로.
2. **Objective 를 별개 레코드 타입으로** — 목표가 여러 개고 AND/OR 로 묶인다는 구조 (D-06 `completion`).
   **단 소유 층은 원본과 다르다**: Bethesda 는 Quest 소유, 우리는 Stage 하위 nest (12.3.3.1).
3. **저널 텍스트를 Stage 가 소유** — D-06 `journal: {stageKey: stringKey}`. 저널 UI(BP-41)가 이걸 그대로 읽는다.
4. **템플릿/슬롯 발상** — 퀘스트 개요 스키마 `QuestOutline`(D-14 2단계)이 곧 템플릿이고, 슬롯이 bind 단계에서 채워진다. **[BP-32](32_generation_harness.md) 가 상세화.**
5. **사건 → 퀘스트 기동의 중개자** — `world_event_bus`(D-11). 전투 승리가 어떤 퀘스트의 `defeat` 목표를 진행시킬지 퀘스트가 직접 폴링하지 않고 버스가 라우팅한다.

| 4 | **Stage 에 붙는 스크립트 조각(Papyrus fragment)** | 12.9 참조 — 스크립트를 데이터에 심는 순간 검증 불가. `Effect[]` 로 강등 |
| 5 | **정수 Stage 번호를 유일 키로 쓰는 것** | D-04 이름 있는 ID. `index` 는 정렬용으로만 유지 |

## 12.4 Obsidian 계열 (Fallout: New Vegas) — 다중 해결 경로 · 실패 가능 퀘스트 · 평판

### 12.4.1 핵심 아이디어

- 하나의 퀘스트에 **여러 해결 경로**가 있다. 전투로도, 설득으로도, 우회로도 끝난다. 경로마다 **다른 결말과 다른 후폭풍**이 붙는다. [부분확인 — 개념 수준, 널리 알려진 설계 특징]
- **퀘스트는 실패할 수 있다.** NPC 를 죽이거나 시간을 놓치면 그 경로가 영구히 닫힌다. 실패도 정당한 종료 상태다.
- **평판이 축(axis)** 으로 존재해서, 개별 선택이 진영 단위 상태를 누적시키고 그게 다시 대화·상점·엔딩 조건이 된다. [부분확인]
- 대화 선택지에 **능력치/스킬 체크가 명시**된다 — "[말솜씨 50] …" 처럼 조건이 플레이어에게 **보인다.** [부분확인]

### 12.4.2 데이터 구조 대응표

| FNV 개념 | 본 기획서 대응 | 상태 |
|---|---|---|
| 다중 해결 경로 | `Stage.next: [{when: Condition, go: stageId}]` (D-06 분기) | **채택** |
| 실패 상태 | `Quest.failConditions`, `onFail`, 상태 `failed` (D-06, D-05 `fail_quest`) | **채택 — 이미 스키마에 있음** |
| 진영 평판 | `var.core.party.reputation_<faction>` + `var_cmp` (D-05) | **부분 채택 — D-16 선택 스코프** |
| 스킬 체크 선택지 | `Choice.when` + 텍스트에 조건 표기 | **부분 채택** ↓ |
| 선택지 잠금 표시 | 조건 불충족 선택지를 회색으로 보여줄지, 감출지 | **Q-12-2** |
| 퀘스트 간 상호 배제 | `prerequisites` 에 `quest_state(other, failed)` 조합 | **채택 — 표현 가능** |

### 12.4.3 Hadar2026 적용 가능성: **부분 채택**

- **채택되는 부분은 이미 D-06 에 들어와 있다.** `failConditions` / `onFail` / `Stage.next` 조건 분기 / `quest_state` op 는 전부 FNV 형 설계의 최소 표현이다. 이 절의 역할은 그 필드들이 **왜** 있는지를 밝히는 것.
- **평판은 D-16 에서 "선택(권장하되 1차 스코프 밖)" 으로 분류**됐다. 이 장은 그 결정을 뒤집지 않는다. 다만 **평판을 나중에 넣어도 스키마 변경이 필요 없다**는 점을 확인해 둔다 — `var_cmp` 하나로 표현 가능하고, `add_var` 로 누적 가능하다. 즉 **1차에서 빼도 손해가 없다.**
- 우리 원작 톤(12.14)은 90년대 콘솔형 RPG 에 가깝고, FNV 급 분기 밀도는 콘텐츠 예산을 폭발시킨다. **1차 캠페인은 "주 경로 1개 + 선택 목표 + 소수의 실패 가능 퀘스트"** 로 제한한다.

### 12.4.4 차용할 것

1. **실패를 1급 종료 상태로** — 검증기가 "완주 증명"뿐 아니라 **"실패 경로도 데드락 없이 종료되는가"** 를 확인해야 한다. → [BP-34](34_headless_sim_and_solver.md) 요구사항.
2. **경로마다 다른 Effect** — `Stage.next[].when` 으로 갈라진 각 가지가 서로 다른 `onExit`/보상을 갖는다.
3. **조건이 플레이어에게 보이는 선택지** — 숨긴 조건은 "왜 이 선택지가 없지?" 를 낳는다. 표시 정책은 BP-41 로 넘긴다.
4. **퀘스트 간 상호 배제의 명시적 표현** — 진영 A 를 도우면 진영 B 퀘스트가 닫힌다. `prerequisites` 로 표현되고, **솔버가 "동시 완주 불가 쌍" 을 계산해 리포트**해야 한다 (D-13).

### 12.4.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|
| 1 | 대규모 진영 평판 매트릭스 | D-16 선택 스코프. 1차는 단일 `reputation_lore` 정도로 제한 |
| 2 | 대화 내 스킬 체크의 확률 판정 | `chance` op 는 있으나 검증 부담(양 분기 탐색)이 크다. 1차는 **결정론적 조건만** 권장 |
| 3 | "모든 NPC 를 죽일 수 있음" 급 자유도 | NPC 사망 상태를 모든 대화·퀘스트가 고려해야 함 → 검증 폭발. `npc_state` 로 **필요한 NPC 만** 표현 |

## 12.5 CD Projekt Red (The Witcher 3) — 퀘스트 ↔ 대화 강결합, 조건부 씬

### 12.5.1 핵심 아이디어

- 퀘스트가 **단계의 그래프**로 편집되고, 그 노드 중 상당수가 **대화 씬 자체**다. 즉 퀘스트 진행과 대화 진행이 **하나의 그래프**로 관리된다. [부분확인 — 개념 수준]
  *(내부 편집 툴의 노드 타입 명칭은 공개 자료로 확인되지 않아 쓰지 않는다.)*
- 같은 NPC 와의 대화가 **퀘스트 상태에 따라 다른 씬**으로 라우팅된다. "조건부 진입" 이 시스템의 중심.
- 저널이 **선택의 결과를 서술**한다. 단순 체크리스트가 아니라 서사 요약. [부분확인]
- 시간 제한/기회 상실 퀘스트가 존재한다. [부분확인]

### 12.5.2 데이터 구조 대응표

| CDPR 개념 | 본 기획서 대응 | 상태 |
|---|---|---|
| 퀘스트 그래프의 노드 = 씬 | `Stage.onEnter: [{do:"play_dialogue", id:...}]` (D-05) | **채택** |
| 조건부 씬 라우팅 | `Dialogue.entry[] {when, go}` (D-07) | **채택** |
| 대화 선택이 퀘스트를 진행 | `Objective.kind: "choose"(dialogueId, choiceId)` (D-06) | **채택 — 이미 스키마에 있음** |
| 서술형 저널 | `Stage.journal: stringKey` (D-06) | **채택** |
| 씬 연출(카메라·모션캡처) | 대응 없음 | **기각** |
| 퀘스트 그래프 전용 편집기 | 콘텐츠 서버의 그래프 뷰 (D-12) | **부분 채택** — 12.8 참조 |

### 12.5.3 Hadar2026 적용 가능성: **부분 채택 — 결합 방향만 채택, 단일 그래프는 기각**

CDPR 이 주는 교훈은 **"퀘스트와 대화를 따로 만들면 둘이 어긋난다"** 는 것이다. 하지만 우리는 **둘을 하나의 그래프로 합치지 않는다.**

```
CDPR 스타일:     [단일 퀘스트-대화 그래프]  ← 강력하지만 편집기 없이는 못 씀

Hadar2026:       Quest (Stage FSM)  ──play_dialogue──▶  Dialogue (Node 그래프)
                       ▲                                        │
                       └──── Objective.kind:"choose" ───────────┘
                                (선택 → 퀘스트 진행)
```

- **두 파일로 분리하되 양방향 참조를 스키마로 못 박고, 빌드가 그 참조를 검증**한다. `play_dialogue(id)` 가 없는 대화를 가리키면 하드 실패(D-15). `choose(dialogueId, choiceId)` 가 없는 선택지를 가리켜도 하드 실패.
- 분리 이유:
  1. **LLM 생성 단위가 다르다.** 퀘스트 개요(D-14 2단계)와 대화 집필(3단계)은 다른 에이전트·다른 프롬프트다. 한 파일이면 부분 재생성이 어렵다.
  2. **재사용**: 같은 대화 그래프를 여러 퀘스트가 참조할 수 있다.
  3. **파일 크기**: 한 퀘스트 = 한 파일 규칙(D-03)을 유지하려면 대화가 분리돼야 한다.

### 12.5.4 차용할 것

1. **`play_dialogue` 를 Effect 로** — 퀘스트가 대화를 부른다 (D-05, 이미 확정).
2. **`choose` 를 Objective 로** — 대화가 퀘스트를 진행시킨다 (D-06, 이미 확정).
3. **양방향 참조 무결성 검사를 Hard gate 로** — D-15 "미해결 참조 0" 의 구체 항목으로 명시. → [BP-33](33_validation_and_lint.md).
4. **서술형 저널** — 체크리스트가 아니라 문장. 그래야 90년대 톤(12.14)과 맞는다.

### 12.5.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|
| 1 | 퀘스트-대화 단일 그래프 | 부분 재생성 불가, 파일 분할 규칙(D-03) 충돌 |
| 2 | 연출 타임라인(카메라·애니메이션) | 우리 표현 매체는 288x320 타일맵 + 512x320 텍스트 콘솔 |
| 3 | 시간 경과 기반 퀘스트 만료 | 게임 내 시계가 없다. `time_of_day` op 는 day/night 뿐(D-05) |
| 4 | 레벨 스케일링된 퀘스트 보상 | 우리 exp 테이블은 고정 21단계(GROUND_TRUTH §10). 보상은 저작 시점에 고정 |

## 12.6 Ink (inkle) — 텍스트 우선 서사 언어

### 12.6.1 핵심 아이디어

- **텍스트가 1급**이고 구조가 그 위에 얹힌다. 산문을 쓰다가 필요할 때만 구조를 넣는다.
- 구조 단위: **knot**(장면 덩어리), **stitch**(knot 안의 하위 절), **weave**(선택지가 자연스럽게 다시 합류하는 들여쓰기 구조), **divert**(`->` 이동), **tunnel**(`->knot->` 서브루틴처럼 갔다가 돌아옴).
- 선택지에 **한 번만 쓰이는 것과 계속 쓰이는 것**의 구분이 문법에 있다. [확인됨 — 문법 수준]
- 변수와 조건 분기를 언어가 직접 지원한다.
- **컴파일 산출물이 JSON 이고, 런타임(스토리 엔진)이 그 JSON 만 해석**한다. 저작 언어와 실행 표현이 분리돼 있다. [확인됨]

### 12.6.2 데이터 구조 대응표

| Ink 용어 | 정의 | 본 기획서 대응 |
|---|---|---|
| knot | 이름 붙은 장면 덩어리 | `Dialogue` 또는 `Node` — 입도에 따라 다름 |
| stitch | knot 안의 하위 진입점 | `Node` (D-07) |
| divert `->` | 다음으로 이동 | `Node.next` / `Choice.go` (D-07) |
| weave (`*` / `+`) | 선택 후 자동 합류 | ⚠ **대응 없음** — 우리는 `go` 를 명시 |
| `*` (한 번만) | 소진되는 선택지 | `Choice.once: true` (D-07) |
| `+` (계속) | 소진 안 되는 선택지 | `Choice.once` 생략(기본) |
| tunnel `->k->` | 갔다가 돌아옴 | ⚠ **대응 없음** — **Q-12-3** |
| `VAR` | 변수 선언 | `var.<pack>.…` (D-04) |
| `LIST` | 상태 열거형 | `npc_state` / `quest_state` 로 부분 대응 |
| EXTERNAL 함수 | 호스트 게임 호출 | **`Effect` 닫힌 집합** (D-05) — 임의 호출 불가 |
| 컴파일된 story JSON | 런타임 입력 | `content.bundle.json` (D-03) |

### 12.6.3 Hadar2026 적용 가능성: **부분 채택 — 아키텍처는 채택, 언어는 기각**

Ink 에서 가져올 가장 중요한 것은 문법이 아니라 **파이프라인 형태**다.

```
Ink:        .ink 소스 ──[inklecate 컴파일]──▶ story.json ──▶ 런타임 엔진
Hadar2026:  content/*.json ──[hadar_content build]──▶ content.bundle.json ──▶ ContentRuntime
                                                     └ D-01 Build/Runtime 분할과 정확히 동형
```

D-01 의 3분할(Authoring/Build/Runtime)은 Ink 가 이미 검증한 형태다. 우리는 여기에 **Authoring 자리에 LLM 을 넣는다**는 점만 다르다.

**언어를 기각하는 이유** — 그리고 이것이 D-02 의 핵심 근거다:

| Ink 의 장점 | 왜 우리에겐 단점인가 |
|---|---|
| 산문 흐름 그대로 쓸 수 있음 | **사람이 쓸 때의 장점.** LLM 은 오히려 스키마가 있는 편이 안정적 |
| 문법 설탕(weave, 자동 합류) | 파싱 규칙이 늘어남 = LLM 이 문법 오류를 낼 표면적이 늘어남 |
| 표현력 높은 변수·함수 | 정적 분석이 어려워짐. "이 스토리가 어떤 플래그를 세우는가" 를 뽑기 힘듦 |
| EXTERNAL 로 게임과 연결 | **열린 집합.** D-05 의 닫힌 op/do 원칙 위배 |
| 성숙한 런타임 존재 | **Dart 런타임을 우리가 유지보수해야 함.** 게다가 D-12 는 "저작 시맨틱 = 런타임 시맨틱" 을 위해 평가기를 domain 에 두라고 요구 |

> **핵심 논거**: LLM 생성물에서 우리가 원하는 것은 **표현력이 아니라 검증 가능성**이다. Ink 는 사람 작가의 표현력을 극대화하려고 만든 언어고, 우리는 기계 생성물의 오류율을 최소화하려는 포맷이 필요하다. 목적 함수가 반대다.

### 12.6.4 차용할 것

1. **컴파일 산출물 / 런타임 분리** — D-01, D-03 의 `build/` 디렉토리.
2. **소진되는 선택지(`once`)를 스키마 1급 필드로** — D-07 `Choice.once`. 이게 없으면 "이미 물어본 질문" 처리를 매번 플래그로 해야 한다.
3. **"소스는 사람이 읽을 수 있어야 한다"** — 컴파일 산출물이 최적화돼도 **소스는 diff 가능한 텍스트**여야 한다. D-03 이 소스를 JSON 으로 두는 이유.
4. **재현성** — 같은 소스 → 같은 산출물. D-15 "결정론 재빌드 해시 일치".

### 12.6.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|
| 1 | Ink 문법 전체 | D-02. 파싱 표면적 = LLM 오류 표면적 |
| 2 | weave 자동 합류 | 암묵적 제어 흐름은 정적 도달성 분석을 어렵게 함. 우리는 `go` 명시 강제 |
| 3 | tunnel | 호출 스택이 생기면 WorldState 직렬화가 복잡해짐 → **Q-12-3** |
| 4 | EXTERNAL 함수 | 열린 집합. D-05 위배 |
| 5 | ink 런타임을 Dart 로 포팅 | 유지보수 부담 + D-12 의 "평가기 공유" 요구와 충돌 |

### 12.6.6 열린 질문

- **Q-12-3 (tunnel / 공용 서브대화)**: "상점 열기", "예/아니오 확인" 같은 **재사용 대화 조각**을 어떻게 표현할지 미결. `Node.next` 로 갔다가 돌아올 방법이 스키마에 없다. 후보 (a) 호출 스택 도입 — WorldState 직렬화 복잡화, (b) 빌드 시점 **인라인 전개(inline expansion)** — 번들 크기 증가하나 런타임 단순, (c) 미지원. **(b) 를 권고**하되 결정은 [BP-24](24_dialogue_model.md).

## 12.7 Yarn Spinner — 노드 그래프 + 명령 + 정적 분석

### 12.7.1 핵심 아이디어

- 대화가 **이름 붙은 노드**의 집합이다. 노드에 헤더 메타데이터(제목·태그)가 붙고 본문이 이어진다. [확인됨 — 문법 수준]
- 노드 사이 이동은 명시적 점프. 선택지, 조건문, 변수 설정이 문법에 있다.
- **명령(command)** 이 호스트 게임으로 디스패치된다 — 대화가 게임에게 "카메라 흔들어" 같은 걸 시킬 수 있다.
- **각 대사 줄에 고유 line ID 가 부여되고, 실제 텍스트는 별도 문자열 테이블(string table)로 추출**된다. 로컬라이제이션과 음성 녹음이 이걸로 굴러간다. [확인됨 — 공개된 워크플로 수준]
- 컴파일러가 **정적 검사**를 한다: 존재하지 않는 노드로 점프, 선언되지 않은 변수, 타입 불일치 등. [부분확인 — 버전별 차이 있음]

### 12.7.2 데이터 구조 대응표

| Yarn Spinner 용어 | 정의 | 본 기획서 대응 | 상태 |
|---|---|---|---|
| Node | 대화 단위 | `Node` (D-07) | **채택 — 이름까지 같음** |
| Node 헤더 태그 | 메타데이터 | `Quest.tags[]`, `Node.header` | 부분 채택 |
| jump | 노드 이동 | `Node.next`, `Choice.go` | **채택** |
| option (`->`) | 선택지 | `Choice` | **채택** |
| `<<if>>` / `<<set>>` | 조건·대입 | `Condition` / `Effect` (D-05) | **채택, 단 닫힌 집합** |
| `<<declare>>` | 변수 선언 + 타입 | ⚠ **대응 없음** → **R-12-3** ↓ | **차용 대상** |
| **command `<<...>>`** | 호스트로 임의 명령 전달 | `Effect` 닫힌 집합 | **기각(열린 부분)** |
| **line ID (`#line:xxxx`)** | 대사 줄의 안정 식별자 | **stringKey** (D-03 `strings/ko.json`) | **채택 — 핵심 차용** |
| string table | ID→텍스트 분리 파일 | `strings/ko.json` | **채택** |
| 컴파일 산출물(프로그램+테이블) | 런타임 입력 | `content.bundle.json` + strings | **채택** |

### 12.7.3 Hadar2026 적용 가능성: **채택 (13개 참조원 중 우리 대화 모델과 가장 가까움)**

D-07 의 `Dialogue { nodes: {nodeId: Node} }` 는 사실상 Yarn Spinner 의 노드 모델이다. 차이는 두 가지뿐:

1. **저작 표면이 텍스트 DSL 이 아니라 JSON** — D-02. Yarn 문법을 파싱할 필요가 없다.
2. **command 가 닫힌 집합** — Yarn 은 호스트로 명령을 던질 수 있고, 그 유효성 검사는 **호스트 쪽 등록에 부분적으로 의존**한다.
   *(Yarn 이 커맨드 시그니처를 프로젝트에 선언하면 일부 정적 검사가 가능하다는 점은 확인했다. 따라서 "컴파일러가 전혀 알 수 없다" 는 초판 서술은 과했고, 정확히는 **런타임 등록에 의존하는 부분이 남는다**가 맞다.)*
   그 남는 부분이 **cm2 의 "Unknown command → 스킵"(GROUND_TRUTH §9)과 같은 실패 모드**다.
   우리는 `Effect.do` 를 스키마로 못 박아 **런타임 등록에 의존하는 여지를 0 으로** 만들고 빌드에서 하드 실패시킨다.

### 12.7.4 차용할 것 (이 절이 가장 실용적)

| # | 차용 | 근거 · 우리 구현 |
|---|---|---|
| 1 | **line ID / string table 분리** | D-03 `strings/ko.json` 의 직접적 출처. **부수 효과가 크다**: (a) 대사 diff 가 구조 diff 와 분리됨, (b) 문체 린트(BP-43)를 문자열 파일 하나만 훑어 수행 가능, (c) D-17 이 미룬 다국어의 구조만 열어둠, (d) LLM 이 텍스트만 재생성해도 그래프가 안 깨짐 |
| 2 | **`<<declare>>` 형 변수 선언** | → **R-12-3**: 팩이 사용하는 모든 `flag.*`/`var.*` 를 **선언 목록에 등재**하게 하고, 미선언 키 사용을 빌드에서 하드 실패시킨다. cm2 의 "0 반환 오분기" 를 구조적으로 막는다 |
| 3 | **컴파일러 정적 검사 목록을 그대로 베끼기** | 없는 노드로 점프 / 미선언 변수 / 도달 불가 노드 / 타입 불일치 → D-15 Hard gate 항목 |
| 4 | **노드 태그** | 문체 린트·검수 루브릭(D-14 7단계)에서 "이 노드는 상점 대사" 같은 분류에 사용 |

### 12.7.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|
| 1 | Yarn 문법 자체 | D-02. JSON 이 LLM 출력 스키마 강제와 궁합이 좋음 |
| 2 | 임의 command 디스패치 | 열린 집합 = 침묵 실패. D-05 닫힌 do 집합 |
| 3 | Unity 통합 계층 | 우리 호스트는 Flutter/Bonfire. `UiHost` 포트가 그 자리 |
| 4 | 런타임 변수 타입 추론 | 우리 변수는 `int` 와 `bool`(flag) 둘뿐 (D-08). 타입 시스템 불필요 |

## 12.8 Twine / Harlowe — 그래프 편집기 UX, 도달성의 시각화

### 12.8.1 핵심 아이디어

- **패시지(passage)** 를 카드로 놓고 링크로 잇는 **시각적 그래프 편집기**. 구조가 곧 화면이다. [확인됨 — 도구 성격 수준]
- 링크 문법(`[[…]]`)이 곧 간선이라, 링크를 쓰면 노드가 생기고 그래프가 자란다.
- **끊어진 링크(존재하지 않는 패시지로의 링크)가 편집기에서 시각적으로 표시**된다 — 화살표 끝의 X 표시. [확인됨]
- Harlowe 등 스토리 포맷이 매크로로 조건·변수를 제공한다.
- 시작 패시지가 명시되고, 거기서 도달 못 하는 섬(island)은 **그래프를 보면 눈에 띈다.** 다만 자동 도달성 분석이 도구 기본 기능인지는 [미확인 — 검증 필요].

### 12.8.2 데이터 구조 대응표

| Twine 개념 | 본 기획서 대응 |
|---|---|
| Passage | `Node` (D-07) |
| 링크 `[[text->target]]` | `Choice {text, go}` (D-07) |
| Start passage | `Dialogue.entry[]` (D-07) |
| 끊어진 링크 표시 | 빌드 Hard gate "미해결 참조 0" (D-15) |
| 고립된 패시지 | 빌드 Hard gate "도달 불가 노드 0" (D-15) |
| 스토리 포맷(Harlowe/SugarCube) | 런타임 = `dialogue_runtime.dart` (D-11) |
| 시각적 그래프 캔버스 | **콘텐츠 서버의 읽기 전용 그래프 뷰** (D-12) |

### 12.8.3 Hadar2026 적용 가능성: **부분 채택 — 시각화는 채택, 시각적 저작은 기각**

이 절의 결론은 한 문장이다: **"그래프는 보여주되, 그래프로 쓰게 하지는 않는다."**

```
Twine:       사람 ──[그래프 캔버스에서 직접 편집]──▶ 스토리
Hadar2026:   LLM/사람 ──[Content API/CLI]──▶ JSON ──[빌드]──▶ 그래프 뷰(읽기 전용)
                                                            └ 검수자가 눈으로 확인
```

- **기각 사유**: 우리의 1차 저자는 **LLM 에이전트**다. 에이전트는 캔버스를 드래그하지 않는다. 시각적 편집기를 만드는 비용이 D-14 파이프라인을 만드는 비용과 경쟁한다.
- **채택 사유**: D-14 7단계 `critic` 과 사람 검수는 **구조를 한눈에 봐야** 한다. 40개 노드짜리 대화 그래프의 JSON 을 읽어서 "이 가지가 막혔다"를 알아채는 건 비현실적이다. 맵 에디터가 이미 `preview.png` 로 같은 문제를 푼 선례가 있다(GROUND_TRUTH §11) — **같은 철학의 대화판**이다.

### 12.8.4 차용할 것

1. **읽기 전용 그래프 뷰** — 콘텐츠 서버에 `GET /api/content/dialogue/{id}/graph`(구조) + 렌더 뷰. 맵 에디터의 `preview.png` 선례를 따른다. → [BP-31](31_content_server_api.md), [BP-36](36_map_editor_extension.md).
2. **문제 노드의 시각적 강조** — 도달 불가 노드, 미해결 `go`, 종료 없는 사이클을 색으로 표시. 검증 결과(D-15)를 그래프에 오버레이.
3. **"구조가 곧 화면"** — 검수자에게 보여줄 때는 텍스트 덤프가 아니라 그래프. 검수 리포트(D-14 7단계)에 그래프 이미지를 첨부.
4. **시작점 명시 강제** — Twine 의 start passage 처럼 `Dialogue.entry[]` 는 필수 필드이고 최소 1개 이상.

### 12.8.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|

## 12.9 Papyrus vs 데이터 선언 — 스크립트 언어를 쓸 때 치르는 대가

> **이 절은 "차용" 이 아니라 "반면교사" 다.** 우리 cm2 문제와 1:1 로 겹친다.

### 12.9.1 핵심 아이디어 (그리고 그 대가)

- Bethesda 는 퀘스트·오브젝트에 **Papyrus 스크립트**를 붙인다. 컴파일되어 VM 위에서 실행된다. [부분확인]
- 스크립트는 강력하다 — 조건·루프·함수·이벤트 핸들러가 다 된다.
- **대가로 알려진 것들** [부분확인 ~ 미확인]:
  - 스크립트 인스턴스 상태가 **세이브 파일에 함께 저장**되어, 콘텐츠(모드)를 빼면 세이브에 죽은 참조가 남는다. [부분확인 — 모딩 커뮤니티에서 널리 알려짐]
  - VM 이 지연·큐잉을 가져 "이벤트가 늦게 온다" 류 타이밍 버그가 생긴다. [미확인 — 검증 필요]
  - **정적 분석이 사실상 불가능**하다. "이 퀘스트를 끝까지 진행할 수 있는가" 를 코드로 증명할 수 없다.
    [확인됨 — **Papyrus 에 한정**. 루프·재귀·함수를 갖는 범용 언어의 일반 성질이다]

> **⚠ 이 근거는 cm2 에 전이되지 않는다** (부록 E-3).
> 초판은 위 "정적 분석 불가" 를 cm2 에도 그대로 적용했으나 **오류였다.**
> cm2 는 12.9.2 표가 스스로 밝히듯 **while/for 도 함수 정의도 없다**(`packages/cm2_script/lib/src/parser.dart`, GROUND_TRUTH §9).
> 루프도 재귀도 없는 언어는 정지 문제를 갖지 않고, 상태 공간도 유한하다(`maxFlags 256` / `maxVariables 256`, §12).
> 즉 **cm2 프로그램의 도달성은 원리적으로 결정 가능하다.** Papyrus 에 대해 참인 명제를 cm2 에 옮겨 적은 것이 잘못이었다.
>
> **D-02 는 그대로 유지된다.** cm2 를 AI 생성 타깃에서 제외하는 근거는 튜링 완전성이 아니라
> GROUND_TRUTH §9 에 실측된 네 가지다 — **① 미등록 함수가 0을 반환해 조용히 오분기 · ② 맵 전환 시 전역 소실 ·
> ③ `.assign` 재실행 · ④ 스키마 부재(강제 출력이 불가능한 저작 표면)**. 아래 12.9.2~12.9.3 은 이 논거로 다시 세운 것이다.

### 12.9.2 우리 cm2 와의 대응 — 같은 병이 아니라 **다른 병**

| 문제 축 | Papyrus | 우리 cm2 (GROUND_TRUTH §9 실측) |
|---|---|---|
| 표현력 | 높음(루프·함수·이벤트) | **낮음** — while/for 없음, 함수 정의 없음, 산술은 `Add` 뿐 |
| 정적 검증 | **원리적으로 불가**(루프·재귀 보유) | **원리적으로는 가능**(루프·함수 부재, 상태 유한). 그러나 **실무적으로 무의미** — 검사기를 만들어도 침묵 실패·전역 소실·상태 3중 분열은 **언어 밖 문제**로 남는다 |
| 실패 모드 | 컴파일 에러는 잡힘 | **미등록 함수 → "Unknown function" 출력 후 0 반환 → 조용한 오분기** |
| 상태 지속 | 세이브에 저장(과잉) | **저장 안 됨** — 맵 전환 시 `loadScript` 가 엔진 전역을 전부 날림 |
| 재실행 시맨틱 | 명시적 | **`run()` 이 모든 `.assign` 을 매번 재실행** → 상단 `score.assign(0)` 이 매 루프 상태를 지움 |
| 툴 지원 | 컴파일러·디버거 있음 | 없음 |
| **저작 표면** | 텍스트 코드 | 텍스트 코드 — **스키마 강제 출력 불가, 부분 재생성 단위 없음** |
| **실측 사례** | — | **부록 A-3**: 네이티브 티어의 조건 분기가 **한 번도 동작한 적 없음**(아래 12.9.4 참조) |

**정정된 결론**: 우리 cm2 는 Papyrus 의 "검증 불가능성" 을 물려받은 것이 **아니다** — 오히려 언어가 빈약해서 원리적으로는 더 검증하기 쉽다.
문제는 다른 데 있다: **① 언어 밖에서 실패한다**(미등록 심볼이 0을 반환하고, 맵 전환이 전역을 지우고, `.assign` 이 재실행된다).
**② 저작 표면이 LLM 에 부적합하다**(JSON Schema 같은 강제 수단이 없고, 텍스트와 부작용이 한 파일에 섞이며, 부분 재생성 단위가 없다).
검사기를 아무리 잘 만들어도 이 둘은 남는다. 이것이 **D-02 가 cm2 를 AI 생성 타깃에서 제외한 정확한 이유**다.

### 12.9.3 Hadar2026 적용 가능성: **기각 (스크립트 확장 노선 자체를 기각)**

한때 그럴듯해 보이는 대안 — **"cm2 를 개선해서 AI 가 생성하게 하자"** — 를 여기서 명시적으로 죽인다.

> **논거 재구성 안내**: 초판은 이 표의 3행에서 "검사기 작성 비용 ≈ 새 스키마+검증기 작성 비용" 이라는 **근거 없는 비용 등식**을 들었다.
> 실제로는 반대쪽(D-03 팩 포맷 + D-05 DSL + D-11 런타임 + D-12 서버·CLI·MCP + D-13 하네스·솔버 + D-14 8단계 + D-15 게이트)이
> 훨씬 크다. **비용으로는 이 기각을 방어할 수 없다.** 등식을 삭제하고, 아래처럼 **"저자가 LLM 이다"** 라는 사실로 논거를 갈아끼운다.
> 비용 비교가 필요하면 [BP-50](50_roadmap.md)/[BP-51](51_task_breakdown.md) 의 실제 추정과 연결할 것.

기각의 진짜 근거는 넷이며, **전부 검사기를 만들어도 남는 문제**다.

| # | 남는 문제 | 왜 검사기로 못 없애나 |
|---|---|---|
| **(a)** | **스키마 강제 출력이 불가능하다** | LLM 에게 JSON Schema 를 주면 구조 위반을 생성 시점에 막을 수 있다. cm2 는 그런 강제 수단이 없어 **틀린 출력이 일단 만들어진 뒤** 검사기에 걸린다 — 재시도 비용이 구조적으로 높다 |
| **(b)** | **부분 재생성 단위가 없다** | D-14 는 "3단계 초안만 다시" 같은 부분 재개를 전제한다(파일 단위). cm2 스크립트는 한 파일에 맵 전체 로직이 들어 있어 **한 대사를 고치려면 파일 전체를 다시 생성**해야 한다 |
| **(c)** | **텍스트와 부작용이 한 파일에 섞인다** | 문자열 분리(R-12-4)가 불가능해 문체 린트가 코드를 훑어야 한다. `strings/ko.json` 같은 축이 서지 않는다 |
| **(d)** | **침묵 실패가 런타임까지 살아남는다** | 검사기를 붙여도 **런타임 인터프리터는 그대로** 미등록 심볼에 0을 반환한다. 검사기를 우회한 스크립트(핫로드·수기 편집)가 조용히 오분기한다 |

| cm2 개선안 | 왜 안 하는가 |
|---|---|
| 미등록 함수를 **에러**로 바꾸기 | **개선 자체는 해야 한다**(→ **R-12-5**). (d) 를 줄인다. 하지만 (a)(b)(c) 는 그대로 남는다 |
| cm2 에 루프·함수 추가 | 표현력이 늘면 **원리적 검증 가능성마저 잃는다**(12.9.1 의 Papyrus 자리로 이동). **거꾸로 간다** |
| cm2 정적 타입 검사기 작성 | (d) 를 부분적으로 줄일 뿐 (a)(b)(c) 는 못 건드린다. 그리고 **레거시 스크립트를 디버깅하는 데는 유용**하므로 기각이 아니라 **R-12-5 로 축소 채택** |
| LLM 에게 cm2 를 생성시키기 | (a)~(d) 전부에 걸린다. **기각** |

### 12.9.4 차용할 것 (반면교사로서)

1. **"스크립트는 남기되 새 콘텐츠는 데이터로"** — D-02 그대로. cm2/네이티브 Dart 는 **특수 연출 전용**으로 존속(D-10 티어 1·2).
   **⚠ 단, A-3 수정이 선행돼야 한다.** GROUND_TRUTH 부록 A-3 이 실증하듯
   `hadar2026_app/lib/application/scripting/map_script.dart:41-48` 의 `isFlagSet()` 는 `return false;` 만 하는 **미구현 스텁**이고
   `setFlag()` 는 빈 본문이다. `HDNativeScriptRunner` 에 실제 구현이 있으나 맵 스크립트는 **자기 자신의 스텁**을 호출한다.
   → **네이티브 티어의 모든 조건 분기가 항상 `false` 로 평가되어 왔다. 한 번도 동작한 적이 없다.**

   이 사실은 이 절의 논증에 두 방향으로 작용한다.
   - **"스크립트 노선의 실패" 의 가장 강한 실증**: 스크립트 티어는 검증 장치가 없어서, 조건 분기가 통째로 죽어 있어도
     **아무도 몇 년간 알아채지 못했다.** 컴파일도 통과하고 실행도 되고 로그도 안 남는다.
     같은 코드가 선언적 데이터였다면 `{"op":"flag","id":…}` 는 빌드 검증(D-15)에서 미해결 참조로 즉시 걸렸을 것이다.
     **이것이 "검증 가능한 표현을 쓴다" 는 D-02 의 가치를 비용 논쟁 없이 증명한다.**
   - **"존속" 권고의 전제 조건**: 네이티브 티어를 특수 연출용으로 남기려면 그 티어가 **실제로 동작해야** 한다.
     A-3 이 고쳐지지 않은 채 티어 1 을 유지하는 것은 죽은 코드를 유지하는 것이다.
     → [BP-28](28_migration_and_coexistence.md) 이 A-3 수정을 이관 선결 과제로 잡을 것. **R-12-14.**
2. **세이브에 스크립트 상태를 담지 않기** — WorldState 는 **선언된 이름 있는 키만** 담는다(D-08). 임의 스크립트 객체를 직렬화하지 않는다. Papyrus 의 세이브 오염 문제를 구조적으로 회피.
3. **R-12-5**: cm2 의 침묵 실패를 **최소한 시끄럽게** 만든다 — 미등록 커맨드/함수를 디버그 빌드에서 예외로. 신규 콘텐츠는 안 쓰더라도 레거시 디버깅 비용이 준다. → [BP-28](28_migration_and_coexistence.md).
4. **콘텐츠와 코드의 배포 단위 분리** — 콘텐츠 팩 버전과 세이브 호환 판정(D-08 `contentVersion`)이 이 문제의 우리 쪽 해법.

### 12.9.5 버릴 것

## 12.10 데이터 드리븐 밸런스 테이블 (라이브 서비스 운영 일반)

> 특정 회사의 내부 툴 세부는 [미확인] 이므로, **공개적으로 관찰 가능한 운영 형태**만 일반화해 서술한다.

### 12.10.1 핵심 아이디어

- 수치(스탯·비용·확률·드롭)를 **코드가 아니라 데이터 테이블**에 둔다. 밸런스 변경이 코드 변경이 아니게 된다. [확인됨 — 업계 일반 원리]
- 테이블은 **스키마가 있고 CI 가 검사**한다: 필수 컬럼, 참조 무결성(존재하는 아이템 ID 인가), 범위(음수 금지), 유일성.
- 변경은 **diff 로 리뷰**된다. "누가 언제 이 수치를 왜 바꿨는가" 가 VCS 에 남는다.
- 상속/오버라이드로 중복을 줄인다 — 기본 테이블 위에 변형을 겹친다. [부분확인]
- 운영 지표가 다시 테이블로 피드백된다. (우리에겐 해당 없음 — 싱글플레이)

### 12.10.2 데이터 구조 대응표

| 라이브 서비스 관행 | 본 기획서 대응 | 상태 |
|---|---|---|
| 밸런스 테이블 | `items/items.json`, `domain/battle/enemy_data.dart`(현행 하드코딩 **75엔트리 / 실사용 74종**) | 부분 채택 |
| 스키마 검사 | D-15 Hard gate "스키마 유효" | **채택** |
| 참조 무결성 검사 | D-15 "미해결 참조 0" | **채택** |
| 테이블 상속/오버라이드 | **팩 합성** `dependsOn` (D-03) | **채택 — 이미 확정** |
| diff 리뷰 | Git + `hadar_content diff` (D-12) | **채택** |
| 핫픽스 배포 | 해당 없음 (오프라인 빌드) | 기각 |
| A/B 테스트·텔레메트리 | 해당 없음 (싱글플레이, D-17) | 기각 |

### 12.10.3 Hadar2026 적용 가능성: **부분 채택**

- **팩 합성(D-03 `dependsOn`)이 곧 테이블 오버라이드 모델이다.** `core` 팩이 기본 아이템·NPC 를 정의하고 `gen_ep1` 이 겹쳐 쓴다. 이 절은 그 결정의 출처를 밝힌다.
- **`hadar_content stats`(D-12)** 서브커맨드의 존재 이유가 여기 있다: 보상 총량, 대사 길이 분포, 퀘스트 난이도 분포를 표로 뽑아 **Soft gate(D-15)** 판단 재료로 쓴다.
- **현행 갭**: 적 데이터가 Dart 코드에 하드코딩돼 있고(`hadar2026_app/lib/domain/battle/enemy_data.dart:33` 의 `enemyTable`),
  `assets/maps/books.json` 의 무기 데이터는 **아무 코드도 로드하지 않는다.** 즉 우리는 "데이터 드리븐" 의 반대편에 있다. → **R-12-6**.
- **수치 정정 (부록 B-1)**: 초판은 "76종" 이라고 적었으나 실제는 **75엔트리(id 0~74)** 이고,
  `hadar2026_app/lib/application/battle.dart:43-46` 의 `if (enemyTableId <= 0 …) return;` 가드 때문에
  **id 0 은 영원히 소환할 수 없다.** 콘텐츠가 참조 가능한 적은 **id 1~74, 74종**이다.
  → `defeat` 목표의 `enemyId` 참조 무결성 검사는 **1~74 범위**로 구현해야 한다. 이런 종류의 "표에는 있지만 쓸 수 없는 항목" 이
  코드 안에 숨어 있는 것 자체가 12.10 이 주장하는 "데이터로 빼야 하는" 이유다.

### 12.10.4 차용할 것

1. **팩 합성 = 오버라이드** (D-03, 확정됨).
2. **CI 가 콘텐츠 데이터를 검사** — D-15 의 "콘텐츠 변경 PR 에서 validate + sim" 은 이 관행의 직역.
3. **`stats` 리포트** — 수치의 분포를 사람이 볼 수 있게. AI 생성 콘텐츠는 **평균적으로 그럴듯하지만 분포가 이상해지기 쉽다**(모든 퀘스트 보상이 비슷비슷해지는 등). 분포 리포트가 이걸 잡는다.
4. **R-12-6**: `items/items.json` 을 실제 로드하는 경로를 만들고, `enemy_data.dart` 의 하드코딩 테이블을 **콘텐츠 팩으로 이관하는 것을 로드맵에 등재**. 1차 필수는 아니나 `defeat` 목표가 `enemyId` 를 참조하므로(D-06) **참조 무결성 검사를 하려면 적 목록이 데이터여야 한다.** → [BP-42](42_item_and_inventory.md), [BP-50](50_roadmap.md).

## 12.11 퍼즐 검증 관행 (Zachtronics / Baba Is You 계열) — 솔버로 증명하기

### 12.11.1 핵심 아이디어

- 게임 세계가 **결정론적 시뮬레이터**로 표현되면, "이 문제가 풀리는가" 를 **탐색으로 증명**할 수 있다.
- Zachtronics 류는 플레이어 해답을 **결정론적 재생(replay)으로 검증**한다 — 같은 입력이 같은 결과를 낸다는 보장이 있어야 성립. [부분확인]
- 절차적 퍼즐 생성의 표준 형태는 **generate → solve → 통과분만 채택** 루프다. 솔버가 못 푸는 문제는 버린다. [확인됨 — PCG 일반 원리]
- 솔버는 부산물로 **난이도 추정치**(최단 해의 길이, 분기 수, 탐색 노드 수)를 준다. [확인됨 — 일반 원리]
- 반례가 나오면 **최소 재현 시퀀스**로 줄여 보고한다. [확인됨 — 일반 원리]

### 12.11.2 데이터 구조 대응표

| 퍼즐 검증 개념 | 본 기획서 대응 | 상태 |
|---|---|---|
| 결정론 시뮬레이터 | `HeadlessUiHost` + `SimDriver` (D-13) | **채택** |
| 상태 공간 노드 | `WorldState` (D-08) | **채택** |
| 전이(action) | 앵커 상호작용 / 선택지 / Effect 적용 | **채택** |
| 솔버 | `QuestSolver` (D-13) | **채택 — 이 절이 직접 출처** |
| 해답 존재 증명 | D-15 Hard gate "솔버 완주 증명 성공" | **채택** |
| 난이도 추정 | 최단 해 길이 → Soft gate | **부분 채택** |
| 최소 재현 시퀀스 | D-13 산출물 | **채택** |
| 퍼징(랜덤 입력) | `SimDriver` policy `random` (시드 고정) | **채택** |

### 12.11.3 Hadar2026 적용 가능성: **채택 — D-13 의 직접 출처**

**"퀘스트는 퍼즐이다"** 라는 관점 전환이 이 절의 핵심 기여다.

```
퍼즐:    초기 상태 ──[플레이어 조작]──▶ 목표 상태.  솔버가 경로 존재를 증명.
퀘스트:  WorldState₀ ──[대화 선택·앵커 상호작용·전투]──▶ quest.completed.  솔버가 경로 존재를 증명.
```

이게 성립하려면 **D-01 의 결정론 요구**가 필수다. 런타임에 LLM 이나 비시드 난수가 끼면 상태 공간이 정의되지 않고 솔버가 무의미해진다. 즉 **D-01 은 안전 요구이자 검증 가능성의 전제**다. 두 결정이 서로를 지탱한다.

### 12.11.4 차용할 것

1. **완주 증명을 Hard gate 로** — D-15. "AI 가 쓴 퀘스트가 애초에 클리어 불가능" 은 가장 흔하고 가장 치명적인 실패다.
2. **반증도 산출물** — 완주 불가 시 **어디서 막혔는지**(도달 가능한 최대 스테이지, 미충족 목표)를 리포트. 그래야 D-14 7단계 `critic` 이 수정 지시를 낼 수 있다.
3. **상태 공간 폭발 대비** — 전 상태 완전 탐색은 불가능하다. **퀘스트 단위 국소 탐색 + 관련 플래그 집합만 추적**하는 축소가 필요. → **Q-12-4**, [BP-34](34_headless_sim_and_solver.md).
4. **난이도 부산물** — 최단 해의 상호작용 수, 필요 이동 거리, 필요 전투 수를 뽑아 Soft gate 로.
5. **골든 회귀** — 통과한 트레이스를 저장해 두고 콘텐츠 변경 시 diff (D-14 6단계 "회귀 골든 비교").

### 12.11.5 버릴 것

|---|---|---|
| 1 | 완전 상태 공간 탐색 | 조합 폭발. 국소 탐색으로 축소 |
| 2 | 최적해(최단) 요구 | 우리는 "존재" 만 증명하면 된다. 최단은 난이도 추정용 부산물 |
| 3 | 전투 시뮬레이션의 정밀 재현 | 전투는 **추상화**한다 — "이 인카운터를 이 레벨에서 이길 수 있는가" 를 근사 판정. 완전 시뮬은 비용 대비 효용 낮음 → BP-34 |

## 12.12 절차적 서사 (Dwarf Fortress / Caves of Qud)

### 12.12.1 핵심 아이디어

- **세계를 먼저 시뮬레이션하고, 서사를 거기서 파생**시킨다. 문명·인물·전쟁·유물의 역사를 생성한 다음, 그 역사를 조회해서 이름·전설·퀘스트가 나온다. [부분확인 — DF 의 world gen / legends 는 널리 알려진 특징]
- 결과적으로 **모든 고유명사가 내부 일관성**을 갖는다. "이 검은 누가 언제 만들었고 누구를 죽였다" 가 데이터로 존재한다.
- Caves of Qud 는 **손으로 쓴 서사 뼈대 + 절차적 세부**를 섞는다. 절차적 요소가 손으로 쓴 축을 대체하지 않는다. [부분확인]
- 대가: 서사가 **구조적으로는 일관되지만 극적으로는 밋밋**해지기 쉽다. 사람이 읽어서 재미있는 순간은 여전히 손으로 만들어진다. [부분확인 — 통념]

### 12.12.2 데이터 구조 대응표

| 절차적 서사 개념 | 본 기획서 대응 | 상태 |
|---|---|---|
| World generation | **`world/lore.json`, `factions.json`, `places.json`** (D-03) | **부분 채택** ↓ |
| 역사 시뮬레이션 | 대응 없음 — **손으로 쓴 세계관 바이블**로 대체 | 기각 |
| 역사 조회 → 이름 생성 | D-14 1단계 `context` 의 컨텍스트 팩 | 부분 채택 |
| Legends 모드(열람) | `hadar_content stats` / 세계관 뷰 | 참고만 |
| 손 뼈대 + 절차적 세부 | **D-03 `core` 팩(손) + `gen_ep1` 팩(생성)** | **채택** |
| 런타임 세계 시뮬레이션 | **기각** | D-01 |

### 12.12.3 Hadar2026 적용 가능성: **부분 채택 — "생성 시점" 은 같고 "생성 주체" 가 다르다**

우리와 DF 의 관계는 미묘하다. **둘 다 "콘텐츠를 자동 생성" 하지만 층위가 다르다.**

| 축 | Dwarf Fortress | Hadar2026 |
|---|---|---|
| 생성 시점 | **게임 시작 시(런타임)** | **배포 전(오프라인)** — D-01 |
| 생성 주체 | 절차적 알고리즘 | **LLM 에이전트** + 결정론적 빌드 |
| 결과의 가변성 | 플레이마다 다름 | **모든 플레이어에게 동일** |
| 텍스트 품질 | 템플릿 조합 | 자연어 생성 |
| 검수 가능성 | 불가(런타임 생성) | **가능 — 이게 우리 구조의 핵심 이점** |
| 일관성 보장 | 시뮬레이션이 보장 | **세계관 바이블 + 검증기 + 검수 에이전트**가 보장 |

**우리가 DF 에서 실제로 가져오는 것은 "세계 먼저, 서사 나중" 이라는 순서**다. D-03 이 `world/` 를 `quests/` 보다 앞에 두고, D-14 1단계가 `context`(세계관 바이블 주입)인 이유가 이것이다. 세계관 축 없이 퀘스트를 생성하면 LLM 이 매번 다른 세계를 상상한다.

**기각하는 것은 "역사 시뮬레이터를 만드는 것"** 이다. 시뮬레이터를 만드는 비용이 세계관 바이블을 손으로 쓰는 비용보다 훨씬 크고, LLM 은 이미 "바이블을 읽고 일관되게 확장" 하는 걸 잘한다.

### 12.12.4 차용할 것

1. **세계 → 서사 순서** — D-03 디렉토리 순서, D-14 1단계.
2. **손 뼈대 + 생성 세부의 층 분리** — `core` 팩은 사람이 쓰고 잠근다. `gen_*` 팩만 AI 가 만든다. **팩 경계가 곧 신뢰 경계.** → **R-12-7**.
3. **모든 고유명사가 출처를 갖게 하기** — 새 NPC/장소는 `places.json`/`factions.json` 의 기존 엔티티를 **반드시 참조**해야 한다. 참조 없는 고아 엔티티는 린트 경고. → [BP-22](22_world_bible_model.md), [BP-33](33_validation_and_lint.md).
4. **"구조적 일관성 ≠ 극적 재미"** 라는 경고 — 검증 게이트를 다 통과해도 지루할 수 있다. **D-14 7단계 `critic` 은 생략 가능한 단계가 아니다.** Hard gate 는 "안 깨졌다" 만 보증한다.

### 12.12.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|
| 1 | 런타임 세계 생성 | D-01 |
| 2 | 역사 시뮬레이션 엔진 | 비용 > 효용. 바이블 + LLM 으로 대체 |
| 3 | 플레이마다 달라지는 콘텐츠 | 검수 불가 = 우리 구조의 이점을 버리는 것 |
| 4 | 무한한 세계 규모 | 유한 캠페인. 맵 15개 규모(GROUND_TRUTH §6) |

## 12.13 LLM 기반 게임 콘텐츠 파이프라인 (일반론)

> ⚠ **[미확인 — 검증 필요]**: 이 절은 특정 제품·회사의 파이프라인을 서술하지 않는다. 확신 없는 제품명·수치를 쓰지 않기 위해 **공개적으로 반복 관찰되는 패턴만 일반 원리 수준**으로 정리한다. 구체 사례가 필요하면 별도 조사 후 BP-92 에 등재할 것.

### 12.13.1 반복 관찰되는 패턴 5가지

| 패턴 | 내용 | 우리 대응 |
|---|---|---|
| **P1. 오프라인 배치 생성** | 런타임 LLM 은 비용·지연·비결정성·검열 리스크가 크다. 배포 전에 굽는다 | **D-01** |
| **P2. 스키마 강제 출력** | 자유 텍스트가 아니라 구조화 출력을 요구한다. 스키마 위반은 재시도 | **D-02, D-14 3단계** |
| **P3. 다단계 분업** | 개요 → 초안 → 바인딩 → 검증 → 검수를 **다른 호출**로 쪼갠다. 한 번에 다 시키면 품질이 무너진다 | **D-14 8단계** |
| **P4. 결정론적 검증 게이트** | LLM 출력은 반드시 **프로그램**이 검사한다. LLM 이 LLM 을 검사하는 것만으로는 부족 | **D-15 Hard/Soft 분리** |
| **P5. 사람 최종 승인** | 통과분도 사람이 표본 검수. 특히 톤·설정 위반 | **D-14 7~8단계** |

### 12.13.2 반복 관찰되는 실패 모드 6가지

| 실패 모드 | 증상 | 우리 방어 |
|---|---|---|
| **F1. 유령 참조** | 존재하지 않는 NPC·아이템·맵을 언급 | D-15 "미해결 참조 0" (Hard) |
| **F2. 미완결 그래프** | 대화가 끝나지 않거나 도달 못 하는 노드 | D-15 "도달 불가 노드 0", "사이클 0" (Hard) |
| **F3. 논리적 클리어 불가** | 열쇠 없이 못 여는 문 뒤에 열쇠가 있음 | **D-13 QuestSolver** (Hard) |
| **F4. 톤 붕괴** | 90년대 레트로 RPG 에 현대 구어체·이모지 | BP-43 문체 린트 (Soft) + `critic` |
| **F5. 균질화** | 모든 NPC 가 비슷하게 말하고 모든 퀘스트가 "가서 가져와" | `stats` 분포 리포트 (Soft) + `critic` 루브릭 |
| **F6. 설정 드리프트** | 회차를 거듭할수록 세계관이 원본에서 이탈 | `core` 팩 잠금 + 컨텍스트 팩 재주입 (D-14 1단계) |

**F5 와 F6 은 Hard gate 로 잡을 수 없다.** 이것이 D-15 가 Soft gate 와 검수 에이전트를 별도로 둔 이유다. 그리고 **F3 은 사람 검수로도 잡기 어렵다** — 이것이 솔버가 필요한 이유다. 즉:

```
        │ 기계가 잘 잡음        │ 사람/LLM 이 잘 잡음
────────┼──────────────────────┼─────────────────────
구조 오류│ F1 F2 F3  ← Hard gate │ (비효율)
품질 저하│ F5 부분적 ← stats     │ F4 F5 F6 ← critic + 사람
```

### 12.13.3 Hadar2026 적용 가능성: **채택 (D-14 · D-15 의 골격)**

- D-14 의 8단계와 "LLM 은 2·3·7 단계에서만" 규칙은 P3 + P4 의 직접 구현이다.
- **각 단계 입출력이 파일이고 재개 가능**해야 한다는 D-14 의 요구는 실무적으로 중요하다: 6단계에서 실패하면 3단계 산출물부터 다시 굴린다. 전체 재생성은 비용·비결정성 때문에 피한다.

### 12.13.4 차용할 것

1. **재시도 예산과 실패 격리** — 스키마 위반 시 몇 번 재시도하고 몇 번째에 포기할지, 포기한 항목을 어떻게 격리(quarantine)할지. → **R-12-8**, [BP-32](32_generation_harness.md).
2. **컨텍스트 팩의 명시적 구성** — "무엇을 프롬프트에 넣는가" 를 문서화된 규칙으로. 즉흥적으로 붙이면 재현이 안 된다. → [BP-37](37_prompt_contracts.md).
3. **생성 출처 기록** — `pack.json#generatedBy` (D-03 확정). 어떤 모델·프롬프트 버전이 만들었는지가 회귀 분석의 유일한 단서다.
4. **검수 루브릭의 수치화** — `critic` 이 "좋다/나쁘다" 가 아니라 축별 점수 + 수정 지시를 내야 자동화 루프가 성립. → [BP-37](37_prompt_contracts.md).

### 12.13.5 버릴 것

| # | 버림 | 사유 |
|---|---|---|
| 1 | 런타임 LLM (동적 NPC 대화 등) | **D-01·D-17 명시적 제외** |
| 2 | LLM 검수만으로 게이트 통과 | P4. Hard gate 는 반드시 프로그램 |
| 3 | 단일 프롬프트로 퀘스트 전체 생성 | P3 위배. 품질·재개성 모두 손해 |
| 4 | 생성물을 파일에 직접 쓰게 하기 | **D-12: AI 는 API/CLI 로 쓴다.** 정규화·검증·되돌리기 강제 |

## 12.14 Ultima / Wizardry / 1990년대 국산 RPG 계보 — 톤을 지키기 위해 안 할 것들

### 12.14.1 핵심 아이디어

- **Ultima 계열의 키워드 대화** — NPC 에게 이름·직업 같은 **키워드를 물어보는** 방식. 대화가 트리가 아니라 **주제 사전**에 가깝다. [부분확인 — 시리즈/작품별 차이 있음]
- **Wizardry 계열** — 텍스트가 극도로 절제되고, 서사보다 **던전 구조와 파티 운용**이 주역. [부분확인]
- **원작 Hadar 의 관습** — 본 레포에서 실측 가능한 것들:
  - 푯말이 1급 상호작용이고 전용 헤더를 갖는다: `host.setHeader('@B푯말에 써 있기를:')`
    (`hadar2026_app/lib/application/tile_event_dispatcher.dart:116-117`) [확인됨] — **`Node.header` 의 진짜 계보** (12.2.2 각주)
  - 콘솔이 좁다: **13줄/페이지**, 진행 스크롤백 200줄 (`HDConfig.maxLinesPerPage=13`, `maxProgressLines=200`) [확인됨]
  - 인벤토리가 **food/gold 정수 2개뿐** [확인됨 — GROUND_TRUTH §10]
  - 장비가 **정수 ID 1개씩**, 이름은 `"무기$weapon"` 플레이스홀더 [확인됨]
  - 적 **74종**(테이블 75엔트리 중 id 0 은 `hadar2026_app/lib/application/battle.dart:43-46` 가드로 소환 불가)의 고정 테이블, 랜덤 인카운터 [확인됨 — 부록 B-1]
  - 상호작용 종류가 **talk / sign / enter / event** 네 가지뿐 (`HDTileAction`) [확인됨]
- 즉 원작의 톤은 **"짧은 대사, 명시적 푯말, 열쇠와 문, 상점, 그리고 대부분의 시간은 이동과 전투"** 다.

### 12.14.2 데이터 구조 대응표

### 12.14.3 Hadar2026 적용 가능성: **채택 (톤 제약으로서)**

이 절의 결론은 **"우리가 할 수 있는 것의 상한을 톤이 정한다"** 는 것이다. 앞의 12개 절이 전부 "더 할 수 있다" 를 말했다면 이 절은 **"하지 마라"** 를 말한다.

레트로 톤이 우리 설계에 주는 **선물**도 있다 — 제약이 곧 검증 가능성이다.

| 톤 제약 | 기술적 이득 |
|---|---|
| 짧은 대사 | 노드당 `lines` 가 짧아 13줄 페이지 제약을 넘지 않음. 페이지네이션 경고(D-07)가 거의 안 뜸 |
| 적은 상호작용 종류 | `Anchor.kind` 6종으로 충분. 디스패치 테이블이 작음 |
| 단순한 인벤토리 | `has_item(id, count)` 만으로 충분. 무게·내구도·소켓 없음 |
| 명시적 푯말 | 세계관 정보를 대화가 아닌 **푯말로** 전달 가능 → NPC 대화 그래프가 단순해짐 |
| 선형에 가까운 진행 | 솔버의 상태 공간이 작음 (12.11) |

### 12.14.4 차용할 것

1. **푯말을 서사 전달 채널로 적극 활용** — AI 생성 시 "세계관 설명은 푯말에, 감정은 NPC 대화에" 라는 배분 규칙. → [BP-43](43_content_style_guide.md).
2. **대사 길이 상한을 문체 규칙에 명시** — 13줄 콘솔 기준. Soft gate 로 분포 감시.
3. **화자 헤더 관습 유지** — `@B` 같은 기존 마크업 관습을 문자열 규약으로 문서화. → **Q-12-5**.
4. **"대부분의 시간은 이동과 전투"** — 퀘스트 밀도를 과하게 올리지 않는다. 맵당 앵커 수 상한을 Soft gate 로. AI 는 방치하면 모든 타일에 대화를 붙이려 한다.

#### 12.14.5.1 선택지 개수 상한 — 근거 정정

| 구분 | 값 | 근거 |
|---|---|---|
| **구조적 상한** | **6** | `hadar2026_app/lib/domain/window/selection_window_data.dart:11` `maxVisibleItems = 6`. 초과분은 스크롤 처리(`:26`, `:36`) [확인됨] |
| **톤 권고치** | **4** | "스크롤 없이, 한 번에 다 읽히게" 라는 **문체 판단**. 구조적 근거가 아니라 취향값임을 명시한다 |

- 초판은 상한 4 의 근거로 **"콘솔 폭 제약"** 을 들었으나 **틀렸다.** 콘솔은 512×320 이고 제약은 세로 13줄이며,
  둘 다 **선택지 개수와 무관**하다. 폭이 문제였다면 상한은 "선택지 문구 길이" 여야 했다.
- 실제로 코드에 존재하는 개수 상한은 **6**이다. 따라서 규범을 두 층으로 나눈다.
  - **구조 규칙**: 선택지 7개 이상 = 스크롤 발생 → 빌드 **경고**(Soft gate).
  - **톤 권고**: 4개 이하 → 문체 가이드의 권고치. 위반해도 실패시키지 않는다.
- 수치의 최종 소유는 [BP-24](24_dialogue_model.md)(대화 모델)와 [BP-43](43_content_style_guide.md)(문체)다 — D-18.

### 12.14.6 열린 질문

- **Q-12-5 (텍스트 마크업 규약)**: 기존 대사에 `@B` 같은 인라인 마크업이 존재한다. 콘텐츠 팩의 `strings/ko.json` 이 이 마크업을 그대로 담을지, 구조화 필드로 승격할지 미결. 마크업을 문자열에 담으면 문체 린트가 마크업을 오탐할 수 있다. → [BP-24](24_dialogue_model.md), [BP-43](43_content_style_guide.md).

## 12.16 결론 — Hadar2026 이 채택하는 설계 계보

### 12.16.1 한 문단 요약

Hadar2026 의 콘텐츠 아키텍처는 **"Yarn Spinner 의 대화 노드 그래프 위에 Bethesda 의 Stage/Objective 퀘스트 상태 기계를 얹고, 그 둘을 잇는 조건 표현을 RPG Maker 의 페이지 조건에서 가져와 닫힌 JSON DSL 로 굳힌 다음, Ink 가 검증한 '저작 소스 → 컴파일 → 런타임' 3분할 위에 올린 것"** 이다. 여기에 두 가지를 더 붙인다. 첫째, **Radiant 의 템플릿-슬롯 발상을 런타임에서 빌드 시점으로 끌어내려** LLM 이 슬롯을 채우게 하고(D-14 `bind`), 그 결과물을 사람이 검수할 수 있게 만든다. 둘째, **Zachtronics 류 퍼즐 검증의 "솔버로 클리어 가능성을 증명한다" 는 관행을 퀘스트에 그대로 적용**해(D-13), LLM 이 만든 퀘스트가 애초에 완주 불가능한 가장 흔한 실패를 기계가 막게 한다. 반대로 명시적으로 거부하는 계보는 **Papyrus/cm2 형 스크립트 노선**이다. 다만 그 거부의 이유는 흔히 말하는 "스크립트는 정적 검증이 안 된다" 가 아니다 — cm2 는 루프도 함수도 없어 오히려 원리적으로는 검증하기 쉬운 언어다(12.9.1 정정, 부록 E-3). 진짜 이유는 **저자가 사람이 아니라 LLM 이라는 사실**에 있다: 스키마로 출력을 강제할 수 없고, 부분 재생성 단위가 없고, 텍스트와 부작용이 한 파일에 섞이고, 침묵 실패가 런타임까지 살아남는다. 이 넷은 검사기를 아무리 잘 만들어도 남는다. 그리고 그 대가가 얼마나 조용한지는 우리 레포가 이미 증명했다 — **네이티브 스크립트 티어의 조건 분기는 미구현 스텁 위에서 항상 `false` 를 반환하며, 그 사실을 아무도 알아채지 못한 채 지금까지 왔다**(부록 A-3). 마지막으로 **Ultima/Wizardry 계열과 원작 Hadar 의 절제된 톤이 이 모든 능력의 상한을 정한다** — 우리가 표현할 수 있는 것보다 훨씬 적게 쓰는 것이 이 프로젝트의 미학이자, 검증 가능성을 지키는 예산 관리다.

### 확정한 것

1. **설계 계보의 출처가 문서로 고정됐다.** D-01~D-17 각각이 어느 선행 사례에서 왔는지 12.16.3 역참조표로 추적 가능.
2. **RPG Maker MV 모델의 취사 경계 확정** — 조건부 변형(pages) 개념은 채택, 명령 코드 인터프리터는 기각. 현재 `hadar2026_app/lib/domain/map/map_event.dart:75-88` 이 `pages[0]`·`code==401` 만 읽는다는 사실을 갭의 기술적 정체로 규명. **코드 101 을 버리는 것은 결함이 아니라 의도적으로 옳은 동작**임을 부록 E-1 로 확정.

5. **"퀘스트는 퍼즐이다"** 관점 확립 (12.11) — D-13 솔버의 이론적 근거이자, D-01 결정론 요구가 안전 요구인 동시에 **검증 가능성의 전제**임을 밝힘.

8. **R-12-1 ~ R-12-14** 요구사항 14건 도출.
9. **D-18(SSoT 소유권) 준수 선언** (12.1.1) — 이 장은 어떤 스키마도 소유하지 않고 계보만 밝힌다. 대응표의 SSoT 는 BP-92.
