## 1. 치명 결함 (반드시 고쳐야 함)

### F-30-01 §3.1 이 §3.5·R-30-2 와 정면으로 모순한다 — "쓰기 시점에 서버가 DSL op 를 잡는다"
- **위치**: `30_toolchain_overview.md:185` (§3.1 표 2행)
- **문서 주장**: "파일에 직접 쓰면 `"op":"has_flag"` 같은 존재하지 않는 op 가 디스크에 남고, 빌드 시점까지 발견되지 않는다. **API 는 415 를 즉시 돌려주고** hint 로 올바른 op 를 알려준다"
- **실제 규정**:
  - **R-30-2**(같은 문서 `:154`) — "Content Server 는 콘텐츠의 **형태(shape)** 만 본다: JSON 파싱 가능성, 필수 필드 존재, ID 정규식, 파일명-슬러그 일치, 좌표 범위. 의미 검증은 전부 CLI 에 위임한다."
  - [BP-31 R-31-20] — "op 4~8(경로 편집)은 **어떤 의미 검증도 하지 않는다.** 경로가 존재하는지·타입이 맞는지만 본다. DSL 유효성은 CLI 가 본다."
  - **같은 문서 §3.5 표**(`:257`) — "포맷은 맞지만 없는 op 사용 | `"op":"has_flag"` | **4겹 `validate`** | 에러의 `hint` 가 허용 op 목록을 준다"
- **파급**: `has_flag` 는 Condition **DSL op** 이지 배치 편집 op 가 아니다. 서버는 이것을 잡을 수 없고, 잡으면 R-30-1(평가기 Dart 한 벌)을 스스로 어긴다. 이 표 2행은 **1겹(권한) 방어가 필요한 이유의 핵심 논거**인데, 그 논거가 사실이 아니다.
- **부수 오류**: **415 Unsupported Media Type** 은 이 API 어디에도 없는 상태 코드다. [BP-31 §5.1] 은 `unknown_op` 을 **400** 으로 규정한다. 레포 전체 `grep 415` 결과 이 한 줄뿐.
- **요구 조치**: 2행을 "포맷/ID 규약 위반은 서버가 즉시 400 으로 막고, **DSL op 오류는 CLI `validate` 가 잡는다**(§3.5). 어느 쪽이든 파일 직접 쓰기보다 **발견이 빠르다**" 로 재작성. `415` → `400`. §3.5 표와 상충하지 않게 통일.

### F-30-02 R-30-15 / R-30-17 의 CI grep 이 **위반이 없을 때 실패**한다 (논리 역전)
- **위치**: `30_toolchain_overview.md` §4.5 (R-30-15, R-30-17)
- **문서 주장**:
  ```bash
  grep -rn -v -E "^\s*(//|export |$)" hadar2026_app/lib/domain/content/ && exit 1
  grep -rn "package:flutter" packages/hadar_content/lib/ && exit 1
  ```
- **실제 동작**: GitHub Actions 의 `run:` 블록은 **마지막으로 실행된 명령의 종료 코드**가 스텝 결과다. 위반이 **없으면** `grep` 이 1을 반환하고 `&&` 가 단락되어 `exit 1` 이 실행되지 않으므로, **스크립트의 종료 코드가 grep 의 1** 이 되어 **정상 상태에서 CI 가 빨개진다.** 위반이 **있으면** grep 이 0 → `exit 1` → 실패. 즉 **항상 실패**한다.
- **대조군**: 같은 레포의 기존 `ci.yml:54-65` 는 정확히 이 함정을 피하는 형태로 짜여 있다 — `hits="$(grep -rn "$@" ... || true)"` 후 `[ -n "$hits" ]` 로 판정.
- **요구 조치**: 두 grep 을 기존 `check()` 헬퍼 호출로 바꾼다. D-23 이 이미 `check "..." -E "..."` 형태를 정본으로 지정했으므로 형식도 일치한다:
  ```bash
  check "domain/content must contain only re-exports" -v -E "^[[:space:]]*(//|export |$)"
  ```
  (`\s` 는 GNU grep 확장이므로 POSIX 문자 클래스가 안전하다.)

### F-30-03 R-30-27 이 **존재하지 않는 환경변수**를 실행 가능한 명령처럼 제시한다
- **위치**: `30_toolchain_overview.md` §7.4 R-30-27
- **문서 주장**: `HADAR_EDITOR_PORT=5311 pnpm dev` + `HADAR_EDITOR_URL=http://localhost:5311`
- **실제**: `tools/mapEditor/vite.config.ts:143` 은 `server: { port: 5310 }` 로 **하드코딩**되어 있고, 파일 전체에서 읽는 환경변수는 `HADAR_ASSETS`(`:11`) 하나뿐이다. `HADAR_EDITOR_PORT` 는 레포에 존재하지 않는다. (`HADAR_EDITOR_URL` 은 `mcp/server.mjs:9` 에 실재 ✅)
- **파급**: 같은 절이 확정한 R-30-26(`strictPort: true`)과 짝이 되어야 하는데, R-30-27 은 그 전제 변경을 요구하지 않고 이미 되는 것처럼 적었다. 워크트리 2개를 여는 사람이 그대로 따라 하면 5310 을 다시 잡는다.
- **요구 조치**: R-30-26 을 "`server: { port: Number(process.env.HADAR_EDITOR_PORT ?? 5310), strictPort: true }` 로 바꾼다" 로 확장하고, R-30-27 은 그 변경에 의존함을 명시.

## 4. D-12 핵심 문제(순수 Dart CLI ↔ `domain/content/`)의 해결 여부 — **판정: 성립한다**

- **문제 정의 정확성**: §4.3 이 짚은 세 가지 — ① `flutter: sdk` 전이 의존, ② lock 의 `sdks.flutter` 제약, ③ **`dependency_overrides` 는 루트 패키지에만 적용** — 은 pub 의 실제 동작과 일치한다. ③은 `hadar2026_app/pubspec.lock` 에서 `flame: dependency: "direct overridden"` 로 확인되며, CLAUDE.md 가 금지한 flame 승격이 CLI 쪽에서 조용히 일어난다는 지적은 **타당하다**.
- **선례 정합**: `packages/cm2_script/pubspec.yaml` 은 실측 10줄, `dev_dependencies: test` 하나, `flutter` 의존 0, 앱(`hadar2026_app/pubspec.yaml:40-41`)과 CUI 데모(`cm2_script_sample`) **양쪽이 path 의존으로 소비**한다. 안 A 는 이 선례와 **구조적으로 동형**이다. ✅
- **CI 정합**: 기존 `cm2_script` 잡(`ci.yml:77-101`)이 `dart-lang/setup-dart@v1` + `dart analyze` + `dart test` 로 되어 있어 R-30-23("콘텐츠 잡은 Flutter 를 설치하지 않는다")이 **복제 가능한 실물 선례**를 갖는다. ✅
- **배럴 전략의 위험**: R-30-14 의 re-export 배럴은 BP-21~28 의 `lib/domain/content/condition.dart` 경로 인용을 살리는 영리한 수인데, **R-30-15 의 강제 grep 이 F-30-02 로 작동하지 않는다.** 배럴이 로직을 품기 시작하면 D-12 가 조용히 무너지므로 이 게이트는 반드시 고쳐야 한다.
- **BP-20 와의 명칭 차이**: [BP-20 Q-20-1] 의 후보 ①은 `packages/hadar_content_core/`, 이 장은 `packages/hadar_content/`. 소유가 BP-30 이므로 문제없으나, BP-20 §4.3 에 "BP-30 이 `packages/hadar_content/` 로 확정" 을 반영해야 한다(→ §7 전파).

- **부록 B-5(웹 45MB) 연결이 약하다**: 현행 `assets/assets/` 9.7MB 대비 소스 JSON 이 수 MB 가 아니면 이득이 작다는 B-5 의 단서를 이 장이 인용하지 않는다. 예산 `≤ +600 KB`([BP-20 §8.2])만 인용. **개선 제안 S-30-02** 참조.

## 6. 개선 제안 (선택)

### S-30-01 `--fix-format` 의 소유가 불명
§3.5·§3.6·§4.7 이 `hadar_content build --fix-format` 를 반복 호출하는데, 이 플래그의 **정의는 [BP-31 §2.7] 의 `fixFormat`** 와 CLI 양쪽에 흩어져 있다. 어느 쪽이 정본인지 한 줄로 지정할 것.

### S-30-02 부록 B-5 실측을 §5.3 검증표에 기준선으로 넣을 것
`build/web` 총 45MB, `assets/assets/` 9.7MB 라는 실측이 있으므로, "≤ +600KB" 를 절대치가 아니라 **9.7MB 대비 +6%** 로도 표기하면 판단이 쉬워진다.

### S-30-03 §6.1 워크플로에 `content_gen` 경로가 등장하지 않는다
[BP-32 §32.2.3] 이 `content_gen/` 을 레포 루트에 두기로 확정했는데 이 장 §5.1 트리에 `content_gen/` 이 없다. 툴체인 전경 트리이므로 (하네스 소유임을 명시한 채로) 한 줄 넣는 편이 지도로서 완결된다.

### S-30-04 `pnpm-workspace.yaml` 서술 근거
§7.1 이 "`allowBuilds` 는 pnpm 11 정책 대응" 이라 적었으나 실측 파일은 `allowBuilds: esbuild: true` 2줄뿐이고 pnpm 버전 정책과의 관계는 확인되지 않는다. 근거를 붙이거나 문구를 줄일 것.

- **§1.3/§1.4 의 반례 반박**이 이 기획서에서 가장 밀도 높은 설계 논증 중 하나다. "합치면 안 되나?" 5안을 전부 실측(줄 수·의존 그래프·CI 셋업 비용)으로 기각했다.

- **D-25 준수 완벽** — §0 의 "중복 금지 규약" 표가 선언에 그치지 않고 실제로 지켜져, op/do·앵커 필드·이벤트 payload 를 한 건도 전재하지 않았다.
