# 검수 보고서 — BP-50 마일스톤 로드맵 M0~M6

- **검수자**: R10 · **대상 파일**: blueprint/50_roadmap.md (540줄)
- **판정**: **조건부 합격**
- **점수**: A4 B3 C4 D3 E4 F4 G5 = **27/35** (합격선 26 통과, 전 축 3점 이상)

## 요약

이 장은 **로드맵으로서 옳은 판단을 했다.** "AI 파이프라인이 아니라 기반 복구로 시작한다" 는 결론과
그 근거인 사슬 CH-1~CH-5 는 부록 A~F 의 실측과 정확히 대응하고, 권장안 순서를 3곳 뒤집은 §1.3 의
논증은 각각 소유 장의 텍스트에 실제로 근거가 있다(BP-32 R-32-77, D-20, BP-34 §2.5 — 셋 다 직접 대조해 확인).
완료 판정을 "자기 보고는 증거로 인정하지 않는다"(R-50-7)로 못박은 것은 부록 D-2 를 정확히 겨눈 설계다.

문제는 **최신 사실 갱신을 따라잡지 못했다**는 것이다. 세 가지가 미반영이다 —
① **D-26**(솔버 판정 2축 + 발행 지점 레지스트리)이 한 글자도 없고, ② **부록 B-4 의 정정**("웹 빌드는
실빌드로 성공했다")을 무시한 채 "웹 빌드가 깨져 있다" 를 전제한 사슬·가드레일이 남아 있으며,
③ **부록 B-5·G-2·H-1~H-4** 가 §4.2 배치표에 없다. R-50-9 는 "부록 항목은 21건이며 전부 배치했다" 고
확정했지만, 부록이 실제로 열거하는 항목은 **27개**(A-1~F-4 21 + F-0 + B-5 + G-2 + H-1~H-4)다.

## 치명 결함 (반드시 고쳐야 함)

### F-01 D-26(솔버 판정 2축·발행 지점 레지스트리)이 로드맵 어디에도 없다
- 위치: 50_roadmap.md 전체 (`grep -c "D-26" 50_roadmap.md` → **0**, `"레지스트리"` → **0**, `"UNSUPPORTED"` → **0**)
- 문서 주장: §2.3 M2 완료 판정 **G2-2** — "`hadar_content solve` 가 픽스처 퀘스트의 완주 경로를 2개 이상
  증명하고, 그 witness 를 `SimDriver` 가 재생 성공".
- 실제: DECISIONS.md D-26 은 **"솔버 판정은 3값이 아니라 2축"** 으로 확정했다 —
  `PROVEN/REFUTED/UNKNOWN` × `SUPPORTED/UNSUPPORTED`. 그리고 **"`PROVEN + UNSUPPORTED` 는 하드 게이트
  통과가 아니다"** 를 못박았다. 그 판정을 가능하게 하는 것이 **빌드가 굽는 "이벤트 → 발행 지점 레지스트리"** 다.
- 왜 치명적인가: 이 로드맵은 **M2(검증)를 M3(게임 시스템)보다 앞에** 둔다. 그 순서에서는 M2 시점에
  `item_gained`/`item_lost`/`enter_place` 가 **아직 미발행**이다(D-20 말미, 로드맵 자신이 §1.3 ②에서 인용).
  즉 **M2 의 G2-2 는 정확히 D-26 이 막으려 한 상황 — `PROVEN` 인데 게임에서 안 도는 콘텐츠 — 을 통과시킨다.**
  로드맵은 §1.3 ②에서 이 위험을 말로는 지적해 놓고, 그것을 기계가 잡는 장치(레지스트리)는 배치하지 않았다.
- 요구 조치:
  1. §2.3 M2 **포함** 항목에 "이벤트 → 발행 지점 레지스트리 생성(BP-35 소유)" 과
     "솔버의 실행 가능 축 대조(BP-34 소유)" 를 추가할 것.
  2. **G2-2 를 2축으로 재서술**할 것 — "완주 경로 2개 이상 `PROVEN`" 에 더해
     "그 경로가 소비하는 이벤트가 전부 레지스트리에 등재(`SUPPORTED`)이거나, `UNSUPPORTED` 인 경우
     팩이 **미활성**으로 표시되고 릴리스 게이트에서 차단됨을 테스트가 고정" 을 넣을 것.
  3. §2.4 M3 **G3-1**(12종 미발행 0)과 레지스트리의 관계를 명시할 것 — G3-1 이 통과하는 순간
     레지스트리의 `unpublished` 가 0이 된다는 것이 M3 의 실질적 종료 명제다.
  4. §6 가드레일에 **WS-2-5** 를 신설할 것: "솔버가 `PROVEN` 을 냈는데 그 경로의 이벤트에 발행 지점이 없다".

### F-02 부록 B-4 의 정정을 무시하고 "웹 빌드 파손" 을 전제한 서술이 2곳 남아 있다
- 위치 ①: 50_roadmap.md:46 — 사슬 **CH-5** 의 "막고 있는 것" 열에 **"웹 빌드"** 가 들어 있다.
- 위치 ②: 50_roadmap.md:370 — **WS-0-4** "`flutter build web` 이 **여전히** 실패한다 /
  왜 치명적인가: **배포 경로가 죽은 채** 6개 마일스톤을 쌓게 된다".
- 실제: GROUND_TRUTH 부록 B-4 는 **명시적으로 정정되었다** —
  "초판 B-4 는 '`dart:io` 때문에 웹 빌드가 깨져 있을 것' 이라고 추정했다. **이 추정은 틀렸다.**
  `flutter build web --release` 를 실제로 실행한 결과 **성공**했다(Flutter 3.41.4, 컴파일 16.5초,
  exit code 0)." 그리고 **"'웹 빌드가 깨진다' 를 근거로 쓰지 말 것"** 이라고 지시한다.
- 근거 대조: 나 자신도 부록 B-5 가 산출물 45MB 를 실측했다는 사실로 이를 재확인했다 —
  빌드가 실패했다면 산출물 크기 표가 존재할 수 없다.
- 왜 결함인가: WS-0-4 는 **"켜져 있으면 다음 마일스톤 착수를 금지" 하는 가드레일**이다.
  존재하지 않는 파손을 전제한 가드레일은 (a) 절대 켜지지 않아 무의미하거나,
  (b) 빌드 환경 문제로 우연히 켜졌을 때 M1 착수를 잘못 막는다.
  CH-5 의 "웹 빌드" 항목은 B-3(이동 루프 추출)과 B-4 를 하나로 묶어 **이동 추출이 웹 배포를 막고 있다**는
  거짓 인상을 준다.
- 요구 조치:
  - CH-5 "막고 있는 것" 에서 **"웹 빌드" 를 삭제**하고, 대신 부록 B-4-4(신규·미확인)의 정확한 서술
    — "웹 런타임에서 `exit(0)` 메뉴를 눌렀을 때의 동작이 미확인" — 으로 대체할 것.
  - WS-0-4 를 **"`flutter build web --release` 가 회귀로 실패하게 되었다"** 로 바꾸고,
    "왜 치명적인가" 를 "현재 성공하는 경로를 우리가 깨뜨렸다는 뜻" 으로 정정할 것.
  - G0-6(웹 빌드 성공)은 그대로 두어도 된다 — 그것은 **회귀 방지 게이트**로서 유효하다.
    단 §3 능력 획득표의 M0 행 "웹 빌드가 깨졌는지 CI 가 알려준다" 는 옳으므로 유지.

### F-03 R-50-9 의 "부록 21건 전부 배치" 가 실제 부록 항목 수와 맞지 않는다 — 6건 미배치
- 위치: 50_roadmap.md:235-262(§4.2 배치표 21행), :486(R-50-9)
- 문서 주장: "부록이 열거하는 항목은 A-1~F-4 총 21건이다(F-0 은 버그가 아니라 재확인이라 제외).
  … **본 로드맵은 21건 전부를 태스크로 배치한다**", R-50-9 "부록 항목은 **21건**이며(F-0 제외) 전부 마일스톤에 배치했다".
- 실제: 21건이라는 **집계 자체는 부록 G-1 을 정확히 따랐고 옳다.** 문제는 부록에 **G-1 이 세지 않은 항목이
  6개 더 있다**는 것이다. 실측(`grep`):

  | 부록 항목 | 내용 | 50_roadmap.md 출현 |
  |---|---|---|
  | **B-5** | 웹 페이로드 45MB 실측(canvaskit 31MB + 자산 9.7MB) | **0건** |
  | **G-2** | `TOWN2` 는 맵 없이 스크립트만 등록 — 도달 불가 코드 | **0건**(§2.7 M6 에 `TOWN2` 이관 언급은 있으나 G-2 인용 없음) |
  | **H-1** | `powOfShield`/`powOfArmor` 는 죽은 필드 — 장비를 쓰려면 전투식 선행 변경 | **0건** |
  | **H-2** | `ac` 척도가 `books.json` 과 불일치(10/20 → 2/5 재척도 필요) | **0건** |
  | **H-3** | `books.json` id 공간과 `HDPlayer.weapon` 정수가 무관 | **0건** |
  | **H-4** | 맵 에디터 `registerAs` 는 이미 `json` 필드를 쓴다 — 수리 대상은 **기존 데이터뿐** | **0건** |

  (`grep -c "B-5\|H-1\|H-2\|H-3\|H-4\|D-26" 50_roadmap.md` 는 전부 0. "H-1" 이 잡히는 7줄은 전부 `CH-1`·`D-1`.)
- 왜 결함인가:
  - **H-1·H-2 는 M3 의 실행 가능성을 직접 좌우한다.** M3 는 "인벤토리·아이템(D-16-2)" 을 포함하는데,
    부록 H-1 은 "장비 성능의 근거로 `powOfWeapon`/`powOfArmor` 를 삼으려면 **전투식을 먼저 바꿔야 한다**"
    고 못박았다. 로드맵은 M3 포함 목록에 이 선행 조건을 넣지 않았다.
  - **B-5 는 §2.2 M1 의 `pubspec.yaml` 에셋 선언(부록 A-4) 판단의 유일한 실측 근거다.**
    B-5 는 "소스 JSON 을 웹 페이로드에서 빼는 선택이 실질적 이득인지 이 수치로 판단해야 한다
    (소스가 수 MB 가 아니라면 이득이 작다)" 고 명시했다. 로드맵은 판단 없이 A-4 를 M1 에 넣었다.
  - **H-4 는 T-004 계열 작업의 범위를 좁혀 준다** — 신규 맵은 이미 올바르게 등록되므로 고칠 것은 기존 15엔트리뿐.
- 요구 조치: §4.2 배치표를 **27행으로 확장**하고 R-50-9 를 "부록이 열거하는 검증 사실은 21건(G-1 집계) 이며,
  그 밖에 배치가 필요한 부록 항목 6건(B-5·G-2·H-1~H-4)을 함께 배치한다" 로 정정할 것. 권장 배치:
  B-5 → M1(A-4 와 한 묶음), G-2 → M6(TOWN2 처분), H-1·H-2·H-3 → **M3 (인벤토리 선행)**, H-4 → M0(T-004 범위 확정).

### F-04 G3-4("픽셀 동일")를 측정할 수단이 계획에 없다
- 위치: 50_roadmap.md:125 G3-4, :379 WS-3-2
- 문서 주장: "콘텐츠 팩이 없을 때 화면이 변경 전과 **픽셀 동일**"(BP-40 R-40-17).
- 실제: 픽셀 동일 판정은 **골든 위젯/스크린샷 테스트**를 요구한다. GROUND_TRUTH §12 는
  "**위젯 테스트 없음**" 을 실측했고, BP-53 §53.4.6 **N-72** 는 `lib/presentation/` 에 대해
  "**% 목표 없음 · 위젯 테스트 도입은 1차 스코프 밖**" 을 확정했다. BP-51 에도 위젯/골든 이미지
  테스트 태스크가 없다(`grep "골든 이미지\|screenshot\|widget test"` → 0건).
- 왜 결함인가: R-50-7 이 "완료 판정은 전부 기계 측정 가능한 명제" 라고 확정했는데,
  G3-4 는 **기계가 측정할 수 없는 명제**다. 결국 사람 눈으로 보고 "같아 보인다" 로 판정하게 되며,
  이는 §2 서두의 "'잘 동작한다' 는 판정이 아니다" 를 스스로 어기는 것이다.
- 요구 조치: 셋 중 하나를 택할 것 —
  (a) G3-4 를 **관측 가능한 대리 명제**로 분해(BP-53 A-3 이 이미 만든 3종:
      신규 입력 모드 0 · 신규 `UiHost` 메서드 0 · 신규 전역 키 0 + `HDTrackerBar` 높이 0px 단언),
  (b) M3 에 위젯 골든 테스트 도입을 **명시적으로 포함**시키고 BP-53 N-72 와의 충돌을 해소,
  (c) G3-4 를 **사람 판정 항목**으로 강등하고 R-50-7 의 예외로 명시.

### F-05 G6-1·G6-4 는 통과/실패를 가르지 못한다 — 판정 명제가 아니다
- 위치: 50_roadmap.md:161

  **G6-4** "`legacyFlagMap` 크기가 **M3 대비 감소**".
- 실제: G6-1 은 **어떤 값이 기록되어도 참**이다(0.1 이어도 "기록됨"). 임계값이 없다.
  BP-53 은 이 자리에 N-04(`passRate ≥ 0.7`)를 배치했으므로 임계는 존재하는데, BP-50 이 인용하지 않았다.
  G6-4 는 "M3 대비" 라 했으나 **M3 종료 시점의 `legacyFlagMap` 크기를 산출물로 기록하라는 요구가
  §2.4 M3 산출물 목록에 없다.** 비교 기준선이 존재하지 않는다.
- 요구 조치: G6-1 에 임계(BP-53 N-04·N-05 인용)를 붙이고, §2.4 M3 산출물에
  "`legacyFlagMap` 크기 스냅샷" 을 추가할 것.

### F-06 §9.2 가 BP-52 로 넘긴 "WS-* → RK-nn 편입" 이 수신되지 않았다
- 위치: 50_roadmap.md:500 — "가드레일 WS-* 를 리스크 등록부 RK-nn 으로 편입 → BP-52"
- 실제: `grep -c "WS-" blueprint/52_risks.md` = **0**. 20개 가드레일(WS-0-1 ~ WS-6-2) 중
  BP-52 에 편입된 것은 **한 건도 없다.** 역방향도 마찬가지로 BP-50 에 `RK-` 참조가 **0건**이다.

- 왜 결함인가: WS 는 "다음 마일스톤 착수 금지" 라는 **강한 집행력**을 가진 규칙인데,
  리스크 등록부에 없으면 리스크 리뷰에서 점검되지 않는다. 두 문서가 각자 자기 목록만 본다.
- 요구 조치: §9.2 의 인수인계를 **양방향 대응표**로 승격하거나(예: WS-0-3 ↔ RK-05, WS-2-1 ↔ RK-22,
  WS-5-1 ↔ RK-22, WS-6-2 ↔ RK-32), 편입이 실패했음을 열린 질문으로 기록할 것.

### F-07 "M0 가 실패하면 어떻게 되는가" 에 답이 없다 — 대안 경로 부재
- 위치: 50_roadmap.md:452-472 (§8 되돌리기 지점)
- 문서 주장: §8 은 M0 에 대해 두 행을 준다 — ① "맵 이름 수정 후 기존 플레이가 깨짐 → `MapInfos.json` 의
  `json` 필드만 되돌린다", ② "골든 diff 를 설명할 수 없음 → 커밋 전 상태".
- 실제: 둘 다 **개별 변경의 국소 되돌림**이다. 로드맵 전체는 §1.2 에서 "CH-1~CH-3 은 M0 안에서
  **반드시** 끝난다" 고 선언하고 M1~M6 전부를 M0 위에 세웠다. 따라서 **"M0 가 통째로 성립하지 않는 경우"**
  — 예컨대 결정론 교정(C-4) 후에도 G0-3 이 재현되지 않는 경우, 또는 골든 채취(T-28-0) 자체가
  현재 코드의 비결정성 때문에 안정되지 않는 경우 — 에 대한 경로가 없다.
  §6 의 WS-0-3 은 "재수색하라" 고만 말한다. 재수색이 실패하면 어떻게 되는지는 없다.
- 왜 결함인가: 이 로드맵의 유일한 진입점이 M0 이고 선행이 "없음. 지금 시작 가능" 이므로,
  M0 가 막히면 **전 계획이 멈춘다.** 단일 실패점에 대안이 없다.
- 요구 조치: §8 에 **"M0 자체가 성립하지 않을 때"** 행을 추가할 것. 최소한 다음이 답이어야 한다 —
  (a) 골든이 안정되지 않으면 **골든의 입도를 낮춘다**(전체 트레이스 → `UiHost` 메서드 이름 시퀀스만),
  (b) 결정론이 잡히지 않으면 **결정론 의존 게이트(G0-3·N-21·H-8)를 M2 로 미루고 CH-1~CH-3 만으로 M1 진입**,
  (c) 그래도 막히면 **§7.1 PA-1(`domain/content/`)만 진행**해 임계 경로를 유지 —
  이미 §7.4 T-B 트랙이 "M0 를 기다리지 않고 시작 가능" 이라고 확정했으므로 이 대피로는 이미 존재한다.
  §8 이 그것을 롤백 경로로 명시하기만 하면 된다.

### F-08 RK-28(파이프라인 비대) 완화가 로드맵 자신과 충돌한다
- 위치: 50_roadmap.md:197(§3 M2 행), BP-52 RK-28 대응, BP-53 R-53-8
- 문서 주장: RK-28 의 **대응**은 "마일스톤 종료 시 '이번 구간에 새로 플레이 가능해진 콘텐츠' 가 0이면
  **다음 구간의 도구 작업을 전면 중단**하고 콘텐츠만 만든다" 이고, BP-53 R-53-8 이 이를 규칙화했다.
- 실제: BP-50 §3 능력 획득표는 **M2 완료 직후 "여전히 불가능한 것" 에 "퀘스트 아이템을 주고받는 것,
  임무 목록을 보는 것" 을 스스로 적었다.** 즉 **M2 는 정의상 새로 플레이 가능한 콘텐츠를 0건 만든다.**
  (M2 의 유일한 콘텐츠 작업인 MAP003 이관은 G2-4 가 "shadow diff **0**" 을 요구하므로,
  플레이 경험이 **바뀌지 않는 것이 성공 조건**이다.)
  따라서 R-53-8 을 문자 그대로 집행하면 **M2 종료 시점에 M4(저작 도구) 착수가 금지된다.**
- 왜 결함인가: 1인 개발의 최대 위험(TOP-1 리스크)에 대한 유일한 완화 장치가
  **로드맵의 정상 경로에서 반드시 오발동한다.** 오발동하는 규칙은 곧 무시되는 규칙이고,
  무시되면 RK-28 은 "선언만 하고 완화하지 않은" 리스크가 된다.
  이는 사용자가 지목한 "파이프라인이 게임보다 커지는 위험이 실제로 완화되나, 아니면 선언만 하나" 에 대한
  답이 **현재로서는 '선언만 한다'** 임을 뜻한다.
- 요구 조치: 셋 중 하나 —
  (a) R-53-8 의 발동 조건을 "**도구 마일스톤이 2회 연속**(M2·M4) 콘텐츠 0건" 으로 완화,
  (b) M2·M4 를 규칙의 **명시적 예외**로 선언하고 대신 §2.9 의 정신대로 "M2 종료 시 툴체인 줄 수 대비
      `hadar2026_app/lib/` 줄 수" 를 기록하게 할 것(BP-52 TOP-1 조기 경보 ②가 이미 그 지표를 제안),
  (c) M2 에 **"플레이 가능한 산출물 1건"** 을 강제로 넣을 것 — 예컨대 M2 후반의 `core` 팩(T-138)에
      **새 대화 1개**를 포함시켜 "이번 구간에도 게임이 한 뼘 자랐다" 를 물리적으로 보장.
  (c)가 RK-28 의 취지에 가장 부합한다.
