## 1. 치명 결함

### F-32-01 8단계 `commit` 의 **롤백 단위가 정의되지 않았다** — 맵 편집과 콘텐츠 쓰기가 분리 커밋된다
- **위치**: §32.3.8 실패 행동 / R-32-23 9단계 순서 / R-32-24
- **문서 주장**: "실패 행동: 반영 전 검사에서 실패하면 **아무것도 쓰지 않고** 중단(원자성). **부분 반영 금지**"
- **그런데 R-32-23 의 순서**:
  ```
  3. map_ops.<MAP>.json 적용        ← 맵 파일 쓰기 (BP-36 API)
  4. 콘텐츠 소스 파일 쓰기          ← assets/content/**
  5. pack.json 갱신
  6. hadar_content build
  7. 결정론 검증                    ← 여기서 실패하면?
  ```
  3·4·5 는 **서로 다른 API 호출**이고, 6·7 은 이미 쓴 뒤에 돈다. **3이 성공하고 4가 실패하면 맵에는 타일이 놓였는데 앵커·콘텐츠가 없다** — 정확히 [BP-26 M-26-03]("앵커 없는 TALK 타일") 상태가 디스크에 남는다. **7(결정론 검증)이 실패해도** 되돌림 규정이 없다.
- **R-32-24 는 이 순서를 의도적으로 선택**했다("맵 편집이 실패하면 콘텐츠가 존재하지 않는 좌표를 가리킨다"). 즉 한쪽 방향의 고아만 막고 **반대 방향 고아를 허용**한 셈인데, 그 사실이 문서에 없다.
- **관련 실측**: [BP-36 R-36-49] 가 "맵 편집은 **파일 단위 원자성이 한계**" 라고 명시했고, [BP-31 R-31-22] 도 다중 rename 비원자성을 인정하며 `.bak` 되돌림 + `500 partial_commit` 을 두었다. **BP-32 만 "원자성" 을 무조건 선언**한다.
- **요구 조치**: ① "원자성" 을 **"검사 단계(1·2)까지는 무쓰기, 쓰기 단계(3~5)는 best-effort 되돌림"** 으로 정정. ② 3~5 실패 시 복구 절차를 명시(권장: 3 이전에 `git stash`/워킹트리 클린 확인 → 실패 시 `git checkout -- assets/` 안내, [BP-31 R-31-22c] 와 같은 최종 안전망). ③ 6·7 실패 시 이미 쓴 소스를 어떻게 할지(유지 + `manifest.status="blocked"` 권장) 규정.

### F-32-02 호출 예산 15회와 되돌림 예산이 **산술적으로 양립 불가**
- **위치**: §32.3.9 표 + "퀘스트 1건 총 예산 상한" + R-32-26
- **문서 주장**: "LLM 호출 수 **최대 15회**" / R-32-26 "호출 15회를 넘기면 하네스가 **강제 중단**하고 격리한다"
- **산술**: 단계별 **재시도만** 최대로 쌓으면 3(outline) + 3(draft A) + 3(draft B) + 2(repair) + 2(critic) + 2(style) = **15** — 여기까지는 일치한다. 그러나 같은 표가 **되돌림 상한**을 별도로 준다:
  - 4 bind 실패 → 3 draft, 되돌림 **2회** (각 회차마다 draft A+B 최소 2호출 = +4)
  - 5 lint 실패 → 3 Repair, 되돌림 **2회**
  - 6 sim 실패 → 2 outline, 되돌림 **1회** (outline 1 + draft A 1 + B 1 = +3)
  - 7 critic 실패 → 2 또는 3, 되돌림 **1회**
  최소 시나리오만 더해도 9(정상 3단계까지) + 4(bind 2회) + 2(repair) + 3(sim 되돌림) + 2(critic 되돌림) = **20회** 로 15를 넘는다.
- **파급**: R-32-26 이 걸리면 되돌림 예산을 **끝까지 쓸 수 없다.** 즉 §32.3.9 의 "되돌림 상한" 열은 실행되지 않는 죽은 규정이 되고, 실제 격리 사유는 항상 "예산 초과" 로 기록되어 §32.10 의 `retryRate`/`rollbackByStage` 지표가 왜곡된다.
- **요구 조치**: ① 상한을 **재시도 + 되돌림을 합산한 실제 최댓값**으로 다시 계산해 표기(대략 24~28회), 또는 ② "15회" 를 **정상 경로 상한**이 아니라 **비용 상한**으로 두되 되돌림 예산과 함께 성립하도록 조정. 어느 쪽이든 §32.3.9 표와 R-32-26 이 같은 숫자를 가리켜야 한다.

### F-32-03 컨텍스트 예산이 [BP-31] 과 **단위도 값도 다른데** "같은 코드" 라고 선언했다
- **위치**: §32.3.1 "이 단계는 [BP-31] 의 `GET /api/content/context` 와 **같은 코드**를 쓴다. … 산출물은 동일해야 한다" / §32.5.2 "총 예산: 입력 **60,000 토큰** … 컨텍스트 팩에 **57,000**"
- **[BP-31 §2.8]**: "`budget` | ⬜ | **문자 예산(기본 `40000`)**. 초과분은 요약으로 축약"
- **충돌 2건**: (a) **단위** — 토큰 vs 문자. (b) **기본값** — 57,000 vs 40,000. 한국어는 문자↔토큰 비율이 대략 1:1~1:1.5 라 40,000자 ≈ 40~60k 토큰으로 우연히 비슷할 수는 있으나, **같은 코드가 같은 산출물을 내려면 같은 단위·같은 기본값이어야 한다.**
- **파급**: §32.7.2 의 `inputs.contextPackSha256` 이 재생성 판정의 근거인데(§32.7.4), 서버와 CLI 가 다른 예산으로 자르면 **같은 입력에서 다른 해시**가 나온다 → R-32-44(바이트 동일) 위반.
- **요구 조치**: 소유 장을 정하고(컨텍스트 예산 정책은 이 장이 SSoT 라고 §0 에 선언했으므로 **BP-32 가 소유**) [BP-31 §2.8] 을 "토큰 예산, 기본 57000" 으로 맞추게 할 것. 또는 `budget` 을 `{unit, value}` 로.

## 2. 중요 결함

### F-32-04 `context_pack.md` 는 **1개인데** 에이전트마다 블록 구성이 다르다 — 해시 기록과 어긋난다
- **위치**: §32.3.1(출력 = `context_pack.md` 1개), §32.5.4(고정 렌더 템플릿 8블록), **R-32-47**(에이전트별 블록 구성표), §32.7.2(`inputs.contextPackSha256` 1개)
- **모순**: R-32-47 은 Writer 패스 B 가 `P0 P1 **P2(전량)** P5 + 키 목록` 만 받고, StyleEditor 는 `P0 P1 P2(_voice 만)` 만 받는다고 한다. 그러면 **에이전트마다 다른 `context_pack.md` 가 필요**하다. 그런데 산출물도 하나, manifest 해시도 하나다.
- 실제로 [BP-37 §37.3.3/§37.3.5] 는 `{{context_pack}}` 을 쓰지 않고 `{{tone}}`, `{{taboos}}`, `{{speaker_voice}}`, `{{knowledge_whitelist}}`, `{{length_limits}}` 같은 **블록 단위 변수**를 개별 주입한다. 즉 실제 소비 형태는 "블록 사전" 인데 이 장은 "문서 1개" 로 규정했다.
- **요구 조치**: `01_context/` 산출물을 `context_pack.json`(블록 사전) + **에이전트별 렌더** `context_pack.<role>.md` 로 확장하고, manifest 는 `contextPackSha256` 을 **역할별 맵**으로 기록. 그래야 §32.7.4 의 "재생성 — 2단계부터" 판정이 역할 단위로 정확해진다.

### F-32-05 `content_gen/prompts/` 디렉토리 규약이 [BP-37] 이 요구하는 파일을 빠뜨렸다
- **§32.2.3** 목록: `planner.v1.md  writer_struct.v1.md  writer_prose.v1.md  critic.v1.md  style_editor.v1.md  repair.v1.md` — 6개.
- **[BP-37] 이 요구하는 추가 파일**: `_preamble.v1.md`(§37.2, 모든 프롬프트가 `{{_preamble}}` 로 포함), `schemas/*.schema.json`(§37.4 "`content_gen/prompts/schemas/` 에 파일로 둔다"), 루브릭 원문(`{{rubric}}` 의 출처, `rubricVersion` 으로 별도 버전 관리).
- **파급**: **§32.7.2 의 `manifest.prompts[]` 도 역할 6종만 기록**한다. 프리앰블·루브릭·스키마 파일의 해시가 없으므로, **`_preamble.v1.md` 를 한 글자 고치면 모든 프롬프트의 실효 내용이 바뀌는데 manifest 의 어떤 해시도 변하지 않는다.** R-32-64 ②(재현 조건 전량 기록)와 [BP-37 R-37-9] 가 동시에 깨진다.
- **요구 조치**: §32.2.3 트리에 `_preamble.<ver>.md`, `schemas/`, `rubric.<ver>.md` 추가. `manifest.prompts[]` 에 `{role:"_preamble"}`, `{role:"rubric"}`, 그리고 스키마 디렉토리의 **머클 해시 1개**를 추가.

### F-32-06 §32.9 "13종을 기계가 잡는다" — 실제 표를 세면 14종
- **위치**: R-32-72
- **표 실측**: 기계(4~6단계)가 관여하는 것은 F-01~F-12, F-14, F-15 = **14종**. LLM 검수가 유일한 방어선은 F-13, F-16~F-20 = **6종**. 14 + 6 = 20 ✅ 이지만 본문은 "13종" 이라 적었다.
- 이 비율은 R-32-72 가 **설계 건강 지표**("이 비율이 뒤집히면 스키마가 느슨해졌다는 신호")로 쓰는 숫자이므로 정확해야 한다.

### F-32-07 R-32-52(혼합 배치)와 §32.5.2(예산)가 아크 단위에서 충돌한다
- R-32-52: 2단계는 **아크 단위, 최대 5건**을 한 번에 outline.
- §32.3.2 비용: outline 입력 **~40k 토큰** (퀘스트 1건 기준).
- P4(인접 콘텐츠 12k)·P6(팩 전역 6k)·P7(카탈로그 10k)은 아크 크기에 비례하지 않더라도, **`{{order_intent}}` + 5건분의 설계 여지 + 출력 ~6k×5** 는 비례한다. Q-32-6 이 이 위험을 인지했으나 **잠정 답이 없다**("파일럿 다음 단계에서 측정").
- 더 큰 문제: §32.3.9 의 재시도·비용표가 전부 **퀘스트 1건 기준**이라 아크 outline 의 예산이 표 어디에도 없다.
- **요구 조치**: 아크 outline 의 입출력 예산 행을 §32.3.9 에 추가하거나, "아크 크기 상한은 예산이 정한다(현재 미측정 → 파일럿에서 3건으로 시작)" 를 R-32-52 에 명시.

### F-32-08 §32.8.2 자동 승인 조건 ②와 R-32-57 이 충돌한다
- **§32.8.2 ②**: `newEntities` 가 **0개**여야 HG-2 자동 승인 가능.
- **R-32-57**: "예약은 **2단계 outline 승인 직후**(HG-2 통과 시점)에 일괄로 이뤄진다. outline 의 `newEntities[]` 항목마다 슬러그를 확정하고 예약한다."
- 자동 승인된 실행은 `newEntities` 가 0 이므로 예약할 것이 없다 — 논리적으로는 문제없다. 그러나 **퀘스트 자신의 ID**(`quest.<pack>.<slug>`)는 `newEntities` 에 들어가지 않는다([BP-37 `QuestOutline`] 은 `slugHint` 를 최상위 필드로 둔다). 그러면 **퀘스트 ID 는 언제 예약되는가?** §32.6.3 예시 JSON 은 `quest.gen_ep1.missing_scholar` 를 `reservations` 에 담고 있어 예약 대상임이 분명한데, R-32-57 의 문장은 `newEntities[]` 만 순회한다.
- **요구 조치**: R-32-57 을 "outline 의 `slugHint`(퀘스트 자신)와 `newEntities[].slugHint` 전량" 으로 정정. R-32-59(병렬 3 run) 의 충돌 방지가 이 한 줄에 걸려 있다.

## 6. 개선 제안 (선택)

### S-32-01 §32.11.2 P-1~P-5 선결 조건에 **P-6** 추가
[BP-26 §3.5 T1] 의 region 200~255 트리거가 성립하려면 `map_loader.dart:44` + `tile_properties.dart:187` 의 `ixEvent` 마스크 처리를 바꿔야 한다(REVIEW_BP-31 F-31-04 참조). 파일럿의 `trigger` 앵커가 여기에 걸린다.

### S-32-02 `runId` 충돌 규칙
R-32-9 는 "같은 `runId` 로 두 번 실행하면 거부" 인데, R-32-59 는 같은 팩 3 run 병렬을 허용한다. `seq3` 배정을 누가 원자적으로 하는지(예약 파일과 같은 락?) 한 줄 필요.

### S-32-03 `metrics/runs.jsonl` 의 append 원자성
병렬 3 run 이 같은 파일에 append 하므로 줄 섞임 가능. `O_APPEND` 단일 write 또는 run 별 파일 + 병합 규약.

### S-32-04 §32.3.9 표의 "3 draft A: 입력 ~45k×3" 표기
`×3` 이 재시도 배수인지 총합인지 모호. "회당 45k, 최대 3회" 로 풀어 쓸 것.

### S-32-05 HG-1 이 §32.8.1 에만 있고 §32.2.1/§32.2.2 흐름도에 없다
게이트 3곳이 핵심 확정 사항인데 전경 다이어그램에는 HG-2/HG-3 만 있다.

### S-32-06 격리 항목의 `released` ID 재사용 규칙
R-32-61 "슬러그는 영구 회피 목록에 넣는다" 와 §32.6.3 표의 "`released` — 다른 실행이 쓸 수 있나 ✓" 가 표면상 충돌한다. "ID 는 재사용 가능하되 **같은 슬러그는 금지**" 라는 뜻이면 표의 ✓ 옆에 그 단서를 붙일 것.

## 7. 잘된 점

- **§32.3 의 7항목 계약**(입력/출력/주체/성공 판정/실패 행동/재개/비용)을 8단계 전부에 균일하게 적용했다. 이 형식 하나로 축 C·D 가 동시에 채워진다.
- **R-32-64 재현의 정의** — "②를 ①로 만들려는 시도(temperature 0 강제 등)는 하지 않는다. **보장할 수 없는 것을 계약에 넣지 않는다**" 는 이 기획서 전체에서 가장 성숙한 문장 중 하나다.
- **§32.7.4 재생성 vs 재사용 판정표** — 무엇이 바뀌면 어디부터 다시 도는지를 8행으로 확정했고, R-32-67 이 사람에게 이유를 출력하게 했다.
- **R-32-40 고유명사 불변식** — StyleEditor 가 세계관을 조용히 바꾸는 사고를 막는 **유일한 자동 장치**라는 진단이 정확하고, [BP-22 R-22-12] 사전을 재사용해 SSoT 를 지켰다.
- **§32.9 실패 카탈로그 20종** — 각 실패를 "어느 단계가 잡는가" 로 매핑하고, R-32-72 로 **비율 자체를 건강 지표**로 승격한 것이 뛰어나다.
- **§32.11 파일럿** — 범위를 퀘스트 1건으로 좁히고 성공 기준 8개를 수치로 못 박았으며, **R-32-79("범위를 넓혀 성공률을 올리려는 시도는 금지")** 로 자기기만을 차단했다. R-32-78(실제 플레이는 자동화하지 않는다)도 정직하다.
- **R-32-20 이 부록 B-3 을 정면으로 받았다** — 이동·상호작용 루프가 `presentation` 에 있어 헤드리스가 불가능하다는 실측을 인정하고, 축약 시뮬로 시작 + Q-32-7 로 위험을 남겼다.
