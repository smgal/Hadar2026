## 1. 치명 결함 (반드시 고쳐야 함)

### F-01 `enemy.*` 는 BP-21 의 ID 문법을 통과할 수 없는데 스키마 필수 필드가 이를 요구한다

- 위치: 22_world_bible_model.md:811-814 (`enemies.index.json#ref`), :823-824 (R-22-25), :834 (`encounters.members[].enemy` 필수), :848 (예시), :877 (L-22-07)
- 문서 주장: R-22-25 — "`enemy.*` 는 **참조 전용 ID** 다. 콘텐츠 팩이 `enemy.*` 를 정의할 수 없다([BP-21 §4.2] 의 타입 접두사 목록에 `enemy` 가 없는 이유)."
- 실제: BP-21 §4.4 `validateEntityId`(21:393, 406-409)는
  ```
  const kEntityTypes = {'npc','quest','item','dlg','place','anchor','faction','enc','lore'};
  if (!kEntityTypes.contains(type)) return IdError(raw,'bad_type', …);
  ```
  이므로 `enemy.core.orc` 는 **`bad_type` 하드 실패**다. 그런데 `encounters.members[].enemy` 는 **필수 필드**이고 예시(`enc.core.menace_patrol`)가 `"enemy": "enemy.core.dwarf"` 를 담고 있으며, L-22-07 은 그 값의 존재 검사를 hard gate 로 지정했다.
- 즉 이 장이 정의한 인카운터 스키마는 **작성하는 순간 반드시 ID 검증에 걸린다.** R-22-25 는 문제를 인지했으면서 해결책을 제시하지 않았다.
- 요구 조치: 셋 중 하나.
  1. BP-21 §4.2 에 "참조 전용 타입: `enemy`(정의 금지, 빌드 생성 인덱스에만 존재)" 행 추가를 BP-21 에 요청하고 여기서는 링크만 둔다.
  2. `enemy.*` 를 ID 가 아닌 별도 어휘(예: `enemyRef: "orc"`)로 바꾼다.
  3. `enemy.core.orc` 대신 `enc` 하위의 로컬 ID 로 표현한다.

### F-02 부록 B-1 미반영 — 소환 불가능한 적 `id 0` 을 인덱스와 근거표에 넣었다

- 위치: 22_world_bible_model.md:376-377 (§4.6 danger 매핑 근거), :772 (§7.1), :811 (§7.3 인덱스 예시)
- 문서 주장: "id 0 `Orc` lv1 → id 74 `Neo-Necromancer` lv30", 인덱스 예시 첫 행 `{ "ref": "enemy.core.orc", "intId": 0, … }`
- 실제(`battle.dart:43-46`):
  ```dart
  void registerEnemy(int enemyTableId) {
    if (enemyTableId <= 0 || enemyTableId >= enemyTable.length) return;
    enemies.add(HDEnemy(enemyTable[enemyTableId]));
  }
  ```
  `<= 0` 가드 때문에 **`intId: 0`(Orc)은 cm2·콘텐츠 어느 경로로도 소환할 수 없다.** 실제 사용 가능한 적은 id 1~74, 74종이다.
- GROUND_TRUTH **부록 B-1 이 명시적으로 "BP-21/22/23/42 는 74종(id 1~74) 기준으로 쓸 것"** 을 지시했는데 이 장은 75종 기준을 유지했다. Q-22-5 는 "76 vs 75" 만 다루고 "소환 가능 74" 는 다루지 않는다.
- 파급: `enc.core.*` 가 `enemy.core.orc` 를 참조하면 L-22-07(존재 검사)은 통과하지만 **런타임에 적이 0마리인 전투**가 열린다. 이것이 정확히 이 장이 §5.6 에서 없애려 한 "cm2 침묵 실패" 패턴이다.
- 요구 조치:
  1. §7.1 표에 "실사용 가능 74종(id 1~74) — `battle.dart:44` 의 `<= 0` 가드" 행 추가.
  2. §7.3 인덱스 예시의 첫 행을 id 1 로 교체하거나 `"summonable": false` 를 붙일 것.
  3. `enc.members[].enemy` 가 `intId == 0` 을 가리키면 **하드 실패**하는 규칙(L-22-31)을 §8.1 에 추가.

### F-05 R-22-20 이 BP-21 의 하드 규칙에 대한 예외를 스스로 선언한다 (SSoT 침범)

- 위치: :644-646
- 문서: "`effects` 에는 `warp`/`start_battle`/`play_dialogue` 를 넣을 수 없다(아이템 사용은 메뉴 컨텍스트에서 일어나며 **꼬리 호출 규칙 R-21-40 을 만족시킬 수 없음**). 단 `item.core.teleport_ball` 같은 원작 이동 아이템은 **예외로 `warp` 만** 허용하고 배열 끝에 둔다."
- 문제:
  1. BP-21 §0 은 "§6 Condition/Effect DSL 이 이 장의 SSoT 이며 다른 장은 참조만 한다" 고 선언했다. 예외를 만드는 것은 참조가 아니라 재정의다.
  2. BP-21 §6.7 은 **아이템 사용 컨텍스트를 전혀 다루지 않는다.** 즉 이 예외를 받아 줄 자리가 SSoT 에 없다.
  3. `item.core.teleport_ball`(:749)의 `warp(...)` 는 목적지 인자가 비어 있다 — 원작 이동 구슬은 목적지를 플레이어가 고르므로 `warp(map,x,y)` 로 표현할 수 없다. 실제로는 목적지 선택 UI 가 필요하고, 이는 `warp` 의 시그니처를 벗어난다.
- 요구 조치: BP-21 §6.7 에 "아이템 사용 컨텍스트" 절을 추가하도록 요청하고(본 검수의 REVIEW_BP-21 P-04), 이 장은 링크만 남길 것. 이동 구슬은 별도 열린 질문으로 승격.

### F-06 `_aliases` 가 하드 게이트의 유일한 근거인데 어느 필드표에도 없다

- 위치: :518-519 (R-22-12), :596 (액터 예시), :885 (L-22-10 hard), :896 (L-22-16), :902 (L-22-22)
- `_aliases: string[]` 는 R-22-12 의 산문과 액터 예시(:596)에만 등장하고, §3.1(faction) / §4.2(place) / §5.1(actor) / §6.1(item) **어떤 필드 표에도 선언되어 있지 않다.**
- 그런데 L-22-10 은 **hard** 이고 그 검사 방법이 "별칭 사전 문자열 매칭" 이다. 사전의 원천 필드가 스키마에 없으면 구현할 수 없다.
- 요구 조치: `_aliases` 를 4개 엔티티 필드표에 공통 선택 필드로 추가하고, `_` 접두 필드가 빌드에서 제거된다는 BP-21 §8 규약과의 관계(린트는 소스를 보므로 문제없음)를 한 줄로 명시할 것.

### F-07 지식 범위 hard gate 2종의 검사 대상 범위가 정의되지 않았다

- 위치: :885 (L-22-10 hard), :889 (L-22-14 hard)
- 두 규칙 모두 "액터의 **대사**에 …가 등장하면" 을 조건으로 쓰지만, "액터의 대사" 의 정의가 없다. 후보가 최소 4가지다.

### F-08 R-22-15(L-22-06)의 정적 계산 알고리즘이 없는데 hard 이다

- 위치: :563-564 (R-22-15), :876 (L-22-06)
- "`set_npc_state` 를 담은 Effect 의 **도달 가능한 선행 상태를 정적으로 계산**해 검사" — 이 계산은 (a) 모든 대화 그래프, (b) 모든 퀘스트 스테이지 DAG, (c) 앵커 `when` 조건, (d) `play_dialogue` 체인을 가로지르는 도달성 분석을 요구한다. 조건식에 `chance`/`var_cmp` 가 섞이면 정확한 판정이 불가능하고, 근사하면 오탐이 난다.
- 요구 조치: (a) 알고리즘을 BP-33 에 명시 위임하고 심각도를 warn 으로 낮추거나, (b) "보수적 근사: 어떤 경로로도 선행 상태에 도달할 수 없음이 **증명**될 때만 실패" 로 판정 기준을 명문화할 것.

### F-09 `legacy.intId` ↔ `booksJsonId` 대응이 코드 근거 없이 제시되었다

- 예시는 `item.core.short_sword` 에 `{"kind":"weapon","intId":1,"booksJsonId":3}` 을 부여한다. 즉 "`HDPlayer.weapon == 1` 은 단검" 이라는 주장이다.
- 실제: `player.dart:44,91` 은 `int weapon = 0` 과 `getWeaponName() => weapon == 0 ? "맨손" : "무기$weapon"` 뿐이다. **`weapon` 정수에 의미를 부여하는 코드는 레포 어디에도 없다.** `books.json` 은 앱이 읽지 않으므로(R-22-22 가 스스로 확인) 두 정수 체계를 잇는 근거가 존재하지 않는다.

- 요구 조치: `legacy.intId` 를 "**신규로 정하는** 값이며 기존 세이브의 `HDPlayer.weapon` 값에는 의미가 없었다" 로 명시하거나, v1 세이브의 `weapon` 값을 전부 `null` + 경고로 처리한다고 확정할 것. `books.json` 의 1-based/0-based 차이도 한 줄 남길 것.

## 3. 개선 제안 (선택)

### S-01 `taboo.*` / `lore.*` 접두사가 BP-21 §4.2 타입표와 어긋난다
- `taboo.core.no_modern_tech`(:212)의 `taboo` 는 BP-21 의 9개 엔티티 타입에 없다. §2.5 는 `id | string | 금기 식별자` 로 자유 문자열이라 선언했으나, 형태가 엔티티 ID 와 똑같아 검증기가 오탐할 여지가 있다.
- `lore.*` 는 BP-21 §4.2 에서 "연대기 사건" 인데, 이 장은 `lore.core.conflict_necromancer`(갈등축)·`lore.core.mystery_why_suppress`(떡밥)에도 재사용한다. 같은 파일(`world/lore.json`) 소유이므로 큰 문제는 아니나, "`lore` = 연대기 사건" 이라는 BP-21 문구와 맞지 않는다.
- 제안: BP-21 §4.2 에 `lore` 의 의미를 "`world/lore.json` 이 소유하는 세계 축·연대기·갈등·떡밥" 으로 넓히도록 요청하고, `taboo` 는 `id` 형식을 `^[a-z][a-z0-9_]{2,47}$` 로 못박아 ID 처럼 보이지 않게 할 것.

### S-02 `equip.slot` 이 원작의 HEAD/LEG 를 버린다
`ObjTypes.cs:32-46` 의 `ITEM_TYPE` 은 `ARMOR, HEAD, LEG` 3종 방어구 슬롯을 갖고, `ObjItem.cs:574-582` 에 "가죽캡/가죽 투구/가죽 신발" 이 실재한다. `HDPlayer` 가 `armor` 정수 1개뿐이라 v1 축소는 타당하나, §6.2 표에 "원작 HEAD/LEG 는 v1 미지원" 한 줄이 없으면 이식 시 누락으로 오인된다.

### S-03 `danger` ↔ 인카운터 레벨 매핑의 근거를 수치로 고정하라
§4.6 의 "권장 파티 레벨 18+" 는 실제 도달 가능 최대 레벨과 대조가 필요하다. `player.dart:167` 의 `expTable` 은 엔트리 21개이고 승급 루프가 `level.physical < expTable.length - 1` 이므로 **최대 레벨은 20**이다(BP-21 C12 도 같은 지점에서 21 로 잘못 적었다). §4.6 의 5행 "18+" 은 사실상 18~20 의 3레벨 폭이므로 그렇게 적는 편이 정확하다.

### S-04 L-22-12/16/20/22 의 사전·패턴 원천을 지정하라
"감성 어휘 사전", "종결어미 패턴", "정규식 + 사전" 이 어디에 사는지가 없다. warn 등급이라 게이트를 막지는 않으나, BP-43(문체 가이드)에 파일 위치를 지정해 두면 BP-33 이 받기 쉽다. Q-22-7 의 역방향 검사(미등록 로마자 토큰 경고)는 좋은 보완책이므로 v1 필수로 승격을 권한다.

### S-05 `mood` 태그의 "닫힌 집합" 과 R-22-8 이 서로 다른 말을 한다
§4.4 제목은 "닫힌 집합" 인데 R-22-8 은 "새 태그는 `schemaVersion` 승격 없이 추가 가능하지만 린트가 경고" 라고 한다. 열린 집합 + 경고이므로 제목을 "권장 집합" 으로 바꾸는 편이 정확하다.

## 4. 잘된 점

- **부록 D 를 정면으로 반영한 유일한 문서다.** §4.7 의 G-22-1 표(:406-418)는 `TOWN1/GROUND1/DEN1/DEN2/Prolog` 가 `Map004.json` 등으로 잘못 해석되어 로드되지 않음을 실측으로 확정하고, R-22-11("실제 파일로 해석되는지 검사")과 T-22-1(`MapInfos.json` 에 `json` 필드 추가)까지 조치를 제시했다. BP-21 은 같은 지점을 놓쳤고 BP-26 은 A-26-03 한 줄만 참조했으므로, 이 장이 사실상 이 문제의 원천 문서가 되었다.
- **`knowledge` 는 이 기획에서 가장 독창적인 장치다.** "LLM 은 그럴듯한 대사를 쓴다 → 사람은 어색함을 알지만 프로그램은 못 잡는다 → 그래서 액터마다 아는 것/모르는 것을 선언한다"(:465-469)는 문제 정의가 명확하고, `knows` 를 **프롬프트 화이트리스트로도 쓴다**(R-22-13)는 이중 사용이 "생성 → 검증" 루프를 실제로 닫는다. 예방(화이트리스트)과 탐지(린트)를 나눈 2단 방어는 D-14 파이프라인과 잘 맞는다.
- **`states[]` 선언 강제(§5.6)** 는 cm2 의 "미등록 함수 → 0 반환 → 조용한 오분기"(GROUND_TRUTH §9)를 정확히 겨냥한 대응이다. `terminal`/`from` 까지 둔 것은 상태 기계로서 완결적이다.
- **적 카탈로그 3안 비교와 권고(A안)의 논증이 강하다.** 특히 근거 4 — "C안의 이중 관리는 정확히 GROUND_TRUTH §8 의 '3중 분열' 을 다시 만드는 패턴" — 은 현황 감사를 설계 판단에 연결한 좋은 사례다. "밸런스는 콘텐츠가 아니라 시스템이다. 이 던전에 어떤 적이 나오는가는 콘텐츠다" 라는 경계 설정도 명료하다.
- **슬러그 유도 규칙이 실제로 동작한다.** 75종 전량에 `소문자화 → 비영숫자를 _ 로 → 연속 _ 축약` 을 직접 적용해 본 결과 **충돌 0건, BP-21 §4.3 위반 0건**이었다. R-22-24 의 폴백(`enemy_slug_overrides.dart`)까지 준비해 둔 것은 과하지 않고 적절하다.
- **레거시 자산 실측이 철저하다.** `books.json` 1506바이트·8행 값·탭 들여쓰기·참조 0건, `ObjItem.cs` 5개 수치의 원작 대비 충돌을 전부 짚고 Q-22-2 로 열어 두었다. "맵 디렉토리에 아이템 데이터가 있는 것 자체가 오분류"(R-22-22)라는 지적도 타당하다.
- **일관성 규칙 30개에 번호·심각도·검사 방법 3열을 모두 부여**했다. hard 13 / warn 17 의 배분이 명시되어 BP-33 이 그대로 받을 수 있다. E축 4점의 근거다.
- 미확정 표현(`적절히`/`추후`/`TBD`) **0건**. Q-22-1~7 로 불확실성을 전부 열린 질문으로 격리했다.
