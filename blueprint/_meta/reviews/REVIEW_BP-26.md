### F-01 T1(region 200~255 예약)의 "기존 동작 무영향" 주장이 **실제 데이터로 반증**된다

- 위치: `26_entity_registry_and_anchors.md:371-388`(근거 2 · 로더 수정안), `:818`(§9.1 확정 항목 8 — "기존 동작 무영향임을 **마스크 계산으로 증명**")
- 문서 주장:
  - 근거 2 — "region 값 단독으로는 현재 어떤 판정도 일으키지 않는다(0~255 는 `0x00FF0000` 마스크에 걸리지 않음). **따라서 200~255 를 예약해도 기존 동작에 영향이 없다.**"
  - 수정안 — `map.data[index].ixEvent = (region >= 200) ? (0x00010000 | region) : region;`
- **마스크 계산 자체는 옳다**: `region ≤ 255 < 0x10000` 이므로 `region & 0x00FF0000 == 0`. §1.3 의 진단은 정확하다.
- **그러나 결론이 틀렸다.** 무영향 주장이 성립하려면 "예약 구간에 값이 들어 있는 기존 맵이 없다" 가 참이어야 하는데,
  실측 결과 **`assets/maps/Map001.json` 의 (2,3) 칸 region 값이 이미 255** 다:

  | 맵 | region 비영값 | 최대 | ≥200 |
  |---|---|---|---|
  | `Map001.json` (MapInfos `Test`, id 1) | 14 | **255** | **1칸** |
  | `Map010.json` | 39 | 100 | 0 |
  | `Map011.json` | 47 | 12 | 0 |
  | `Map002.json` | 2 | 2 | 0 |
  | 그 외 9개 맵 | 0 | 0 | 0 |

- 그 칸의 실제 데이터: `(2,3)` → `ixTile 1536-0x600=0`, **`ixObj1 = 112`**, `region = 255`.
  현행 판정은 `_getObjectAction(112)` → **`sign`**(통행 불가) 이다.
  T1 수정안을 적용하면 `ixEvent = 0x00010000|255` → 1티어가 먼저 걸려 **`event` 로 바뀐다.**
- **두 가지가 동시에 깨진다**:
  1. **푯말이 사라진다** — `sign` → `event` 로 액션이 바뀌어 `isInteractive` 가 false 가 되고, 마주보고 확인해도 아무 일도 없다.
  2. **벽이 통과 가능해진다** — `HDTileProperties.isUnitPassable`(`tile_properties.dart:101-116`)은
     `none || isInteractive` 만 막는다. `event` 는 둘 다 아니므로 **`return true`**. 즉 통행 불가 칸이 통행 가능해진다.
- 요구 조치:
  - §9.1 항목 8 의 "기존 동작 무영향임을 마스크 계산으로 증명" 문장을 **철회**하고, "현행 region 값이 판정을 일으키지 않음" 까지만 주장할 것.
  - 예약 구간 도입 전 **전 맵 region 스캔이 선행 조건**임을 R-26-9 에 명시(현재 위반 1건: `Map001.json` (2,3)).
  - 마이그레이션 절차에 "예약 구간과 충돌하는 기존 region 값을 0 으로 정리" 태스크를 추가하거나,
    Q-26-1 의 잠정을 "단일 값 예약(예: 250)" 으로 바꿔 충돌 면적을 줄일 것.

### F-02 `WorldEventBus.emit("talk_to", …)` — D-20 이 폐기한 이름

- 위치: `26_entity_registry_and_anchors.md:670`(§7.1 시퀀스 다이어그램 10번), `:672`("`talk_to` 목표 진행")
- 문서 주장: 앵커 상호작용이 끝나면 `WorldEventBus.emit("talk_to", actorId)` 를 발행한다.
- 실제: **D-20 이 12종 이름을 정본으로 고정**했고, 대화 상호작용 이벤트의 이름은 **`talk`** 다
  (소유 장 `23_quest_model.md:1163` — `| 1 | \`talk\` | {actorId, dialogueId?, map, x, y} | Content tier 의 actor 앵커 상호작용 |`).
  D-20 은 "`talked_to` 같은 **변형 이름은 전량 폐기**", "동사 과거형 금지" 를 명시한다.
- `talk_to` 는 **Objective.kind** 의 이름이지 이벤트 이름이 아니다(BP-23 §23.4.2). 두 이름 공간이 섞였다.
  §9.2 의 "BP-23 으로 넘긴 것" 행(`:830`)도 같은 혼동을 반복한다("`talk_to`/`reach` 목표가 …").
  (§9.2 쪽은 **목표 종류**를 말하는 것이므로 정확하다 — 문제는 §7.1 의 `emit()` 인자뿐이다.)
- 요구 조치: `:670` 의 인자를 `"talk"` 로 정정하고, payload 도 `{actorId, dialogueId?, map, x, y}`(BP-23 소유)를 **링크만** 할 것.

### F-07 R-26-12 의 인덱스 키 상한 65536 은 **웹 런타임에서 성립하지 않는다**

- 위치: `:438`(`static int key(int x, int y) => (x << 16) | (y & 0xFFFF);`), `:446`(R-26-12 "65536 초과 맵은 빌드 하드 실패")
- Dart 웹(dart2js/dart2wasm JS 상호운용)에서 `int` 는 배정도 실수이고 **비트 연산은 32비트로 절단**된다.
  `x = 32768` 이면 `x << 16 = 2^31` 이 되어 부호 있는 32비트에서 **음수로 접힌다** → 키 충돌·오조회.
- 안전 상한은 **32768**(즉 `x ≤ 32767`)이다. 65536 은 네이티브에서만 안전하다.
- 이 문서는 웹 배포를 전제로 하는 프로젝트(D-01·BP-35 §3.3)의 **런타임 자료구조**를 정의하므로 상한을 고쳐야 한다.
- BP-33 `V-MAP-021`(`33_validation_and_lint.md:301`)이 "65536 미만" 을 그대로 받아 적었으므로 **함께 정정**이 필요하다.
- 요구 조치: 상한을 32768 로 낮추거나, 키를 `x * 65536 + y`(곱셈 — 웹에서 53비트까지 안전)로 바꿀 것.
  후자가 낫다. §4.2 의 표는 이미 "런타임이 `x * 65536 + y` int 키 `Map` 으로 재해싱"(`:426`)이라 적고 있어
  **표와 코드가 이미 서로 다르다**(표는 곱셈, 코드는 시프트).

### S-01 §3.3 `container` 의 요구 액션이 `talk|sign` 인데 §6.5 자동 배치 대표 타일이 없다
`:623`(R-26-31)은 `actor→B 132, sign→B 116, portal→B 125` 만 정한다. `container`/`battle` 의 대표 타일이 없어
`autoPlaceTile:true` 가 그 두 kind 에서 어떻게 동작하는지 미확정이다. 표를 6종 전량으로 채울 것.

### S-02 A-26-08 의 심각도가 `hard/warn` 로 두 값이다
`:350` 이 한 칸에 `hard/warn` 을 넣었다. BP-33 은 이것을 `V-MAP-009`(ERROR) 하나로 흡수했으므로(`33:289`),
BP-26 쪽을 "맵 불일치=warn, 액터 `place` 불일치=hard" 로 **두 규칙 ID 로 분리**하는 편이 흡수 오류를 막는다.

### S-03 §1.3 의 "로더가 region 값을 파괴한다" 를 G-26-1 과 분리
`:89`의 "이벤트 칸의 원래 region 정보는 복구 불가" 는 F-01 의 전제이기도 하다.
T1 을 채택하면 **레거시 이벤트가 있는 칸에서는 승격이 덮어써진다**(R-26-10 이 이미 명시). 이 상호작용을
§3.5 표에 한 행으로 못 박아 두면 구현자가 순서를 뒤집는 사고를 막을 수 있다.

### S-04 `facing` 의 렌더링 미사용(R-26-7)과 A-26-06 경고의 관계
`facing` 이 렌더링에 안 쓰인다면(`:240`) A-26-06("벽을 보고 서 있음" 경고)은 **관측 불가능한 성질**에 대한 경고다.
생성 컨텍스트 품질용이라면 심각도를 INFO 로 낮추는 편이 WARN 밀도(BP-33 R-33-10)를 아낀다.

## 잘된 점

- **판정 테이블의 실측 정확도가 최상급이다.** `_getObjectAction` 9행 · `_getTileAction` 8행 전량이 코드와
  경계값까지 일치했다. 이 문서를 보고 검증기를 짜면 코드를 다시 읽을 필요가 없다.
- **§1.2 사례 A(고아 대사 파일)는 이 기획서 전체에서 가장 설득력 있는 근거다.** `lore_ep1.cm2` 의 TALK 좌표 8곳을
  `TOWN1.json` 의 objUpper 값과 대조해 "이 파일은 TOWN1 의 것인데 startup 은 Map002 를 띄운다" 를 증명했고,
  검수 과정에서 **8/8 전부 재현되었다**. 앵커 도입의 필요성을 추상론이 아니라 실측으로 세웠다.
- **§3.5 가 자기 설계의 구조적 모순을 스스로 드러냈다.** "`event` 액션을 만드는 경로는 1티어뿐 → R-26-1 과 정면 충돌"
  을 감추지 않고 해결안 3개를 비교했다. 이런 정직성이 검수를 가능하게 한다(F-01 은 그 해결안의 근거 하나가 틀렸다는 것이지,
  문제 인식은 옳다).
- **R-26-17**(같은 좌표+kind 에 무조건 앵커 2개 → 하드 실패)이 §1.1 의 문제 2(좌표당 1개만 유효)를
  구조적으로 재발 방지한다. 결함 진단이 그대로 규칙이 된 좋은 예다.
- **§8.4 의 한계 L1~L8** 이 자동 변환의 실패 모드를 8개나 열거하고 각각에 대응을 붙였다. 행복 경로만 쓰지 않았다.
- D-18 준수가 철저하다 — Condition/Effect op·do 를 한 번도 재서술하지 않고 BP-21 링크만 쓴다.
