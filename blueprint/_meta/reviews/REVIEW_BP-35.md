  > `dart:io` import 자체는 웹 빌드를 막지 않는다. … **→ 조치: … 단 "웹 빌드가 깨진다" 를 근거로 쓰지 말 것.**
- 문서의 다섯 문장:

  | # | 위치 | 문장 |
  |---|---|---|
  | 1 | `:604` | "세 가지 문제가 겹친다: (1) 계층 위반, **(2) `dart:io` 는 웹에서 컴파일되지 않으므로 웹 빌드 파손 가능성** …" |

  | 3 | `:844` | "`dart:io` 처럼 **웹에서만 깨지는 import 가 들어가도 감지되지 않는다.**" — **`web_smoke` 잡 존재 이유의 전부** |
  | 4 | `:869` | (YAML 주석) "**`dart:io` 같은 웹 비호환 import 는 여기서 처음으로 잡힌다** (부록 B-4)." |

- **왜 치명적인가**
  1. **사실이 아니다.** 실빌드가 성공했다. `dart:io` import 는 dart2js 에서 조건부 스텁으로 해소된다.
  2. **한 잡 전체의 정당화가 무너진다.** `web_smoke`(§4.6)의 제시된 존재 이유가 3·4번 문장뿐이다.
     정정 후에는 "`dart:io` 를 잡기 위해" 가 아니라 **부록 B-4 항목 4(신규·미확인)** — "빌드는 되지만
     웹 런타임에서 `exit(0)` 가 호출될 때의 동작은 확인되지 않았다" — 가 근거가 되어야 한다.
     그런데 `web_smoke` 는 **컴파일만** 하므로 그 항목을 보증하지 못한다. 근거를 고치면 **잡의 설계도 바뀐다.**
  3. **부채 정리 순서가 틀어진다.** §8.3 의 `⑦ web_smoke 잡 추가 (①에 의존)` 은 거짓 전제다.
     ①(`menu_flows` 탈-`dart:io`) 없이도 웹 빌드는 성공하므로 ⑦ 은 ① 과 **독립**이며 지금 바로 넣을 수 있다.
  4. **`R-35-49` 의 결론("오늘 닫힌다")이 존재하지 않는 위험을 닫는다고 주장**한다.
- 요구 조치:
  - 다섯 곳 전부에서 "웹 빌드 파손 / 웹에서 컴파일되지 않는다" 를 삭제.
  - §4.3 의 "세 가지 문제" 를 **두 가지**(계층 위반 · `exit(0)` 의 헤드리스 하네스 파괴)로 줄이고,
    부록 B-4 정정 사실을 각주로 남길 것(다른 장이 같은 실수를 반복하지 않도록).
  - §4.6 `web_smoke` 의 근거를 **부록 B-5(웹 페이로드 45MB 실측) + 부록 A-4(에셋 비재귀 선언)**

### F-04 §1.4 번들의 액터 `states` 직렬화가 BP-22 스키마와 어긋난다 — **BP-90 I-19 미해소**

  **객체 배열** `[{id, _desc, terminal, from}]`.
- 이미 접수된 문제: `90_appendix_schemas.md:2414` **I-19** —
  > "액터 `states` 가 소스는 **객체 배열**(`{id,_desc,terminal,from}`)인데 번들 예시는 **문자열 배열**이고

  > 런타임이 할 수 있는지 불명 · **담당: BP-35(번들 정규화)**"
- 이 장은 §1.2 ② `normalize` 에서 "생략된 기본값 채움 / `_` 접두 필드 제거" 만 규정하고,
  **객체 배열 → 문자열 배열 축약을 규정하지 않았다.** 즉 예시가 규칙 없이 형태를 바꿨다.
- 파급: `E13 set_npc_state` 의 `from` 전이 검사(BP-22 가 정의한 상태 기계)를 런타임이 할 수 없게 된다.

### S-02 `V-DET-004`(산출물에 절대 경로 없음)와 `lock.sources[path]` 의 관계

§2.1 에 규약 11번으로 "모든 경로 키는 레포 루트 상대, `/` 구분자" 를 추가하면 `R-35-20`(머신 간 결정론)의 논증이 완결된다.

### S-03 `mapResolution` 이 부록 D-1 을 닫는 방식이 좋다 — 한 걸음 더
`R-35-11` 이 "빌드가 `map_navigation.dart:30-51` 과 똑같은 순서로 해석" 하도록 못 박은 것은 훌륭하다.
다만 **해석 로직이 두 벌**(Dart 런타임 + CLI)이 되면 언젠가 갈린다. `packages/hadar_content/` 에

맵 해석에도 적용된다. `V-DET-*` 로 검사할 수 없는 종류의 드리프트를 구조로 막는 방법이다.

### S-04 `determinism` 잡의 "두 번 빌드" 를 **별도 프로세스**로 명시할 것
`R-35-19` 는 "다른 출력 디렉토리" 만 요구한다. BP-20 `INV-20-02`(`20:797`)는 한 걸음 더 나아가
"**별도 프로세스로** 2회 실행(같은 프로세스 2회는 `hashCode` 기인 순서 흔들림을 못 잡는다)" 을 요구한다.
§2.5 의 예시 셸은 이미 프로세스를 두 번 띄우므로 실무는 맞다 — `R-35-19` 에 그 이유를 한 줄 붙이면
누군가 "성능을 위해 한 프로세스에서 두 번" 으로 바꾸는 것을 막는다.

### S-05 §3.3 의 `R-35-24`("`build/` 는 평평해야 한다")를 검사로 바꿀 것
`R-35-25` 가 "CI 가 검사한다(§4.4 의 `assets-declaration` 스텝)" 고 하지만, §4.4 본문에 그 스텝의

## 잘된 점

- **제시된 CI 스크립트가 실제로 돈다.** 검수자가 4개 grep 을 레포에서 그대로 실행해 **의도한 적중 4건·위양성 0건**을 확인했다.
  기획서의 YAML 이 이 정도로 실행 가능한 경우는 드물다. 특히 `-E "(^|[^A-Za-z0-9_])exit\("` 가
  `exitCode` 를 걸지 않도록 경계 문자를 넣은 것은 **위양성을 미리 계산한 흔적**이다.
- **기존 `check()` 헬퍼의 구조를 정확히 읽고 확장했다.** "기존 스텝을 통째로 교체" 하되 함수 본문은 그대로 두고
  호출만 늘렸으며, **대상 디렉토리가 다른 검사(⑤⑥)만 `check()` 밖으로 뺐다** — `check()` 가 대상 경로를
  하드코딩한다는 사실(`ci.yml:57`)을 알고 있다는 증거다. D-23 이 우려한 두 문제가 모두 해소되었다.
- **`R-35-18`(도입 순서) 이 이 문서의 백미다.** "`T-35-3` 의 grep 은 T-35-1·2 가 끝날 때까지 켜지 않는다.
  대신 `continue-on-error: true` 로 먼저 넣어 경고만 내고, 두 태스크가 끝나는 커밋에서 그 플래그를 제거한다.
  **이 방식이 '언젠가 고치자' 를 방지한다 — CI 로그에 매번 카운트가 찍히기 때문이다.**"
  게이트 도입이 CI 를 빨갛게 만드는 실무 문제를, 게이트를 미루지 않으면서 푸는 방법이다.
- **§2.4 가 빌드 결정론과 런타임 결정론을 분리한 것이 정확하다.** "위 두 코드는 `assets/content/` 를 읽지도 쓰지도 않는다.
  콘텐츠를 백 번 다시 구워도 산출물 해시는 같다. 그러나 골든 회귀와 솔버 완주 증명은 런타임 결정론에 의존한다" —
  두 개념이 섞여 논의가 흐려지기 쉬운 지점을 표 하나로 갈랐고, 대응 태스크 T-35-1~4 까지 선행 관계와 함께 붙였다.
- **§2.1 정규 JSON 규약 10항 + §2.2 배열 순서 규약 11행**이 결정론을 "원칙" 이 아니라 **점검 가능한 목록**으로 만들었다.
  특히 `R-35-14`("규약 2 를 위반하기 가장 쉬운 곳은 `Set` 이다 — 이터레이션 순서는 삽입 순서")는
  실제로 가장 흔한 버그를 정확히 지목했고, §2.2 가 "**의미 있는 배열 / 없는 배열**" 을 11행으로 갈라
  `V-DET-003` 의 검사 대상을 확정했다.
- **§1.1 의 fail-collect vs fail-fast 구분**(`R-35-1`/`R-35-2`) — 단계 **안**에서는 오류를 모으고
  단계 **사이**에서는 즉시 멈춘다. 근거가 "첫 오류에서 멈추면 생성 에이전트가 한 번에 하나씩만 고치게 되어
  재시도 횟수가 폭증한다" 로 BP-33 §7.3 의 AI 포맷과 정확히 맞물린다.
- **`R-35-6`(정규화는 `chance` 를 건드리지 않는다)** — `and`/`or` 평탄화가 `evalPath` 를 바꿔
  **기존 세이브의 분기를 뒤집는다**는 것을 스스로 발견하고, 평탄화를 "서브트리에 `chance` 가 없을 때만" 으로 제한했다.
  D-21a 가 승인한 "구조 경로" 방식의 숨은 위험을 이 장이 먼저 잡아냈다.
- **§3.4** 가 부록 C-3(맵 스냅샷 570KB)을 "이것은 번들 최적화가 아니라 세이브 포맷 문제" 로 정확히 재분류하고
  BP-25 에 넘기되, **두 문제가 만나는 지점 하나**(`mapDelta` 의 기준 원본이 `lock.mapSources` 에 잠긴다)만
  자기 소관으로 남겼다. D-18 의 소유권 규율을 가장 잘 보여주는 절이다.
- **§5.2 게이트 표**가 변경 유형 6종 × 잡 5종 × 시간 예산으로 완결되어 있고, `R-35-30` 이
  "**단 `content` 잡은 항상 돈다** — 코드만 바뀐 PR 에서도 콘텐츠 회귀를 잡아야 한다" 는 예외를 명시했다.
  스킵 최적화가 게이트에 구멍을 내는 흔한 실수를 피했다.
- **§8(현행 CI 부채)** 이 `--no-fatal-infos` 77건과 `dart format` 부재를 "언젠가" 로 두지 않고
  **baseline → 신규 디렉토리 무예외 → 점진 축소** 3단계와 `.git-blame-ignore-revs` 등록까지 구체화했다.
