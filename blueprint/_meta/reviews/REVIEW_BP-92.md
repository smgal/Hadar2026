## 2. 치명 결함 (반드시 고쳐야 함)

### F-01 BP-12 의 "코드 101 = 텍스트 헤더" 오류를 **"확인됨" 등급으로** 3곳에 복제
- **위치 3곳**:
  - `92_appendix_reference_index.md:43` (§92.2 R01 행 — "우리가 가져온 개념" 열은 무관하나 신뢰도 열이 "확인됨")
  - `92_appendix_reference_index.md:68` (§92.3 R01 — **"확인됨: … 텍스트 명령 코드 `101`(헤더) / `401`(본문 한 줄) …"**)
  - §92.4.2 표 — "R01 MV | 코드 101 (텍스트 헤더) | `Node.header`"
- **문서 주장**: MV 명령 코드 101 은 "텍스트 헤더"이며 본서 `Node.header` 에 대응한다. **등급: 확인됨** (= §92.1.1 상 "설계 근거로 인용 가능 ✅").
- **실제**:
  - MV 의 101(Show Text)은 텍스트를 담지 않는다. 파라미터는 `[faceName, faceIndex, background, positionType]` — 얼굴 그래픽 파일명, 얼굴 인덱스, 창 배경 타입, 창 위치다.
  - **본 레포 실측**: `hadar2026_app/assets/maps/Map010.json` 의 `{"code":101,"indent":0,"parameters":["",0,0,2]}`.
    `Map003.json` 의 3개 이벤트도 모두 `[101, 401, 0]` 순서로 같은 형태다.
  - 화자 이름 표시는 **MZ 에서 추가된 별개 기능**(`$gameMessage.setSpeakerName()`)이지 MV 101 의 파라미터가 아니다.
- **왜 치명인가**: §92.1 이 선언한 이 부록의 두 번째 용도가 "외부 문서를 읽다가 이게 우리 뭐에 해당하지? → 92.4 대응표" 다.
  **잘못된 번역표는 부록의 존재 이유를 무효화한다.** 게다가 "확인됨" 등급이라 §92.1.1 규칙상 **설계 근거로 인용해도 되는** 사실로 승인돼 있다.
  이 등급 오류는 §92.5.2 의 검증 백로그에도 잡히지 않는다 — 확인됐다고 표시됐으니 검증 대상이 아니다.
- **요구 조치**:
  1. §92.3 R01 의 "확인됨" 목록에서 `101(헤더)` 를 빼고, **"101 = Show Text 명령 헤더 레코드(얼굴 그래픽·창 배경·창 위치). 텍스트를 담지 않음"** 으로 정정.
  2. §92.4.2 의 101 행 대응란을 `Node.header` → **"✕ 대응 없음 — 얼굴/창 연출 미도입"** 으로 변경.
  3. §92.4.7 역방향 표는 `Node.header` 항목이 없으므로 추가 조치 불필요. 다만 `Node.header` 를 추가한다면 출처는 **R13(원작 `@B푯말에 써 있기를:`) + R06(Yarn 노드 헤더)** 로 적을 것.
  4. BP-12 §12.2.2 / §12.2.3 과 **동시에** 고칠 것. 한쪽만 고치면 두 문서가 어긋난다.

## 3. 중요 결함

### F-02 V-2 의 영향도 판정 "없음" 이 틀림 — MV 규칙은 우리와 **정반대 순서**다
- **위치**: §92.5.2 표 V-2 행 — "MV 의 다중 만족 페이지 선택 규칙 | … | **없음** — 현재 데이터에 다중 페이지 이벤트가 없고(모든 `*Valid`가 false), 우리 규칙은 '첫 true'로 별도 확정"
- **검증 결과**:
  - 전제(다중 페이지 0건, `*Valid` 전부 false)는 **정확하다** — 전 맵 38개 이벤트 전수 스캔으로 확인(W-i).
  - 그러나 MV 의 실제 규칙은 **"가장 높은 번호의 만족 페이지"** 다(W-p). 결정론적이며, **우리 R-12-1("배열 위에서부터 첫 true")과 순서가 반대**다.
- **왜 중요한가**:
  - §92.4.7 역방향 표가 `Dialogue.entry[]` ← "MV `pages[]` 의 조건 선택" 이라고 등재해 두었다.
  - BP-12 §12.2.2 도 `pages[]` → `entry[]` 를 직접 대응시킨다.
  - 따라서 누군가 레거시 다중 페이지 이벤트를 `entry[]` 로 옮길 때 **배열 순서를 보존하면 분기 의미가 통째로 뒤집힌다.**
  - 맵 에디터가 이벤트 CRUD 를 지원하므로(GROUND_TRUTH §11, `POST/PATCH /events`) 다중 페이지 이벤트는 언제든 생길 수 있다. "현재 데이터에 없다" 는 영구 보증이 아니다.
- **요구 조치**:
  - V-2 의 "검증할 것" 을 **완료 처리**하고(규칙 = 최고 번호 만족 페이지), 영향도를 **"없음" → "낮음"** 으로 상향.
  - "왜 필요한가" 열에 **"이관 시 배열 역순 필요 — 순서 보존하면 의미 역전"** 을 명시.
  - §92.4.2 의 `event.pages[]` → `Dialogue.entry[]` 행 비고에 같은 경고 추가.
  - BP-24 / BP-28 로 인계 (BP-92 §92.6 관련 문서 표에 이 인계가 없음).

### F-03 `event.note` → `tags[]` 대응처가 실재하지 않음
- **위치**: §92.4.5 표 — "R01 MV | `event.note` | `tags[]` 로 흡수 | (비고 없음)"
- **문제**:
  - MV 의 `event.note` 는 **이벤트 단위 자유 메모**다. 우리 모델에서 이벤트에 대응하는 것은 §92.4.5 자신이 첫 행에서 밝힌 대로 **`Anchor`**(D-09)다.
  - 그런데 **D-09 의 Anchor 스키마에는 `tags` 필드가 없다.** `{id, kind, actor|dialogue|to, x, y, facing}` 뿐이다.
  - `tags: [string]` 은 **D-06 의 Quest 필드**다. 즉 "이벤트의 메모를 퀘스트의 태그로 흡수한다" 는 대응이 되는데, 두 엔티티는 서로 다른 층에 있다.
  - BP-12 §12.2.2 도 같은 대응을 하며 "대응 문서: D-06" 이라 적어 같은 혼선을 공유한다.
- **요구 조치**: 셋 중 하나. (a) "✕ 대응 없음 — Anchor 는 메모를 갖지 않는다" 로 정정,
  (b) D-09 Anchor 에 `tags`/`note` 필드 추가를 **BP-26 열린 질문으로 인계**,
  (c) `event.note` 를 레거시 폴백 전용으로 명시하고 대응 없음 처리. **(a) + (b) 권고.**

### F-04 §92.4.1 의 출처 열이 자신의 분류 체계를 위반 — 앱 런타임 상태를 "R15 cm2" 로 귀속
- **위치**: §92.4.1 마지막 3행
  - "R15 cm2 | `Flag::Set(n)` / `Flag::IsSet(n)` | …" ← **이건 맞다.** cm2 등록 커맨드/함수(GROUND_TRUTH §9)
  - "R15 cm2 | `HDGameOption.flags: List<bool>(256)` | …" ← **틀렸다**
  - "R15 cm2 | `HDNativeScriptRunner.flags` (저장 안 됨) | …" ← **틀렸다**
- **문제**:
  - §92.1.2 는 분류 코드 **H = "본 레포 자체(Here)"**, **L = "언어/DSL"** 로 정의하고, §92.2 는 R15 를 **`packages/cm2_script` (CM2 DSL)** 로 못 박았다.
  - `HDGameOption` 은 `hadar2026_app/lib/domain/game_option.dart` 계열의 **앱 상태**이고, `HDNativeScriptRunner` 는 **네이티브 Dart 스크립트 러너**다. 둘 다 cm2 패키지와 무관하다.
  - 특히 `HDNativeScriptRunner.flags` 는 cm2 가 **쓰지 않는** 저장소다 — GROUND_TRUTH §8 이 이 둘을 명시적으로 다른 계보(1번 vs 2번)로 분리해 놓았는데, 이 표가 도로 합쳐 버린다.
- **왜 중요한가**: §92.4.1 의 이 3행은 **"상태 3중 분열의 통합"(D-16-4)** 을 설명하는 자리다. 분열의 세 갈래를 하나의 출처로 뭉개면 통합 대상이 몇 개인지가 흐려진다.
- **요구 조치**: 해당 2행의 출처를 `R15 cm2` → **`H 본 레포 런타임 상태 (GROUND_TRUTH §8-1 / §8-2)`** 로 정정.
  세 갈래(`HDGameOption` / `HDNativeScriptRunner` / `HDScriptEngine.variables`)를 **3행으로 나란히** 두면 D-16-4 의 통합 범위가 표에서 바로 읽힌다.
  현재 세 번째 갈래(`HDScriptEngine.variables`, 맵 전환 시 소거)는 **표에 아예 없다.**

### F-05 DECISIONS 문서규약 7(말미 3절 요약) 미준수

### S-03 §92.4.4 의 `ScriptMode()` 행에 와이어 값 범위의 실측 근거를 붙일 것

`hadar2026_app/lib/domain/map/tile_properties.dart:16-32` 와 `test/domain/map/tile_action_test.dart` 를 근거로 달면
"0~4 만" 이라는 진술이 왜 참인지가 표에서 닫힌다.

### S-04 참조원 ID `R01`~`R16` 이 요구사항 ID `R-12-nn` 과 시각적으로 혼동된다

## 6. 잘된 점 (검증으로 확인한 것만)

- **신뢰도 3등급 + 검증 백로그(V-1~V-7)라는 구조 자체가 이 기획서에서 가장 가치 있는 장치다.**

  §92.5.2 말미의 "미확인 사실은 서술의 색을 입힐 뿐, 결정은 언제나 레포 실측 또는 확정 결정에 걸려 있다" 는 원칙 재확인은 그대로 다른 장에 이식할 만하다.
- **레포 실측 주장 정확도 100%.** W-a·W-g~W-n 에서 대조한 **17개 실측 주장 전부**가 코드/데이터와 일치했다.
  특히 `map_event.dart:75-88`, `tile_event_dispatcher.dart:117`, `:166-178` 은 **줄 범위까지** 맞았다.
- **용어 대응표에 오탈자·임의 변형 0건.** 이 검수의 핵심 임무였는데 적발할 것이 없었다.
  `Choice.once`, `Stage {id, index}`, `content.lock.json#legacyFlagMap`, `pack.json#generatedBy` 같은
  **정확한 참조 표기까지 DECISIONS 원문과 일치**한다.
- **§92.3 R12 의 자기 고발이 모범적이다** — "전체가 미확인" 임을 스스로 굵게 표시하고,
  "그럼에도 쓰는 이유" 와 "이 절이 통째로 틀려도 D-14/D-15 는 무너지지 않는다" 를 함께 적었다.
  LLM 이 쓴 문서에서 가장 흔한 실패(모르는 것을 아는 척)의 정확한 반대다.
- **§92.3 R13 의 서술 규율**: "다른 90년대 국산 RPG 개별 작품의 설계 세부 — 확인되지 않은 사실을 쓰지 않기 위해
  **원작 Hadar 의 레포 실측 사실만** 톤 근거로 삼았다" 는 **의도적으로 다루지 않은 것** 절을 둔 것.
  환각 위험이 가장 높은 자리에서 스스로 손을 뗀 기록이 남아 있다.
- **`✕` / `≈` 기호 규약**(§92.4 도입부)이 대응 없음과 부분 대응을 구분한다. 실제로 `✕` 8곳이 전부 정당한 "대응물 없음" 이었다
  (Self Switch, Package, weave, tunnel, Papyrus 프로퍼티, Papyrus 조건식, event.note 는 예외 — F-03).

### RQ-2 D-09 Anchor 스키마에 자유 메모/태그 자리가 없다
- F-03 의 뿌리다. MV `event.note` 는 레거시 맵에 실제로 존재하는 필드이고(레포 맵 JSON 의 이벤트 키에 `note` 포함 — 실측 확인),
  이관 시 갈 곳이 없다. 또한 D-14 7단계 `critic` 이 앵커에 검수 메모를 남길 자리도 없다.
- **요청**: D-09 Anchor 에 선택 필드 `note?: string` 또는 `tags?: [string]` 추가를 BP-26 에서 검토.
  **1차 스코프 밖으로 미뤄도 무방하나, "대응 없음" 이라는 사실은 표에 정직하게 적혀야 한다.**
