### F-01 §1.1 의 고유명사 출현 횟수 3건이 전부 틀렸다 (약 2배)

- 위치: `43_content_style_guide.md:31`
- 문서 주장: `hadar2026_app/assets/lore_ep1.cm2` — "`Necromancer` **29회**, `Lord Ahn` **26회**, `MENACE` **21회**"
- 실측:
  ```
  lore_ep1.cm2 :  Necromancer 14 · Lord Ahn 13 · MENACE 11
  town2.cm2    :  Necromancer 14 · Lord Ahn 13 · MENACE  9
  두 파일 합계 :  28 · 26 · 20
  ```
  문서 숫자는 **두 파일 합계에 가깝다.** `Lord Ahn` 26 은 합계와 정확히 일치한다.
  `lore_ep1.cm2` 와 `town2.cm2` 는 거의 중복 사본이므로(§1.1 스스로 "`town2.cm2` 는 `lore_ep1.cm2` 의 확장본" 이라 적음) 합산 결과를 한 파일에 귀속시킨 것으로 보인다.
- 왜 중요한가: 이 표는 "무엇이 대표 표본인가" 를 정하는 근거다. 빈도가 2배로 부풀면 `lore_ep1.cm2` 하나가 원작 톤의 압도적 표본처럼 읽히고, 실제로는 두 사본에 분산되어 있다는 사실(이관 시 어느 쪽이 정본인지 정해야 한다는 과제)이 가려진다.
- 요구 조치: "`lore_ep1.cm2`: Necromancer 14 · Lord Ahn 13 · MENACE 11 / `town2.cm2` 는 거의 동일 사본(합계 28·26·20)" 으로 정정.

### F-02 마법은 40종이 아니라 **45종**이다 — 4곳

- 위치: `43_content_style_guide.md:326`(§4.1 표), `:355`(§4.3 충돌 회피 ③), `:562`(§7.2 M-10), `:681`(§9.1 확정 표)

- 실측 (`lib/domain/magic/magic.dart` 직접 확인):
  ```
  공격/저주 (id 1~18)   18종
  ```

### F-03 O-7 의 근거 인용 `menace.cm2:16` — `그래 !` 는 그 파일에 없다

- 위치: `43_content_style_guide.md:110`
- 문서 주장: "**`?`/`!` 앞에 공백을 넣는 습관** — `안될까요 ?`, `행운을 빌겠소 !!!`, `그래 !` | `lore_ep1.cm2:104`, `town2.cm2:161`, `menace.cm2:16`"
- 실측:
  - `안될까요 ?` @ `lore_ep1.cm2:104` ✅
  - `행운을 빌겠소 !!!` @ `town2.cm2:161` ✅
  - `그래 !` — **`menace.cm2` 전체에 없다.** 실제 위치는 `lore_ep1.cm2:134` / `town2.cm2:134`
    (`… 가만있자... 어디였더라... 그래 ! MENACE의 가운데쯤에 …`)

### F-04 M-8(지문 종결 검사)의 어미 사전에 `~다` 가 들어 있어 규칙이 **무효화**된다

- 위치: `43_content_style_guide.md:560` (§7.2 M-12 표), `:581` (§7.3 종결 어미 사전)
- 문서 주장:
  | M-8 | 지문(`@7` 구간)의 종결이 과거 완료가 아님 | **어미 사전(`~다`, `~였다`, `~았다/었다`)** | WARN | R-43-5, O-3 |
  - §7.3 사전: "평서 `~다/~였다/~았다/~었다`"
- 문제: 한국어 평서형 종결은 **거의 전부 `~다` 로 끝난다.** 현재형 `~이다`·`~한다`·`~보인다`, 미래·추측 `~것이다` 가 모두 `~다` 에 매칭된다.
  M-8 이 잡으려는 위반이 정확히 "현재형 서술" 인데, 사전에 `~다` 가 있으면 **현재형이 통과한다.**
  예: `등 뒤에서 소리가 난다.` → `~다` 로 끝나므로 M-8 통과. 그러나 O-3("서술은 평서 과거 완료 — 현재형 서술이 거의 없다")과 R-43-5 위반.
- 요구 조치: M-8 의 사전에서 `~다` 를 **빼고** 허용 종결을 `~였다 / ~았다 / ~었다 / ~하였다 / ~보였다 / ~있었다` 등 **과거 표지가 있는 것만**으로 좁힐 것. §7.3 의 "평서 `~다/~였다/…`" 행은 **화계 분류용(M-7)**과 **지문 검사용(M-8)** 을 분리해 두 줄로 쓸 것 — 지금은 한 사전이 두 규칙에 서로 다른 의미로 쓰이고 있다.

### F-05 M-10 의 "첫 2음절 일치 금지" 는 기존 데이터가 이미 대량 위반한다

- 위치: `43_content_style_guide.md:356`(§4.3), `:562`(M-10)
- 문서 주장: "**음절 충돌** | 기존 이름과 **첫 2음절이 같으면 금지**. `메너스`가 있으면 `메너드`를 만들지 않는다" / M-10 심각도 "**ERROR**(완전 일치) / **WARN**(2음절)"
- 실측 — **충돌 사전 자신이 규칙을 위반한다**:
  ```
  마법 화살 · 마법 화구 · 마법 단창 · 마법 불능   ← 첫 2음절 "마법" 공유 (4건)
  한명 치료 · 한명 독 제거 · 한명 치료와 독제거 · 한명 의식 돌림 · 한명 부활 · 한명 복합 치료  (6건)
  모두 치료 · 모두 독 제거 · 모두 치료와 독제거 · 모두 의식 돌림 · 모두 부활 · 모두 복합 치료  (6건)
  ```
  적 이름에도 `Giant` / `Giant Spider` / `Giant Rat`, `Blood Bat` 계열 등이 있다.
- 왜 중요한가: 규칙을 명세대로 구현하면 **신규 이름 대부분이 WARN 을 받는다.** 문서 자신이 R-43-25 에서 경계한 상황("오탐이 쌓이고 WARN 밀도만 올려 경고 전체가 무시된다")이 M-10 에서 발생한다.
- 요구 조치: 검사 대상을 **의미 단위가 아니라 고유명사로 한정**할 것 — 마법·기술명은 "한자어 2음절 + 한자어 2음절" 조합(O-11)이므로 첫 2음절 공유가 **정상**이다. M-10 의 사전을 `인명 · 지명 · 조직명`(§4.1 의 인물 8 / 지명 8) 으로 좁히고, 적 이름·마법명은 **완전 일치 검사만** 적용할 것.

### F-06 M-12 의 정규식이 대표 위반(`공격력 30`)을 잡지 못한다

- 위치: `43_content_style_guide.md:564`
- 문서 주장: M-12 | 아이템 `desc` 에 숫자+단위 | 정규식 `[0-9]+\s*(공격력|방어력|점|골드|gold)` | WARN | F-17
- 실측 검산 — F-17 과 §8 #17 의 나쁜 예에 직접 적용:
  ```
  나쁜 예: "강철 검. 공격력 30, 값 600 골드."
    "공격력 30"  → 숫자가 단위 뒤에 온다 → 정규식 미매칭 ❌
    "600 골드"   → 매칭 ✅
  F-17 의 제시 예: "강철 검. 공격력 30, 값 600."   ← "골드" 가 없어 완전 미매칭 ❌
  ```
  즉 **한국어에서 성능 수치는 `라벨 + 숫자` 순서**(`공격력 30`, `방어력 5`)인데 정규식은 `숫자 + 라벨` 순서만 잡는다.
- 부가: `점` 은 지나치게 넓다 — `3점` 은 잡지만 대사·설명에서 "…" 뒤 숫자 조합에도 오탐 가능.
- 요구 조치: `(공격력|방어력|힘|피해|값)\s*[0-9]+ | [0-9]+\s*(골드|gold|점)` 처럼 **양방향**으로 쓸 것. 또는 더 단순하게 "`desc` 에 아라비아 숫자가 등장하면 WARN"(F-13 이 이미 대사 안 아라비아 숫자를 금하므로 일관적)으로 강화.

### S-06 M-7 은 "결정론적" 이지만 "정확" 하지 않다 — §7.2 머리말 문구를 다듬을 것
- §7.2 머리말: "각 행은 … **전부 결정론적**이며 LLM 을 쓰지 않는다."
- M-7(종결 어미로 화계 분류)은 같은 입력에 같은 답을 낸다는 의미에서는 결정론적이나, 한국어 종결 어미는:
  - 하오체 `~오` 와 해요체 `~요` 가 인접(`~이오` vs `~이요`)
  - 합쇼체 `~십시오` 가 하오체 `~오` 에 부분 일치
  - 간접화법 `~라고 하오`, 인용 `"…습니다" 라고 했소`
  - 명사 종결(`약속이오`)과 서술격 종결이 형태상 동일
  에서 흔들린다. **Q-43-2 가 이 위험을 정직하게 열어 두었고 T-43-2 로 측정 계획까지 세운 것은 좋다.**
- 권고: §7.2 머리말을 "전부 결정론적(LLM 미사용)" → "전부 **기계 실행 가능**하며 LLM 을 쓰지 않는다. 단 M-7·M-9 는 **휴리스틱**이며 정확도 측정(T-43-2) 후 심각도를 확정한다" 로. R-43-21(이중 판정 금지)과 충돌하지 않는다.

### S-07 M-9(고유명사 표기 불일치)에 **별칭 목록**이 없으면 구현 불가
- M-9 판정 방법: "팩 고유명사 사전(`_glossary`)의 정본 표기와 대조. **같은 대상의 두 표기가 한 팩에 공존**"
- "같은 대상" 을 기계가 알려면 `_glossary` 가 `{정본: [별칭…]}` 형태여야 한다. `LORE 성` ↔ `로어성` 이 같은 대상임을 데이터가 말해 주지 않으면 검사가 성립하지 않는다.
- §9.2 는 "고유명사 정본 표기 사전(`_glossary`) 필드 신설 → BP-22" 로 넘기면서 **별칭 필드의 필요를 명시하지 않았다.** 한 줄 추가 권고.

### S-08 §4.1 "적 이름 74종" — 사전 목적에는 75가 맞다
- 부록 B-1 의 "사용 가능한 적 74종(id 1~74)" 을 정확히 반영한 것이나, M-10 의 **이름 충돌 사전**으로 쓸 때는 `enemyTable` 의 **75 엔트리 전부**(id 0 `Orc` 포함)가 필요하다. 같은 행에서 예시로 `Orc` 를 들고 있으므로 이미 실질적으로는 75를 쓰고 있다.
- "소환 가능 74종 / 이름 사전은 75개" 로 나눠 쓸 것.

### S-09 §5.x 예문의 "자수" 검산 1건
- §5.5 예문 1 `나는 '@BLord Ahn@@' 이오.` — "15(태그 제외 12)". 태그 제외 문자열은 `나는 'Lord Ahn' 이오.` 이고, BP-24 §24.5.5 의 `weight(ch)` 규칙(한글 2, 그 외 1, 태그 0)으로 계산하면 한글 5자(나·는·이·오) + 라틴/기호 13 → 한글 환산 약 **11.5자**. 12는 반올림으로 볼 수 있으나, "15" 가 어느 계산인지 불명확하다(태그 4문자를 포함한 문자 수도 아니다).
- 화자별 예문 18개 전체에 대해 계산 방식을 한 줄 명시하거나 자수 열을 빼는 편이 낫다 — 자수는 어차피 M-계열 린트가 잰다.

## 잘된 점

- **인용 25건 전수 대조 결과 문자열 일치 100%.** 원작 대사를 다루는 문서에서 가장 위험한 실패(존재하지 않는 대사 창작)가 0건이다. 특히:
  - `이 안에 갇혀있는 사람들에게는 일체 면회가허용되지 않습니다.` — **원문 오탈자(`면회가허용되지`)를 고치지 않고 그대로 보존**했다. 표본으로서 옳은 태도.
  - `일행은 가장 기본적인 무기로  모두  무장을 하였다.` — **이중 공백까지 보존**.
  - `... 끄~~윽 ... ...` — 물결 수와 공백 위치까지 정확.
- **고유명사 목록(§4.1)의 데이터 근거가 정확하다.** 맵 `displayName` 4건 직접 확인: `TOWN1.json` → `로어성` ✅ / `GROUND1.json`·`Map013.json` → `로어 대륙` ✅ / `DEN1.json` → `메너스` ✅ / `Map015.json` → `라스트디치` ✅. O-9("맵 표시명은 전부 한글화되어 있다 — 화면에 `로어성` 이라 뜨는 맵에서 NPC 는 `LORE 성` 이라 말한다")는 **실측으로 확인된 진짜 균열**이며, 이 장이 발견한 가장 값진 관찰이다.
- **R-43-1("관찰은 파일·줄 번호를 달고, 정한 것은 `R-43-*` 번호를 단다")을 문서 전체가 실제로 지킨다.** O-1~O-11 과 R-43-2~26 이 끝까지 분리되어 있어 "원작이 그랬다" 와 "우리가 정했다" 를 혼동하지 않는다. 이는 다른 장들이 배워야 할 서술 규율이다.
- **R-43-4 가 원작 습관을 그대로 계승하지 않고 기술적 이유로 끊었다.** "`?`/`!` 앞 공백은 원작 습관(O-7)이지만 이것은 **오탈자 계열**이며, 줄바꿈이 어절 단위(§6.2)라 `말이오 ?` 는 `?` 만 다음 줄로 떨어질 수 있다." — 실측 확인: `hd_text_utils.dart splitToLines` 의 `text.split(' ')` 때문에 `?` 는 실제로 독립 어절이 된다 ✅. 감성 보존과 기술적 정확성이 충돌할 때 근거를 대고 후자를 고른 좋은 판단.
- **§6.2 의 `splitToLines` 분석이 정확하다.** 직접 확인:
  ```dart
  final words = text.split(' ');   // ← 공백으로만 어절을 나눈다
  if (currentLineWidth + wordWidth > maxWidth && currentLineChildren.isNotEmpty) { … }
  ```
  "한 어절이 480px 를 넘으면 줄이 나뉘지 않고 그대로 넘쳐 잘린다" ✅. 그리고 **"실제로 30자를 넘기려면 일부러 붙여 써야 한다. 그러나 AI 는 한자어 복합명사를 붙여 쓰는 경향이 있다"** 는 결론이 정직하다 — 원작 실사례 4건을 세어 전부 안전(12/11/15/16자)임을 보이고, 그럼에도 규칙이 필요한 이유를 생성물 특성에서 찾았다.
- **§1.6("톤 규정 대상이 아닌 것")이 표본 오염을 선제 차단한다.** 휴대폰 보조금 뉴스(`town1.cm2:21`)·`Talk script 2-1`·삶은 계란 말장난·제작진 멘트·`### Grocery` 자리표시자 — **7건 전부 실재 확인**. LLM 에게 이 파일들을 그대로 먹이면 무슨 일이 일어날지 아는 사람이 쓴 절이다.
- **R-43-21(이중 판정 금지)** — "같은 문체 위반을 기계가 ERROR 로 막고 Critic 이 다시 감점하면, 통과한 것은 두 번 안전하고 걸린 것은 두 번 벌 받는다. 규칙마다 판정 주체가 정확히 하나여야 한다." 이 문서에서 가장 좋은 규범이며, BP-32/BP-33/BP-37 전체에 적용 가능한 원칙이다.
- **시스템 메시지 문체를 "새로 정하지 않고 맞춘다"(§2.5)** — `menu_flows.dart`/`battle.dart` 의 기존 어투를 6종으로 분류해 규범으로 승격했다. R-43-10 의 예외 처리("시스템은 하오체를 쓰지 않는다 — 단 하나의 예외가 메인 메뉴 제목 `고르시오` 이며, 원작 유산이므로 바꾸지 않는다")가 정확히 실측(`menu_flows.dart:35`)에 걸려 있다.
- **§7.5 의 15줄 압축본**이 실제 프롬프트 슬롯에 그대로 들어갈 수 있는 형태다. 길이·금칙·화계·고유명사를 전부 담고도 15줄이며, T-43-4 가 버전 태그까지 지정했다.
- **§8 의 21쌍(나쁜 예 → 문제 → 좋은 예)** 이 각각 F-nn / M-nn / R-43-nn 에 역참조된다. 검수 에이전트가 판정 근거를 찾아갈 수 있는 구조.
- Q-43-1 이 BP-22 와의 `properNounStyle` 충돌을 **결정을 뒤집지 않고** 열린 질문으로 남기고 잠정 규칙만 제시한 것 — DECISIONS 서문의 지침을 정확히 따랐다.
