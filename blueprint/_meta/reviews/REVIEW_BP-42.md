## 치명 결함 (반드시 고쳐야 함)

### F-01 폐기된 payload `{itemId, count}` 를 정본으로 확정했다 — D-20a 정면 위반

- 위치: `42_item_and_inventory.md:739-753` (§8.2), `:769`, `:782` (§8.3 의사 코드), `:833` (R-42-64~65 요약), `:865` (Q-42-3)
- 문서 주장:
  > "### 8.2 정본 이름과 payload (D-20)
  > | `item_gained` | `{itemId, count}` | … |
  > **R-42-65** payload 는 **`{itemId, count}` 두 필드**다.
  > **Q-42-3** … D-20 의 정본은 `{itemId, count}` 다. **본 장은 D-20 을 따른다.** … D-20 이 명시적으로 payload 를 확정한 개정이므로 D-20 이 우선한다고 본다."
- 실제 (`_meta/DECISIONS.md` 현행 본문):
  - **D-20a (2026-08-30)** — "D-20 표의 `{itemId, count}` 는 메인이 옮겨 적으며 생긴 **오기**였다. **소유 장인 BP-23(§23.11.1, `23_quest_model.md:1164`)의 `{itemId, delta, total}` 가 정본**이다. D-20 표를 그에 맞춰 정정했다."
  - **D-20 본문(개정 후)** — "> **payload 정의는 여기 두지 않는다.** 정본은 소유 장 [BP-23 §23.11.1] 의 12행 표다. (D-20a 의 교훈: 소유 장의 스키마를 결정 문서로 옮겨 적는 행위 자체가 오류원이다. 초판 D-20 은 12행 중 **9행의 payload 를 잘못 옮겨 적었고**, Q-52-7 로 적발되었다.)"
  - **BP-23 §23.11.1 원문** (`23_quest_model.md:1163-1164`, 직접 확인):
    ```
    | 5 | `item_gained` | `{itemId, delta, total}` | `give_item` Effect 적용 후 |
    | 6 | `item_lost`   | `{itemId, delta, total}` | `take_item` Effect 적용 후 |
    ```
- 왜 치명인가 — **셋이 겹친다**:
  1. **결정 위반.** BP-42 가 "D-20 이 명시적으로 payload 를 확정했다" 고 쓴 문장은 현행 D-20 본문과 **정반대**다. D-20 은 payload 를 명시적으로 **자기 관할에서 뺐다**. 즉 BP-42 는 D-20a 이전 판본을 읽고 쓴 뒤, 그 오기를 근거로 소유 장(BP-23)을 이기려 한 것이다. 이는 D-18("충돌 시 소유 장이 항상 이긴다 — 비소유 장은 자기 서술을 지우고 링크로 대체할 것")의 직접 위반이다.
  2. **기능 파손.** D-20a 가 `total` 을 넣은 이유가 명시되어 있다 — "`count` 단일 필드는 **'변화량인가 총량인가' 가 모호**해서 `acquire(itemId, count:3)` 목표의 판정을 흔든다. `total` 이 있어야 카운터형 목표가 이벤트 하나로 판정된다." BP-42 §8.4 는 바로 그 `acquire` 를 "이 발행이 살려 내는 것" 으로 내세우는데, `total` 없이는 **소비자가 인벤토리를 다시 조회해야** 하고 배치 안에서 중간 상태를 보게 된다(R-42-69 가 "각각 별개 이벤트, 합치지 않는다" 로 못박았으므로 중간 상태가 실제로 발생한다).
  3. **일관성 파손.** D-20a 는 "다른 변화 이벤트와 표기가 일관된다: `var_changed {varId, from, to}`, `gold_changed {from, to, delta}`" 를 근거로 든다. BP-23 §23.11.1 실측도 `gold_changed {delta, total}` 이다. BP-42 만 `count` 를 쓰면 12종 중 2종만 표기가 다르다.
- 요구 조치:
  1. §8.2 표를 **삭제**하고 "이름과 payload 의 정본은 [BP-23 §23.11.1](../../23_quest_model.md)" 한 줄 링크로 대체(D-18/D-25).
  2. §8.3 의사 코드를 `emit('item_gained', {'itemId': itemId, 'delta': added, 'total': inventory[itemId]})` / `emit('item_lost', {'itemId': itemId, 'delta': removed, 'total': inventory[itemId] ?? 0})` 로 수정.
  3. R-42-65 를 "`delta` 는 이번 변화량이며 항상 양수, `total` 은 변화 후 소지 수량" 으로 재작성(§8.3 이 이미 두 값을 다 갖고 있으므로 구현 부담 0).
  4. **Q-42-3 을 삭제**한다. 열린 질문이 아니라 이미 D-20a 로 종결된 사안이고, 열어 두면 다음 검수자가 다시 헷갈린다.

### F-02 §7.4 카탈로그의 `가죽 갑옷` grade 가 자기 유도 규칙과 모순

- 위치: `42_item_and_inventory.md:648` vs `:677-683`
- 문서 주장: 15번 `item.core.leather_armor` 가죽 갑옷 — `value` **180**, grade **1**
- 실제 유도 규칙(R-42-59, §7.5): grade 1 = `value` **1~150**, grade 2 = **151~500**
- 재계산: 180 ∈ [151, 500] → **grade 2** 여야 한다.
- 전수 검산 결과 20종 중 **이 1건만** 어긋난다:

  | value | 아이템 | 표기 grade | 유도 grade | 판정 |
  |---|---|---|---|---|
  | 20 마른 양식 / 25 로어 에일 / 30 항해 일지 / 35 대형 횃불 / 40 단도 / 60 회복약·두꺼운 옷 / 70 나무 방패 / 120 단검 | | 1 | 1 | ✅ |
  | **180 가죽 갑옷** | | **1** | **2** | ❌ |
  | 200 단창 / 260 무쇠 방패 / 450 수정 구슬 | | 2 | 2 | ✅ |
  | 600 강철 검 / 700 사슬 갑옷 / 900 이동 구슬 | | 3 | 3 | ✅ |
  | 0 무기고 열쇠 / 0 문지기의 인장 | | 1 (명시) | 예외 | ✅ |
  | 0 황금방패의 조각 | | 4 (명시, `unique`) | 예외 + `unique` 최소 4 | ✅ |

- 왜 중요한가: [BP-23 QV-33](../../23_quest_model.md) 이 `give_item` 아이템의 `grade` 와 퀘스트 `tier` 차이를 **린트로 검사**한다. 카탈로그가 유도 규칙과 어긋난 채 커밋되면 그 린트가 첫 실행부터 스스로를 반박한다.
- 요구 조치: 가죽 갑옷을 **grade 2** 로 올리거나 `value` 를 150 이하로 내릴 것. 가죽 갑옷은 §7.6 에서 `quest_reward`/`chest`(tier 1~2 대응)이므로 grade 2 가 자연스럽다.

### F-04 §7.2 무기 데미지 표의 `Goblin` 열이 잘못된 방어값을 쓴다

- 위치: `42_item_and_inventory.md:580-586`
- 문서 주장: 열 머리글이 "적 방어(**ac1·lv1**) 후" 인데 그 옆 두 열이 `Troll(HP 6)` 과 `Goblin(HP 39)` 이다.
- 실제 (`enemy_data.dart` 직접 확인):
  ```
  id 1 Troll  : strength 9,  endurance 6,  ac 1, level 1   → HP = 6×1  = 6   ✅
  id 9 Goblin : strength 11, endurance 13, ac 3, level 3   → HP = 13×3 = 39  ✅
  ```
  (`domain/battle/enemy.dart` 생성자 `hp = endurance * level`)
  Goblin 의 방어는 `ac 3 · lv 3` 이므로 `damage -= (3 × 3 × rand(1..10)) ÷ 10` = 평균 **4.95** 감소다. ac1·lv1 의 평균 0.55 가 아니다.
- 재계산 (슴갈 `strength 18`, `level.physical 1`, 단검 `power 15`):
  ```
  기본  = (18 × 15 × 1) ÷ 20 = 13            ← 문서의 13 ✅
  감쇠  = 13 − 13×24.5% ≈ 9.8                ← 문서의 ~10 ✅
  Troll  방어 후 ≈ 9.8 − 0.55 ≈ 9.2  → HP 6  → 1타 ✅ (문서 1타)
  Goblin 방어 후 ≈ 9.8 − 4.95 ≈ 4.85 → HP 39 → 약 8타  (문서는 5타)
  ```
  강철 검(power 30)도 마찬가지다: 문서 2타 → 실제 약 3타.
- 왜 중요한가: R-42-51("첫 무기가 레벨 1 적을 한 방에 잡는다") 과 R-42-52("강철 검은 tier 2 이후 — tier 1 에서 주면 레벨 3~4 적까지 2타에 정리되어 경험치 곡선이 무너진다")가 **이 표의 숫자를 근거로 삼는다.** Goblin 열이 낙관적이면 R-42-52 의 위험 판단이 실제보다 강하게 서술된 것이다.
- 요구 조치: 열 머리글을 "각 적의 실제 `ac`·`level` 적용" 으로 바꾸고 Goblin 열을 재계산할 것. Troll 열은 그대로 맞다.

### F-05 §7.3 의 "항상 0" 두 건이 수학적으로 거짓

- 위치: `42_item_and_inventory.md:617-618`
- 문서 주장:
  | `ac` | Troll 상대 |
  |---|---|
  | 10 (books.json 두꺼운옷) | **항상 0** |
  | 20 (books.json 가죽갑옷) | **항상 0** — 6레벨 적까지 무력화 |
- 실제: 피격식(`battle.dart:513-514`)은 **두 개의 독립 난수**를 쓴다.
  ```dart
  int damage = (e.strength * e.level * (Random().nextInt(10) + 1)) ~/ 10;
  damage -= (t.ac * t.level.physical * (Random().nextInt(10) + 1)) ~/ 10;
  ```
  Troll(str 9, lv 1) 최대 피해 = `(9×1×10)÷10` = **9**.
  방어 최소 감소: `ac 10` → `(10×1×1)÷10` = **1** / `ac 20` → `(20×1×1)÷10` = **2**.
  → 최악 조합에서 각각 **8**, **7** 피해가 실제로 들어간다. 두 난수가 독립이므로 이 조합은 확률 1/100 로 매 턴 발생 가능하다.
- 왜 중요한가: R-42-53("`books.json` 의 `ac 10`/`ac 20` 은 초반 전투를 통째로 무효화한다")과 §4.4 의 재척도(10→2, 20→5)가 이 문장을 근거로 든다. **결론(재척도 필요)은 여전히 옳다** — 기댓값 기준으로 `ac 10` 이면 평균 감소 5.5 > 평균 피해 4.95 라 대부분의 턴이 0피해다. 그러나 "항상" 은 틀렸고, 검수를 통과시키려면 근거 문장의 강도를 사실에 맞춰야 한다.
- 요구 조치: "항상 0" → "**기댓값상 음수 — 대부분의 턴이 0피해이며, 두 난수가 최악으로 엇갈릴 때만(약 1/100) 7~8 이 들어간다**" 로 정정. GROUND_TRUTH H-2 도 "무효화" 라는 표현만 쓰고 "항상" 을 쓰지 않는다.

### F-06 R-42-10(획득 거부)이 퀘스트 완주 가능성을 조용히 깨는 경로를 만든다 — 대응 미기술

- 위치: `42_item_and_inventory.md:206-210` (R-42-10, R-42-11), `:869` (Q-42-7)
- 문서 주장: 종류 48 초과 또는 비스택 중복 획득 시 "획득을 **거부**하고 … `item_gained` 를 **발행하지 않는다**. '받은 척하고 사라지는' 동작은 퀘스트 목표를 조용히 망가뜨린다."

- Q-42-7 은 "1차 스코프에서 발생 불가(카탈로그 20종)" 로 넘기지만, 이는 **카탈로그 크기가 아니라 팩 합성(D-03: `core` + `gen_ep1` 겹쳐 쓰기)에 달린 문제**다. 생성 팩이 아이템을 추가하는 순간 20종 전제는 깨진다.
- 요구 조치 (택1):

  어느 쪽이든 **§9.3 Q-42-7 의 "발생 불가" 잠정 답을 팩 합성 전제로 다시 쓸 것.**

### S-02 §7.1 "적 HP `endurance × level`" 의 출처가 반쯤 어긋난다
- 문서는 출처를 "`player.dart` `assignFromEnemyData`" 로 적는다. 그 함수(`player.dart:241`)에도 `maxHp = endurance * level.physical` 이 있어 **식은 맞으나**, 전투에 실제로 등장하는 적은 `HDEnemy` 이고 그쪽 생성자(`domain/battle/enemy.dart`)의 `hp = endurance * level; if (hp <= 0) hp = 1;` 가 정본이다. `assignFromEnemyData` 는 **적을 파티원으로 영입할 때**(`Player::AssignFromEnemyData`) 쓰인다.
- `if (hp <= 0) hp = 1` 이라는 하한도 문서에 없다 — `Phantom`(str 0) 같은 적의 계산에 영향을 준다.

- **R-42-47(마이그레이션은 월드 이벤트를 발행하지 않는다)** — "세이브를 여는 것만으로 `acquire` 목표가 진행되면 안 된다". 놓치기 쉬운 경계 조건.
- **§3.3 이 DSL 을 늘리지 않고 "v1 에서 되는 것 / 안 되는 것" 을 분리**한 뒤, 안 되는 것을 **플래그로 흉내 내지 않겠다고 선언**(R-42-23)한 판단은 옳다 — 다만 카탈로그가 그 선언을 지키지 못했다(F-03).
- **R-42-63 이 D-20 의 "미발행 명시" 의무를 정면으로 이행한다**: "이 장이 구현되기 전까지 두 이벤트는 한 번도 발행되지 않으며, 그에 의존하는 `acquire`/`deliver`/`has_item` 은 **항상 거짓**이다. 다른 장이 '덮는다' 고 쓴 서술은 이 장의 구현 이후에만 참이 된다." D-26 의 정신에 정확히 부합.
- 20종 카탈로그의 분류별 집계(6+5+2+3+1+1+1+1 = 20)와 재사용 11 + 신규 9 = 20 이 **둘 다 산술적으로 맞는다** ✅.
