## 1. 왜 이 장이 필요한가 — 안전망이 없을 때의 실패 모드

현행 콘텐츠 파이프라인(cm2)의 실패는 **조용하다**. GROUND_TRUTH §9 실측:

| 현행 실패 | 관찰되는 증상 | 발견 시점 |
|---|---|---|
| 미등록 cm2 함수 호출 | `Unknown function` 출력 후 **0 반환** → 조건문이 반대로 분기 | 플레이 중, 그것도 운 좋아야 |
| 미등록 커맨드 | `Unknown command` 출력 후 스킵 | 동일 |
| 존재하지 않는 cm2 경로 페어링 (부록 A-1) | 로드 실패 로그 1줄, 게임은 계속 진행 | 발견 안 됨 |
| cm2 로드 실패 시 상태 누수 (부록 A-2) | 이전 맵 스크립트가 계속 실행되는데 정상처럼 보임 | 발견 안 됨 |
| 네이티브 맵 스크립트 플래그 스텁 (부록 A-3) | 모든 조건 분기가 항상 `false` | 발견 안 됨 |
| `MapInfos.json` 이름 해석 파손 (부록 D-1) | 15개 등록 이름 중 **7개가 없는 파일로 해석**, 맵이 안 바뀌는데 `true`(성공) 반환 | 발견 안 됨 |

**LLM 생성물은 이 실패 모드를 증폭한다.** 사람은 오타를 두 번 세 번 만들지 않지만, 생성 에이전트는
같은 실수를 100건의 대화에 균일하게 뿌린다. 따라서 이 장의 설계 원칙은 하나다:

> **R-33-1** 조용한 실패를 만들지 않는다. 검증기가 모르는 것은 통과가 아니라 **실패**다.
> 알 수 없는 `op`/`do`/필드/ID 는 전부 ERROR 이며, "아마 괜찮을 것" 이라는 판정은 존재하지 않는다.

## 2. 검증 5계층

### 2.1 계층 정의

| 계층 | 이름 | 책임 | 입력 | 실행 시점 | 1회 비용(중규모 팩) | 차단력 |
|---|---|---|---|---|---|---|
| **L1** | 스키마(구문) | 파일이 JSON 으로 읽히는가, 스키마를 만족하는가, 열거값·ID 문법이 맞는가 | 소스 파일 1개 | 파일 저장 시 / `validate` / 서버 `POST` 응답 | **파일당 < 1 ms** | ERROR = 이후 계층 실행 안 함 |
| **L2** | 참조 무결성 | 모든 ID 가 실재하는 무언가를 가리키는가, 팩 가시성을 지키는가 | 전 팩 병합 심볼 테이블 | `build` 의 link 단계 | **팩당 < 50 ms** | ERROR = 번들 생성 중단 |
| **L3** | 그래프 구조 | 퀘스트 DAG·대화 그래프가 도달 가능·종료 가능한가 | 링크 완료된 엔티티 | `build` 의 index 단계 직전 | **엔티티당 O(N+E)**, 팩당 < 200 ms | ERROR = 번들 생성 중단 |
| **L4** | 시맨틱·세계관 | 말이 되는가 — 지식 범위, 세력 관계, 보상 밸런스, 텍스트 길이·문체 | 번들 + 바이블 + 맵 데이터 | `lint` (build 이후 독립 실행) | **팩당 1~3 s** (사전 매칭이 지배) | ERROR = 커밋 차단 / WARN = 검수 에이전트 판단 |
| **L5** | 시뮬레이션 | 실제로 완주 가능한가(**모델 증명**), 그 경로가 현행 빌드에서 돌아가는가(**실행 가능**, D-26), 골든과 같은가 | 번들 + 헤드리스 하네스 + [BP-35](35_ci_and_build.md) 의 발행 지점 레지스트리 | `sim` / `solve` — CI 와 야간 배치 | **퀘스트당 1~30 s** | ERROR = 커밋 차단 / **RELEASE = 커밋 통과·릴리스 차단** |

### 2.2 계층 간 관계 — 게이트가 아니라 필터

```
소스 ──L1──▶ (구문 OK) ──L2──▶ (참조 OK) ──L3──▶ (구조 OK) ──▶ content.bundle.json
                                                        │
                                                        ├──L4──▶ lint 리포트 (ERROR/WARN/INFO)
                                                        └──L5──▶ sim 트레이스 + 솔버 증명
```

- **R-33-2** L1 이 ERROR 를 내면 그 파일에 대해 **L2 이후를 실행하지 않는다**. 파싱 실패한 파일의
  참조 무결성을 따지는 것은 의미가 없고, 폭포수 에러가 AI 재시도 프롬프트를 오염시킨다(§7.3).
- **R-33-3** 반면 L1 이 통과한 파일이 여럿이면 **L2 는 전부 모아 한 번에** 돈다. 참조 무결성은
  전역 성질이라 파일 단위로 나눌 수 없다.
- **R-33-4** L4 는 L3 통과를 전제로 하지만 **L3 ERROR 가 있어도 실행한다**(다른 파일 진단을 함께 보기
  위해). 다만 그래프 의존 규칙(`V-L4-021` 난이도 단조성 등)은 스킵하고 그 사실을 INFO 로 남긴다.
- **R-33-5** L5 는 L1~L4 의 ERROR 가 0 일 때만 실행한다. 깨진 콘텐츠를 시뮬레이션하는 것은 비용 낭비다.

### 2.3 계층별 담당 파일 (D-11 배치 준수)

| 계층 | 구현 위치 | Flutter 의존 |

| L2 | `tools/content_cli/lib/validate/link.dart` (심볼 테이블은 `lib/domain/content/`) | 없음 |

- **R-33-6** `tools/content_cli/` 는 **Flutter 를 의존하지 않는 순수 Dart 패키지**다.
  **`packages/hadar_content/`** 를 path dep 으로 끌어 쓰되, 그쪽이 `package:flutter/foundation.dart` 조차

## 3. 규칙 ID 체계와 기존 장 규칙과의 매핑

### 3.1 ID 형식

```
V-<계층>-<번호>
  계층 ∈ { L1, L2, L3, L4, MAP, DET, L5 }
  번호 = 3자리 0-padded, 팩 안에서 불변
```

- `MAP` 은 계층이 아니라 **주제 묶음**이다(앵커·맵 정합). 실제 계층은 표의 `계층` 열이 밝힌다 —
  좌표 범위는 L1, 참조 해소는 L2, 통행 가능성은 L4(맵 데이터를 읽어야 하므로)다.
- `DET` 도 주제 묶음(결정론)이며 계층은 L1/L4/빌드후로 갈린다.
- **R-33-7** 규칙 ID 는 **불변**이다. 규칙을 폐기하면 번호를 비워 두고 재사용하지 않는다.
  CI 억제 주석(`// lint-ignore: V-L4-023`)과 골든 리포트가 번호를 참조하기 때문이다.

### 3.2 다른 장의 규칙 번호와의 관계

각 아키텍처 장은 자기 도메인의 제약을 이미 번호로 정의했다. **이 장은 그 번호를 폐기하지 않고
심각도·메시지·자동수정을 확정해 흡수한다.** 표의 `출처` 열이 그 대응이다.

| 출처 접두 | 정의 장 | 개수 | 이 장의 처리 |
|---|---|---|---|
| `QV-01 ~ QV-38` | [BP-23](23_quest_model.md) | 38 | 심각도 확정 + 메시지 부여 |
| `DV-01 ~ DV-32` | [BP-24](24_dialogue_model.md) | 32 | 동일 |
| `L-22-01 ~ 30` | [BP-22](22_world_bible_model.md) | 30 | 동일 |
| `A-26-01 ~ 12`, `M-26-01 ~ 05`, `RG-01 ~ 08` | [BP-26](26_entity_registry_and_anchors.md) | 25 | 동일 |
| `R-21-nn` | [BP-21](21_content_pack_spec.md) | — | 요구사항 → 규칙으로 승격 |
| `INV-20-nn` | [BP-20](20_target_architecture.md) | **22** | CI 잡으로 이관([BP-35](35_ci_and_build.md)) |
| `M-1 ~ M-12` | [BP-43](43_content_style_guide.md) | 12 | **수용 상태표**로 받는다(§4.4(d)). 4건은 명세 결함 때문에 **조건부** |

> **`INV-20-nn` 개수 정정(REVIEW_BP-33 F-06)**: 초판은 18 로 적었으나 BP-20 의 불변식은
> `INV-20-01 ~ INV-20-21` + `INV-20-05b` = **22개**다. 이 표는 "기존 장 규칙을 이 장이 몇 건 흡수하는가" 의
> 회계이므로 개수가 틀리면 `T-33-F`(카탈로그 동기화 테스트)의 기대값이 어긋난다.

- **R-33-8** 출처가 있는 규칙은 **검사 내용을 재정의하지 않는다**. 원 장이 알고리즘을 바꾸면 이 장의
  표는 심각도만 유지한 채 따라간다. 원 장과 이 장이 어긋나면 **원 장이 이긴다**.

## 4. 규칙 카탈로그

**읽는 법** — `자동 수정` 열: `불가` = 사람/에이전트만 고칠 수 있음 · `자동` = `--fix` 가 무조건 적용 ·
`제안` = `--fix` 가 후보를 제시하되 적용은 사람 승인 필요(§6).
`위반 시 메시지` 는 실제 출력 문구의 템플릿이며 `{…}` 는 치환 슬롯이다. 모든 메시지는 맵 에디터 API 와
같은 `{error, hint}` 규약(GROUND_TRUTH §11)을 따라 **무엇이 틀렸는가 + 어떻게 고치는가** 를 함께 낸다.

> **F-01 조치 — `V-L4-005` / `V-L4-010` 을 ERROR 에서 내린 이유** (REVIEW_BP-33 F-01)
>
> [BP-37 §37.5.2](37_prompt_contracts.md) 가 하드/소프트 경계를 확정했고, 그 표의 Hard 12항목에는
> **"지식 범위 — `unknown` 언급" 만** 들어 있다. **"세계관 정합(모순·시점)" 은 Soft · Critic Q1 · 권한 전권**이며
> `V-L4-005`(비밀 누설)·`V-L4-010`(금기 키워드)은 분류상 그쪽이다. 기계가 ERROR 로 커밋을 차단하면
> Critic 의 전권이 무효가 되고, `R-37-14`("Critic 이 Hard 항목을 지적하면 그 finding 을 폐기한다")와
> **양쪽에서 판정하는 이중 판정**이 된다.
>
> **사전 매칭이 가능하다는 사실은 "기계가 판정해도 된다" 를 뜻하지 "하드 게이트로 승격해도 된다" 를 뜻하지 않는다.**
> 초판 `R-33-9` 는 전자만 논증하고 후자로 건너뛰었다. 따라서 두 규칙은 **WARN** 으로 두고,
> [BP-37 `R-37-15`](37_prompt_contracts.md) 의 `severity:"blocking"` 후보로 올려 **Critic 의 `verdict` 를 통해서만**
> 차단되게 한다. 기계는 사실을 보고하고, 차단 여부는 Soft 축의 판정자가 정한다.
>
> `V-L4-001`(`knowledge.unknown` 언급)만 **ERROR 로 남는다** — BP-37 표가 그것 하나를 Hard 로 명시했기 때문이다.
> 이 세 규칙의 심각도가 BP-37 §37.5.2 표와 **문자 단위로 일치**하는지는 `T-33-G`(§9.4)가 고정한다.

### 4.5 앵커·맵 정합 · 21개 — **D-27 로 4건 강등 · 1건 삭제 · D-28 로 확정**

맵 통행 가능성 판정은 [BP-26 §3.2](26_entity_registry_and_anchors.md) 의 3티어 판정표를 그대로 쓴다.
검증기는 맵 JSON 을 직접 읽거나, 맵 에디터 dev 서버가 떠 있으면 `GET /api/ai/maps/{file}/passability`
(GROUND_TRUTH §11)로 대조한다 — 두 결과가 다르면 `V-MAP-022` 를 낸다.

#### 4.5.0 D-27 이 이 절을 바꾼 두 가지 · **D-28 이 그것을 확정한 것**

**(1) 정합은 런타임 조건이 아니라 저작 품질 문제다 → ERROR 4건을 WARN 으로 강등**

초판은 "앵커 kind 마다 요구되는 타일 액션이 있고 어기면 빌드 하드 실패" 였다. 그 전제는
**앵커가 타일 액션 게이트를 통과해야 발화한다**는 것이었는데, **D-27 이 그 전제를 폐기했다** —
콘텐츠 티어는 `(map, x, y, activation)` 으로 트리거 인덱스를 **직접 조회**하고 타일 액션을 보지 않는다
([BP-26 §2.2·§3.3](26_entity_registry_and_anchors.md), [BP-27 §4.2](27_runtime_engine.md)).
런타임은 타일이 무엇이든 앵커를 발화시키므로, 정합 위반은 **"게임이 의도대로 동작하지 않음이
기계적으로 증명된다"(§5.1 의 ERROR 정의)에 더 이상 해당하지 않는다.**

그렇다고 무해한 것은 아니다. 위반은 **"플레이어가 그 앵커에 물리적으로 닿을 수 없다"** 를 뜻하므로
강한 경고다. 그래서 아래 표의 각 규칙에 **"무엇이 깨지는가"** 를 붙였다 —
경고를 읽는 사람(그리고 검수 에이전트)이 심각도를 스스로 판단할 수 있어야 한다.

> **강등해도 커밋이 막힐 수 있다** — [BP-26 R-26-7b](26_entity_registry_and_anchors.md) 의 2단 구조.
> 도달 불가 앵커를 경유하는 퀘스트는 솔버가 완주 증명에 실패해 `V-L5-001`(ERROR, 하드 게이트)에 걸린다.
> **"런타임은 관대, 게이트는 엄격"** 이며, 정합 규칙 자체를 ERROR 로 둘 필요가 없는 이유다.

**(2) region 기반 검증은 근거가 사라졌다 → `V-MAP-017` 삭제**

`hadar2026_app/lib/application/map_loader.dart:44` 가 region(0~255)을 `ixEvent` **하위 바이트**에 넣는데

`200 & 0x00FF0000 == 0` — **어떤 region 값도 타일 액션을 만들지 못한다.**
따라서 "trigger 앵커 칸의 region 이 200~255 여야 한다"(초판 `V-MAP-017`)는 검사는
**존재하지 않는 메커니즘을 강제**하는 규칙이었다.

- **R-33-42** (D-27) `V-MAP-017` 을 **삭제**한다. `R-33-7`(규칙 ID 불변)에 따라 **번호는 결번으로 두고
  재사용하지 않는다.** 골든 리포트와 억제 주석이 번호를 참조하기 때문이다.

### 4.7 L5 — 시뮬레이션 (BP-34 위임) · 7개 — **D-26 로 2축**

이 절의 규칙은 **판정 기준만** 여기서 확정하고, 탐색 알고리즘·정책·트레이스 포맷은
[BP-34](34_headless_sim_and_solver.md) 가 소유한다. 이 장은 "무엇이 실패인가" 만 정한다.

#### 4.7.0 D-26 — 솔버 판정은 3값이 아니라 2축이다

초판 `V-L5-001` 은 "`QuestSolver` 가 `inactive → completed` 경로를 하나 이상 찾는다" 만 검사했다.
**그것으로는 부족하다** — D-26 이 지적한 결함은 다음이다.

> `deliver`/`acquire` 목표는 `item_gained`/`item_lost` 이벤트에 의존하는데, D-20 은 그 두 이벤트가
> **인벤토리 부재로 현재 미발행**임을 명시한다. 그런데 솔버는 그 퀘스트에 `PROVEN` 을 냈다.
> 정적 증명이 **실행 가능성을 보지 않았기 때문**이다. 이대로면 솔버는 "돌아가지 않는 콘텐츠" 를 통과시킨다.

**확정: 판정은 2축이다.**

| 축 | 값 | 의미 | 이 장의 규칙 |

     스킵**하고 그 사실을 INFO 로 남긴다(`R-33-4` 와 같은 정책). 진행하지 않는 목표를 두고
     데드락을 논하는 것은 의미가 없다.
- **R-33-49** `UNSUPPORTED` 는 **콘텐츠 결함이 아니다.** 에러 메시지가 작성자를 탓하지 않아야 한다 —

  **규칙 자체의 심각도 조정**으로 처리한다(`V-L2-013` 이 그 선례 — F-08).

## 5. 심각도 체계

### 5.1 세 등급의 정의

| 등급 | 정의 | 게이트 | 종료 코드 | 누가 판단하는가 |
|---|---|---|---|---|
| **ERROR** | 이 상태로는 **게임이 의도대로 동작하지 않는다**는 것이 기계적으로 증명된다 | **커밋 차단**. `hadar_content commit` 이 거부하고 CI 가 빨개진다 | `2` | 아무도. 기계가 단독 판정 |
| **WARN** | 동작은 하지만 **품질·일관성이 의심된다**. 판단에 사람/서사 맥락이 필요하다 | 차단하지 않음. 검수 에이전트(D-14 7단계)의 입력이 되고 리포트에 남는다 | `0` (`--strict` 시 `2`) | 검수 에이전트 → 최종 사람 |
| **RELEASE** | 콘텐츠는 정상이지만 **그 콘텐츠가 쓰는 게임 기능이 아직 없다**(D-26 의 `UNSUPPORTED`) | **커밋은 허용.** 팩이 "미활성" 으로 표시되고 **릴리스 게이트에서 차단**된다 | `0` (`--gate=release` 시 `2`) | 기계가 단독 판정 — 판정 근거는 [BP-27 §7.7.2](27_runtime_engine.md) 의 발행 지점 표 |
| **INFO** | 통계·관찰. 위반이 아니다 | 없음 | `0` | 리포트 독자 |

- **R-33-9b** (D-26) `RELEASE` 를 ERROR 로 두지 않는 이유: 마일스톤이 진행되는 동안
  **미리 콘텐츠를 만들어 두는 것을 허용**해야 한다. `acquire` 목표를 쓰는 퀘스트를 BP-42 완료 전에
  써 두는 것은 잘못이 아니다. 반대로 WARN 으로 두지 않는 이유: **배포하면 실제로 진행이 막힌다** —
  검수 에이전트의 판단 대상이 아니고 기계가 단독으로 확정할 수 있는 사실이다.
  ERROR 와 WARN 사이에 이 등급이 없으면 D-26 이 요구한 "커밋 가능 · 릴리스 차단" 을 표현할 수 없다.

- **R-33-9** ERROR 의 판정 근거는 **항상 실행 가능한 검사**여야 한다. "어색하다", "톤이 안 맞는다" 는
  ERROR 가 될 수 없다 — 그 판단이 결정론적이지 않기 때문이다. 사전 매칭으로 기계 판정이 가능한
  세계관 규칙 중 ERROR 로 남는 것은 **`V-L4-001`(모르는 것 언급) 하나**다
  ([BP-37 §37.5.2](37_prompt_contracts.md) 의 Hard 12항목에 그것만 있다).
  `V-L4-005`·`V-L4-010` 은 기계 판정이 가능하지만 **Soft 축이므로 WARN** 이다 — §4.4(a) 의 F-01 조치.
- **R-33-9a** (F-01 침범 3 해소, `R-32-22` 의 역방향 대칭 규칙) **기계는 Soft 축을 ERROR 로 판정하지 않는다.**
  [BP-37 §37.5.2](37_prompt_contracts.md) 가 Soft 로 분류한 축(세계관 정합·톤·문체·보상 적정성)의 승격은
  **Critic 의 `verdict` 로만** 일어나며, §5.2 의 승격 규칙 P1~P4 는 그 축에 적용되지 않는다.
  [BP-32 `R-32-22`](32_generation_harness.md)("Critic 은 Hard gate 를 판정할 권한이 없다")와 쌍을 이루어
  **양방향 이중 판정**을 막는다. 한쪽만 있으면 대칭이 성립하지 않는다.
- **R-33-10** WARN 이 100건 넘게 나오는 팩은 그 자체가 신호다. `hadar_content lint` 는 WARN 밀도
  (`WARN 수 ÷ 엔티티 수`)를 리포트 머리에 찍고, `contentBudget.maxWarnDensity`(기본 0.5) 초과 시
  **INFO 가 아니라 ERROR** 를 하나 추가한다(`V-META-001`). 경고를 무한히 쌓아 무시하는 것을 막는다.

### 5.2 승격 규칙 (WARN → ERROR)

**대전제 (F-01 침범 3 해소)**: 아래 승격 규칙은 **`R-33-9a` 의 제한을 받는다** —
[BP-37 §37.5.2](37_prompt_contracts.md) 가 Soft 로 분류한 축에는 **어떤 승격도 적용되지 않는다.**
승격 대상은 `V-L1-*` · `V-L2-*` · `V-L3-*` · `V-MAP-*` · `V-DET-*` 와,
`V-L4-*` 중 **텍스트 길이·페이지 예산처럼 기계적 사실인 것**(`V-L4-027~037`)뿐이다.

| # | 조건 | 적용 범위 | 예 | 상태 |
|---|---|---|---|---|
| P1 | **배수 초과** — 권장 범위를 정해진 배수 이상 벗어남 | ❌ **보상 밸런스에는 적용 안 함** — [BP-37](37_prompt_contracts.md) 이 "보상 밸런스(권장 범위 안에서의 적정성)" 를 Soft · Critic Q5 · 공동으로 확정했다. `V-L4-015/016` 은 배수를 넘어도 **WARN 에 머문다** | `V-L4-036`(노드 `lines` > 12) 처럼 기계적 사실에만 | 조정됨 |
| P2 | **`--strict` 플래그** | ⚠ **범위 한정.** `V-L1-*`·`V-L2-*`·`V-L3-*`·`V-MAP-*`·`V-DET-*`·`V-L4-027~037` 만 승격한다. `V-L4-001~026`(지식 범위·세계관 정합·소문 단정형·적대 세력 지칭·톤·문체·보상)은 **제외** | `hadar_content lint --strict` | 조정됨 |
| P3 | **반복 위반** — 같은 규칙이 한 엔티티에서 5회 이상 | ⚠ **문체·톤 경고에는 적용 안 함**(Soft 축). 길이·페이지 예산 위반의 반복만 승격 | 한 노드에서 `V-L4-030`(잘리는 어절) 5건 | 조정됨 |
| P4 | **팩 정책** — `pack.json#lintPolicy.promote` 로 팩이 자발적 강화 | ⚠ **구현 보류** — 필드 부재(§4.9.1 F-02). 또한 `R-33-9a` 에 따라 팩이 자발적으로도 Soft 축을 ERROR 로 올릴 수 없다 | — | 보류 |

**초판이 무엇을 잘못했는가** (REVIEW_BP-33 F-01 침범 3):
초판 `P2` 는 "릴리스 태그 빌드에서는 **모든** WARN 이 ERROR" 였다. 그러면 릴리스에서
`V-L4-002`(지식 범위) · `V-L4-003`(소문 단정형) · `V-L4-007`(적대 세력 우호 지칭) · `V-L4-011~013`(문체·톤) 같은
**Critic 전권/공동 축이 전부 기계에 의해 하드 차단**된다. [BP-32 `R-32-22`](32_generation_harness.md) 가
"Critic 은 Hard gate 를 판정할 권한이 없다" 를 확정했으므로, **역방향 대칭 규칙 `R-33-9a`**
("기계는 Soft 축을 하드 판정하지 않는다")가 없으면 이중 판정이 성립한다.

- **R-33-54** Soft 축 WARN 의 승격은 **오직 Critic 의 `verdict`** 로만 일어난다
  ([BP-37 `R-37-15`](37_prompt_contracts.md) 의 `severity:"blocking"`). 기계는 그 축에서
  **사실만 보고**하고 게이트를 건드리지 않는다.
- **R-33-55** 어떤 규칙이 Soft 축인지의 정본은 [BP-37 §37.5.2](37_prompt_contracts.md) 표다.
  이 장은 그 표를 **전재하지 않고**(D-25) 규칙별 심각도만 그것에 맞춘다.
  일치는 `T-33-G`(§9.4)가 기계로 고정한다 — 두 문서가 어긋나면 CI 가 빨개진다.

### 5.3 강등 규칙 (ERROR → WARN)

강등은 **원칙적으로 금지**한다. 예외는 두 가지뿐이다.

| # | 조건 | 절차 | 만료 | 상태 |
|---|---|---|---|---|
| D1 | **마이그레이션 유예** — 레거시 콘텐츠 이관 중 일시적 위반 | `pack.json#lintPolicy.demote: [{rule, until, reason}]` 에 **만료 버전 명시** | 그 버전 도달 시 자동 복구. 만료된 항목이 남아 있으면 `V-META-002` ERROR | ⚠ **구현 보류** — 필드 부재(§4.9.1) |
| D2 | **개별 억제** — 의도된 예외 1건 | 소스에 `"_lintIgnore": ["V-L4-027"]` 필드 + `"_lintIgnoreReason"` **필수** | 없음. 단 억제 총량이 팩당 20건을 넘으면 `V-META-003` ERROR | ⚠ **구현 보류** — 필드 부재 + `V-L1-003` 자기모순(R-33-52) |

> **두 예외가 모두 보류이므로, 현재 유효한 강등 경로는 없다.** 이관기의 위양성은
> **규칙 자체의 심각도 조정**으로 처리한다 — `V-L2-013`(F-08)이 그 방식의 선례다.
> 개별 억제가 없다는 것이 `R-33-1`(조용한 실패 금지)과 충돌하지 않는지는 §4.9.1 R-33-53 에서 다뤘다.

- **R-33-11** 억제는 **사유 문자열이 없으면 억제되지 않는다**. `_lintIgnore` 만 있고
  `_lintIgnoreReason` 이 없으면 원래 규칙 + `V-META-004`("사유 없는 억제") 둘 다 낸다.
- **R-33-12** L1·L2·`V-DET-*` 는 **어떤 방법으로도 억제할 수 없다**. 구문이 깨졌거나 참조가 없거나
  결정론이 깨진 것은 취향의 문제가 아니다.

| **실행 가능 축** — 완주 경로가 소비하는 이벤트에 발행 지점이 있는가 | `V-L5-007`(`RELEASE`) | **커밋은 통과.** 릴리스 태그 빌드(`--gate=release`)에서 차단. 팩은 "미활성" 표시 |

- **R-33-56** (D-26) D-15 의 하드 게이트 목록에 `V-L5-007` 을 **넣지 않는다.**
  D-26 이 "커밋은 가능하되 릴리스에서 차단" 을 명시했으므로 하드 게이트가 아니다.
  그러나 **`PROVEN + UNSUPPORTED` 를 "하드 게이트 통과" 로 보고해서도 안 된다** —
  §7.2 의 CI 리포트는 두 축을 **각각** 출력한다(`modelVerdict` / `supportVerdict` 두 필드).
  한 필드에 뭉치면 D-26 이 막으려던 오판이 리포트 수준에서 재발한다.
- **R-33-57** 릴리스 게이트의 실제 배치(어느 워크플로가 `--gate=release` 를 켜는가, 미활성 팩을
  번들에서 어떻게 빼는가)는 [BP-53](53_acceptance_criteria.md) 과 [BP-35](35_ci_and_build.md) 소관이다.
  이 장은 **무엇이 실패인가**만 정한다.

## 6. 자동 수정(autofix)

### 6.1 원칙

> **R-33-13** 자동 수정은 **의미를 만들지 않는다.** 기계가 고칠 수 있는 것은
> (a) 표현 형식, (b) 유일하게 결정되는 값, (c) 삭제해도 동작이 안 바뀌는 죽은 데이터뿐이다.
> **작가의 의도를 추측해야 하는 수정은 전부 `제안` 이며 사람/에이전트 승인을 거친다.**

### 6.2 `자동` — `--fix` 가 무조건 적용

| 규칙 | 수정 내용 | 왜 안전한가 |
|---|---|---|
| `V-L1-018` | 파일을 `expectedPath` 로 이동 | `id` 가 정본이고 파일명은 파생물이다. 반대로 고치면 참조가 깨진다 |
| `V-L1-027` | 값이 `""` 인 키 삭제 | 빈 문자열은 어떤 경우에도 표시할 것이 없다 |
| `V-L2-011` | 고아 문자열 키 삭제 | 참조가 0인 것이 정적으로 증명됨. 단 `--fix-orphan-strings` 를 따로 켜야 함(§6.4) |
| `V-L3-004` | 마지막 분기의 `when` 을 `{"op":"true"}` 로 설정 | 그 자리에 올 수 있는 값이 하나뿐 |
| `V-L3-014` | `maxDepth` 를 기본값 32 로 클램프 | 범위 밖 값은 무의미 |
| `V-L3-017` | `nodes` 사전 키를 `node.id` 로 맞춤 | `id` 가 정본 |
| `V-MAP-012` | 겹친 `onceFlag` 를 앵커 id 기반 유일 키로 재발급 | 플래그 이름은 표시되지 않는 내부 값 |
| `V-DET-002` | 산출물 키 재정렬 | 순수 형식 |
| `V-DET-003` | 배열을 규약 순서로 재정렬 | 순서 규약이 §BP-35 §2.2 에 확정되어 있음 |
| `V-DET-004` | 비결정 값 필드 제거 | 산출물에 들어가서는 안 되는 값 |
| `V-DET-006` | `chance(0)`→`{"op":"false"}`, `chance(100)`→`{"op":"true"}` | 의미가 완전히 동일 |
| `V-DET-008` | 재빌드 후 산출물 커밋 | 파생물 재생성 |
| `V-DET-014` | 소스의 `chanceSeedId` 필드 삭제 | **빌드가 반드시 다시 굽는 값**이므로 소스의 값은 무슨 값이든 무의미하다. 남겨 두면 `V-L1-003`(미지 필드)으로 어차피 막힌다 |

### 6.3 `제안` — 후보 제시, 적용은 승인 필요

| 규칙 | 제안 방식 | 승인이 필요한 이유 |
|---|---|---|
| `V-L1-003` / `V-L1-008` / `V-L1-009` / `V-L1-010` | 편집 거리(Levenshtein ≤ 2) 로 가장 가까운 허용값 제시 | `set_flag` 오타가 `clear_flag` 일 수도 있다. 반대로 고치면 논리가 뒤집힌다 |
| `V-L1-015` / `V-L1-025` | 소유 엔티티에서 유도한 키를 발급(`strings/mint`)하고 인라인 텍스트를 그 키로 치환 | 슬롯 이름은 작가가 정한다 |
| `V-L1-026` | 닫히지 않은 태그에 `@@` 삽입 위치 후보 제시 | 어디까지 강조인지 사람만 안다 |
| `V-L2-001`~`V-L2-009`, `V-L2-019`~`V-L2-021` | 같은 타입 안에서 편집 거리 최소 후보 3개 | 존재하지 않는 액터가 오타인지 미작성인지 알 수 없다 |
| `V-L2-017` | `replacedBy` 가 있으면 그 ID 로 치환 | `replacedBy` 가 없으면 제안 불가 |
| `V-L3-011` / `V-L3-016` | 마지막 선택지/entry 항목의 `when`·`once` 제거 | 조건을 지우면 서사가 바뀔 수 있다 |
| `V-L4-021` / `V-L4-022` | 해당 Effect 를 `rewards`→`onComplete` 로 이동 | 실행 순서가 바뀐다 |
| `V-L4-028` | 문장 분할 지점 후보(어절 경계) 제시 | 문장을 나누는 것은 집필이다 |
| `V-MAP-001` | 맵 에디터 배치 op 를 그대로 만들어 제시 (§6.5) | 지형을 바꾸는 것은 부작용이 크다 |
| `V-MAP-016` | `MapInfos.json` 에 `"json": "<이름>.json"` 추가하는 패치 제시 | 어느 파일이 정본인지 사람이 확인해야 함(부록 D-1 의 7건) |
| `V-DET-013` | (a) 조건을 `and(not(flag <제안키>), <원래 chance>)` 로 감싸고 (b) 분기 Effect 맨 앞에 `set_flag <제안키>` 를 넣는 **2단 패치**를 제시. 제안 키는 소유 엔티티에서 유도(`flag.<pack>.<domain>.<slug>_rolled`) | **재굴림이 의도일 수 있다.** 래치를 넣으면 무작위 연출이 1회성으로 굳어 서사가 바뀐다 — 무엇이 의도인지는 작가만 안다. 또 래치 플래그는 세이브에 영구히 남으므로 이름을 사람이 승인해야 한다 |

### 6.4 `불가` — 절대 자동 수정하지 않는 것과 근거

| 범주 | 예 | 근거 |
|---|---|---|
| **누락된 콘텐츠 생성** | `V-L2-010` 문자열 키 누락 → 문장 지어내기 | 기계가 대사를 쓰면 그것은 검증 대상이 아니라 생성이다. 파이프라인 3단계로 되돌려야 한다 |
| **그래프 재배선** | `V-L3-001` 사이클 → 간선 삭제 | 어느 간선을 끊느냐가 곧 서사 구조 결정 |
| **밸런스 수치 조정** | `V-L4-015` 경험치 → 권장 범위 중앙값으로 | 보상은 서사 비중의 표현이다. 기계가 균질화하면 모든 퀘스트가 같아진다 |
| **세계관 위반 수정** | `V-L4-001` 모르는 것 언급 → 문장 삭제 | 삭제하면 앞뒤가 안 맞고, 액터의 `knows` 를 늘리는 것이 옳은 답일 수도 있다 |
| **적 id 치환** | `V-L2-018` id 0 → id 1 | Orc 를 Troll 로 바꾸는 것은 콘텐츠 변경 |
| **통행 불가 좌표 이동** | `V-MAP-003` 포털 도착지 이동 | 도착지는 연출의 일부. [BP-26 §6.4](26_entity_registry_and_anchors.md) 의 자동 수복은 **반경 2·후보 1개** 라는 훨씬 좁은 조건에서만 동작한다 |
| **결정론 코드 수정** | `V-DET-009` `Random()` → `WorldRng` | 런타임 코드 리팩터링이며 테스트가 따라와야 한다 |

- **R-33-14** `--fix` 는 **소스 파일만** 고친다. 맵 JSON 은 절대 직접 쓰지 않고, 맵 에디터 API
  (`POST /api/ai/maps/{file}/edit`)를 통해서만 변경한다(D-12: AI 는 파일을 직접 쓰지 않는다).
- **R-33-15** `--fix` 는 적용 후 **반드시 재검증**한다. 수정이 새 위반을 만들면 롤백하고
  `V-META-005`("자동 수정이 새 위반을 유발") 를 낸다.

### 6.5 제안의 형식 — 실행 가능한 패치

제안은 산문이 아니라 **적용 가능한 op** 다. 맵 에디터 API 의 `{error, hint}` 규약을 확장한다.

```json

  "severity": "ERROR",

  "error": "앵커 \"anchor.gen_ep1.town1_scholar_wife\" 는 kind=actor 인데 (34,12) 의 타일 액션이 move 입니다.",

    "kind": "suggest",

      "method": "POST",
      "path": "/api/ai/maps/TOWN1.json/edit",

### 7.3 AI 재시도용 (`--format=ai`)

**그대로 생성 에이전트의 다음 턴 프롬프트에 붙여 넣어 자기수정을 유도할 수 있어야 한다.**

## 8. 성능과 증분 검사

### 8.1 목표 규모와 시간 예산

| 규모 | 퀘스트 | 대화 노드 | 문자열 | 앵커 | 목표 시간 (L1~L3) | 목표 시간 (L1~L4) |
|---|---|---|---|---|---|---|
| 소 (현재 프로토타입) | 7 | 150 | 400 | 40 | < 0.2 s | < 2 s |
| 중 (에피소드 1개) | 40 | 900 | 2,500 | 200 | < 0.6 s | < 6 s |
| **대 (목표 상한)** | **200** | **5,000** | **14,000** | **1,000** | **< 3 s** | **< 25 s** |
| 초과 (경고) | 400 | 12,000 | — | — | — | CI 가 `V-META-006` INFO |

- **R-33-25** L1~L3 전체 검사는 **대 규모에서도 3초 미만**이어야 한다. 이 예산은 콘텐츠 서버가
  저장할 때마다 전량 검사를 돌릴 수 있게 만드는 것이 목적이다(D-12: API 를 통해서만 쓴다).

### 8.2 왜 L4 가 느린가 — 지배항 분석

| 검사 | 복잡도 | 대 규모 추정 |
|---|---|---|
| 지식 범위 매칭(`V-L4-001/002/004/005`) | 문자열 수 × 별칭 사전 크기 | 14,000 × 600 = 8.4M 비교 → **Aho–Corasick 으로 O(총 문자수 + 적중수)** 로 낮춤 |
| 길이·어절 계산(`V-L4-027~037`) | O(총 문자수) | 14,000 × 평균 45자 = 630K 문자, < 100 ms |
| 통행 가능성(`V-MAP-*`) | 앵커 수 × O(1) + 맵 로드 | 맵 15개 × 최대 161 KB 파싱이 지배 → **맵 파싱 결과 캐시** |
| 보상 밸런스(`V-L4-015~018`) | O(퀘스트 수²) (팩 내 상대 비교) | 200² = 40K, 무시 가능 |
| 중복 서사(`V-L4-038` 계열) | O(문자열 수²) 순진 구현 | **MinHash + LSH 로 O(N)** 근사 |

- **R-33-27** 사전 매칭은 반드시 **Aho–Corasick 오토마톤**을 쓴다. 별칭 사전은
  `content.index.json#aliases` 에 정렬 상태로 구워 두고, 오토마톤 구축 결과를 `.hadar_cache/` 에 캐시한다.
- **R-33-28** 유사도 검사는 **MinHash 시그니처(128 permutation) + LSH 밴딩**으로 후보를 추린 뒤
  후보 쌍만 정확 비교한다. 시그니처는 결정론적 해시(FNV-1a 64)로 만들어 재현 가능해야 한다.

### 8.3 증분 검사 전략

```
변경 파일 집합 Δ  ──▶  영향 범위 계산  ──▶  재검사 대상
```

| 계층 | 증분 가능? | 재검사 범위 |
|---|---|---|
| **L1** | ✅ 완전 증분 | Δ 안의 파일만. 파일 간 의존 없음 |
| **L2** | ⚠ 부분 증분 | Δ 가 **정의**한 ID 집합이 바뀌지 않았으면 Δ 파일의 참조만. 정의 집합이 바뀌면 그 ID 의 `referencedBy`(역참조 인덱스, [BP-26 §5](26_entity_registry_and_anchors.md))에 있는 파일까지 |
| **L3** | ⚠ 엔티티 단위 증분 | 퀘스트/대화는 **자기 안에서 닫힌 그래프**다. Δ 의 엔티티 + `play_dialogue`/`prerequisites` 로 연결된 엔티티만 |
| **L4** | ⚠ 부분 증분 | 문자열이 바뀌면 그 문자열만 재매칭. 바이블(`world/*.json`, `actors/*.json`)이 바뀌면 **전량 재검사**(사전이 바뀌었으므로) |
| **MAP** | ⚠ 맵 단위 | 맵 JSON 이 바뀌면 그 맵의 앵커 전량. 앵커가 바뀌면 그 앵커만 |
| **DET** | ❌ 불가 | 산출물 전체 해시 비교이므로 증분 개념 없음 |
| **L5** | ⚠ 퀘스트 단위 | Δ 가 영향을 주는 퀘스트만. 영향 판정은 역참조 인덱스 |

- **R-33-29** 증분 검사의 정확성은 **역참조 인덱스의 정확성에 전적으로 의존**한다. 따라서
  `hadar_content validate --full` 을 CI 에서 항상 돌리고, 증분은 **로컬·서버 응답용**으로만 쓴다.
  "증분이 놓쳤다" 를 잡는 것은 CI 의 전량 검사다.
- **R-33-30** 증분 캐시(`.hadar_cache/`)는 **커밋하지 않는다**(`.gitignore`). 캐시 키는
  `(파일 SHA-256, 규칙 카탈로그 버전, CLI 버전)` 삼중이며, 셋 중 하나라도 다르면 캐시 미스다.

## 9. 런타임과 검증기의 시맨틱 일치 보장 (D-12)

### 9.1 문제

같은 `Condition` 을 검증기와 런타임이 다르게 평가하면 **검증이 아무 의미가 없다**.
cm2 가 정확히 이 실패에 빠져 있다 — 스크립트가 뜻하는 바와 엔진이 하는 일이 다른데
(GROUND_TRUTH §9: 미등록 함수 0 반환) 그것을 대조할 방법이 없다.

### 9.2 구조적 해결 — 평가기를 하나만 만든다

```
lib/domain/content/condition.dart   ← Condition 모델 + evaluate(WorldStateView)   [유일한 구현]
lib/domain/content/effect.dart      ← Effect 모델 + apply(WorldStateMutator)       [유일한 구현]
        ▲                                   ▲
        │ import                            │ import (path dep)
        │                                   │
lib/application/content/*           tools/content_cli/lib/**
  (런타임)                            (검증기 · 린트 · 솔버)
```

| 규칙 | 내용 |
|---|---|
| **R-33-32** | Condition/Effect 를 해석하는 코드는 `lib/domain/content/` 에 **정확히 한 벌**만 존재한다. CLI 는 그것을 import 한다. 재구현·번역·복제 금지 |
| **R-33-33** | (REVIEW_BP-33 F-05 정정) `tools/content_cli/pubspec.yaml` 은 **`packages/hadar_content/`** 를 path dep 으로 잡는다([BP-30 R-30-13/14](30_toolchain_overview.md)). 초판이 쓴 `hadar_domain` 이라는 패키지는 **존재하지 않으며**, "CLI 가 `hadar2026_app` 을 path dep 으로 잡으면 Flutter 가 전이로 딸려온다" 는 것은 [BP-30 §4.4](30_toolchain_overview.md) 가 실측으로 기각한 안이다. 따라서 콘텐츠 코어는 **순수 Dart 패키지로 물리 분리**되고 `hadar2026_app/lib/domain/content/` 는 **얇은 re-export 배럴**만 남는다. 컴파일 단계 강제는 그 물리 분리가 만든다 |
| **R-33-34** | TypeScript 콘텐츠 서버는 평가기를 **갖지 않는다**. 평가가 필요하면 CLI 를 서브프로세스로 부른다. 정규식 3종만 `hadar_content stats --emit-regex` 로 생성해 넣는다(R-21-15) |
| **R-33-35** | 검증기가 런타임보다 **더 관대할 수 없다**. 런타임이 `StateError` 를 던지는 입력은 검증기가 반드시 ERROR 로 잡는다. 반대(검증기가 더 엄격)는 허용된다 |

### 9.3 차이의 유일한 합법적 원천 — `chance`

검증기와 런타임이 **다르게 행동해도 되는 것은 `chance` 하나뿐**이다.

| | 런타임 | 검증기·솔버 |
|---|---|---|
| `chance(30)` | 시드에서 유도한 값 하나로 한쪽 분기 — `mix([seed, step, chanceSeedId])`([BP-21 §6.5](21_content_pack_spec.md)) | **양 분기 모두 탐색**(R-21-35) |
| `step` 의 역할 | 시드 입력. 스텝이 진행하면 같은 위치도 값이 바뀐다(D-30) | 무시한다 — 어차피 양 분기를 보므로 `step` 값이 판정을 바꾸지 않는다 |
| 근거 | 플레이 경험 | "운이 나쁘면 막힌다" 를 배포 전에 잡기 위함 |

이 차이는 `ConditionEvaluator` 의 **주입 가능한 `ChanceOracle`** 로 표현한다.

```dart
// lib/domain/content/condition.dart
abstract interface class ChanceOracle {
  /// null 을 돌려주면 "양쪽 다 가능" 이라는 뜻 — 탐색기가 분기한다.
  /// `chanceKey` = BP-21 §6.5 의 `<contextId>#<evalPath>`. 번들의 `chanceSeedId` 를 역참조하지 않고
  /// 저작 시점 키를 그대로 받는다 — 진단 메시지에 사람이 읽을 위치를 실어야 하기 때문이다.
  bool? roll(int percent, String chanceKey);
}

class SeededChanceOracle implements ChanceOracle { /* 런타임: 항상 true/false */ }
class BranchingChanceOracle implements ChanceOracle { /* 솔버: 항상 null */ }
```

- **R-33-36** `evaluate()` 의 시그니처에는 **시계도 난수 생성기도 들어가지 않는다.**
  `WorldStateView` 와 `ChanceOracle` 뿐이다. 이 시그니처 자체가 결정론의 강제 장치다.
